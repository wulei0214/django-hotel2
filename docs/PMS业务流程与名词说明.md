## 1. 这套系统在管什么

酒店 PMS（Property Management System，物业管理系统）管理一条完整业务链：

```
顾客公开预订 → 支付/押金 → 前台办理入住（排房）→ 在住消费 → 退房结账 → （必要时）退款
     │              │              │                    │            │
   库存预留      账本收款凭证      账单开立/押金凭证      房费入账      结清/退差价
```

所有"钱"的动作都落在同一个地方：**账单（Folio）下的账本（LedgerEntry）**。理解了账本，理解了一切。

## 2. 名词解释

### 2.1 订单与入住

| 名词 | 英文/代码 | 含义 |
|---|---|---|
| 酒店/物业 | Property | 一家酒店。当前系统为单店模式（DEFAULT 店） |
| 预订 | Reservation | 客人的一次订房申请，含日期、房型、间数、总价、入住人 |
| 预订编号 | booking_no | `R` 开头的唯一订单号，如 `R6588F7D959519C1E64CE` |
| 预订房间明细 | ReservationRoom | 预订里的每一间房：房型、价格（**房费合同额**）、入住时段 |
| 入住单 | Stay | 办理入住后生成的记录（一间房一张），状态：在住 / 已退房 / 已作废 |
| 排房 | assign room | 给预订房间明细分配一间真实客房；办理入住前必须完成 |
| 库存 | Inventory | 某房型某天可卖的数量；预订成功会**预留 15 分钟**（hold），超时未支付自动释放 |
| 房费合同额 | line.amount | 预订确认时锁定的总价快照。后续按这个数收钱、入账，不受调价影响 |
| 访问令牌 | BookingAccessToken | 顾客管理自己订单的唯一凭据（查询/取消/支付都用它），下单时一次性展示 |
| 幂等键 | Idempotency-Key | 防重复提交的请求标识：网络重试不会造成重复收款 |

### 2.2 钱与账本

| 名词 | 英文/代码 | 含义 |
|---|---|---|
| 账单 | Folio | 一张订单一本**主账单**（MASTER）。订单的生命周期内记录全部收支 |
| 账本凭证 | LedgerEntry | 账本里的一行，**只追加、永不修改删除**（审计要求）。每行带正负号 |
| 房费凭证 | ROOM_CHARGE | 正数，客人欠的房费；夜审可按营业日逐晚过账，退房时仅补当前 Stay 尚未入账的房费 |
| 押金凭证 | DEPOSIT | 负数，前台收到的押金（客人多付的钱） |
| 收款凭证 | PAYMENT | 负数，客人付的钱（线下收款/在线支付） |
| 退款凭证 | REFUND | 正数，退还此前收款；以追加凭证抵回原负数收款 |
| 红字冲销 | REVERSAL | 与原凭证**等额反向**的更正凭证（记错了用冲销纠正，不删原账） |
| 账本余额 | balance | **= 账本全部凭证的带符号合计**。见 §3 三态解读 |
| 应收余额 | outstanding | 客人**此刻还欠多少**：`应收余额 = 账本余额 + 合同房费总额 − 已入账房费`。见 §4 |
| 押金 | Deposit | 客人预先交的钱。**允许账本余额变负**（= 客人预存款） |
| 预存款 | （余额为负） | 账本余额 < 0 时，绝对值就是酒店欠客人的钱（多付未消费部分） |
| 收银班次 | CashierShift | 前台收银员的一段当班时间。**所有现金收付必须挂在本人开立的班次下** |
| 备用金 | opening_float | 开班时清点投入的零钱底金（可以为 0，不影响收款） |
| 长短款 | over/short | 关班时"实际清点现金 vs 系统应有现金"的差额，需解释原因 |
| 审批 | ApprovalRecord | 退款等高风险操作的留痕流程；**申请、审批、执行必须是三个不同账号**（职责分离） |

### 2.3 房与房态

一间客房有三个**互相独立**的状态维度（`apps/inventory/models.py`）：

| 维度 | 取值 | 谁在改 |
|---|---|---|
| 占用状态 | 空闲 / 在住 | 入住、退房自动流转 |
| 清洁状态 | 净房 / 脏房 / 清洁中 / 待检查 | 客房部工作台 |
| 维护状态 | 正常 / 维护中 | 排房时维护中的房间不可分配 |

## 3. 账本余额的三态解读（最重要的一张表）

把主账本想成一张**酒店内部的欠条**：客人消费记正数，客人付钱记负数。

| 账本余额 | 含义 | 例子 |
|---|---|---|
| **> 0** | 客人还欠酒店钱（待收） | 入账房费 1000，只付了 600 → 余额 +400 |
| **= 0** | 两讫 | 消费 = 收款 |
| **< 0** | 客人预存款（酒店欠客人） | 押金收了 500，还没消费 → 余额 −500 |

**为什么收款/押金是负数？** 账本记录的是"客人欠酒店多少"的角度：付钱让欠款变少，所以记负。
这是复式记账的常见约定，报表里的"已收/抵扣"取的就是这些负数凭证的绝对值。

## 4. 应收余额公式（本次三个报错的根源）

前台"登记线下收款"时，系统按这个公式算客人还能被收多少（`apps/billing/services_v2.py` `collect_payment`）：

```
应收余额 = 账本余额 + 未入账合同房费 − 已入账房费

若 本次收款金额 > 应收余额 → 拒绝："收款金额超过当前应收余额 X.XX"
```

- **合同房费总额**：预订锁定的房费合同金额；它是整段入住的应收基准，不代表当前尚未入账金额。
- **已入账房费**：当前 Stay 已由夜审/退房服务写入账本的 ROOM_CHARGE 合计；尚未入账房费 = 合同房费总额 − 已入账房费。公式先把合同总额纳入应收，再扣除已经包含在账本余额中的房费，避免重复计算。

### 4.1 用真实案例走一遍（预订号 R6588F7D959519C1E64CE，房费 3728）

客人下单时在线支付了 3728（全款），随后办理入住：

| 时点 | 账本余额 | 未入账合同房费 | 已入账房费 | 应收余额 | 系统行为 |
|---|---|---|---|---|---|
| 入住后、收押金前 | −3728（已付全款） | +3728 | 0 | **0.00** | 登记 100 → 拒绝 ✅（客人不欠钱） |
| 登记入住押金 50 后 | −3778 | +3728 | 0 | **−50.00** | 再收任何金额 → 拒绝 ✅（客人已多付 50） |

**结论：两个报错都是正确的业务守卫，不是 bug。**

### 4.2 收款 vs 押金：什么时候用哪个

| | 登记线下收款（收款） | 登记入住押金（押金） |
|---|---|---|
| 业务含义 | 收**客人欠的钱**（结账） | 收**客人预交的钱**（担保/预存） |
| 金额限制 | ≤ 当前应收余额（不能多收） | > 0，且**累计押金 ≤ 房费合同额** |
| 对余额的影响 | 余额减少但不会变负 | 余额可以变负（= 预存款） |
| 典型场景 | 退房时补收差额 | 入住时收押金；客人想多存点钱也走这里 |
| 代码守卫 | `services_v2.py` `collect_payment` | `services_v2.py` `receive_deposit` |

**"值必须大于或等于 0.01"**：前端输入框的 HTML `min="0.01"` 原生校验——收款/押金为 0 没有业务意义，直接拦截。

### 4.3 为什么"收款"要限制不能多收

1. **语义清晰**：多收的钱本质是押金/预存款，应走押金通道（有自己的上限与审计口径），避免两套通道混用造成对账困难
2. **防误操作**：前台手滑多录一个 0，客人就被多收了几千块；押金上限挡住累计风险
3. **审计一致**：押金凭证、收款凭证分开后，"这笔钱是担保性质还是结算性质"在账本上一目了然

## 5. 预订状态机（`apps/reservations/models.py`）

```
PENDING 待支付 ──在线支付成功 / 前台人工收款或押金成功──→ CONFIRMED 已确认 ──办理入住──→ CHECKED_IN 已入住 ──退房──→ CHECKED_OUT 已退房
   │                              │                          │
   ├─15分钟未支付→ EXPIRED 已过期   ├─客人取消→ CANCELLED 已取消  └─到店未入住（次日）→ NO_SHOW 未到店
   └─客人取消→ CANCELLED 已取消
```

- **PENDING**：下单成功未支付，库存按 Hold 策略预留；可由在线支付回调确认，也可由前台人工收款/押金成功后自动确认；同一手机号在途上限按配置执行
- **CONFIRMED**：在线支付回调或前台人工收款/押金成功后确认，可办入住；确认动作同步确认库存并写审计
- **CHECKED_IN**：在住。账单开着，可继续收款/押金
- **CHECKED_OUT**：退房完成，账单结清关闭
- 顾客侧操作（取消/查询/续付）一律凭**访问令牌**，手机号不作为凭据（安全设计 §P0-08）

## 6. 全流程走读

### 6.1 公开预订（顾客自助，`/reserve/` 页面）

1. 选日期/间数 → 查实时可订房型与逐晚价
2. 填入住人姓名+电话 → 提交 → 系统生成 **PENDING** 订单 + **预留库存 15 分钟**
3. 页面展示**预订编号 + 访问令牌**（令牌只显示这一次，请客人保存；刷新后可凭这两项在"04 继续支付"面板找回订单）
4. 测试环境可使用本地模拟支付；未预付订单也可由前台在线下收款/收押金成功后自动转为 **CONFIRMED**，同步确认库存并写入收款/押金凭证与审计。
   - 真实生产环境只有接入支付服务商后才由渠道回调确认；人工收款/押金是独立的前台业务路径，不代表真实渠道已接入。

### 6.2 前台收款与押金（前台接待工作台）

> 前置：**现金**收付必须先在"收银班次"区开班（输入备用金，可为 0）；刷卡/转账不需要班次。

1. 找到订单（待抵店/在住列表）→ 展开「登记线下收款」或「登记入住押金」
2. 收款：金额 ≤ 当前应收余额（§4 公式）；押金：累计 ≤ 房费合同额。PENDING 订单可通过成功的前台收款/押金完成确认
3. 提交后账本追加凭证，列表与账单即时刷新；现金类同时挂到本人班次
4. 系统会弹确认框"请确认这笔款项已经实际收到"——系统只登记，不发起真实扣款

### 6.3 排房与入住

1. 待抵店订单 →「排房」：按房型选一间 空闲 + 净房 + 非维护 的房
2. 「办理入住」：生成入住单（Stay：在住），预订变 CHECKED_IN，房间占用状态变"在住"
3. 可同时登记入住押金

### 6.4 在住

- 客人可随时补收款/补押金（规则同 §6.2）；夜审按营业日对符合条件的在住 Stay 过账房费，使用稳定 reference 防重复入账
- 客房部在清洁工作台更新房态（退房后房间变脏房 → 清洁中 → 净房，回到可卖循环）

### 6.5 退房结账（关键账本时刻）

退房时系统自动做三件事（`apps/reservations/front_desk_services.py` `check_out_stay`）：

1. **房费补账**：夜审可能已经按营业日逐晚记入本 Stay 的 ROOM_CHARGE。退房服务按本 Stay 归集夜审已入账金额，计算「本间合同房费−本间已入账房费」，只追加剩余正数差额；不得将整笔合同额再次入账
2. **检查余额**：
   - 余额 > 0 → 拒绝退房："账单尚有应收余额 X，请先完成收款"（先收钱再退房）
   - 余额 < 0 且是最后一间房 → 拒绝："仍有客人余额 X，需先处理退款或余额结转"（先把多收的退给客人）
3. 余额 = 0 → 退房成功，账单关闭，房间变脏房

**为什么预付全款的客人能顺利退房？** 退房瞬间：账本余额（−3728）+ 房费入账（+3728）= 0，两讫。

### 6.6 退款（职责分离，三步三账号）

```
申请（前台/财务）→ PENDING 待审批 → 审批（值班经理/店长）→ APPROVED → 执行（财务第三账号确认实际退款）→ 追加 REFUND 正数凭证
                    └─审批驳回→ REJECTED
```

- 申请人、审批人、执行人必须是**三个不同账号**；申请人不能审批，审批人不能执行同一笔退款
- 执行时必须勾选"确认退款已实际支付给客人"
- 退款审批与财务查看权限分离（§P0 权限整改）

### 6.7 收银班次（现金安全链）

```
开班（登记备用金）→ 当班期间：现金收款/现金押金/现金退款全部挂本班次 → 关班（清点实际现金）
                                        ↓
              系统算"应有现金 = 备用金 + 现金收入 − 现金支出"，与实点差额 = 长款/短款 → 对账
```

- 备用金为 0 完全可以开班——它只是关班对账的起点，不影响任何收款
- 没开班就登记现金收款 → 报错"请先开立本人收银班次"（不是故障，是审计要求：每笔现金都要能追到人和班次）

## 7. 常见报错速查

| 报错原文 | 触发原因 | 正确操作 |
|---|---|---|
| 收款金额超过当前应收余额 0.00 | 客人不欠钱（通常已预付全款） | 要收的钱本质是预存 → 走「登记入住押金」 |
| 收款金额超过当前应收余额 −50.00 | 客人已多付（余额为负） | 无需再收；退房时会走退款流程退差价 |
| 值必须大于或等于 0.01 | 前端 min 校验 | 收 0 元无意义；确实要登记 0 元场景请联系开发评估 |
| 请先开立本人收银班次 | 现金收付前未开班 | 工作台「收银班次」→ 开班（备用金可为 0）→ 重试 |
| 累计押金不能超过当前预订房费总额 | 押金上限守卫 | 押金只能覆盖房费总额；超出的部分不属于押金业务 |
| 该幂等键已用于其他收款/押金登记 | 请求标识被复用且内容不同 | 刷新页面重新发起；不要手工复用幂等键 |
| 账单尚有应收余额 X，请先完成收款 | 退房时余额 > 0 | 先收款结清，再退房 |
| 预订编号或访问令牌不正确 | 顾客侧令牌错误 | 核对令牌；令牌丢失需前台按店内流程核实身份后协助 |

## 8. 新人常见误区

1. **"收款是负数，是不是记错了？"** —— 不是。账本以"客人欠酒店"为正方向，收款让欠款变少所以记负。报表展示层已做翻译（"已收/抵扣""客人预存款"）
2. **"押金能收、收款不能收，是不是押金绕过了风控？"** —— 不是。押金有自己的上限（累计 ≤ 房费总额）与班次/幂等守卫，两者只是业务语义不同
3. **"入住时为什么余额是 0，房费去哪了？"** —— 房费在**退房时**才入账；在住期间它以"未入账合同房费"参与应收余额计算，不会漏
4. **"备用金 0 是不是没法收款？"** —— 备用金只是关班对账的基数，0 完全能开班收款
5. **"红字冲销能不能直接改账本？"** —— 永远不能改。错了就补一条等额反向的冲销凭证，原凭证保留（审计链完整）
