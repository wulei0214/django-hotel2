### 2.1 P2/P3 的校正

1. 分页不能笼统写成“没有分页”。后端 `paginate()` 已返回 page/page_size/total/has_next/has_previous；财务、清洁、通知等页面已出现页码信息和跳转/条数控件。夜审多个独立列表仍需逐一核对交互，不能假设全部共用同一分页实现。
2. 报表是聚合结果，不要求按列表分页；报表导出是独立能力，不能用分页代替。
3. `LedgerEntry.reference` 当前模型已有全局 `unique=True`，撤销“缺唯一约束”结论。
4. 夜审查看权限与执行权限不同是正确的最小权限设计；不应为通过旧测试而把执行权限塞回只读矩阵单元格。
5. 旧代码注释与测试说明必须同步；不能让历史描述继续指导开发人员使用已废弃的权限码。

## 3. 截图对应问题的当前代码判断

### 3.1 图 1：维修登记 HTTP 403

当前 main 的维修 API 要求 `inventory.maintenance_manage`，并非 CSRF 权限；当前模板已从服务端渲染的 CSRF token 取值。测试中值班经理拥有该专项权限，客房服务员没有。

因此 403 可能是正确的拒绝，也可能是目标账号角色矩阵未授予维修权限；**不能只凭截图认定为 CSRF 缺陷，也不能通过给演示账号开全权限来掩盖授权问题**。必须在目标数据库核对该账号有效任职、角色组和权限矩阵，再使用 Apifox/浏览器区分：
- 403 + `PERMISSION_DENIED`：权限不满足；
- 403 + CSRF 失败：令牌/Session 问题；
- 其他 403：读取响应错误码和服务端日志。

### 3.2 图 2：员工抽屉姓名/登录账号/最后登录标签对齐

当前 main 的员工中心样式 `static/css/staff_center.css` 中 `.pms-kv th` 已明确 `text-align: left`；当前员工中心动态生成的档案键值表也使用 `pms-kv`。本轮不增加全局 CSS 覆盖，以免改变其他表格。需要在用户实际运行版本确认静态 CSS 是否加载到最新版本、缓存是否清理；若仍右对齐，再检查更高优先级的全局选择器。

### 3.3 图 3：营业日重开申请 Unexpected token '<'

当前 main 的夜审 API helper 已先读取 response.text，再尝试 JSON 解析，并在 HTTP 非成功时优先给出状态码/错误消息，不应再把 HTML 403/500 直接暴露为 JSON parse 错误。仍需目标环境实测确认错误码与真实拒绝原因。

### 3.4 图 4：夜审表格出现 [object HTMLTableCellElement]

当前 main 已修复 Node 子节点 append；本轮增加模板回归守卫，防止退化。

### 3.5 图 5：账单显示负余额

当前账本约定：消费/房费为正数，收款/押金为负数；`balance = LedgerEntry.amount` 带符号求和。正余额表示客人尚欠，负余额表示客人预付款/贷方余额，不代表系统计算错误。

当前前台 JS 的 `renderFolioBalance()` 已把负余额显示为“客人预存款”并展示绝对值，正余额显示为“待收余额”，零显示“已结清”。如果用户本地仍显示“当前余额 -34144”，说明运行的前端 JS 可能落后于当前 main、缓存未刷新，或账单数据确有未匹配房费/收款事实。不能把负号简单改为正数，也不能虚构房费入账。下一步应按同一 booking_no 核对 ReservationRoom.amount、Folio、LedgerEntry、Payment、Stay、NightAuditRun 的关联和业务状态，确认房费应在哪个业务时点过账。

- 清洁统计和清洁工作清单统一使用 `inventory.housekeeping_view`；清洁流转使用 `inventory.housekeeping_update`；维修操作使用 `inventory.maintenance_manage`。
- 夜审只读接口使用 `core.night_audit_view`，执行接口使用 `hotelapp.night_audit_execute`。
- 前台只能关闭本人收银班次；财务/主管可代关本物业其他员工班次，关班审计记录实际操作人。
- 冲销领域服务自身执行物业过滤，不能只依赖 API 层先查一次。
- `ApprovalRecord` 申请事实不可改写；ORM QuerySet 批量 update/delete/bulk 写入被拒绝。
- `AuditEvent` QuerySet 批量 update/delete/bulk 写入被拒绝；模型 save/delete 仍保持只追加语义。

### 8.3 MySQL 与只追加事实保护

- CI workflow 配置 MySQL 8 服务，负责迁移和数据库约束回归；必须以最新 workflow 结果为准。
- 新增 `apps/core/sql/audit_immutability.sql`，提供 MySQL 8 对 `core_auditevent`、`billing_ledgerentry`、`billing_cashiershiftmovement` 的 6 条 BEFORE UPDATE/DELETE 触发器。
- 新增命令 `python manage.py check_mysql_append_only_guards`，核验六条触发器是否存在且表/事件/时机正确。
- 新增《PMS2 MySQL财务与审计不可变事实部署说明.md》，说明运行账号与迁移账号分离、表级 REVOKE 和触发器部署步骤。
- **远程代码提交不能替代用户目标 MySQL 的现场部署**。本地先前 `Access denied for user 'wu'lei'@'localhost'` 仍需由 DBA/本机管理员核对用户名、授权 Host 和密码；不得把凭据写入仓库。

### 8.4 新增回归证据

- 支付状态更新不再查询 Refund 专属字段。
- Refund 审批/执行事实不可覆盖。
- 退款申请、审批、执行三账号分离；执行幂等重放不重复追加凭证。
- 数据库 CHECK 约束通过基础 QuerySet 更新旁路测试，验证不是只依赖模型 save。
- 现金退款余额不足时零账本副作用；补入备用金后才能执行。
- 现金退款按执行班次扣减；原现金收款仍归属收款班次；两个班次分别正确关账。
- 超额现金 OUT 被拒绝；关班后的班次事实不可修改或删除。
- 前台不能关闭其他收银员班次；财务/主管可以代关并记录真实关班人。
- 跨物业红字冲销在领域服务层拒绝。
- 退款列表 API 返回完整三方执行事实和历史流程标记。
- 财务 UI 对非现金退款要求渠道参考号，并对历史退款显示只读提示。
- OpenAPI 权限矩阵按只读/执行权限分离；路径集合与当前 URL 注册表比对，不再硬编码旧的 97 条数量。

### 8.5 仍未关闭的验收项

1. **CI**：本节记录提交之后触发的 MySQL `Django CI` 和 `tests` 必须全部完成且通过；排队/运行中不能标记通过。
2. **真实 MySQL**：必须在目标实例应用 0016 迁移，执行六条触发器部署和 `check_mysql_append_only_guards`，验证应用账号无法 UPDATE/DELETE。
3. **真实浏览器 E2E**：当前新增的是 Django HTTP/模板回归测试，不等同于 Playwright 浏览器测试；需覆盖登录、CSRF、收款、退款、班次补入/支出、关班、维修、夜审、通知。
4. **OpenAPI 静态快照**：`docs/接口文档/openapi.json` 仍需由当前 `build_openapi()` 生成并与运行时 `/api/v1/openapi.json` 对齐；不可把旧静态文件当作当前接口基线。
5. **历史退款数据**：执行 0016 后核对 `legacy_workflow=True` 的数量和业务清单；不得把无法证明执行人的历史退款伪装为新流程三方证据。
6. **旧 FinanceRecord**：`/finance/` 已 302 到 `/manage/finance/`，`/finance_add/` 为 410；历史 FinanceRecord 的数据映射/对账仍须有独立迁移清单，不得双写。

**结论修订：退款三分离、班次现金核算、维修权限专项迁移、个人通知已读和跨物业冲销等代码缺口已实施相应修复；但 MySQL 现场部署、最新 CI、真实浏览器 E2E、OpenAPI 静态快照和历史数据核对仍未验收。因此 PMS2 仍不得冻结，也不得启动 PMS3.0 新功能排期。**
