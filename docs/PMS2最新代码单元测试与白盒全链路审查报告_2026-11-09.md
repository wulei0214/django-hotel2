## 2. 核心业务路径白盒核对

用户指定主链路：

**公开下单（不预付）→ test_front 收押金并自动确认 → 排房入住 → 夜审 → 退房补款 → 清洁放行 → 退款三权分立。**

### 2.1 逐步状态与数据断言

| 步骤 | 操作账号 | 应有业务结果 | 必须核对的数据事实 |
|---|---|---|---|
| 1. 公开下单、不预付 | 匿名顾客 | Reservation=PENDING；不得创建 Payment 成功事实；库存 Hold 按既有策略建立 | Reservation、ReservationRoom、InventoryHold、BookingAccessToken；公开预订不创建 Django User |
| 2. 前台收押金 | test_front | 押金成功登记后自动确认：Reservation=PENDING→CONFIRMED | Payment=SUCCEEDED 且 payment_kind=DEPOSIT；DEPOSIT LedgerEntry；库存确认；AuditEvent；幂等重放不重复收款 |
| 3. 排房、入住 | test_front | 分配真实房间后创建 Stay=IN_HOUSE；房间 OCCUPIED | ReservationRoom.room、Stay、Room occupancy、MASTER Folio、操作审计 |
| 4. 夜审 | test_duty | 夜审执行成功，营业日关闭；按营业日对每间 Stay 过账房费 | NightAuditRun=SUCCESS、BusinessDate=CLOSED、ROOM_CHARGE reference 幂等；不得重复过账 |
| 5. 退房补款 | test_front | 未结清时拒绝退房；补收后余额归零并退房 | 退房房费只补“本 Stay 合同房费−本 Stay 已由夜审过账金额”；Stay=CHECKED_OUT；房间 occupancy=VACANT、housekeeping=DIRTY |
| 6. 清洁与放行 | test_housekeeping / test_duty | 客房服务员推进 DIRTY→CLEANING→INSPECTING；值班经理/店长执行净房放行→CLEAN | 每次状态转换、操作者、时间和审计；客房服务员不得自行净房放行 |
| 7. 退款三权分立 | test_front / test_duty / test_finance | 申请、审批、执行由三个不同账号完成 | Refund.requested_by / approved_by / executed_by 三者不同；审批不产生 REFUND LedgerEntry；执行成功只追加一次退款凭证；现金退款归执行人本人班次 |

### 2.2 已核实的关键代码行为

1. `apps/reservations/front_desk_services.py::collect_manual_payment` 允许 PENDING 预订走前台人工收款；收款成功后调用库存确认逻辑，再将 Reservation 更新为 CONFIRMED 并写审计。
2. `apps/reservations/lifecycle_services.py::receive_manual_deposit` 明确允许 PENDING、CONFIRMED、CHECKED_IN；统一委托 `BillingService.record_deposit`，不另开账务写入口。
3. `BillingService.record_deposit` 对 Reservation 行加锁，校验押金累计不超过房费合同额；同幂等键同事实返回原 Payment。
4. `check_out_stay` 不再按整笔合同金额重复入账，而是按 Stay 维度扣除夜审已入账房费后，只补剩余金额；多房共用 Folio 时不会把兄弟房间房费算到当前 Stay。
5. 夜审正式执行由 `NightAuditService` 完成；`test_duty` 所属值班经理角色是当前已启用的夜审执行角色。
6. 退款服务已拆分 `request_refund`、`approve_refund`、`execute_refund`；申请、审批、执行的操作者必须分离，只有执行成功才产生 REFUND 凭证。

### 2.3 账本方向需要统一文档

当前账本带符号约定为：

- ROOM_CHARGE / 其他消费：正数（增加客人应付）。
- DEPOSIT / PAYMENT：负数（减少客人应付，可能形成客人预存款）。
- REFUND：正数（退款将此前负数收款抵回，增加账本余额）。
- REVERSAL：与被冲销凭证等额反向追加，不改写或删除原凭证。

历史版业务流程文档曾把 REFUND 描述为负数，并声称房费只在退房时第一次入账；本轮已将当前业务流程说明校准为 REFUND 正数、夜审分晚过账和退房净额补账。历史审计快照保留原文并标注历史效力。

| 账号 | 角色 | 注册表状态 | 本轮验收定位 |
|---|---|---|---|
| test_front | 前台 | ACTIVE | 下单接待、押金/收款、排房入住、退房、退款申请 |
| test_duty | 值班经理 | ACTIVE | 夜审执行、净房放行、退款审批；不得执行同笔退款 |

| test_owner | 店长 | ACTIVE | 管理与审计/报表查看；不得通过员工工作台给自己授权 |
| test_housekeeping | 客房服务员 | ACTIVE | 清洁链推进；不得净房放行 |

## 4. 白盒测试发现：36 项 HTTP 串测脚本暂不具备验收资格

检查文件：`scripts/e2e_full_chain.py`。

| 等级 | 发现 | 影响 | 必须整改 |
|---|---|---|---|
| P1 | 使用 `date`、`timedelta`、`re`、`json`，但文件没有对应 import | 脚本在设置 CHECK_IN/请求/登录阶段即可能 NameError，无法作为可复现串测入口 | 补齐 import，并加入 py_compile/脚本启动自检 |
| P1 | 脚本硬编码测试账号密码 | 公开仓库泄露测试凭据，且不利于环境隔离 | 改为强制读取本地环境变量或安全输入；缺失即退出，不允许默认值 |
| P1 | 清库保护只检查 DEBUG 与 DJANGO_ENV=dev，没有严格验证 DB host/name allowlist 和显式破坏性确认 | 远程开发库或误指向数据库可能被清空 | 增加本机 host、专用数据库名前缀、显式 `PMS_E2E_ALLOW_RESET=1`、备份/目标库二次确认 |
| P1 | F1 通知断言含 `or True` | 通知断言恒通过，不能证明本单通知/待办生成 | 断言实际关联对象、事件类型、状态和员工可见范围 |
| P1 | F2 审计断言只判断列表长度 `>=0` | 空审计列表也通过 | 断言存在当前订单/夜审的指定 AuditEvent，并校验 actor/entity/action |
| P1 | E4 把 HTTP 200、403、409 都视为职责分离成功 | 值班经理若错误地成功执行退款，测试仍会 PASS | 对无执行权账号必须严格断言 403；并核对无 REFUND 凭证副作用 |
| P1 | D2 未结清退房接受 200/201/409 多种状态 | 可能放过“欠款仍允许退房”的业务回归 | 按该测试数据预期严格断言 409；补款后严格断言成功与余额归零 |
| P2 | 脚本声明 2 晚，但 CHECK_OUT 使用 date.today()+3 | 测试日期跨度与说明不一致，可能误判夜审次数/房费金额 | 统一测试日期和晚数口径 |
| P2 | 36 项脚本未纳入两条 CI 工作流；当前 CI 仅执行 Django Test Suite | Commit 标题的 36/36 不等于 CI 可复现证据 | 增加独立隔离 DB 的 E2E job，上传逐步断言、请求响应和 DB 核对报告 |
| P2 | 串测只使用 test_front/test_duty/test_finance/test_housekeeping/test_owner，没有逐一覆盖 test_nightaudit/test_fnb/test_fnbsup/test_parking | 九角色账号初始化测试不等于九角色登录/权限边界验收 | 增加 9 账号认证矩阵；4 个 PLANNED 角色必须断言无业务权限 |

**因此：当前仓库 commit message 中的“36/36 PASS”只能视为提交者声明，尚未达到可复现验收证据标准。** 在脚本修复并于隔离 MySQL 测试库重新执行前，不得在 README、验收报告或 PMS3 门禁中写“36 项全链路验收通过”。
