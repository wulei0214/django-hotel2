## 2. 当前未决事项状态

### 2.1 生产 HTTPS、Secure Cookie、HSTS
状态：**暂缓，属于正式部署验收，不是本地开发阻塞项。**

本地开发阶段沿用当前开发配置。正式上线前必须结合真实域名、TLS 证书、反向代理拓扑验收：HTTP 到 HTTPS 跳转；Session/CSRF Cookie Secure、HttpOnly、SameSite、Path；Django 对可信代理 HTTPS 头的识别；HSTS max-age 及 includeSubDomains/preload 风险评估；登录、登出、CSRF 写请求和回调链路回归。

不得在没有域名、证书和代理拓扑的情况下声称生产 HTTPS/HSTS 已验收。

### 2.2 浏览器兼容性
状态：**低优先级，后续安排。**

当前不要求 Firefox/WebKit 作为本轮交付门槛。Chromium 的覆盖声明必须以可追溯的浏览器自动化配置、运行报告、浏览器版本、commit SHA 为证据；Django Test Client 不等于真实浏览器 E2E。项目稳定后再建立 Chromium/Firefox/WebKit 矩阵。

### 2.3 F-02 账号与测试数据治理
状态：**已获准在本地开发/测试环境执行清理方案；尚不代表已经执行数据库清理。**

目标：
1. 清除员工 User 上冗余的 User.groups 直接岗位授权，岗位授权统一通过 PropertyStaffMembership + StaffRoleAssignment + AuthorizationService。
2. 对历史孤儿账号、停用账号逐个分类，确认无用途后禁用；默认不物理删除 User 和有历史关联的业务记录。
3. 清理测试数据前生成数据库备份和只读盘点报告。
4. 重新初始化物业、角色目录、测试员工、房型房间、住客、预订等测试数据。
5. 保留必要平台超级管理员；平台管理员不得自动获得门店岗位权限。
6. 清理与重建仅可针对明确的本地/专用测试数据库。生产环境和未知目标环境一律拒绝。

禁止把“本地数据混乱”解释为可以无条件 flush 当前连接数据库。任何破坏性操作必须显式提供数据库目标确认、执行预览和备份检查。

### 2.4 九角色测试账号验收
必须为以下角色各创建一个独立员工账号：前台、值班经理、财务、店长、客房服务员、夜审员、餐饮服务员、餐饮主管、停车安保。

每个账号必须满足：
- User.is_active=True；
- 关联 StaffProfile；
- 存在当前物业有效的 PropertyStaffMembership；
- 存在有效 StaffRoleAssignment；
- 通过员工登录入口完成真实认证；
- 角色权限测试证明允许动作成功、禁止动作被拒绝；
- 不依赖 User.groups 直接授权；
- 账号密码不得写入仓库、日志、文档或命令输出。密码通过本地交互输入或安全环境变量注入；测试环境凭据与生产凭据隔离。

不得给九个账号设置 is_staff/is_superuser，不得把九个账号提升为平台管理员。

### 2.5 Apifox 手工测试集合
状态：**OpenAPI 与环境模板已提交；实际导入、用例集合和执行报告仍由测试人员完成。**

最低交付：导入当前 main 对应的 OpenAPI JSON；配置本地 Base URL、员工账号变量、CSRF Cookie/Token、Booking Access Token；建立认证、公开预订、前台履约、住客、财务、审批、夜审、员工、权限安全分组；保存正常、参数错误、未认证、无权限、跨物业、重复提交等关键用例；保存运行报告并记录环境、数据库版本和 commit SHA。禁止保存真实密码、Session、住客 PII 或生产密钥。

## 3. F-02 执行流程与安全门禁

### 阶段 A：备份和盘点
1. 确认当前数据库名称、主机、端口、数据库引擎和 DJANGO_ENV。
2. 通过数据库工具或 mysqldump 备份；记录备份文件、时间和校验值。
3. 执行 classify_users 只读盘点，导出 JSON/CSV。
4. 输出用户、档案、任职、角色授权、User.groups 直授、业务外键引用的数量和明细。
5. 检查九角色 Group 是否齐全及其权限矩阵。

### 阶段 B：清理预览
1. 对直接组授权逐个对比当前有效的 StaffRoleAssignment（包括物业、员工档案、任职状态和授权有效期）。
2. 仅移除与当前有效 StaffRoleAssignment 同名的 User.groups 镜像授权；未被承接的组授权保留并进入人工复核。
3. 孤儿账号按平台技术账号、业务员工、历史公开注册嫌疑、测试账号分类。
4. 默认停用没有 StaffProfile 的普通孤儿账号，不物理删除历史身份；超级管理员和平台 staff 跳过。
5. 对测试业务数据制定明确删除范围和外键影响清单；本轮账号收敛命令不删除业务测试数据。
6. 输出预览报告，包含将修改对象数、停用对象数、人工复核数和保留对象数。

### 阶段 C：执行与回归
1. 再次核对数据库目标和备份。
2. 仅在本地/专用测试环境执行；生产或环境不明时拒绝。
3. 清理后重建九角色账号和业务测试数据。
4. 验证九角色登录、授权、越权拒绝和身份链完整性。
5. 验证平台 admin 登录独立于 PMS 员工登录。
6. 保存清理前后报告、测试报告和 commit SHA。

## 4. 文档治理规则

### 4.1 文件命名
- 新增 Markdown 文档优先使用中文文件名。
- OpenAPI、Apifox JSON、机器读取配置、标准化审计工具文件可使用英文/标准英文命名。
- docs/audit/phase0 属机器维护的审计证据目录，现有英文文件名保留，避免破坏引用和工具链。
- 截图、OpenAPI JSON、Apifox 环境 JSON 不强制中文命名。
- 不为中文化而破坏已有链接；重命名必须同步修复所有相对链接和索引。

### 4.2 内容一致性
代码变更涉及路由、页面入口、认证与 Session；模型、字段、约束、迁移；API 路径、参数、响应、错误码；角色权限、审批、敏感字段和审计；环境变量、依赖、启动/测试命令；UI 结构、表单和截图；测试覆盖、已知限制和验收状态时，必须在同一提交更新对应文档。

### 4.3 状态标记
统一使用：已实现、已测试、已验收、待部署验收、待外部工具验收、暂缓、未实现、待决策。不得把“有模型”“有页面”“OpenAPI 可导入”直接写成业务功能已验收。
