## 2. DEC-02-A1：原负债冻结、独立调整

### 2.1 领域语义

RefundLiability.amount 是登记时原始财务事实，永久保持不变。remaining_amount 不能通过普通编辑增加；实际退款成功仍由 Refund 执行事实减少已退款余额。退房后新增费用、费用冲销、应退增加或抵扣必须通过独立调整记录表达，不能回写原始负债。

建议复用现有账务凭证语义，评估新增 FolioAdjustment / RefundLiabilityAdjustment 或等价模型；不得先建表后再决定会计含义。调整记录至少包含：
- property、reservation、folio、refund_liability（若影响该负债净额）；
- adjustment_type：新增应收/抵扣、费用冲销/增加应退等明确枚举；
- amount、currency、reason_code、reason_text/evidence；
- status、idempotency_key、source/reference；
- requested_by、approved_by、executed_by、时间戳；
- 原业务日期、实际操作日期（适用时）。

### 2.2 金额口径

展示并可重建以下独立金额：
- 原始退款负债；
- 已执行退款（仅成功 Refund + REFUND 凭证）；
- 已批准且已执行抵扣；
- 已批准且已执行增加应退调整；
- 未处理调整金额；
- 当前可退款净额。

计算口径必须由唯一服务实现，前端不得自行拼接权威余额。建议概念公式：

`可退款净额 = 原始负债 + 已生效增加应退调整 - 已生效抵扣 - 已成功退款`

所有调整必须有明确方向与状态，未审批、已拒绝、执行失败、已撤销的调整不影响可退款净额。任何净额不得小于零；超额调整必须拒绝并返回可解释错误。

### 2.3 工作流与职责

- 财务人员发起调整并提供原因/证据。
- 值班经理或明确授权审批角色审批；申请人不得自批。
- 只有批准的调整可执行；重复审批/执行幂等。
- 执行时锁定 RefundLiability/Folio 和相关资金占用记录，重算余额后再写入。
- 调整记录、对应独立凭证、余额投影/状态、AuditEvent 同事务提交。
- 退款执行与抵扣执行竞争同一负债时必须串行化；不得分别读到相同可退余额并双双成功。
- 抵扣不得生成 REFUND；实际退款仍走既有 Refund 执行服务。

## 3. DEC-02-B2：授权异常放行、待财务核查

### 3.1 触发条件

正常负债登记无法证明资金来源时触发异常流程，包括：无成功 Payment、缺失可追溯 PAYMENT/DEPOSIT 凭证、候选可退余额不足、Payment 与凭证/物业/Reservation/Folio/币种关联不一致。不得通过伪造 Payment、跳过来源检查或创建负债绕过。

### 3.2 独立异常实体

建议新增 CheckoutException / CheckoutFinancialReview 或等价实体，不能复用 RefundLiability。字段至少包含：
- property、reservation、folio/stay；
- exception_code、description、amount、currency；
- payment_review_status、ledger_review_status、evidence_refs；
- status（待审批、批准待核查、核查中、已解决、已驳回等）；
- requested_by、approved_by、checkout_executed_by、reviewed_by；
- approval_reason、resolution_code、resolution_note；
- idempotency_key、created_at、approved_at、resolved_at。

### 3.3 流程

1. 前台正常退房检查失败后，获得结构化原因；只有有权限人员可发起异常申请。
2. 值班经理或更高明确授权角色审批，申请人与审批人分离。
3. 审批通过、退房执行、异常记录落库必须有一致事务边界；如果跨事务/外部操作，需使用可恢复状态机和 Outbox，不允许“已离店无记录”。
4. 异常放行不创建 RefundLiability、Refund、REFUND 凭证，也不增加可退款余额。
5. 异常进入财务待核查，必须持续可见、可分派、可追踪 SLA；不允许因列表分页/状态误置而消失。
6. 财务补齐真实 Payment、账本凭证及余额证据后，调用正式负债登记/财务纠正服务转换；转换记录源异常 ID，且只能成功一次。
7. 若核查不需要退款，按审批关闭并保存证据；记录不可物理删除。

## 4. D1 多笔原支付分配规则

- 默认按 Payment 原始发生时间升序分配；同时间按稳定主键排序。
- 财务可选择候选 Payment 人工指定；必须记录原因、操作者、原候选集合/分配结果。
- 一笔 Refund 只关联一个 Payment；跨多个 Payment 的退款创建多笔 Refund。
- 同一 RefundLiability 可关联多笔 Refund，成功退款聚合冲减负债。
- 任何分配都须验证同物业、同 Reservation、同 Folio、同币种、成功支付、存在有效 PAYMENT/DEPOSIT 凭证、Payment 可退余额充足。
- 待审批/已批准未执行退款应占用可申请额度；拒绝/撤销/过期应释放占用且幂等。
- 退款执行、调整抵扣、退款申请占用必须使用一致的锁序/互斥策略，防止超额承诺。
- 不允许把候选关系当作已分配金额；需有明确分配事实或每笔 Refund 的 Payment 关联。

## 5. API 与页面需求

API 应按现有路由风格纳入 OpenAPI 契约，具体路径在代码盘点后确定，不能另建平行 API：
- 负债详情/汇总：原始负债、已成功退款、已执行抵扣、增加应退、可退净额、候选原支付及分配情况。
- 调整申请、审批、执行、撤销（撤销规则需限制在未执行状态）。
- 异常放行申请、审批、退房执行、财务核查、证据补录、转正式负债、解决/驳回。
- 多笔原支付分配预览、人工指定、退款申请及执行状态。
- 所有写 API 使用 CSRF/认证、物业权限、对象级归属校验、幂等键、审计与标准错误码。

页面：
- 财务中心区分“正式待退款负债”和“待财务核查异常”两个队列。
- 负债详情展示原始金额、退款、抵扣、增加应退和净额构成。
- 多笔支付显示默认分配建议，人工变更需原因并展示每笔 Payment 的可退余额。
- 前台退房页仅对授权用户展示异常放行入口及结构化原因；普通前台不能自批。
- 详情页展示审批链、执行人、证据和时间线。

## 6. P0/P1 与测试矩阵

P0：
- 原负债不可变；调整独立记录。
- 退款与抵扣竞争不超额。
- 异常放行审批/退房/记录事务一致。
- 异常放行不产生虚假负债/退款/账本。
- 多笔 Payment 关联正确且不超额。
- 物业、币种、Reservation、Folio 隔离。

P1：
- 待办分派、SLA、财务核查效率、批量对账、异常报表。

必须测试：补记费用、费用冲销、增加应退、拒绝、重复审批、重复执行、退款与抵扣并发、异常无支付/缺凭证/余额不足、申请人自批、重复退房、记录落库失败回滚、转正式负债重复调用、跨物业访问、跨币种、SQLite 与 MySQL 同 SHA；MySQL 真实行锁并发。

## 10. 六项决策确认后的 DEC-02 补充基线

负责人已确认 D1—D6。本文件中 DEC-02 直接受 D1、D3、D5 约束；D2/D4/D6 分别约束支付-Hold、库存差异和渠道事实边界。此前任何“多笔原支付规则待确认”表述均已关闭，统一按下述规则执行。

### 10.1 D1：多笔原支付分配规则（已确认）

1. 默认按原 Payment 发生时间升序，时间相同按 Payment 主键升序。
2. 财务允许人工指定候选 Payment，但需原因代码和说明，并保留原候选集合、排序、操作者、时间和指定结果。
3. 一笔 Refund 只对应一笔 Payment；一笔 RefundLiability 可以通过多笔 Refund 分批结清。禁止系统把一笔 Refund 静默拆分到多个 Payment。
4. 每笔申请均校验 Payment 与负债的物业、Reservation、Folio、币种、成功状态、原始 PAYMENT/DEPOSIT 凭证及剩余可退金额。
5. 待审批/已批准申请必须占用可退款额度；拒绝/撤销/过期幂等释放；实际执行成功并形成 REFUND 凭证才减少负债已退款额。

### 10.2 DEC-02-A1 与 D5：退房后独立调整

原始 RefundLiability 金额和历史事实不可改写。新增 FolioAdjustment 或等价独立凭证；影响退款净额的调整必须引用原负债。调整需类型、金额、币种、原因/证据、幂等键、申请/审批/执行人及时间，申请人与审批人分离。抵扣不得生成 REFUND 凭证；退款仍只能通过 Refund 执行。调整执行、账务凭证和净额更新同事务提交，并与退款竞争做并发保护。

### 10.3 DEC-02-B2：异常放行不是退款负债

无成功支付、无可追溯 PAYMENT/DEPOSIT 凭证、候选可退余额不足或支付/账本不一致时，建立独立异常放行/待财务核查记录。授权审批后可完成退房，但异常记录本身不得生成 RefundLiability、Refund 或 REFUND 凭证。财务核实真实支付及凭证后，才可通过正式负债/纠正服务进入退款流程；转换必须幂等，异常原始记录保留。

### 10.4 DEC-02 验收闭环

- A1：原负债冻结；调整独立追加；退款与抵扣并发不超额；申请/审批职责分离；失败整体回滚。
- B2：异常原因分类、审批、退房事务一致、财务待办、证据核查、正式转换、重复转换保护及全程审计。
- D1：多 Payment 候选按稳定顺序，人工覆盖有理由；多 Refund 逐笔关联；申请占用、失败释放和执行冲减均可对账。
- 所有测试覆盖 SQLite 与 MySQL；MySQL 覆盖锁竞争；最新 main SHA 的 SQLite/Django 与 MySQL CI 均通过后方可标记工程验收。
