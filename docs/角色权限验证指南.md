# 角色权限验证指南（代码基线修订版）

> 状态：测试执行说明；历史实测结果不代表当前 main 现状。核对基线：main @ 610fe3c28bfc43058b69b2d4054c8adbefee70a1；日期：2026-11-04。

## 1. 当前授权模型

- Django User：认证身份、密码和 Session。
- StaffProfile：员工档案，与 User 一对一（允许尚未绑定）。
- PropertyStaffMembership：员工在具体物业的任职关系。
- StaffRoleAssignment：任职期间的岗位授权；Group 是权限模板，不等于员工任职。
- AuthorizationService：结合用户状态、物业上下文、员工档案、任职和岗位分配计算业务权限。
- superuser 是平台技术身份，不自动获得门店业务岗位权限；分别验证 /admin/ 与前台业务页面。

## 2. 当前范围限制

- 当前按 DEFAULT 单物业上下文运行；不把多物业登录/切换列为已实现。
- /manage/staff/ 主要为读取工作台；员工账号、任职和岗位写操作仍存在于 /staff_accounts/。迁移完成前不得声称员工入口已统一。
- 预留角色的实际访问能力以当前权限目录、路由和自动化测试为准，不按角色名称推断。
- Guest/住客预订与员工 User 是不同访问场景；公开预订不应创建员工 User。

## 3. 必测场景

### 登录与账号
- 正确凭据、错误密码、停用 User、无有效员工任职、无角色分配。
- 登录失败对外提示不得泄露账号存在、离职或停用状态。
- next 参数：站内相对路径允许；//evil.example、外域和不安全 scheme 必须拒绝。
- 公开注册不得创建 Django User；登录页不得出现员工公开注册链接。

### 员工生命周期
- 创建员工档案但未开通账号；开通/邀请/接受/过期/撤销/重复接受（邀请功能上线后）。
- 绑定已有 User，不重复创建身份。
- 分配/结束岗位；暂停物业任职与停用全局账号必须区分。
- 管理员重置密码后强制改密；员工邀请设置密码后不应被错误要求再次改密。

### 权限边界
- 每个业务动作同时测菜单可见性、页面直接 URL、API 直接请求。
- 新员工通过 StaffRoleAssignment 获权后，审批、财务明细、PII reveal 等能力必须与权限矩阵一致。
- 检查所有直接读取 User.groups/has_perm 的业务代码，确保与 AuthorizationService 结果一致。
- superuser 的平台权限与门店岗位权限分开验证。

### 住客与支付
- /reserve/ 创建预订不创建 Django User。
- booking_no + phone 查询：错误组合、共享号码、重复尝试、限流、审计、脱敏。
- 生产环境调用 mock payment intent 必须失败；dev/test 模拟支付回归正常。
- 公开预订创建应验证幂等、库存并发和刷单防护。
