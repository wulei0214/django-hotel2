## 2. 本次已实施内容

### 2.1 数据模型

新增 `billing.RefundLiability`：
- 物业、预订、Folio 关联；
- 原始负债金额、待处理余额、币种；
- OPEN / PARTIALLY_SETTLED / SETTLED 状态；
- 全局唯一幂等键；
- 登记人、登记时间、结清时间；
- 与多个候选原支付 Payment 的多对多关系。

增加数据库约束：
- 原始负债金额必须大于零；
- 待处理余额必须在 0 与原始金额之间；
- 状态、余额、结清时间必须匹配。

负债原始金额、物业、预订、Folio、币种、幂等键和登记人不可修改；待处理余额禁止回增；已结清负债不可重新打开。QuerySet 批量 update/delete 被禁止。

### 2.2 原支付追踪

`source_payments` 只保存与该 Folio 关联且仍有候选可退款余额的成功支付流水，作为财务核对候选集合。

**重要：候选关联不等于金额分配。** 当前不自动按时间、支付顺序或其他算法分配退款金额。多笔原支付的实际分配仍待 DEC-02 参数确认。

### 2.3 退房行为

修改 `check_out_stay()`：
- 最后一间房退房后若 Folio 余额为负，不再仅因负余额拒绝退房；
- 在同一数据库事务中登记待退款负债；
- 没有可追溯的原支付候选、币种/物业/账单不一致、可退款余额不足时，退房仍然失败并回滚；
- 登记负债失败，退房不会部分提交；
- 负余额不会被清零，Folio 结账后仍可通过 RefundLiability 查询；
- 不自动创建 Refund，不自动审批或执行退款。

### 2.4 退款申请与执行关联

- Refund 增加可选 `refund_liability` 外键。
- `BillingService.request_refund()` 增加可选 `refund_liability_id`；财务仍须显式选择已有 Payment，服务验证该 Payment 属于负债候选集合。
- 同一负债下 PENDING/APPROVED 退款金额会预占待处理余额，避免并发申请超过负债金额。
- 退款实际执行成功后，才扣减 `remaining_amount`；部分退款保留余额，全部处理完转 SETTLED 并记录结清时间。
- 退款申请幂等重放校验包含负债关联，不能用同一幂等键切换负债。
- 执行成功审计事件记录负债 ID 和剩余金额。
- 退款模型校验退款、负债、原支付属于同一物业、预订、Folio 和币种，且 Payment 必须在负债候选原支付集合中。

### 2.5 API 与后台查询

- 新增 `GET /api/v1/billing/refund-liabilities`，仅财务权限可查询待退款负债及候选原支付。
- `POST /api/v1/billing/refunds` 可选传入 `refund_liability_id`，由现有财务退款申请流程继续审批与执行。
- 新增 RefundLiability 只读 Django Admin 页面；不允许后台直接新增、编辑或删除负债事实。退款列表增加待退款负债关联列。

## 4. 自动化测试

新增两组回归用例：
- 退房集成：客人支付 700.00、实际房费 600.00，最后退房形成 100.00 负余额：
- 退房成功；
- 生成 100.00 待退款负债；

- API 层：财务可查询负债和候选支付，创建退款申请时可关联负债；申请阶段不扣减负债。
