### 2.1 Q1 手机号加密与 HMAC 索引

1. 手机号原文只允许在业务必要的受控内存路径中短暂出现；数据库持久化字段必须保存认证加密后的密文。
2. 查询使用独立 HMAC 派生值，不允许用可逆加密密文直接承担等值检索，也不允许将普通 SHA 哈希作为手机号索引。
3. 加密密钥、HMAC 索引密钥必须与 Django `SECRET_KEY` 分离；用途分离，禁止同一密钥跨用途复用。
4. 密文和索引均应具备 key version / algorithm version；轮换期间支持新旧版本受控双读/双写，完成回填和验证后停用旧版本。
5. 唯一性和索引范围必须结合物业隔离策略设计；共享手机号不是住客唯一身份，不得借 HMAC 索引推导为自然人唯一键。
6. 所有手机号查询、揭示、批量导出遵守角色、物业范围、用途理由和审计规则；普通展示默认脱敏。
7. 测试必须覆盖加密往返、错误密钥/篡改密文、HMAC 一致性、跨物业隔离、密钥轮换、历史数据回填、日志无明文泄露。

### 2.2 Q2 旧身份证明文迁移与清理

1. 先全仓搜索模型字段、迁移、表单、序列化器、模板、导入导出、管理命令、报表和测试夹具，建立完整读写清单。
2. 迁移采用 expand-migrate-verify-contract：新增加密字段和版本元数据；以可重入批次迁移历史记录；记录成功/失败数量；抽样及全量校验；切换读写路径；确认无旧字段依赖后再删除明文字段。
3. 身份证件使用独立 PII 密钥和认证加密；禁止回退到 `SECRET_KEY`。不得把证件明文写入日志、异常、审计 before/after、测试报告或 Git。
4. 迁移期间对缺失、格式异常、重复和无法解密记录建立隔离清单；不得静默丢弃或伪造数据。
5. 删除旧字段前必须完成数据库备份、恢复验证、迁移回滚预案、应用版本兼容检查和负责人验收。
6. 删除明文字段后，旧备份中的历史明文按备份保留与到期销毁策略治理；不能因线上字段删除就宣称所有历史副本已消除。

### 2.3 Q3 MySQL Outbox + Django Worker

1. 业务服务在同一个数据库事务中写入业务事实和 Outbox 事件；事务回滚时两者一并回滚。
2. Worker 从数据库领取事件，使用原子条件更新/行锁和租约字段实现多 Worker 安全抢占；至少包含状态、尝试次数、下次执行时间、租约到期时间、最后错误、完成时间、关联业务对象和幂等键。
3. 采用有限次数指数退避并加入抖动；超出重试上限进入死信/人工核查，不得无限重试。
4. Worker 必须具备租约过期回收、进程崩溃恢复、重复消费幂等、人工重放、审计和积压巡检。
5. 对外部支付渠道等不可纳入数据库事务的操作，采用“先持久化意图/事件，再调用外部系统，再持久化结果”的可恢复流程；禁止把外部 HTTP 调用放进长数据库事务。
6. `transaction.on_commit()` 可以用于唤醒 Worker，但不能替代 Outbox 持久化事实。
7. 本轮不要求引入 Celery、Redis 作为队列或唯一任务存储；未来若扩展，MySQL Outbox 仍是业务事件可靠性的来源，不能退化成仅依赖内存队列。
8. 验收覆盖双 Worker 抢同一任务、Worker 中途崩溃、数据库提交后进程退出、外部调用成功但本地落库失败、重复回放、死信恢复和 MySQL 锁等待/死锁。

### 2.4 Q4 RPO/RTO 与备份恢复

1. 目标定义：
   - **RPO ≤ 15 分钟**：灾难发生时，允许丢失的已确认业务数据时间窗口不超过 15 分钟。
   - **RTO ≤ 4 小时**：从启动灾难恢复流程到核心 PMS 业务恢复可用的目标时间不超过 4 小时。
2. 采用每日全量备份与连续 binlog 归档/PITR 组合；仅有每日全量备份不能满足 15 分钟 RPO。
3. 备份必须加密、异地保存、限制访问；备份密钥与数据库备份分离管理，恢复人员权限最小化。
4. 备份任务必须监控成功/失败、备份时间点、文件大小、校验结果、binlog 连续性和存储容量。
5. 定期执行完整恢复演练：恢复数据库、应用配置、PII 密钥、附件（若存在）、Worker 和网络入口；验证迁移状态、核心数据、财务账本、支付/退款、库存、员工权限和审计事实。
6. 恢复演练记录开始/结束时间、恢复点、实际数据丢失窗口、核心业务恢复时间、校验结果和遗留问题。只有实测满足目标，才能标记达标。
7. RPO/RTO 是目标值，不得在没有备份链路和演练证据时写成当前已实现能力。

### 2.5 Q5 按数据类型配置保留期限

必须建立数据分类与保留策略登记表，至少包含：数据类别、业务目的、法律/合同依据、保留起算点、期限、访问范围、到期动作、法律保全例外、执行作业、审计和恢复策略。

至少分别管理：
- 住客身份与联系方式；
- 预订、入住、账单和服务履约数据；
- Payment、Refund、LedgerEntry、财务凭证；
- 审批、权限变更和不可变审计事实；
- 应用日志、访问日志和异常堆栈；
- Session、重置令牌、一次性令牌和其他认证凭证；
- 幂等记录、Outbox、死信和任务执行记录；
- 数据库备份、binlog 和导出文件。

不得给所有数据套用一个统一期限。财务、审计和法律保全数据不得因个人信息到期清理而被直接删除；应根据适用法律、经营地要求、会计/税务规则和合同义务确定期限。未完成法律依据确认前，期限字段应标记为待合规确认，不得由开发人员自行编造年限。

到期处理应区分删除、匿名化、加密密钥销毁、归档和限制访问；每次批量处理须可审计、可复核，并防止误删仍在保全期的数据。

### 2.6 Q6 异常追踪与结构化日志

1. 日志采用结构化 JSON，至少包括时间、级别、环境、服务、request_id/trace_id、property_id、user_id（必要时）、模块、动作、路由模板、HTTP 状态、耗时、错误码和异常类型。
2. 审计日志、应用日志、访问日志分开定义权限、保留期限和脱敏规则；访问日志不得直接记录完整 query string、手机号、身份证号、Token、密码或支付敏感信息。
3. 关键请求和后台任务共享可关联的 request/correlation ID；Outbox 事件记录 event_id、业务对象 ID 和执行尝试。
4. 接入异常追踪，采集未处理异常、堆栈、版本、环境和关联 ID；发送前进行敏感信息过滤。
5. 本阶段建立关键异常告警和人工处置路径；至少关注支付回调/补偿失败、死信积压、退款长期未处理、负债与账本差异、库存差异、夜审失败、Worker 停摆、认证失败异常峰值和 PII 揭示异常。
6. 完整指标平台、仪表盘和长期 SLI/SLO 体系作为后续扩展，不作为本轮先决技术依赖；但应用必须预留可观测性接口和指标采集点。
7. 不得将“已写日志”视为“已监控”；验收必须证明日志可检索、异常可关联、告警可触发且处置人可收到。

### 2.7 Q7 生产安全配置强制校验

生产环境启动前必须完成配置自检，任一关键项缺失、使用弱默认值或相互冲突，进程必须拒绝启动并输出不含秘密值的明确错误。

至少检查：
- `DEBUG=False`；
- `SECRET_KEY` 使用独立强随机值，不能使用仓库默认值；
- `DJANGO_PII_KEY` 或正式 PII 密钥配置存在、格式有效且与 SECRET_KEY 分离；
- 数据库使用生产指定连接，禁止意外落到 SQLite/开发库；
- `ALLOWED_HOSTS` 非空且无通配符滥用；
- HTTPS、Secure Cookie、HSTS、CSRF trusted origins 等生产安全设置正确；
- Mock/模拟支付在生产环境必须关闭；
- Outbox Worker 已配置并可运行，队列积压和租约回收可监测；
- 备份、binlog/PITR、日志目录和异常追踪配置达到生产要求；
- 不允许将密钥、数据库密码、支付凭证写入代码或日志。
  
启动自检应区分开发、测试和生产环境；不能为了让测试通过而放宽生产校验。配置失败信息只指出变量名和失败原因，不回显变量值。部署 CI 应有生产配置安全测试和负向测试，证明缺失配置时确实 fail-fast。

## 3. 工程质量整改范围（26 个维度）

以下 26 个维度构成本轮工程质量总清单。每项均需给出现状证据、目标设计、代码变更、自动化测试和验收结果。

### A. 数据与事务基础

1. **数据库设计与约束**：主外键、唯一约束、检查约束、非空、金额精度、状态合法性、物业隔离、业务自然键和索引必须与领域规则一致。
2. **数据一致性**：建立 Payment/LedgerEntry、Refund/负债、Folio/ChargeLine、InventoryHold/库存、Reservation/Stay/房态、Employee/Membership 等跨表对账。
3. **事务边界**：领域服务负责原子业务事务；禁止跨外部网络调用持有长事务；明确锁顺序、回滚语义和事务提交后的事件发布。
4. **数据版本与并发控制**：关键库存、退款额度、预订状态、审批快照和配置采用行锁、条件更新或版本号；并发冲突必须可识别。
5. **存储方案**：MySQL 是业务事实来源；Redis 如后续引入仅承担缓存、限流或协调，不作为唯一业务事实；附件对象存储按实际需求另行设计。

### B. API 与前后端契约

6. **请求与响应**：统一成功/失败封套、分页、时间及时区、Decimal、枚举和错误码。
7. **参数校验**：字段类型、范围、长度、嵌套深度、请求体大小、未知字段、跨字段约束在 API 与领域服务双层校验。
8. **接口幂等**：修复 PROCESSING 重入、并发重复执行、失败终态和匿名主体唯一性等缺陷；请求幂等与业务事实唯一性分开治理。
9. **性能优化**：慢查询、N+1、索引、分页、EXPLAIN 和 Query Count 预算；先解决 SQL 和数据访问问题，不以盲目缓存替代。
10. **前后端契约**：OpenAPI 与实际路由、请求/响应 schema、前端类型保持一致；契约变更必须同步文档和回归测试。

### C. 身份、权限与安全

11. **身份认证**：登录、会话、CSRF、密码策略、员工离职失权、会话撤销和高风险操作验证统一。
12. **权限控制**：按路由、权限码、物业范围、数据范围、敏感字段范围建立矩阵；后端服务层必须二次授权。
13. **数据安全**：PII 加密、HMAC 查询、密钥分离轮换、字段脱敏、导出控制、备份加密和数据保留策略。
14. **请求安全**：HTTPS、Cookie、CSRF、CSP、来源校验和安全重定向。
15. **接口防护**：多维限流、Webhook 签名/时间戳/重放保护、请求体限制、敏感查询审计和越权测试。

### D. 架构与运维治理

16. **分层结构**：视图/API 层、领域服务层、模型/持久化层职责清晰；禁止跨模块直接写表绕过服务。
17. **配置管理**：环境配置与秘密管理分离；生产 fail-fast；配置项有类型、默认值、合法范围和说明。
18. **错误处理**：异常映射统一、错误码稳定、敏感堆栈不暴露给客户端，任务失败可重试或进入死信。
19. **日志记录**：结构化日志、审计日志、访问日志分离；禁止记录敏感原文；request_id 可贯穿链路。
20. **测试覆盖**：模型、服务、API、集成、并发、故障注入和浏览器 E2E 分层验证；关键资金/权限/库存路径必须验证数据库最终状态。

### E. 跨模块可靠性与生命周期

21. **业务状态机与跨模块闭环**：明确状态图、合法迁移、操作者、原因、时间和跨模块副作用；不得只依赖散落的 status 字段赋值。
22. **异步任务与故障恢复**：按 Q3 实施 Outbox + Django Worker；提供租约、重试、退避、死信、重放和积压巡检。
23. **数据生命周期与隐私治理**：按 Q5 分类保留、到期处置、法律保全、匿名化和审计。
24. **备份、恢复与灾难恢复**：按 Q4 建立全量+binlog/PITR、异地加密备份和恢复演练。
25. **部署、迁移与发布管理**：环境隔离、expand-migrate-contract、迁移锁风险评估、备份和发布回滚；CI 是发布门禁。
26. **监控告警与运营管理**：按 Q6 建立结构化日志、异常追踪和关键业务告警；指标平台后续扩展。

## 4. 分阶段整改优先级

### P0：资金、隐私、可靠性和生产安全阻断项

- Q1 手机号加密 + HMAC 索引及密钥治理。
- Q2 身份证件历史明文迁移、读写路径切换和旧字段清理。
- Q3 Outbox + Django Worker 基础设施及支付补偿、任务幂等。
- 接口幂等并发安全、业务事实唯一性和退款额度并发保护。
- 支付、账本、退款负债、库存 Hold 和 Folio 的一致性巡检。
- Q7 生产配置 fail-fast、Mock 支付关闭、PII 密钥强制配置。
- 日志和异常中敏感字段脱敏。

### P1：工程治理与可运营性

- API 错误封套、OpenAPI/前端契约和参数 Schema。
- 状态迁移统一、权限矩阵自动化和跨物业越权测试。
