# PMS2 三项业务政策基础设施实施方案（2026-11-09）

## 1. 文档目的与边界

本文承接《PMS2三项业务政策DEC待确认说明_2026-11-09.md》，将已确认的 DEC-01、DEC-02、DEC-03 转化为可实施的基础设施任务。

本方案最初用于指导基础设施建设。根据 2026-11-09 main 分支实际代码复核，DEC-02 已有模型、迁移、登记服务、退房接入、财务查询和退款执行结算实现；本轮又修复了前台押金凭证无法进入候选原支付集合的问题。DEC-01、DEC-03 仍受未决参数约束，不启用未确认的收费规则。DEC-02 的实现仍须以 SQLite/MySQL CI、端到端业务测试和财务验收结果为准，不得将代码已存在等同于最终验收通过。

基线：GitHub 仓库 `wulei0214/django-hotel2` 的 `main`。实施必须遵循现有 Django ORM、服务层事务、不可变财务凭证、物业隔离和 SQLite/MySQL 双数据库约束。

## 2. 当前代码事实

### 2.1 DEC-01 提前离店

- `ReservationRoom` 已包含 `reservation`、`rate_plan`、`check_in`、`check_out`、`nightly_rates`、`amount`，适合按房间明细计算实际入住晚数。
- `RatePlan` 当前只有文本型 `cancellation_policy` 和 `deposit_policy`，没有独立提前离店配置。
- `CancellationPolicy` 的取消语义不能直接复用为提前离店罚金语义。
- 当前 `check_out_stay()` 尚未按提前离店后的实际晚数重算；本阶段不改变它的收费行为。

### 2.2 DEC-02 待退款负债

- `Folio` 关联 `Reservation`，`LedgerEntry` 记录不可变账务凭证。
- `Refund` 当前关联单笔 `Payment`，具有申请、审批、执行人和执行状态。
- 当前已有 `RefundLiability`（迁移 `apps/billing/migrations/0023_refund_liability.py`），关联 Property、Reservation、Folio，并通过 `source_payments` 记录候选原支付；该候选关系不表示已分配退款金额。
- `apps/billing/liabilities.py::register_refund_liability()` 在最后一间房退房事务内登记负债；`apps/reservations/front_desk_services.py::check_out_stay()` 已接入，负余额不再因等待财务退款而直接阻止离店。
- 财务可通过 `/api/v1/billing/refund-liabilities` 查询负债与候选支付；退款申请可关联 `refund_liability_id`，但退房时不自动创建 Refund。
- `BillingService.execute_refund()` 只有在退款执行成功并形成 REFUND 账本凭证的同一事务中，才减少负债余额；部分退款保留余额，全部执行成功才结清。
- 多笔原支付仍未自动分配。当前登记服务检查候选支付的可退余额总额，但不会替财务决定具体 Payment 分配。
- 2026-11-09 复核发现押金使用 `DEPOSIT/deposit:` 凭证而普通收款使用 `PAYMENT/payment:`；本轮已修复候选识别并增加 API 回归测试。

### 2.3 DEC-03 押金

- `DepositPolicy` 已按 `RatePlan` 关联，字段包含 `deposit_type`、`deposit_value`、`due_before`、`refundable`。
- `Property.timezone` 已存在，为 IANA 时区名。
- `Reservation.total_amount` 是整张预订单房费总额。
- 当前 `DepositPolicy` 缺少最低/最高金额；`record_deposit()` 不读取政策模型，也没有执行 30%、截止时间及计划级可退性。
- 多个 RatePlan 共存时的整单最低/最高金额合并规则尚未确认。

## 3. 目标数据结构（设计要求，尚非代码）

### 3.1 提前离店政策

建议新增独立的 `EarlyDeparturePolicy`，按物业和 RatePlan 归属，至少应具备：
- 物业、RatePlan 关联；
- 启用/停用状态及生效区间；
- 罚金类型与数值（字段形态待 DEC-01 参数确认后定稿）；
- 创建、更新人及时间；
- 版本/快照标识，确保历史预订不会因后续改价而静默改变政策。

订单侧需要保留预订时适用的政策快照；具体快照字段和时点须在负责人确认政策快照规则后确定。不能仅依赖实时关联的 RatePlan 当前政策。

逐个 `ReservationRoom` 计算；每条明细的实际入住晚数由实际离店日期与该明细入住日期决定，房费金额以该明细 `nightly_rates` 快照为准。罚金公式在 DEC-01 参数确认前不得实现为生产收费逻辑。

### 3.2 待退款负债

已新增独立 `RefundLiability` 待退款负债实体，当前字段与关系如下（不再是待建模型）：
- Property；
- Reservation；
- Folio；
- 负债金额、币种；
- 形成时间、形成原因；
- 状态（待财务处理、部分处理、已处理、冲销/异常等状态需结合会计语义定稿）；
- 幂等键；
- 创建人、操作审计和时间戳。

另需设计负债与原 Payment 的分配明细关系，以支持一个负债对应多笔支付、或按原支付拆分追踪；但分配策略尚未确认，基础结构不得自动推断分配金额。

财务后续发起 Refund 时，应将 Refund 与负债/分配明细关联，防止同一待退款金额重复申请。只有关联退款实际执行成功并形成账务凭证，才可减少对应待退款余额；部分退款保留剩余负债。不能以退款申请已创建或已批准作为负债完成条件。

退房放行与负债登记必须在同一事务内完成；登记失败则退房不得部分成功。退房服务必须锁定一致的 Reservation/Folio/负债相关记录，并建立唯一幂等约束。

### 3.3 押金政策

在不启用政策执行前，可先扩展结构以承载明确已确认的政策：
- 押金比例固定政策值 30%（不把比例写死在代码中，仍作为可审计配置/版本快照）；
- 计算基数标识为整张 Reservation 的 `total_amount`；
- 按 RatePlan 保存最低金额、最高金额；
- 按 RatePlan 保存 `refundable`；
- 截止规则为入住日期当地时间 00:00 前 48 小时；
- 创建订单时不足 48 小时则立即到期/收取；
- 物业当地时区取 `Property.timezone`。

但多 RatePlan 整单最低/最高合并规则、上下限应用顺序、政策快照时点仍未确认。相关字段可先进行兼容性设计，强制校验和生产执行必须等待这些参数补齐。不得给最低/最高字段填默认金额。

## 4. 分阶段实施顺序

### 阶段 A：只读结构与数据关系设计
1. 核实现有模型、约束、迁移依赖和服务调用入口。
2. 完成三项政策模型关系图和字段字典。
3. 确认历史数据迁移策略；旧文本政策字段保留，不直接转换成未经确认的结构化规则。
4. 增加只读管理展示/诊断，不触发收费和退款行为。

### 阶段 B：DEC-02 负债基础（工程验收完成；业务决策待确认）

1. [x] 新增 `RefundLiability`、候选原支付 M2M 关系及 `0023_refund_liability` 迁移。
2. [x] 增加幂等键、金额范围/状态约束、物业/预订/账单/币种关联校验。
3. [x] 增加 `register_refund_liability()`，并接入最后一间房退房事务。
4. [x] 财务查询 API 与 Refund 关联字段已接入；退房不自动创建 Refund，也不自动分配多笔支付金额。
5. [x] `BillingService.execute_refund()` 由外层 `transaction.atomic` 包裹；退款账本凭证、Refund 成功状态、负债余额/状态、Payment 状态、押金回减和审计事件同事务提交。
6. [x] 普通收款与前台押金凭证类型候选识别测试通过。
7. [x] 真实退房服务测试通过：押金形成负余额后登记负债、关闭账单、不自动创建 Refund。

14. [x] 财务负债列表跨物业隔离测试通过；本物业财务账号不能读取其他物业负债。

18. [ ] 多笔原支付候选的金额分配/分配关系仍待负责人明确。当前财务可以逐笔选择单个 Payment 发起 Refund，但系统不创建金额分配明细，也不自动推断分配。该业务参数确认前，DEC-02 不标记为正式业务验收完成。


注意：当前代码登记时仍要求找到有效原支付候选且候选可退余额足以覆盖负债；这项保护不允许被绕过。若真实业务出现无法映射到原支付的负余额，应作为账务异常阻断自动退款并进入人工核对，而不是伪造支付来源。

### 阶段 C：DEC-03 押金结构与快照
1. 扩展 DepositPolicy 最低/最高金额字段，允许既有数据以 NULL 过渡，不自动填值。
2. 定义订单级政策快照结构。
3. 实现物业时区截止时间计算工具和纯函数测试。
4. 在多 RatePlan 合并规则、上下限裁剪顺序和快照时点确认前，不启用收款强制校验。
5. 参数补齐后再接入 `record_deposit()`，以服务层统一执行。

### 阶段 D：DEC-01 提前离店结构与结算
1. 新增独立 EarlyDeparturePolicy 及版本/快照结构。
2. 以 ReservationRoom 为计算单元，读取 nightly_rates 快照。
3. 增加提前离店结算明细及幂等标识，避免重复退房/重复计罚。
4. 罚金类型、基数、未配置行为、快照时点未确认前，只允许管理配置和只读预览，不允许生成收费凭证。
5. 参数确认后接入退房服务并测试多房、部分房间提前离店、跨日、时区、重放等场景。

## 5. 必须覆盖的测试矩阵

| 领域 | SQLite | MySQL | 业务场景 |
|---|---|---|---|
| DEC-01 | 模型/约束/服务单测 | 迁移、约束、并发锁 | 多房仅一间提前离店；多晚价格快照；重复请求 |
| DEC-02 | 负债登记、退款关联、事务回滚 | 行锁、唯一约束、并发重复登记 | 多笔支付、部分退款、退款失败、重复执行、跨物业隔离 |
| DEC-03 | 时区纯函数、模型约束 | 迁移、Decimal 精度、唯一约束 | 48小时边界、DST/时区、临近入住、多个 RatePlan |
| 回归 | 既有预订/退房/退款测试 | 全量 MySQL 回归 | 不改变未确认政策下的旧行为 |

禁止以 SQLite 通过替代 MySQL 验证；涉及 `select_for_update`、唯一约束和并发行为必须在 MySQL 真实测试。

## 6. 发布与验收门禁

- 每个阶段均需模型、迁移、服务、API、权限、审计、测试和中文文档同步。
- 不得在迁移中为历史订单推断或补造收费政策。
- 不得删除或改写历史 Payment、Refund、LedgerEntry 等财务事实。
- 不得把负余额直接置零、把待退款负债记成退款完成。
- 不得让前台绕过现有退款申请/审批/财务执行职责分离。
- 不得把政策配置变更追溯应用到历史订单。
- SQLite 和 MySQL CI 必须针对同一 main SHA 通过；相关失败必须修复后重新验收。
- 本文档提交不等于代码开发完成，也不代表 PMS2 最终验收通过。

## 7. 尚待负责人补齐的决策参数

以《PMS2三项业务政策DEC待确认说明_2026-11-09.md》第 7 节为唯一决策来源。本方案不重复推断或填补：
- DEC-01：罚金类型/数值、比例基数、政策快照时点、未配置政策时行为。
- DEC-02：多笔原支付的负债分配规则（本轮工程实现不自动分配；需负责人确认是否以财务逐笔选择单个 Payment、每笔 Refund 独立关联的方式作为正式规则）。
- DEC-03：各 RatePlan 最低/最高金额、上下限应用顺序、政策快照时点、多 RatePlan 合并规则。

上述参数补齐后，应先更新决策基线，再实施对应的生产规则。
