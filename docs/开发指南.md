# 开发与本地运行指南

## 1. 环境要求

- Python 版本以项目 CI 配置为准。
- 当前依赖锁定见根目录 `requirements.txt`。
- 默认数据库配置为 MySQL；也支持 PostgreSQL、SQLite（主要用于测试/轻量开发）。
- 推荐使用独立虚拟环境，禁止把真实生产密钥写入仓库。

## 2. 获取代码

```bash
git clone https://github.com/wulei0214/django-hotel2.git
cd django-hotel2
git checkout main
git pull origin main
```

已有本地仓库更新：

```bash
git switch main
git pull --ff-only origin main
```

## 3. 安装依赖

Windows PowerShell：

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

macOS / Linux：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

## 4. 配置数据库和环境变量

默认数据库引擎为 MySQL，默认库名为 `hotel`。请先创建数据库，并设置：

```text
DJANGO_ENV=dev
DJANGO_DEBUG=true
DJANGO_SECRET_KEY=本地随机密钥
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
DJANGO_DB_ENGINE=mysql
DJANGO_DB_NAME=hotel
DJANGO_DB_USER=你的数据库用户
DJANGO_DB_PASSWORD=你的数据库密码
DJANGO_DB_HOST=127.0.0.1
DJANGO_DB_PORT=3306
DJANGO_TIME_ZONE=Asia/Shanghai
DEFAULT_PROPERTY_CODE=DEFAULT
PAYMENT_WEBHOOK_SECRET=本地随机回调密钥
```

如果仅需快速执行测试，可按 CI 的 SQLite 配置运行；不要将 SQLite 测试结果等同于 MySQL/PostgreSQL 生产并发验证。

## 5. 数据库迁移与启动

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate
python manage.py runserver
```

启动后主要入口：

- 顾客端新预订页：`http://127.0.0.1:8000/reserve/`
- API OpenAPI JSON：`http://127.0.0.1:8000/api/v1/openapi.json`
- Django Admin：`http://127.0.0.1:8000/admin/`
- 顾客端正式直订页：`http://127.0.0.1:8000/reserve/`
- 旧顾客预订页 `/booking/`：已冻结（AUTH-02，302 → `/reserve/`）；旧写路径代码保留待退役，不要在其上新增功能。

物业数据需先初始化。当前默认物业编码由 `DEFAULT_PROPERTY_CODE` 控制，默认值为 `DEFAULT`。房型、物理房间、房价计划、每日价格及库存日历必须有数据，顾客端才会显示可订结果。库存日历同步命令示例见 Phase 2 开发记录。

## 6. 测试与质量门禁

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
```

提交前至少检查：

1. Django system check 通过。
2. migration check 通过。
3. 自动化测试通过。
4. 新增/修改 API 的成功、参数错误、权限错误、幂等、并发边界测试覆盖。
5. 业务 UI 的空数据、加载中、错误提示、窄屏布局检查。
6. 文档与界面路由、字段、截图同步更新。

CI 是合并依据之一，但 SQLite CI 不能替代真实 MySQL/PostgreSQL 的锁、隔离级别和并发压测。

## 7. 分支与提交规范

- 本项目当前按项目负责人确定的协作方式，以 `main` 作为唯一开发和验收基线；经负责人明确授权的修改可直接提交 `main`。
- 每次提交前先读取最新 `main`，更新文件时校验最新文件 SHA，避免覆盖并发提交。
- 不创建与本项目约定冲突的长期功能分支；如未来调整分支策略，须由项目负责人另行确认。
- 每个 PR 必须写中文说明：本次开发内容、修复问题、影响模块、迁移/配置变化、测试结果、已知限制、UI 是否变化及截图更新情况。
- Commit 标题可使用 Conventional Commits 类型，但正文与 PR 描述必须中文，例如 `feat(pms2): 完成顾客预订页`。
- 不允许只写“更新代码”“修复问题”而不列出具体内容。

## 8. 每次推送必须同步维护的文档

| 变更类型 | 必须更新 |
|---|---|
| 新增业务模块/模型/API | `docs/系统架构说明.md`、对应模块文档、`docs/更新日志.md`、README |
| Bug 修复 | `docs/更新日志.md`，必要时更新对应业务规则和回归用例 |
| 页面结构/交互修改 | `docs/PMS2员工中心最终UI规范与权限管理入住管理一致性审查.md`、README 页面说明；使用最新截图替换旧截图 |
| 配置/依赖/部署变化 | 本文、`docs/系统架构说明.md`、部署说明 |
| 数据库迁移 | 模块文档注明迁移影响、备份/回滚注意事项 |

## 9. 版本边界

PMS 3.0 不新增业务功能，仅处理现有功能完善、Bug 修复、权限/安全、性能、兼容性和自动化回归。任何新业务需求应先单独讨论是否属于下一版本，不能以“顺手优化”为由扩张范围。
