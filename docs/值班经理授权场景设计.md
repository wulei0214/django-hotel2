# 值班经理授权场景设计（RBAC 决策 4 落地稿）

> 对应《PMS_RBAC_权限管理改造方案_评审稿》评审点 3："哪些场景需要值班经理授权？"
> 用户决策：由开发方基于项目代码与功能做经验总结与预测，按本文场景开发；
> 后续补充遗漏场景——因此每个场景都以**独立权限点**落地（而非写死角色名），权限授予
> 在「权限管理」页可随时调整，这是健壮性的核心保障。

## 一、设计原则

1. **动作级授权**：每个高危场景一个独立 Django 权限点（hotelapp app，中文权限名），
   不复用笼统的 change_*。新增场景 = 新增权限点 → 角色组勾选 → 视图挂判断，三步完成。
2. **默认最小授权**：高危权限点默认只授予 值班经理、店长；前台默认无。
3. **菜单不承担安全**：菜单按权限显隐，但直接 URL/AJAX 由视图层权限判断兜底。
4. **单店现实**：店长/值班经理常为同一人（老板本人），暂不做金额阈值与双人复核；
   复核链以「冲账人/原因/审计日志」留痕，多店上线时按 §三.5 升级为双人复核。

## 三、扩展指南（健壮性约定：新增一个授权场景的固定三步）

1. **定义权限点**：在 `hotelapp/migrations/` 新迁移中 `Permission.get_or_create`
   （codename 英文稳定码，name 中文「能××」，挂到对应模型 ContentType）；
2. **默认授权**：同迁移中授给默认角色组；并在 `apps/identity/permission_admin.py`
   的 `ACTION_PERMS` 注册（矩阵页「高危动作」区即出现勾选行）；
3. **视图挂判断**：`request.user.has_perm("hotelapp.<code>")`，失败返回 403 中文提示；
   补一条权限测试（参照 `hotelapp/tests.py` 的 HighRiskActionPermissionTests）。

> 反模式警示（历史教训）：不要用 `_has_role(user, "值班经理")` 这类组名硬编码判断高危动作
> ——组名换目录/兼岗授权时会静默失效。本次已把反结账/未到/夜审/净房放行/财务入口全部
> 从组名判断迁到权限点判断。

## 四、与评审方案的对应关系

- 方案 §3.1 高风险动作边界 → S1–S7 全部按"独立权限 + 条件留痕"实现；
- 方案 §4.3 职责分离 → 单店阶段以审计留痕替代双人复核；`ApprovalRecord` 结构
  预留在方案 §5.1，多店启用时把"冲账人"字段升级为"执行人 + 复核人"两字段即可；
- 方案 §7 验收清单 → 已由 `hotelapp/tests.py` 覆盖：注册止血、URL 直达拒绝、
  动作与 CRUD 分离（拥有 view 不代表拥有 reverse/execute）、导出独立校验。
