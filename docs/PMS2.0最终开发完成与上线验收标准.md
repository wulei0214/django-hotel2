# PMS 2.0 最终开发完成与上线验收标准

> 文档状态：正式验收基线（负责人确认）
> 适用范围：`wulei0214/django-hotel2` 的 PMS 2.0 既定开发范围
> 基线分支：`main`
> 生效原则：本文件定义 PMS 2.0 最终验收的统一判定门槛；与既有正式决策基线冲突时，身份、权限、敏感字段、财务审批和业务规则以对应正式决策为准，本文件规定其验收方法与通过条件。
> 重要声明：本文件是验收标准，不是项目完成报告；列入本文件的功能不因此被认定为已经实现或验收通过。

---

## 1. 目的与不可变原则

本标准用于判定 PMS 2.0 是否真正完成开发、是否具备进入正式上线准备的质量条件，以及是否允许启动 PMS 3.0。

验收遵循以下原则：

1. **以冻结范围为准**：只验收已批准的 PMS 2.0 需求、正式决策、开发基线及其批准变更，不临时扩大范围。
2. **以真实实现为准**：模型存在、页面存在、接口返回成功、代码已提交，均不能单独证明功能完成。
3. **以业务结果为准**：必须核对操作前后数据、关联记录、状态、金额、权限和审计结果。
4. **以目标数据库为准**：MySQL 8 是最终数据库验收依据；SQLite 通过不能替代 MySQL 8 验收。
5. **以证据为准**：每项结论必须绑定代码版本、环境、测试用例和可复核证据。
6. **开发与验收分离**：开发人员提交自测结果，独立验收人员复核；关键安全、财务和数据完整性项目不得仅由开发人员自证。
7. **不允许带阻断项通过**：P0、P1、P2 缺陷必须全部关闭；强制测试不得存在未解释的失败、跳过或无证据执行。
8. **不以文档替代代码，也不以代码替代文档**：需求、实现、数据库、API、页面、测试和运行证据必须相互对应。

“最终验收通过”表示在明确的版本、环境、数据规模和测试范围内达到本标准，不代表系统永远不存在缺陷，也不替代正式生产变更审批。

## 2. 验收范围与范围冻结

### 2.1 范围依据

验收范围以以下资料的当前有效版本为依据：

- PMS2 身份认证与员工住客账户体系改造开发方案 2.0；
- PMS2 全业务中心闭环补齐开发基线 2.0；
- 已确认的敏感字段权限边界、角色权限、审批、财务、夜审及旧入口退役决策；
- 已批准的专项开发方案、缺陷整改任务和变更记录；
- 本文件及其后续经负责人批准的修订版。

历史评审稿、过期代码审查报告和历史测试记录仅作为追溯材料，不自动构成当前验收依据。

### 2.2 范围冻结规则

正式验收启动前，项目负责人必须确认：

- 本次验收对应的 Git commit SHA；
- 纳入验收的需求编号和任务清单；
- 已批准的范围变更及其影响；
- 暂缓项、排除项及其批准依据；
- 目标运行环境、数据库版本、配置和数据规模。

验收期间不得通过临时删除需求、降低缺陷等级、缩小测试范围或将未完成能力改称“后续优化”来制造通过结论。任何范围调整必须有负责人书面批准、影响分析和更新后的追踪矩阵。

| 身份权限 | 九个正式角色的菜单、API、数据范围和敏感字段边界通过 |
| 安全合规 | 不存在未关闭 P0/P1/P2 安全或合规缺陷，审计要求通过 |
| 自动化测试 | 强制测试全部通过，无未解释的失败或跳过 |
| 系统运行 | 部署、Redis、日志、健康检查、任务调度、备份恢复通过 |

## 4. 业务中心验收标准

本项目按 11 个业务中心验收。每个中心必须先核对真实代码现状，再依据已批准需求确认适用的页面/API形态。对明确不要求页面的后台能力，不得机械要求新增页面；但必须有正式需求依据。

| 业务中心 | 必须验证的业务能力与结果 |
|---|---|
| 员工中心 | 员工档案、邀请/账号开通、入职、任职、角色授权、调岗、暂停、离职、再入职及历史保留；身份、任职和岗位授权不得混为一体 |
| Guest 360 | 客人档案、联系人、共享手机号人工复核、证件保护、预订联系人与实际入住人区分、同住人、入住/房间段、账单及业务时间线关联 |
| 房态与库存中心 | 房型、房间、房态、价格日历、逐日库存、库存冻结/释放、停售/恢复，以及清洁维修状态联动 |
| 会员中心 | 会员与 Guest 关联、等级及状态变更、暂停/恢复、历史记录和重复关联控制 |
| 预订与入住中心 | 可订检查、预订创建/确认/取消、入住、实际入住人、续住、换房、退房、未到处理、异常恢复及库存账务联动 |
| 财务与账单中心 | Folio、费用、收款、退款申请/审批/执行、冲销、发票/对账（如已纳入范围）、营业日归属和账务一致性 |
| 夜审与营业日中心 | 营业日读取、夜审预览、全部阻断项收集、警告区分、执行、失败恢复、运行历史、重开及复核 |
| 清洁与维修中心 | 任务生成、分配、开始、完成、检查、驳回、维修登记/处理/恢复、超时处理及房态库存联动 |
| 审计与合规中心 | 关键事件完整记录、检索/详情授权、敏感信息最小化、留存口径、数据库级不可变保护及完整性核验 |
| 报表分析中心 | 指标定义、数据来源、计算口径、物业/角色范围、时间范围、页面或约定交付入口、导出和数据核对 |
| 通知与待办中心 | 事件触发、去重、待办分配/处理/转交、失败重试、源业务状态核验、处理结果回写及审计 |

### 4.1 单项功能的完整交付定义

每个适用功能至少核验：

1. 需求编号和业务规则明确；
2. 数据模型/字段及迁移存在且正确，或有理由复用既有模型；
3. 领域服务承载业务规则，事务边界正确；
4. API 或其他正式操作入口存在并执行服务端授权；
5. 页面/菜单接线正确（若需求要求页面）；
6. 状态转换、异常分支、幂等和并发行为正确；
7. 审计、通知及跨模块联动符合要求；
8. 自动化测试覆盖正常、异常、权限和边界场景；
9. 实际验收证据能证明数据和业务结果正确。

仅有模型、迁移、静态页面、占位按钮、Mock 数据、未接线 API 或仅有 happy-path 测试，均不得判定功能完成。

## 5. 核心业务端到端闭环

以下链路为强制验收链路。测试应在专用验收数据和 MySQL 8 环境执行，并保留请求、响应、数据库核对及审计证据。

### 5.1 预订—入住—退房—清洁—库存

至少验证：

1. 创建预订并检查逐日房型库存；
2. 同一时段并发预订时不超卖；
3. 确认预订及适用的押金/支付记录；
4. 入住并登记实际入住人、同住人及房间段；
5. 执行续住、换房及入住期间费用；
6. 结账退房，核对 Folio、Payment、LedgerEntry 和营业日；
7. 退房后生成清洁任务；
8. 清洁完成、检查通过后正确更新房态；
9. 维修中的房间不得被错误计入可售库存；
10. 任务重复触发、请求重放或失败重试不得产生重复业务事实。

### 5.2 财务—审批—营业日—夜审

至少验证：

1. 业务费用、收款和账务分录生成；
2. 退款申请、审批、执行及失败/拒绝路径符合正式决策；
3. 冲销与原始分录关联，不能直接改写历史账务；
4. 金额、币种、精度、借贷方向和营业日归属正确；
5. 夜审预览能一次性收集全部阻断项并区分警告；
6. 存在硬阻断时不能执行夜审；
7. 执行成功后营业日状态及运行历史正确；
8. 执行失败、重复执行、并发执行和恢复场景正确；
9. LedgerEntry、ChargeLine、TaxLine、Payment、Folio 等数据按既定口径可核对；
10. 夜审后新入住、营业日重开等行为符合正式规则。

### 5.3 员工—身份—权限—审计

至少验证：

1. 管理员按正式流程创建员工并开通账号；
2. 登录身份、员工档案、物业任职和岗位授权分别正确；
3. 九个正式角色只能执行获准操作；
4. 越权 API、修改 URL/对象 ID/请求体物业 ID 均不能绕过授权；
5. 敏感字段显示、揭示、导出和理由记录符合决策；
6. 调岗、暂停、离职后旧授权按规则失效；
7. 再入职不破坏历史任职和授权记录；
8. 关键操作能够追溯到用户、物业、对象、时间、原因和结果。

### 5.4 清洁—维修—房态—库存

至少验证：

1. 退房或其他正式事件触发清洁任务；
2. 任务分配、执行、检查、驳回和重新处理状态正确；
3. 维修登记、维修中、恢复及取消状态正确；
4. 净房放行权限和双重复核按正式决策执行；
5. 清洁或维修任务不得错误地提前释放可售库存；
6. 状态变化同步到房态和库存；
7. 重复操作、并发操作和失败回滚正确。

## 6. 数据库验收

数据库最终验收以项目目标 MySQL 8 版本为准。必须同时覆盖全新建库和已有数据库升级两条路径。

| 检查项 | 通过标准 |
|---|---|
| 字段定义 | 字段含义、类型、长度、精度、默认值、NULL规则和维护方明确 |
| 关系完整性 | 外键/关联约束正确，关键业务不存在未解释孤儿记录 |
| 唯一性 | 业务编号、工号、幂等键等唯一规则符合业务范围 |
| 索引 | 高频过滤、排序、关联和唯一校验具备合理索引，并有执行计划或性能证据 |
| 状态规则 | 状态值和允许迁移与正式状态机一致，非法迁移被拒绝 |
| 金额 | 使用精确数值类型，币种、舍入、正负值和合计口径一致 |
| 时间 | UTC/本地时间、物业时区、业务时间和营业日归属明确 |
| 事务 | 关键多表写入原子性正确，失败能够回滚 |
| 并发 | 锁、唯一约束、冲突重试正确，不重复扣款/退款/入住/分配 |
| 迁移 | 空库可完整迁移，已有库可升级，无未提交迁移漂移 |
| 历史数据 | 账务、审计、审批、订单和员工历史按保留规则处理，不随意物理删除 |
| 数据对账 | 迁移前后数量、金额、状态、关联和抽样明细可核对 |
| 恢复能力 | 备份文件有效，恢复演练成功并记录耗时和数据时间点 |

强制命令和证据至少包括：

- `python manage.py check --deploy`（按实际部署配置执行并解释所有例外）；
- `python manage.py makemigrations --check --dry-run`；
- 全量迁移从空库执行记录；
- 已有数据库升级记录；
- MySQL 8 下约束、索引、事务和并发测试结果；
- 迁移前后数据核对报告；
- 备份及恢复演练记录。

SQLite 测试可以作为快速反馈，但不能替代以上 MySQL 8 证据。

## 7. API 验收

必须生成完整 API 路由清单，并将每个接口映射到需求、视图、服务、权限码、请求/响应契约和测试用例。

每个 API 至少检查：

- URL、HTTP Method、认证方式和响应封套；
- 权限码、对象级授权、物业数据范围和默认拒绝；
- 请求参数、类型、长度、枚举、日期和金额校验；
- 服务层业务规则和状态迁移；
- 幂等键、请求指纹、重复提交和并发冲突；
- 分页、稳定排序、日期范围和最大页大小；
- 统一错误码、HTTP 状态和可安全展示的错误消息；
- Request ID 生成、透传和日志关联；
- 敏感字段最小化、导出理由、限流和审计；
- OpenAPI 与实际路由/字段/错误响应一致。

### 7.1 强制 API 安全用例

至少覆盖：

1. 未登录访问受保护接口；
2. 已登录但无权限访问；
3. 普通角色访问高权限操作；
4. 修改 URL 中的对象 ID 进行水平越权；
5. 伪造或修改 property_id；
6. 跨物业读取或写入；
7. 伪造 action_code 或 payload 字段；
8. 重复审批、重复退款、重复收款和重复夜审；
9. 非法状态迁移；
10. 敏感字段揭示、批量导出和 PII 枚举；
11. 非法分页、超大分页和不合理日期范围；
12. 高频调用、限流和限流存储故障场景。

HTTP 200、接口返回 success 或前端隐藏按钮均不能单独证明接口验收通过。

## 8. 身份、角色与敏感信息验收

### 8.1 九个正式角色

必须按已确认的角色权限基线逐一验证：

- 前台；
- 值班经理；
- 财务；
- 店长；
- 客房服务员；
- 夜审员；
- 餐饮服务员；
- 餐饮主管；
- 停车安保。

每个角色均需验证登录、菜单、页面操作、API、对象范围、物业范围、敏感字段、导出、审批和审计。仅有角色账号或菜单截图不构成验收证据。

### 8.2 敏感信息

按正式决策核验：

- 身份证件加密存储、密钥配置、解密权限和揭示审计；
- 手机号码按角色遮罩，完整揭示受权限、理由和审计控制；
- 工资数据的查看/修改边界；
- 财务退款、冲销和审批分离；
- 批量导出权限、理由、审批（如适用）、脱敏和审计；
- Guest 联系方式、共享手机号及重复身份核验；
- 日志、错误响应、审计列表和导出不得泄露明文 PII、密码、Session Key、令牌或密钥。

### 8.3 安全零容忍阻断项

以下问题任一项可复现，即安全验收不通过：

- 未认证读取受保护数据；
- 水平或垂直越权；
- 敏感信息未授权泄露；
- 未授权审批、退款、冲销或财务写入；
- 绕过领域服务修改关键业务状态；
- 审计记录可被普通业务账号篡改；
- 重放或并发导致重复扣款、重复退款或关键业务重复执行；
- 生产环境暴露调试能力、测试支付路径、默认密钥或高危配置。

## 9. 自动化测试与回归验收

### 9.1 测试层次

必须有可执行测试并保留结果：

| 层次 | 必须覆盖 |
|---|---|
| 单元测试 | 业务规则、状态转换、权限决策、金额和日期计算 |
| 服务层测试 | 事务、回滚、幂等、并发、异常恢复 |
| API 测试 | 认证、授权、参数、响应、错误码和数据范围 |
| 数据库测试 | MySQL 约束、索引、迁移、锁和并发 |
| 集成测试 | 跨模块数据流、事件触发和状态同步 |
| E2E 测试 | 真实页面/接口操作的核心业务链路 |
| 安全测试 | 越权、敏感数据、导出、限流、审计 |
| 回归测试 | 既有业务、旧入口迁移和历史兼容范围 |

### 9.2 强制通过率

- P0/P1/P2 对应的强制测试：通过率必须为 100%；
- 核心业务端到端链路：通过率必须为 100%；
- 九角色权限矩阵中的强制用例：通过率必须为 100%；
- 迁移、MySQL 8 和数据完整性强制用例：通过率必须为 100%；
- 强制测试不得有未解释的 skip、xfail、屏蔽、条件跳过或未执行项；
- 测试失败必须定位原因，不能通过删除测试或放宽断言制造绿色结果。

测试总数和代码覆盖率不能代替业务覆盖。建议核心业务服务行覆盖率不低于 90%，但覆盖率仅作为辅助门槛；关键规则、权限分支、金额计算、状态迁移、并发冲突和异常路径必须有针对性测试。

测试报告必须记录 commit SHA、执行命令、环境、数据库版本、测试总数、通过数、失败数、跳过数、耗时和报告附件。

## 10. Redis、运行环境、部署与运维验收

### 10.1 Redis

如果正式配置将 Redis 用于共享缓存、幂等协调、限流或其他跨进程能力，必须验证：

- 多进程/多 worker 共享状态；
- 键空间、TTL、过期和清理策略；
- 连接池、超时和认证配置；
- Redis 中断时的降级行为及安全边界；
- 缓存失效、并发竞争和恢复；
- 不能把“使用 Redis”当成限流、幂等或分布式锁正确的证明，业务逻辑仍须独立测试。

### 10.2 运行与部署

必须在目标验收环境验证：

- 配置与密钥由环境注入，不提交仓库；
- Django、WSGI、MySQL、Redis 和静态资源正常；
- readiness 能准确反映关键依赖状态；
- 日志结构化且 Request ID 能贯通请求、服务和审计；
- 后台任务有互斥锁、超时、重试、失败记录和告警/人工处理路径；
- Cookie、CSRF、HTTPS、安全响应头和可信代理配置符合部署基线；
- 服务重启、迁移顺序和优雅关闭正确；
- 备份成功，且恢复演练真实成功；
- 监控能发现数据库、缓存、任务积压和关键业务错误。

生产 HTTPS/HSTS 等已由负责人明确暂缓的事项，应列为“批准的上线前置条件/部署门禁”，不能误报为已完成；正式生产上线前仍必须按部署决策完成。

## 11. 性能与容量验收

性能验收必须先冻结测试环境和容量假设，至少记录：

- CPU、内存、磁盘、网络；
- Python/Django、WSGI、MySQL、Redis 版本和配置；
- 数据规模、热点分布、连接池；
- 并发用户数、请求模型、测试时长；
- 预热方式、采样窗口和压测工具版本。

建议初始目标（负责人确认后作为正式性能门槛）：

| 场景 | 初始目标 |
|---|---:|
| 普通查询 API | P95 ≤ 500 ms |
| 普通写入 API | P95 ≤ 800 ms |
| 复杂报表查询 | P95 ≤ 3 s |
| 核心事务 | 无重复写入、无数据丢失、无未处理死锁 |
| 稳态压测 | 达到冻结并发量，错误率和资源使用符合容量基线 |

以上响应时间是建议起始值，不是脱离硬件和数据规模的绝对 SLA。正式验收前必须由项目负责人确认目标并冻结。压测报告应提供 P50/P95/P99、吞吐量、错误率、资源曲线、慢查询和瓶颈分析。不得只提供单次手工请求耗时。

## 12. 旧入口与兼容治理验收

按已批准的旧入口退役矩阵逐项核验：

- 旧页面是否重定向、只读、关闭或返回约定状态；
- 旧 API 是否仍可写入；
- 旧模型/旧表是否仍被页面、命令、信号或后台任务使用；
- 是否存在双写、双重业务入口或绕过 PMS2 服务层的写路径；
- 旧数据映射是否有来源、匹配规则、人工复核、冲突处理和对账结果；
- 退役后菜单、文档、OpenAPI、测试和运维说明是否同步。

不得为追求“代码整洁”而直接删除账务、审计、订单、审批或员工历史数据。退役必须遵循冻结的迁移、只读、归档和删除门禁。

## 14. 缺陷分级与关闭规则

| 等级 | 定义 | 最终验收要求 |
|---|---|---|
| P0 | 重大安全漏洞、资金错误、严重数据丢失、权限绕过、核心业务全面不可用 | 必须修复并复测 |
| P1 | 重要业务流程错误、关键功能不可用、关键数据关联/账务错误 | 必须修复并复测 |
| P2 | 已批准范围内的功能缺陷、边界错误、可复现的数据或权限问题 | 必须修复并复测 |
| P3 | 不影响安全、资金、数据完整性、权限、业务正确性和主要操作的轻微体验问题 | 可按批准的遗留清单管理 |

最终验收时 P0、P1、P2 未关闭数量必须为 0。P3 仅可在独立验收人员确认其确实不影响业务正确性和安全后保留；必须有缺陷编号、影响说明、责任人、修复期限、规避措施和复核计划。

缺陷等级不得由开发人员单方面下调。发现缺陷后必须保留复现步骤、影响范围、根因、修复 commit 和回归证据。

## 16. 验收组织与流程

### 阶段一：开发完成申报

开发负责人提交范围冻结清单、代码 SHA、迁移、文档、接口、测试和 16 项证据包目录。缺少关键交付物不得进入下一阶段。

### 阶段二：独立静态审查

独立审查人员对照正式基线检查代码、模型、服务、路由、权限、菜单、旧入口和测试。识别占位实现、未接线功能、绕过服务层的写入和文档失真。

### 阶段三：自动化与集成验证

在目标 CI/验收环境执行强制测试、MySQL 8、Redis、安全、API、集成和 E2E 测试。失败必须修复并在新 SHA 上重跑相关测试及必要回归。

### 阶段四：实际环境业务验收

由验收人员在专用数据环境执行九角色登录、核心业务链路、敏感字段、财务对账、夜审、清洁维修、备份恢复和部署验证。涉及用户本地数据库的备份、预览、清理、账号初始化和登录检查，必须由用户在本地亲自执行并提供证据；远程代码审查不得冒充本地验收。

### 阶段五：最终签署

逐项检查所有门槛和证据，形成最终报告。任何强制项不通过，退回整改；修复后必须在新 commit SHA 上复验。

## 17. 最终结论与 PMS 3.0 门禁

最终只允许三种结论：

| 结论 | 判定条件 | 是否允许启动 PMS 3.0 |
|---|---|---|
| 通过 | 所有强制维度通过；P0/P1/P2 为零；证据包完整；独立验收签署 | 允许 |
| 有条件整改 | 存在未关闭缺陷、证据缺失、环境未验收或批准前置条件未完成 | 不允许 |
| 不通过 | 存在重大缺陷、核心链路失败、数据/资金错误或安全问题 | 不允许 |

只有“通过”结论允许冻结 PMS 2.0 最终版本，并启动 PMS 3.0。CI 全绿、代码提交完成、页面能够打开或开发人员声明完成，均不能单独触发 PMS 3.0。
