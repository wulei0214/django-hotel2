# PMS2 财务账务与营业日 P0/P1 专项整改需求（2026-11-09）

> 目标：确保 Folio、ChargeLine、Payment、Refund、Deposit、LedgerEntry、RefundLiability、NightAuditRun 与 BusinessDate 的金额和状态可重建、不可篡改、可恢复。先复用现有账务模型、BillingService、夜审服务及 MySQL append-only guards，不重复造账本。

## 1. 现状基础与核查边界

项目已有 Folio、ChargeLine、Payment、Refund、LedgerEntry、押金/退款负债和夜审相关模型/服务；MySQL append-only 部署说明已覆盖 AuditEvent、LedgerEntry、CashierShiftMovement 等只追加事实保护。不能将账务系统描述为从零开始。

本轮需重新核查：
- 每种业务事实是否恰好产生对应账本凭证；
- Folio 余额是否由明细/账本权威重建，还是存在可被绕过的冗余余额；
- 所有账本写入是否走唯一服务；
- CLOSED 检查是否覆盖所有写入口和异步任务；
- 夜审重复执行、失败恢复、并发退房/退款是否安全；
- SQLite/MySQL 对 append-only 保护的差异及生产部署状态。

## 2. P0 账本不可变与凭证语义

- LedgerEntry 一经入账不得 UPDATE/DELETE；更正只能追加反向冲销或独立调整凭证。
- Payment、Refund、Deposit 等状态型表按状态机更新，不应一律 append-only；禁止通过直接改状态伪造资金事实。
- PAYMENT、DEPOSIT、REFUND、CHARGE、REVERSAL/ADJUSTMENT 等类型语义必须唯一、明确；抵扣不得使用 REFUND。
- 每个凭证具备 property、folio、reservation（适用时）、currency、amount、business_date、occurred_at、posted_at、source_type/source_id、idempotency_key、created_by 等必要追溯字段；先盘点已有字段，缺失才迁移。
- 金额精度统一 Decimal；借贷方向/正负号约定必须写入字段字典和计算服务。
- 数据库约束阻止重复业务凭证；应用层幂等不能替代唯一约束。
- MySQL append-only guards 需有生产部署与 DBA 验收记录；CI 临时库通过不代表生产已部署。

## 3. P0 Folio 与账本一致性对账

建立只读核对服务，至少检查：
- ChargeLine ↔ CHARGE/相应收入凭证；
- Payment ↔ PAYMENT 凭证；
- Deposit ↔ DEPOSIT 凭证；
- Refund ↔ REFUND 凭证；
- 冲销/调整 ↔ 原凭证和反向凭证；
- Folio 展示余额 ↔ 全部有效业务事实；
- RefundLiability ↔ 原始负债、调整、已成功退款净额；
- 物业、币种、Reservation、Folio 关系一致。

差异不能自动改写账本或 Folio。生成差异报告，按来源分类，授权财务发起更正申请，经审批后使用追加凭证/专用服务处理。每次核对保存 run_id、计算口径版本、时间、数量、差异金额和处理状态。

## 4. P0 CLOSED 营业日保护与 D5 特批

所有账务写服务必须校验目标业务日期对应 BusinessDate 状态，不能只在页面或单个 API 做判断。普通写入对 CLOSED 拒绝。特殊退款、冲账、补记和调整必须经过申请/审批，专用服务执行，保留原业务日期和实际操作日期。

时间字段至少区分：
- occurred_at：交易实际发生时间；
- provider_confirmed_at：渠道确认时间（支付相关）；
- received_at：PMS 接收时间；
- posted_at：账本入账时间；
- business_date：归属营业日；
- property_timezone：业务日期计算依据；
- operation_at：员工/任务实际操作时间。

跨午夜回调不能简单以服务器当前日期覆盖业务日期。不得通过普通请求参数传入任意 business_date 绕过保护。审批必须包含金额、币种、原凭证、原因、证据、申请/审批人；申请人与审批人分离。重开营业日是独立授权操作，不自动替代特批流程。

## 5. P1 夜审可靠性与并发

- NightAuditRun 有明确唯一范围（Property + BusinessDate + run type/版本），重复请求不得重复过账。
- 夜审处理每个 Folio/房间的收费必须有幂等键和唯一凭证约束。
- 中断后可从持久化进度恢复；不能简单重新执行全部产生重复费用。
- 夜审与退房/退款/补记竞争时使用统一锁序和一致业务日期策略。
- 夜审失败保留错误、已处理项目、未处理项目和恢复入口；重试前校验账务事实。
- 夜审完成后禁止普通角色修改历史业务日期；经批准重开要生成新运行/修订记录，不能删除旧记录。

建议锁序需结合实际外键和服务调用验证后冻结；不得在未检查当前锁序前机械实施。统一目标是所有竞争服务遵守相同顺序，并具备 MySQL 死锁检测、有限重试和幂等。

## 6. 权限、审计与不可变部署

- 财务创建收费/收款/退款申请/调整的权限分离。
- 退款审批、冲账审批、营业日重开、特殊营业日操作使用独立权限码。
- 申请人与审批人分离；高权限 break-glass 必须填写理由并告警。
- 导出、敏感字段揭示、批量财务操作按既有决策要求记录 reason code。
- AuditEvent 记录主体、动作、对象、物业、前后状态摘要、原因、request_id、时间；不得记录支付密钥或敏感完整报文。
- 保持 MySQL append-only guards；生产环境 DBA 部署、运行账号权限和备份恢复均需单独验收。

## 7. P0/P1 验收矩阵

P0：凭证不可改写；每笔资金事实与凭证一一对应；重复支付/退款不重复入账；Fol io 余额可重建；退款/调整不超额；CLOSED 普通写入被所有入口拒绝；D5 审批后才能执行；跨日时间字段正确。

P1：夜审重放不重复收费；中断恢复；并发退房/退款/夜审无账实差异；统一锁序；对账差异可定位并经审批修复；生产 append-only 保护验证。

SQLite 做业务规则、事务回滚和 API 测试；MySQL 做 InnoDB 并发、行锁、唯一约束、触发器和死锁恢复。所有报告绑定同一最新 main SHA。
