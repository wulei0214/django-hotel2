## 2. 为什么这是缺口（而非「不属于 NS-E-05 范围」）

### 2.1 T02-3 的本质就是「缺权限码」

`ApprovalActionSpec` 必填 `request_permission` 与 `approve_permission` 两个**权限码字段**。

要登记 `privacy.retention_execute`，**必须先确定这两个权限码**。而按 NS-E-05 裁定：

> 「不批准批量扩展 L3 权限码，按具体业务动作逐项审批」
> 「未逐项批准前，**不改** `apps/identity/registry.py` 与迁移」

→ **T02-3 的修复本质上是一次「逐项权限审批」**，与 FIN-06/MB-11 同属一类，只是当时未被列入候选清单。

### 2.2 不纳入的后果

| 后果 | 说明 |
|---|---|
| 数据清理功能无法正规启用 | `plan_retention_cleanup(dry_run=False)` 的审批门无法被合法满足 |
| 缺口不会自动消失 | 即使 FIN-06/MB-11 全部获批，T02-3 仍是 OPEN |
| 存在被「顺便绕开」的风险 | 如测试所示，操作者会直接用裸 QuerySet 改审批状态，跳过三层校验 |

## 3. 建议

### 3.1 将 `privacy.retention_execute` 补入 NS-E-05 候选清单

需按 NS-E-05 六要素补一份候选方案：

| 字段 | 待定内容 |
|---|---|
| 候选权限码（request） | 建议复用 `hotelapp.finance_access`（现有）或新申请 `privacy.retention_request` |
| 候选权限码（approve） | 建议复用 `billing.refund_approve`（现有高危审批）或新申请 `privacy.retention_approve` |
| 业务动作 | 「隐私数据保留期满清理」的申请与审批执行 |
| 适用岗位 | 申请：财务/店长；审批：店长/值班经理（**须与退款审批分离**） |
| 数据范围 | 仅本物业 |
| 操作类型 | 审批（申请 / 批准 / 执行三步分离） |
| 审批要求 | 是（第二人审批） |
| 审计要求 | `AuditEvent` 记录申请/批准/执行；执行写 `RetentionExecution` |
| 拒绝场景 | 无审批 / 审批非本物业 / 未通过 / 申请人自执行 |
| 测试用例 | 已具备（我已在 `fix_verify.txt` 中验证 5 种拒绝 + 1 种正向） |

> **优先建议复用现有码**，避免新增权限码带来的治理成本。但「复用哪个」属业务授权决策，**须负责人裁定**。

### 3.2 若负责人决定不纳入

则应明确：
- `privacy.retention_execute` 的审批动作码登记移交 PMS3；或
- 数据清理功能标记为「不可用/仅 dry-run」，并写入限制说明。

**无论哪种，都需明确书面结论，不能让 T02-3 悬空。**
