### 2.5 第 4 项：建议的唯一正式状态体系

> **性质：建议（WAITING_OWNER）。** 依任务书第 14 章"由负责人确认最终口径后，统一修改"，本节只给方案、风险与影响，**不代替负责人拍板**，也**不在本轮实施**任何受其约束的文档改动。

#### 2.5.1 建议方案：采用任务书第 16 章 8 词为唯一正式状态体系，PMS3 8 态降级为"处置码列"

| 建议状态 | 建议定义（用于**条目状态列**） | 建议定义（用于**结论列**） | 解除/闭合条件 |
|---|---|---|---|
| `DONE` | 条目已实现，且验证与文档证据闭合，绑定 SHA/证据路径 | 交付物已完成并落档 | — |
| `PASS` | **不用于条目状态**（需求不能被"通过"） | 门禁/验收结论通过且无保留项 | — |
| `PASS_WITH_RESERVATIONS` | 部分完成、缺验证或缺文档，**保留项须逐条列明** | 结论有条件通过，保留项逐条列明 | 保留项闭合 → `DONE`/`PASS` |
| `WAITING_OWNER` | 等待负责人裁定，未经批准不得实现 | 同左 | 负责人裁定落档 → 回到原状态 |
| `WAITING_ENVIRONMENT` | 等待生产或外部环境资源（服务器/DBA/渠道/Redis/密钥托管/演练环境） | 同左 | 资源到位 → 回到原状态 |
| `DEFERRED_TO_PMS3` | 已批准移交 PMS3.0，PMS2.0 不实施 | 同左 | PMS3 承接条目建立 |
| `NOT_STARTED` | 尚未开发（含仅设计、仅登记、确认不实施） | 同左 | 重新立项 |
| `FAIL` | 验收不通过 / 已正式否决 | 门禁不通过 | 重新立项 → `NOT_STARTED` |

**一条词表、两种用法（建议）**：
- **条目状态列**（需求行、遗留项、生产项）：`DONE` / `PASS_WITH_RESERVATIONS` / `WAITING_OWNER` / `WAITING_ENVIRONMENT` / `DEFERRED_TO_PMS3` / `NOT_STARTED` / `FAIL`（7 个，`PASS` 不用）。
- **结论列**（验收门禁、交付报告）：`PASS` / `PASS_WITH_RESERVATIONS` / `DONE` / `FAIL`。
- **处置码列**（PMS3 继承用，**不是状态**）：保留 PMS3-REQ-001 的 8 个原值 `INHERIT`/`EXTEND`/`CARRY_OVER`/`NEW`/`WAITING_OWNER`/`WAITING_EXTERNAL`/`DEFERRED`/`DEPRECATED` **一字不改**，仅在台账侧**并列显示**（新增引用列，不改写 PMS3 文档）。
- 理由：状态回答"**现在是什么**"，处置码回答"**下一版做什么**"，两者正交；混列是 12 态与 9 态长期并存却从未对账的根因（PMS3 矩阵 `:65-66` 已明文"不改变 89 条的处置码"，说明 PMS3 侧不能被状态统一改造）。

#### 2.5.2 建议的合法状态跃迁（单向 + 回落，禁止跳步）

```
NOT_STARTED ──▶ PASS_WITH_RESERVATIONS ──▶ DONE
      │                    │                 │
      │                    └──▶ FAIL ◀────────┘（验收不通过）
      ▼
WAITING_OWNER ──(负责人裁定落档)──▶ 回到裁定前状态（不得直接跳 DONE）
WAITING_ENVIRONMENT ──(资源到位)──▶ 回到等待前状态
```
