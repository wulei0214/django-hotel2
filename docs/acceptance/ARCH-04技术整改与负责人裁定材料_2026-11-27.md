#### 3.1.6 可选方案与代价

**方案 A｜维持现状 + 只读盘点（不迁移未映射行）**

- 内容：不登记任何未映射行；旧表保留；员工中心继续显示「历史员工档案：尚未映射」；把 `--report` 盘点结果作为正式核对产出。
- 代价：零实现；但 R1 持续存在（未映射在岗员工永远无法进入新栈），R7 无法关闭。
- 风险：业务侧会持续提「某些人排班查不到」的重复需求。

**方案 B｜人工逐条确认后登记映射（受控迁移）**

- 内容：以 `--report` 未映射清单为输入，**人工确认**后逐条 `--link`（幂等，走服务层，落审计）；未确认的保留在旧表；对每条登记写明 `match_method` 与 `reason`。
- 代价：人工工时随未映射行数线性增长；需配套「同名人歧义裁决」规则与抽样复核（台账有 `mapping_status` 可支撑 `MATCH_CANDIDATE` / `CONFLICT` / `IGNORED` 状态流转）。
- 风险：R2/R3/R4 的误匹配与虚假在职风险 —— 必须先定「旧 `启用=False` 行是否映射」「超白名单职务如何落 `position_code`」两条规则。

**方案 C｜批量匹配 + 冲突清单（工号/姓名/职务启发式）**

- 内容：以「物业 + 姓名 + 职务」启发式批量生成候选，写入 `mapping_status=MATCH_CANDIDATE`，冲突项置 `CONFLICT`、明确忽略置 `IGNORED`，人工只审 `CONFLICT` 与高风险项。
- 代价：需新增候选生成逻辑（可复用 `link_legacy_staff` 命令扩展），并新增「候选→已链接」的审批/复核用例；台账 `MappingStatus` 已预留 `MATCH_CANDIDATE`/`CONFLICT`/`IGNORED` 三态，可直接承载。
- 风险：启发式误判；**不得**自动把 `MATCH_CANDIDATE` 提升为 `LINKED`（提升路径必须经服务层与人工确认）。

**方案 D｜不迁移旧行，只在新栈「重建」在岗人员（脱钩历史）**

- 内容：未映射旧行视为「历史人员」，在新栈按当前在岗名单**重新建档**（不从旧表搬历史），旧表只作历史查证锚点；台账登记 `IGNORED` + `note` 说明忽略原因。
- 代价：需负责人给「旧人在岗判定」的权威来源（无系统来源时需人工台账）；新档案与旧行**永久无映射关系**，历史追溯链断（仍可按旧 `员工id` 在归档表与旧业务快照列中人工对位）。
- 风险：与 R5 叠加——同一人在新旧两套体系并存，薪酬与岗位口径分裂更明显。

#### 3.1.7 推荐及理由

**推荐：方案 B（人工逐条确认后登记映射）**，并以方案 A 为**默认兜底**（未确认的一律不动）。

理由：
1. 台账模型已把「映射唯一 / 可追溯 / 异常可恢复 / 删除保护」四件事做实（B1），且**状态机已预留** `MATCH_CANDIDATE` / `CONFLICT` / `IGNORED`（`models.py:613-618`）→ 方案 B/C 的落地**不需要新表、不需要新迁移**。
2. 方案 B 的每一步都有可核对产物：`--report` 盘点 → `--link` 登记（写 `identity.legacy_staff_mapped` 审计，含操作者/前值/后值）→ `--recover` 恢复；符合「一切事实现取现核」纪律。
3. 方案 C 的收益（省人工）不足以抵消其在 R2/R3/R4 上的误判代价；建议在 B 执行中积累「歧义类型」后，再决定是否升级到 C 的**候选生成**（候选生成不自动提升为已链接）。
4. 方案 D 断链代价与 C14（保留策略）冲突：旧表若最终保留，历史映射链就应尽量完整。
5. 无论选哪个方案，**先决条件是负责人给出两条映射规则**（旧 `启用=False` 是否映射；超白名单职务如何落 `position_code`），否则 R3/R4 无法闭合。

#### 3.2.8 可选方案与代价

**方案 A｜不迁移，保留旧表 + 归档（维持现状）**

- 内容：新档案仍不承载薪酬；旧表与归档表保留明文；不新增任何权限码与展示位。
- 代价：零实现、零泄露面、零审计改造。
- 风险：S2 事实分裂长期存在；旧表一旦按 C14 退役，薪酬只剩归档表（仍是明文，但已无主档语义）。
- 解除依赖：C14 的最终口径。

**方案 B｜迁移到 `StaffProfile`（自然人层）**

- 内容：新增 `monthly_salary`（或 `salary_text` 保留字符串语义）+ `service_years` 字段，值自旧表迁入（含未映射行的处理规则）。
- 代价：跨物业继承（一人薪酬对多物业可见）；需新增迁移 + 映射规则 + 审计；需与 Q-03 的可见性裁定同步。
- 风险：S1 + S5；**必须**同时落地独立权限码与读取审计，否则等于给通用查看权开后门。

**方案 C｜迁移到 `PropertyStaffMembership`（任职层）**

- 内容：薪酬落在「物业 × 任职」上，一人多物业需分别维护。
- 代价：数据录入成本按任职数放大；调薪要逐任职更新；需明确「跨物业调动时薪酬如何结转」。
- 风险：S4、S5 的另一面；实现复杂度高于 B。

**方案 D｜迁移但只做「引用/指针」不搬值**

- 内容：新档案只存旧行指针 + 是否已裁定，不复制薪酬值；任何读取仍需回旧表 → 与 C1（在线零读旧表）直接冲突。
- 代价：与已闭环的 C1 门禁冲突，需要为该指针开例外（例外清单是「只允许离线命令」）。
- 风险：重新打开 C1 绕过口；**不建议**。

#### 3.2.9 推荐及理由

**推荐：方案 A（不迁移，维持现状），并把 C12 与 Q-03 的可见性裁定合并处理。**

理由：
1. **当前无任何业务能力依赖薪酬**：在线零入口、Admin 未注册、新档案零承载、导出不含薪酬列 → 迁移的直接收益为零（Q-03 已核「财务岗位当前无任何路径能读到薪酬」）。
2. 迁移会**新增高敏字段落点**而仓库无字段级遮罩、无读取审计 → 收益为零、风险为高（S1、S3）。
3. 归档链已把旧薪酬完整落档（明文列 + 恢复演练覆盖），历史可追溯性不依赖「迁移到新档案」（S2 的分裂只影响「哪一处是权威」而非「能否查到」）。
4. 若业务确有定薪需求，应**先由 Q-03 裁定可见性（谁看、能否导出、是否留审计）**，再据此决定 C12 的落点；**顺序反了会出现「有数据、无管控」**。
5. 方案 B/C 的**建模口径差异（自然人层 vs 任职层，S5）影响面大**，必须由负责人先定口径，不宜由整改侧默认。

> 若负责人裁定为「迁移」，本报告的建议附带顺序：① 先定落点层级（B 还是 C）→ ② 先做 Q-03 的可见性与审计裁定 → ③ 再开工迁移；且迁移必须与 `staff`/`legacy_staff_archive` 的**权威口径**一并写明，避免第三处副本。

**方案 A｜长期保留旧表（只读冻结）**

- 代价：零实现；表继续占用存储；`staff` 的备份责任需在生产侧明确（仓库内无备份作业证据）。
- 风险：T5 随时间累积（未映射旧行只增不减）；无技术到期压力，容易演变为「永久遗留」。

**方案 B｜归档落定 + 保留旧表（推荐基调）**

- 内容：先在**生产库**执行 `archive_legacy_finance`（含 staff spec）并留存 `LegacyArchiveRun` 批次证据，跑 `legacy_restore_drill` 演练通过 → 旧表继续保留，但历史事实已有归档冗余；把「归档批次 + 行数 + 摘要 + 演练结果」作为 C14 的审批附件。
- 代价：一次离线归档 + 一次恢复演练；归档表含**明文薪酬列**（C12 未裁定时是已知敏感面，须限制归档表访问）；`legacy_staff_archive` 与 `staff` 双份存储。
- 风险：归档快照非逐行等价（只 7 列映射）→ T4 仍在；归档表明文列成为新的敏感面（Q-03 D8 已提「保持现状 + 明文禁止接入读通道」）。

**方案 C｜保留旧表 + 冻结写路径 + 登记到期条件（与 A/B 组合）**

- 内容：在 A 或 B 之上补一条**书面到期条件**（例如「C11 关闭 + C12 裁定 + 归档批次验证通过 + 负责人书面批准」四条件同时满足后重新评估），到期前不动表。
- 代价：需负责人签字确认条件；不产生实现成本。
- 风险：条件若不可观测（如「归档批次覆盖全部旧行」无自动断言）会变成空条款 → 建议条件写成**可执行的查询/命令**（`--report` 未映射 = 0、`LegacyArchiveRun` 行数 == `staff` 行数、`legacy_restore_drill` exit 0）。

**方案 D｜退役并物理删表（本轮不建议）**

- 内容：删表 + 删相关 FK/映射。
- 代价：需要新增迁移（删表 + 清 `legacy_staff` 指向）、需要**先**补一套「重建旧表 + 回填」的迁移以保住回滚能力（当前 `0022` 反向依赖旧表存在）；
- 风险：T1/T2/T3/T5/T6 全部正面命中；**且**必须先完成 C11、C12（否则未映射行与薪酬归属无解）；与 ARCHITECTURE §1.7/§1.8 直接冲突。
- **本报告明确不推荐**，且在下列条件全部满足前**不得**进入该方案：（a）C11 关闭且未映射 = 0；（b）C12 裁定并落位；（c）生产归档批次已执行且行数覆盖全部旧行；（d）`legacy_restore_drill` 通过；（e）回滚迁移（重建旧表 + 回填）已实现并在 MySQL 脏数据上实测可逆；（f）负责人书面批准。

#### 3.3.7 推荐及理由

**推荐：方案 B + C 组合（先归档落定、再补到期条件，旧表继续保留）。**

理由：
1. **不删表**是任务书与 ARCHITECTURE 的硬约束（任务书 §A：「旧表暂时保留」「不得在没有数据映射、备份、回滚方案时删除旧表」；`ARCHITECTURE.md:24-25`）。方案 D 的五个前置条件中有三个（C11 / C12 / 回滚迁移）**当前都不具备**。
2. 方案 B 能用**最小代价**消除最高风险 T1：归档批次一旦落定且行数覆盖，旧表的历史事实就有了第二副本；这是「保留旧表」与「防止永久遗留」之间的最优解。
3. 方案 C 把「保留」从默认状态变成**有条件的、有到期复查点的**状态，避免 T5 无限累积；条件写成可执行命令/查询，保证不流于形式。
4. 归档落定同时为 C11/C12 的裁定提供**数据基础**（未映射行的字段分布、薪酬缺失率只能在真实旧表上统计）。
