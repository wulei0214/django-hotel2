# 改密冷却期窗口边界缺陷——修复前证据归档

本目录保存**修复前**的取证日志，用于证明缺陷真实存在、以及修复的必要性。
修复后的同基线证据在 `docs/acceptance/evidence/g14-final-20261127/`。

## 1. 缺陷现象

同一根因在两次全量回归里以两种形式出现：

| 证据文件 | 被测树 | 规模 | 结果 |
|---|---|---|---|
| `../g14-20261127-defect-baseline/sqlite-full-6b30df5.log` | `6b30df5` | 2220 例 | **1 FAIL**：`test_cooldown_blocks_even_correct_password_after_threshold` |
| `../g14-20261127-defect-baseline/sqlite-dbg-6b30df5.log` | `6b30df5`（工作区含 2 项未提交变更） | 2220 例 | OK（skipped=32） |
| `sqlite-789d313-prefix-fail.log`（本目录） | `789d313` | 2224 例 | **1 FAIL**：`test_cooldown_quota_resets_when_window_rolls_over` |

第一次是**偶发**（同一提交复跑即绿）——因为判定结果取决于「5 次连续失败」与
「第 6 次请求」是否恰好落在限流计数窗口的两侧；第二次是**确定性**——滑动窗口
修复落地后，原来钉住弱语义的用例与新实现直接冲突。

两次红的断言文本完全一致：

```
AssertionError: 302 != 200 : 冷却期内即使口令正确也不得放行改密
```

`302` = 改密成功重定向，即**用户提供的正确口令穿过了冷却期**。

## 2. 根因

`apps/core/rate_limit.py` 的计数按**纪元对齐的固定窗口**分桶：

- 计数行按 `window_start`（纪元对齐）唯一；
- 判定（peek）只看「当前窗口起点」那一条行，跨过窗口边界即视为计数归零；
- 冷却期**没有独立的 `lock_until`**，完全由该计数行派生
  （见 `apps/identity/services.py::check_current_password`）。

于是「阈值达成后的冷却」实际只持续到**当前窗口结束**——落在窗口末尾时，
冷却几乎是零长度，紧接着的一次请求（哪怕口令正确）就能穿过。

## 3. 为什么这是缺陷而不是「窗口化限流的固有语义」

合同口径写的是**固定 300 秒**，三处既有基线一致：

| 出处 | 原文 |
|---|---|
| `apps/identity/services.py::check_current_password` | 「进入 `PASSWORD_REAUTH_COOLDOWN_SECONDS` 秒冷却，冷却期内即使密码正确也拒绝校验」 |
| `docs/acceptance/前端opt-in与三开发线复核修复报告_2026-11-26.md` | 「5 次失败后进入 300 秒不可重试窗口」 |
| `docs/文档处置清单_重复过期冲突_2026-11-27.md` | 「5 次失败后进入 300 秒冷却」 |

固定窗口把冷却截断到 0~300 秒，**短于合同约定的 300 秒**——这是实现未兑现
既有约定，不是新增或变更安全策略。因此按「合同一致性缺陷」定级处理，
不属 L4 策略变更。

另有裁定时使用）。
