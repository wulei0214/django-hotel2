## 二、逐项要求核查

### 要求 1：密码修改只能作用于当前授权账户 —— **符合**

| 检查点 | 事实 | 证据 |
|---|---|---|
| 目标账户来源 | `force_password_change` 通过 `StaffProfile.objects.filter(user=request.user).first()` 定位**当前登录用户的本人档案** | `hotelapp/views.py:1010` |
| `system_info` | `user = request.user`，后续所有写操作均以 `user` 为目标 | `hotelapp/views.py:1327`、`:1349-1357` |
| 写入范围 | 仅 `request.user.set_password(new1)` + `user.save(update_fields=("password",))`；强制改密页额外只改**本人** `StaffProfile` 的 `must_change_password`/`last_password_change` | `hotelapp/views.py:1029-1034`、`:1349-1357` |
| 表单参数面 | 两个 POST 处理只读取 `new_password1` / `new_password2` 两个键，**不存在** `user_id` / `员工id` / `pk` 之类的目标标识参数 | `hotelapp/views.py:1015-1016`、`:1333-1334` |
| 模板 | 改密表单只有两个密码输入框，无隐藏目标字段 | `templates/pms/me.html:54-62`、`templates/force_password_change.html` |

**结论**：不存在「代改他人密码」或「越权指定目标」的参数面，改密目标恒为当前授权账户。

### 要求 2：密码策略、会话失效和重新认证 —— **部分符合（1 项缺口）**

#### 2.1 密码策略 —— 符合

| 机制 | 实现 | 证据 |
|---|---|---|
| 最小长度（服务端） | `len(new1) < 6` → 拒绝 | `hotelapp/views.py:1017-1018`、`:1335-1336` |
| 两次一致性 | `new1 != new2` → 拒绝并回显原因 | `:1019-1020`、`:1337-1338` |
| Django 校验器 | `validate_password(new1, user=request.user)`，启用 4 个校验器：`UserAttributeSimilarityValidator`（不得与账号/姓名相似）、`MinimumLengthValidator`、`CommonPasswordValidator`（弱口令字典）、`NumericPasswordValidator`（纯数字） | `hotelapp/views.py:1023-1027`、`:1341-1345`；`hotel/settings.py:160-165` |
| 回归 | 两次不一致被拒且旧口令不变 | `apps/identity/test_platform.py:322-329` |

#### 2.2 会话失效 —— 符合

| 机制 | 实现 | 证据 |
|---|---|---|
| 其他会话失效 | `set_password()` 改变 `session_auth_hash` → Django 的 `AuthenticationMiddleware` 在后续请求校验哈希不符即视为未登录，其他已登录会话随之失效 | `hotelapp/views.py:1029`、`:1349` |
| 当前会话保持 | `update_session_auth_hash(request, request.user)` 同步刷新当前会话哈希 | `:1040-1041`、`:1347-1351` |
| 审计 | `AuditEvent.record(action="identity.password_changed", entity_type="StaffProfile", actor=request.user)` | `:1036-1039`、`:1358-1362` |
| 回归 | 改密后当前会话仍可访问 `/system/`（200） | `apps/identity/test_platform.py:319-320`、`apps/identity/test_cookie_isolation.py:650-652` |
| 强制改密不可绕过 | `staff_required` 对 `must_change_password` 用户，把除 `/force-password-change/` 与 `/logout/` 外的**所有**路径重定向到强制改密页（fail-closed） | `hotelapp/views.py:130-134` |

#### 2.3 重新认证 —— **不满足（唯一安全缺口）**

两处改密**均未要求二次身份确认**：

- 表单不要求输入**当前密码**（`templates/pms/me.html:57-58`、`templates/force_password_change.html` 仅有新密码与确认新密码）；
- 无「近期认证」时间戳校验、无「重新登录后再改密」流程；
- 只要持有有效会话，即可直接改密并保持该会话。

**风险**：会话被劫持（XSS 窃取 Cookie、共享终端残留会话等）时，攻击者可直接改密，从而长期占有账号，且改密会**主动使受害者其他会话失效**、清除其强制改密标记（`hotelapp/views.py:1352-1357`），进一步掩盖痕迹。

**处置建议（待负责人裁定，未擅自实现）**：改密表单增加「当前密码」字段并以 `request.user.check_password()` 校验；或引入「近期认证时间戳」（登录/改密时记录，超过阈值要求重新登录）。属安全增强，需负责人确认后纳入 PMS3.0 范围。

### 要求 3：系统信息不得泄露密钥、数据库凭据和敏感环境变量 —— **符合**

| 检查面 | 事实 | 证据 |

| 密钥扫描 | 仓库有独立 `scripts/scan_secrets.py` 且已入 CI（`secret-scan` job），本轮全量回归通过 | `.github/workflows/`、`scripts/scan_secrets.py` |

### 要求 4：未授权访问必须拒绝 —— **符合**

| 场景 | 行为 | 证据 |
|---|---|---|
| 匿名访问 `/system/`、`/force-password-change/` | `login_required(wrapped, login_url='/login/')` → 302 到 `/login/` | `hotelapp/views.py:136`、`:114-135` |
| 已登录但无有效任职（档案非在职 / DEFAULT 任职非 ACTIVE / 无有效角色授权，fail-closed 判定链） | `raise PermissionDenied("当前账号没有有效任职或岗位授权，无法访问员工域页面")` → Django 默认 403 处理 → 渲染 `templates/403.html` | `hotelapp/views.py:87-91`（判定链）、`:127-129`（拒绝）、`templates/403.html` |

## 四、结论与未关闭事项

### 结论

| 要求 | 判定 |
|---|---|
| 1. 密码修改只作用于当前授权账户 | **PASS** |
| 2. 密码策略 / 会话失效 / 重新认证 | **PARTIAL** —— 策略与会话失效 PASS；**重新认证缺口** |
| 3. 系统信息不泄露密钥、凭据、敏感环境变量 | **PASS** |
| 4. 未授权访问必须拒绝 | **PASS** |
| 5. 文档说明归属与保留理由 | **PASS** |
| 归属裁定（暂留 hotelapp，不迁目录） | **PASS**（本报告给出理由） |

**总体判定：PASS_WITH_RESERVATIONS** —— 唯一保留项是改密缺二次认证。

### 未关闭事项（如实登记，均需负责人裁定，未擅自实现）

1. **改密无二次身份确认**（要求 2）。建议方案：表单增加「当前密码」字段 + `check_password` 校验；或引入近期认证时间戳。需确认是否纳入 PMS3.0，且需评估对「管理员重置密码后用户自助改密」流程的兼容性。
2. **两处改密逻辑重复**：`hotelapp/views.py:1017-1027` 与 `:1335-1345` 为同规则的两份复制。后续调整需同步，存在漂移风险。建议提取共用校验函数——属重构，不在本轮（架构治理为渐进式）范围，登记为 PMS3.0 候选。
3. **客户端最小长度弱于服务端**：`templates/pms/me.html:57-58` 与强制改密模板用 `minlength="6"`，而 Django `MinimumLengthValidator` 的默认下限更高，客户端提示会先于后端拒绝出现，造成「填了 6 位仍被拒」的观感。属文案与配置一致性小项，不构成安全缺口。
4. **`403.html` 的应用内触发路径已确认**（§要求 4），与 ARCH-03 矩阵结论一致；本轮未修改该模板。
