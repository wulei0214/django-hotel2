## 二、基线结果（本轮首次建立）

| 接口 | 状态 | 中位数 | p95 | SQL 条数(中位/最大) |
|---|---|---:|---:|---:|
| `/api/v1/front-desk/overview` | 200 | 22.52 ms | 24.49 ms | 15 / 15 |
| `/api/v1/front-desk/reservations` | 200 | 36.31 ms | 59.05 ms | 11 / 11 |
| `/api/v1/front-desk/arrivals` | 200 | 16.75 ms | 17.88 ms | 7 / 7 |
| `/api/v1/front-desk/rooms` | 200 | 14.24 ms | 14.51 ms | 6 / 6 |

原始 JSON：`docs/acceptance/evidence/arch-perf-baseline-20261125/perf-mysql.json`。

### 观察

1. 四个接口 SQL 条数**中位数与最大值相等**，说明查询数稳定、不随数据量波动——与 `apps/api/test_query_budget.py` 的防 N+1 断言互相印证。
2. `reservations` p95（59 ms）高于中位（36 ms），存在偶发抖动；在本机样本量（12）下不足以判定为缺陷，建议后续以更多样本复核。
3. 全部接口中位延迟均低于 40 ms，本机环境下没有明显热点。

---

## 三、边界与限制（不得超出解读）

- **本机测量，非生产容量证明**。生产需在目标服务器 + 真实数据量 + 并发下另行压测（`PRODUCTION_PENDING`）。
- 样本量 12，p95 代表性有限；结论用于**同环境前后对比**，不用于对外性能承诺。
- 未测量写接口与报表导出（导出已有行数上限保护）。
- 未涉及缓存效果评估：当前 dev 为 LocMemCache，生产 Redis 未部署。

---

## 四、后续使用方式

1. 任何优化改动前后，各跑一次本脚本，对比 `median_ms` / `p95_ms` / `queries_median`。
2. 若查询数上升或 p95 显著劣化（建议阈值：>+50%），需在 PR 说明中给出原因。
3. 生产接入后，用同一脚本在预发布环境复测，替换本节基线。
