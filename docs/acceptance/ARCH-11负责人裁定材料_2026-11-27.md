## 一、裁定项一：是否新增专用审批历史表

### 1.1 待决问题

> 是否批准在 `apps.billing` 新增一张**只追加**的审批事件表 `billing_approvalevent`（模型 `ApprovalEvent`），并同步扩展 `GET /api/v1/approvals` 的检索维度（增加申请人 / 审批人 / 时间区间）？
>
> 本表**不承载审批当前状态**——状态权威仍唯一留在 `ApprovalRecord`；本表只追加、不改状态、不删除。
>
> 补充子问题：若批准，`AuditEvent` 侧的审批事件如何处置（保持现状双写 / 收敛为一条带 `approval_record_id` 的摘要）？

### 1.2 现状事实（带证据）

**F1-1｜审批事实是「单记录状态机」，不是事件流。**
`ApprovalRecord` 共 13 个字段（`apps/billing/models.py:41-72`），状态枚举 PENDING/APPROVED/REJECTED/EXPIRED/CANCELLED（`apps/billing/models.py:34-39`）；`save()` 只允许 PENDING→终态的单次跃迁（`apps/billing/models.py:121-129`）。**表内无「事件」概念**：无 `updated_at`、无 `rejected_at`、无「重新提交 / 转交 / 撤回」字段。

**F1-2｜`CANCELLED` 终态无生产写路径。**
全仓检索 `Status.CANCELLED` 在 `apps/` 下的命中中，`ApprovalRecord.Status.CANCELLED` 仅出现在测试（`apps/billing/test_night_audit_reopen.py:128`）与模型守卫（`apps/billing/models.py:127`）；**无任何服务/视图将审批单置为 CANCELLED**。

**F1-3｜审计侧已写入审批动作事件，但锚点错位。**
`ApprovalService` 在申请/批准/驳回/过期时分别写 `approval.request` / `approval.approve` / `approval.reject` / `approval.expire`（`apps/billing/services_v2.py:131-140,163-171,177-185,207-215`）。但这些事件的 `entity_type`/`entity_id` 写的是**目标业务对象**而非审批单：
`entity_type=entity_type, entity_id=str(entity_id)`（`apps/billing/services_v2.py:133-135,166-169,180-183,209-214`），
其中 `entity_type`/`entity_id` 取自审批单字段（`apps/billing/models.py:48-49`）。
→ **从 `AuditEvent` 无法反查 `ApprovalRecord.pk`**；同一业务对象可存在多条审批（重试派生幂等键 `apps/billing/services_v2.py:97-103`；夜审重开要求「重开必须有新申请事实」`apps/billing/night_audit.py:654-660`），映射天然多对多。

**F1-4｜审批类审计事件缺请求链路信息。**
`approval.request` 传 `request=getattr(requested_by, "_request", None)`（`apps/billing/services_v2.py:139`）——`requested_by` 是 User 实例，该属性恒为 `None`；`approve`/`reject`/`expire` 事件**根本未传 `request=`**（`apps/billing/services_v2.py:163-171,177-185,207-215`）。故这些事件的 `request_id`/`ip`/`user_agent` 恒空，而 `ARCHITECTURE.md:168` 要求「关键操作审计应包含操作者、物业、动作、目标对象、时间、原因和请求链路信息」。

**F1-5｜现有历史检索仅满足 2/5 维。**
`GET /api/v1/approvals` 的过滤参数只有 `status`（`apps/api/approval.py:101-103`）、`action_code`/`entity_type`/`entity_id`（`apps/api/approval.py:104-109`），排序 `-created_at,-id`（`apps/api/approval.py:110`）。
- 申请人：`requested_by` **仅回传不筛选**（`apps/api/approval.py:126`）；无审批权者时被收敛为「仅见本人发起」（`apps/api/approval.py:98-100`）。
- 审批人：`approved_by` **仅回传不筛选**（`apps/api/approval.py:127`）。
- 时间：**无区间过滤**。
→ 动作 ✓、结果 ✓；申请人 ✗、审批人 ✗、时间 ✗。

**F1-6｜审计中心已有可直接复用的检索范式。**
`apps/api/audit_center.py:343-379` 的 `_filtered_events` 已实现 `action`/`entity_type`/`entity_id`/`actor`（按 `actor__username`）/`date_from`/`date_to`（**按物业时区换算自然日闭区间**，`:365-378`），且列表与导出**共用同一筛选口径**（`apps/api/audit_governance.py:3,65-68,111`）。

**F1-7｜数据库层保护不对称。**
`AuditEvent` 有模型层 + QuerySet + MySQL 触发器三重 append-only 保护（`apps/core/models.py:56-69,144-150`；`apps/core/sql/audit_immutability.sql:17-31`）；而 `ApprovalRecord` **无数据库级 append-only 触发器**（`apps/core/sql/audit_immutability.sql:5` 明示 ApprovalRecord 属有状态机业务事实，不适用该脚本）**且无数据库级 SoD CheckConstraint**（`apps/billing/migrations/0020_reversal_approval_sod.py:123-138` 的约束对象是 `LedgerEntry`）。
对照物：第二套审批模型 `PermissionMatrixApproval` **有**三条数据库级约束（`apps/identity/models.py:467-487`）。

**F1-8｜`privacy.legal_hold` 绕过唯一写入口且不在动作白名单。**
`request_legal_hold` 直接 `ApprovalRecord.objects.create(...)`（`apps/guests/retention.py:349-364`），而写入口自我声明为「审批流程唯一写入口」（`apps/billing/services_v2.py:30`）；其动作码 `privacy.legal_hold`（`apps/guests/retention.py:34`）**不在** `ApprovalActionRegistry._ACTIONS` 的 5 个动作中（`apps/billing/approval_registry.py:223-294`）。
→ 该路径**既不写 `approval.request` 审计**，也不受 payload 白名单 / 目标对象存在性 / entity_type 一致性校验（`apps/billing/approval_registry.py:321-358`）。

### 1.5 推荐方案与理由

**推荐：方案 B（新增只追加事件表 `billing_approvalevent`），并同步扩展 `approval_list` 检索维度。**

建议表结构（草案，与前置材料 §2.3.2 一致）：

```
ApprovalEvent → billing_approvalevent（只追加）
  approval      FK -> billing.ApprovalRecord (PROTECT, related_name="events")
  property      FK -> core.Property (PROTECT)
  event_code    CharField(32)   # REQUEST/APPROVE/REJECT/EXPIRE/CANCEL/TRANSFER/RESUBMIT/EXECUTE
  operator      FK -> AUTH_USER_MODEL (PROTECT)
  occurred_at   DateTimeField
  from_status   CharField(12, blank)
  to_status     CharField(12, blank)
  action_code   CharField(64)      # 冗余，便于直接筛
  entity_type   CharField(64)      # 冗余，便于按业务对象追溯
  entity_id     CharField(64)      # 冗余
  reason        CharField(240, blank)
  request_id    CharField(64, blank)
  ip            GenericIPAddressField(null/blank)
  user_agent    CharField(240, blank)
  created_at    DateTimeField(auto_now_add=True)
  Meta: ordering=("-occurred_at","-id")
        indexes = idx_appevent_approval(approval,-occurred_at) / idx_appevent_entity(entity_type,entity_id,-occurred_at)
                  idx_appevent_operator(operator,-occurred_at) / idx_appevent_property_time(property,-occurred_at)
  不可变：save() 禁改（pk 已有值抛错）、delete() 抛错、QuerySet 禁 update/bulk_*（对齐 apps/core/models.py:56-69,144-150）
  数据库层：追加 trg_billing_approvalevent_no_update/no_delete，并入 apps/core/sql/audit_immutability.sql 同批脚本
```

**理由**：

1. **锚点是决定性因素**。方案 A 的不可行不是「成本高」，而是审计事件以业务对象为锚点（F1-3），「按业务对象追溯完整审批链」在数据结构层面**不可能**实现；任务书第二阶段对此有硬要求（`:437`）。
2. **满足任务书第二阶段四项要求**：操作者/时间/动作/结果/关联对象五要素齐备；支持按业务对象追溯完整审批链；权限隔离沿用 `billing.approval_view` + 动作级 `approve_permission`（`apps/billing/approval_registry.py:315-318`）；补 MySQL/SQLite 双引擎测试。
3. **不制造第二权威**（`AGENTS.md:23` 红线）：状态权威唯一留在 `ApprovalRecord`，事件表只追加。
4. **同时收敛现有双写**：建议 `AuditEvent` 侧对审批动作**只保留一条带 `approval_record_id` 的摘要事件**（替代现四条 `approval.*` 全量重复），使「重复审计」变为「可关联的两层记录」；是否采纳此项作为**独立子决策**（见 1.8）。
5. **顺带修复 F1-4 / F1-8**：`ApprovalEvent` 直接落请求链路字段；`privacy.legal_hold` 登记进 `ApprovalActionRegistry` 并改走 `ApprovalService`——**这两项不依赖新表，可在本裁定项一获批前先行**，亦可单独批准（见 1.8 子决策）。

2. 审计事件与审批单**继续不可关联**（F1-3），跨系统核对（如财务凭证 ↔ 审批单 ↔ 审计）需人工按业务对象拼接，效率与准确性均受限。
3. `approval.request` 等审批类审计事件**继续缺请求链路信息**（F1-4），与 `ARCHITECTURE.md:168` 的要求持续存在差距（须在后续验收材料中如实登记为已知差距）。
4. `privacy.legal_hold` 的**白名单绕过与审计缺失**（F1-8）若一并搁置，将作为**已知高风险治理缺口**登记（前置材料 R2，等级「高」），并在 PMS3.0 继承矩阵中留项。
5. 不得据此宣称 ARCH-11 通过或 MC11/G14 相关项通过；本任务维持 `WAITING_OWNER`。

## 二、裁定项二：是否建设审批附件能力

### 2.1 待决问题

> 是否批准建设**审批附件能力**：新增附件元数据模型 + 上传/下载端点 + 附件权限（上传校验、下载鉴权）+ 保留期 + Legal Hold 交互 + 删除审批？
>
> 若批准，需一并裁定：
> (a) 文件本体存储位置（本地卷 / 对象存储）；(b) 附件保留期限与 Legal Hold 优先级；(c) 附件类别是否纳入现有 `RetentionPolicy.DataCategory`；(d) 删除审批是否适用三人分离。

### 2.2 现状事实（带证据）

**F2-1｜PMS2 不存在任何文件存储能力。**
全仓 `*.py` 检索 `FileField|ImageField|upload_to|DEFAULT_FILE_STORAGE|MEDIA_ROOT|ContentFile` → **0 命中**；检索 `MEDIA_ROOT|MEDIA_URL|STORAGES|DEFAULT_FILE_STORAGE|FileSystemStorage` → **0 命中**（2026-11-27 现取）。
→ 不止「缺附件模型」，而是**无文件落盘/对象存储通道、无上传端点、无下载端点、无附件生命周期概念**。

**F2-2｜唯一的「文件」语义是导出字节流，不落库。**
`Content-Disposition: attachment` 出现在 `apps/api/audit_governance.py:137-142,175-177`、`apps/api/report_export.py:124-126,169-171`、`hotelapp/views.py:378-380`。既有范式明确：**只登记「谁在何时、以何用途、按什么口径导出过、有效期到何时」，下载内容不落库；凭证只把一次性 token 映射回同一查询口径，绝不缓存或复制业务事实**（`apps/core/models.py:899-907`）。

**F2-3｜法律冻结现行语义与覆盖范围。**
`LegalHold` 语义为「冻结期内对应对象的一切清理动作跳过（skipped），不得删除」（`apps/guests/models.py:579-585`）；`target_type` **当前取值仅 GUEST**（`apps/guests/models.py:582`），冻结对象是 `target_id`（`:598`）；**无附件维度**。`LegalHold.delete()` 抛 `RuntimeError`（`:684-685`），已解除冻结不可再变更（`:680-681`）。

**F2-4｜保留策略模型现行类别不含附件。**
`RetentionPolicy.DataCategory` 仅 `GUEST_PROFILE` / `GUEST_DOCUMENT` / `MARKETING_CONSENT`（`apps/guests/models.py:490-493`）；每物业每类仅一条启用策略（`enabled_policy_key` 唯一键 `:519-527`）；保留天数与依据字段在 `:509-517`。

**F2-5｜清理执行的跳过/失败语义与审批引用。**
`RetentionExecution` 有 `skipped_count`（冻结/关联跳过数）与 `failure_count`（`apps/guests/models.py:731-739`），正式执行必须引用一条 APPROVED 的 `ApprovalRecord`（`:695-696,769-771`），审批引用字段为 `approval_reference`（`:751-753`）；`LegalHold` 亦有 `approval_reference`（`:620-622`）。
→ **「引用审批记录」的既有范式可直接复用于附件删除审批。**

**F2-6｜审批动作白名单与权限绑定机制已成熟。**
`ApprovalActionSpec` 支持绑定 `request_permission` / `approve_permission` / `payload_fields` / `expires_hours` / `api_requestable` / `validate_entity` / `sod_rule`（`apps/billing/approval_registry.py:78-123`）；已登记的 `privacy.retention_execute` 采用「申请人≠审批人≠执行人（三人分离）」SoD（`:292`）。→ 附件删除审批可直接按此范式登记 `privacy.attachment_delete`。

**F2-7｜审批单本身已有「凭证引用」范式（以字符串引用审批 pk）。**
`LegalHold.approval_reference`（`apps/guests/models.py:620-622`）、`RetentionExecution.approval_reference`（`:751-753`）均为 `CharField(64)` 存 `ApprovalRecord.id` 字符串。
→ **注意**：这是字符串引用而非外键，`ApprovalRecord` 无法反向约束其存在性；附件若沿用此范式需在应用层校验（参照 `apps/api/privacy_center.py:182-190` 的 `approval_reference` 校验写法）。

### 2.4 风险评估

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| 文件上传安全（类型伪造/超大文件/路径穿越/恶意内容） | **高** | 强制 content_type 白名单 + 大小上限 + 数量上限；**存储键服务端生成**（`sha256` + 扩展名），**禁用用户原始文件名作路径**；文件名安全化（去目录前缀、禁控制字符）；复用 `apps/billing/approval_registry.py:20-72` 的敏感值扫描做兜底；病毒扫描列入 PMS3.0（PMS2.0 不作为放行前置） |
| 合规敞口（审批凭证无法留存 → 事后无法证明申请依据） | **中** | 附件缺失不影响资金正确性（审批链本身已留痕），但影响争议举证能力；按「已知缺口」登记 |
| 保留期与成本失控 | **中** | 保留年限须负责人裁定；到期**不自动删除**，仅生成待办；删除必须走删除审批（避免误删） |
| Legal Hold 交互遗漏 → 冻结期内附件被删 | **中** | 推荐**按审批单维度**判定冻结（附件所属审批单的 `entity_type`/`entity_id` 命中 `ACTIVE` LegalHold 即冻结其全部附件），避免扩展 `target_type`（现仅 GUEST，`apps/guests/models.py:582`）；冻结优先于保留期；冻结命中时删除返回 409 |
| 删除审批被绕过（直接物理删文件） | **中** | 文件本体删除**必须**在删除审批通过后执行；元数据行**永不物理 DELETE**（只置 `status=DELETED` + `deleted_at/by/reason`），对齐 `LegalHold.delete()` 抛错（`apps/guests/models.py:684-685`）与 `ApprovalRecord.delete()` 抛错（`apps/billing/models.py:139-140`） |
| 审计脱敏泄露（`storage_key` 外泄 → 凭键越权直取对象） | **中** | 导出与列表**一律不含 `storage_key`**；下载必须过服务端鉴权（见 2.5.2），不得提供直链/预签名 URL 直出 |
| 「审批记录引用」为字符串非外键 | **低** | 附件删除审批引用沿用 `approval_reference` 字符串范式（`apps/guests/models.py:620-622`），但**必须**在应用层校验其存在性与 APPROVED 状态（参照 `apps/api/privacy_center.py:182-190`） |

### 2.5 推荐方案与理由

**推荐：方案 A（建完整附件能力），但分两期落地，且以「先裁定口径、后实施」为前提。**

**设计要点（草案，详见前置材料 §2.4–§2.5）：**

**① 元数据模型**：`billing_approvalattachment`（`ApprovalAttachment`）
`property` FK PROTECT ｜ `approval` FK→`ApprovalRecord` PROTECT `related_name="attachments"` ｜ `attachment_kind` ｜ `file_name` ｜ `storage_key` unique ｜ `content_type` ｜ `size_bytes` ｜ `sha256` ｜ `uploaded_by` FK PROTECT ｜ `uploaded_at` ｜ `status`(ACTIVE/REPLACED/PENDING_DELETE/DELETED) ｜ `legal_hold` ｜ `retention_until` ｜ `deleted_at`/`deleted_by`/`delete_reason` ｜ `delete_approval_reference`
索引：`idx_apptattach_approval(approval,status)`、`idx_apptattach_property_time(property,-uploaded_at)`、`idx_apptattach_sha(sha256)`、`idx_apptattach_retention(status,retention_until)`
**文件本体不入库**（对齐 `apps/core/models.py:901-902`）。

**② 上传校验**：鉴权前置（`_require_membership` 同制，`apps/api/approval.py:38-54`）+ `billing.approval_view` + 审批单须为 PENDING + 类型白名单 + 大小/数量上限 + 文件名安全化 + 服务端生成存储键 + 敏感值兜底扫描。

**③ 下载鉴权**：认证+任职+`billing.approval_view`+该动作 `approve_permission`+附件所属审批单属当前物业（否则 404，不泄露存在性）+`status != DELETED`；**每次下载写 `AuditEvent`**。

**④ 保留期**：不自动删除；到期仅生成待办；**年限须负责人裁定**（可对齐审计 10 年口径 `apps/api/audit_governance.py:44-49`，但该年限不适用于二进制附件；建议对齐财务凭证最低留存口径）；建议新增 `RetentionPolicy.DataCategory` 附件类别（现仅 3 类，`apps/guests/models.py:490-493`）。

**⑤ Legal Hold**：按**审批单维度**判定冻结（不改 `target_type`）；冻结优先于保留期；冻结期间删除请求 409。

**⑥ 删除审批**：新增动作码 `privacy.attachment_delete` 登记进 `ApprovalActionRegistry`（`apps/billing/approval_registry.py:223-294`），绑定申请权/审批权，**三人分离**（对齐 `privacy.retention_execute` 的 `sod_rule` `:292`）；执行人（≠申请人≠审批人）执行：删对象 → 元数据置 DELETED + 留痕 → 写 `AuditEvent`；**元数据行永不物理删除**。

**理由**：

1. 任务书明确要求「附件元数据模型设计」+「附件权限、存储、保留和删除设计」**两项齐备**（`:426-427`），且「附件能力单独批准后实施」（`:441`）——本裁定项即该单独批准点。
2. 现有系统**无任何文件能力**（F2-1），不存在「既有附件治理没收口」的历史包袱；现在设计成本低于 PMS3.0 补做。
3. 沿用仓库既有成熟范式（`ExportCredential` 只登记口径不落业务事实 `apps/core/models.py:899-907`；`approval_reference` 引用范式 `apps/guests/models.py:620-622`；`ApprovalActionRegistry` 动作级权限绑定 `apps/billing/approval_registry.py:78-123`），**不发明新机制**。
4. 该能力**不触碰资金正确性主链**（附件是审批的证据补充，不是审批状态载体），回归半径可控。

### 2.6 影响范围

### 2.7 若不批准的后果

1. 审批申请**无法附带任何凭证材料**（发票、截图、签字件、异常说明）；审批人只能看到 `reason`（≤240 字，`apps/billing/models.py:67`）与白名单受限的 `payload_snapshot`（`apps/billing/models.py:68`，且被敏感值规则严格限制，`apps/billing/approval_registry.py:342-356`）。
2. 任务书「附件元数据模型设计」与「附件权限、存储、保留和删除设计」**两项保持未满足**，ARCH-11 保持 `WAITING_OWNER`。
3. 争议举证能力受限：部分高危审批（如 `billing.reversal` 冲销、`privacy.retention_execute` 清理）**缺少申请依据的物证**，只能依赖审批理由文本。
4. 缺口须如实登记到 PMS3.0 继承矩阵与最终验收材料，**不得在 MC11/G14 相关材料中宣称该维度通过**。
5. 若后续 PMS3.0 决定建设，等于**从零设计**（F2-1 现状为零基础），且历史审批单**永远不会有附件**，历史证据缺口不可回补。

### 2.8 解除条件与子决策

**解除条件（本裁定项整体）**：负责人在 §四 决策位签署，并**至少同时明确 2.1 的 (a)(b)(c)(d) 四个附属口径**（存储位置 / 保留期与 Legal Hold 优先级 / 是否纳入 `RetentionPolicy.DataCategory` / 删除审批是否三人分离）。任一口径缺失时，本项保持 `WAITING_OWNER`，不进入实施。

**建议拆出的子决策**：

| 子决策 | 内容 | 建议 |
|---|---|---|
| 2.8-A | 附件是否必须纳入 `RetentionPolicy.DataCategory`（涉及已启用策略唯一键与数据迁移） | **建议先不纳入**：先用附件表自身 `retention_until` 字段承载，降低迁移风险；PMS3.0 再统一归口 |
| 2.8-B | 附件删除审批是否强制三人分离 | **建议强制**（对齐 `privacy.retention_execute` `apps/billing/approval_registry.py:292`） |
| 2.8-C | 病毒扫描是否作为 PMS2.0 放行前置 | **建议否**，列为 PMS3.0 增强（`DEFERRED_TO_PMS3`） |

### 3.5 推荐方案与理由

**推荐：方案 A（完整导出），且与裁定项一解耦实施——即使裁定项一不批准，仍可先交付「方案 B 维度」的可用导出，并如实标注筛选维度受限。**

**设计要点（草案）**：

① **导出授权**：新增专项权限码 **`billing.approval_export`**（建议授予店长/值班经理，默认不授予财务与前台）；导出须同时持 `billing.approval_view` **且** `billing.approval_export`；用途说明强制 8–240 字符（`apps/api/audit_governance.py:52-55` 同制）。

② **范围**：物业强制过滤（`filter(property=request.property)`，同 `apps/api/audit_center.py:345`）；可见范围沿用 `apps/api/approval.py:98-100`（有审批权见全部，否则仅本人发起）；行数上限建议 `MAX_EXPORT_ROWS = 10000`（对齐 `apps/api/audit_governance.py:32`），超限**如实标注截断**（`apps/api/report_export.py:74-75` 同款 `# truncated:` 写法）；时间区间按**物业时区**换算自然日闭区间（复用 `apps/api/report_center.py` 的 `_parse_day`/`_property_tz_bounds`，`apps/api/audit_center.py:34,365-378`）。

③ **脱敏**：列白名单 `created_at`/`action_code`/`entity_type`/`entity_id`/`status`/`from_status`/`to_status`/`requested_by`/`approved_by`/`operator`/`occurred_at`/`reason`（截断 240）；**禁列** `payload_snapshot`、`before_json`/`after_json`、任何 PII、`storage_key`；导出前用 `apps/billing/approval_registry.py:20-72` 的敏感值识别对 `reason` 做一次扫描，命中列整列置空并在文件头标注脱敏字段数。

④ **导出行为自身审计**：导出写 `AuditEvent(action="approval.export", entity_type="ApprovalExport", entity_id=SHA-256(筛选参数)[:32])`，`after` 记 `row_count`/`filters`/`columns`/`credential_id`/`expires_at`（`apps/api/audit_governance.py:119-136` 同款）；下载写 `approval.export_download`（`entity_type="ExportCredential"`，`:165-174` 同款）。

⑤ **凭证与到期**：`ExportCredential.Kind` 新增 **`APPROVAL`**（现仅 `AUDIT`/`REPORT`，`apps/core/models.py:910-912`）；TTL 15 分钟（`apps/core/services.py:22`）；下载时复核筛选口径一致（`:162-163`）；凭证不缓存业务事实（`apps/core/models.py:901-902`）。

⑥ **审计不可变性**：模型层只追加（`apps/core/models.py:56-69,144-150`）+ 数据库层触发器（`apps/core/sql/audit_immutability.sql:17-31`，需 DBA 手工执行）；**上线声明中必须写明数据库层保障的启用条件与当前状态**。

**理由**：

1. 任务书对导出的要求是**三要素合一**：「导出功能必须同时实现权限检查、审计记录和敏感信息脱敏」（`:443`）——三者在本方案中都有明确落点与现有范式。
2. 现有两个导出范式（审计/报表）结构完全可复用（3.2 F3-2、F3-3），本项**不发明新机制**，实现风险低。
3. 审批历史外带价值明确：财务/审计/客诉场景需按人、按时间、按动作**离线核对审批链**，当前 API 只能在线分页、无区间筛选（3.2 F3-5）。
4. 导出而非直接开放明细表，可通过「专项权限 + 用途说明 + 行数上限 + 到期令牌 + 逐次审计」形成可追溯的外带闭环。
