## 4. 并行版的实质缺口（建议补，非拒收理由）

### 缺口：高危事件无入队拦截

任务书 TASK-05 明列禁止事项：

> - 不允许后台 Worker 自动重跑已完成的账务、退款、支付或夜审操作。

**现状**：并行版 `enqueue_outbox_event()` 只校验 `event_type` / `aggregate_type` / `aggregate_id` 非空，**不限制任何 `event_type` 前缀**。即账务/退款/支付/夜审类事件可正常入队；worker 侧虽有「无注册消费者则重试」的兜底，但**入队阶段无护栏**。

并行版的防护**仅存在于注释**：

```
# 治理约束（NS-E-05）：新增消费者不得引入新权限码；第一批只落结构化日志，
# 不接任何高风险资金/夜审业务动作。
```

注释不构成运行时保护——后续任何调用方传入 `billing.refund.execute` 等类型即可入队。

**本会话版本的做法**（供参考，不要求照搬）：

```python
HIGH_RISK_EVENT_TYPES = (
    "billing.ledger", "billing.payment", "billing.refund",
    "billing.post_entry", "night_audit.run", "night_audit.close",
    "business_date.reopen", "reservation.checkout",
)

def _is_high_risk(event_type: str) -> bool:
    return any(event_type.startswith(p) for p in HIGH_RISK_EVENT_TYPES)

# enqueue 内：
if _is_high_risk(event_type):
    raise OutboxError(...)
```

**建议**：在并行版 `enqueue_outbox_event` 中补入同等护栏，并加回归测试（本会话版第 2 组 `HighRiskEventGuardTests` 可直接改写移植）。

**风险等级**：中。当前无业务代码调用 `enqueue`，故暂无实际危害；但一旦开放接入即为隐患，应在首次接入前补齐。
