# 取证隔离库改名（`test_hotel` → `test_hotel_e2e`）与 DBA 授权请求

> 生成时间：2026-11-27 ｜ 关联分支：`feature/pms2-r7-db-rename` ｜ 性质：取证工具链变更说明 + DBA 授权请求
> 适用范围：`scripts/acceptance/` 取证工具、`scripts/e2e_full_chain.py` 隔离库护栏

## 一、根因

Django 的 MySQL **测试库名 = `test_` + `DJANGO_DB_NAME`**。开发库名是 `hotel`（来自 `.env`），
所以 Django 的 MySQL 测试库就叫 **`test_hotel`**。

取证隔离库此前也取名 `test_hotel` → 与 Django 的测试库**同名** → 任何一次
`manage.py test` 的收尾阶段都会把这个隔离库删掉（2026-11-27 实测发生过一次，
导致已建好的隔离库丢失）。

本机 MySQL 应用账号 `hotelhotel@127.0.0.1` 的授权现状（实测）：

```
GRANT USAGE ON *.* TO `hotelhotel`@`127.0.0.1`
GRANT ALL PRIVILEGES ON `hotel`.* TO `hotelhotel`@`127.0.0.1`
GRANT ALL PRIVILEGES ON `test_hotel`.* TO `hotelhotel`@`127.0.0.1`
```

应用账号**没有建库权限**（`CREATE DATABASE` 非 IF NOT EXISTS 会被拒），因此**新增一个
隔离库需要 root/DBA 侧一次 GRANT**。

## 二、新库名口径

| 项 | 值 |
|---|---|
| 取证隔离库（新） | **`test_hotel_e2e`** |
| Django 的 MySQL 测试库（禁用作隔离库） | `test_hotel` |
| 开发库（只读种子来源） | `hotel` |

新名满足全部既有守卫：

- 含 `test` → 通过本仓「库名必须含 test」守卫（`scripts/acceptance/prepare_isolated_db.py`）；
- 不等于 `test_hotel` → 不再与 Django 测试库撞名；
- 不被 `scripts/e2e_full_chain.py` 守卫拒绝：该守卫拒绝 `hotel` / `*_dev` / `prod*`，
  且要求库名以 `_e2e`/`_test` 结尾或以 `test_` 开头 —— `test_hotel_e2e` 同时满足。

## 三、DBA 授权请求（**尚未在本机落地**，2026-11-27 实测确认）

新隔离库需要 root 侧一次授权。**请用 MySQL root 执行**（必须连到本项目使用的那台实例：
`-h 127.0.0.1 -P 3306`；应用侧 `.env` 的 `DJANGO_DB_HOST=127.0.0.1`、`DJANGO_DB_PORT=3306`）：

```sql
CREATE DATABASE IF NOT EXISTS `test_hotel_e2e` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
GRANT ALL PRIVILEGES ON `test_hotel_e2e`.* TO 'hotelhotel'@'127.0.0.1';
FLUSH PRIVILEGES;
```

授权后，`scripts/acceptance/prepare_isolated_db.py` 即可用默认库名建库并
migrate + seed。授权前该脚本会打印上面这段命令并以退出码 2 退出（不抛裸异常）。

> 说明：AGENTS.md「不追加 `test_%` 通配授权」的纪律不变 —— 本次是**单个库名**的
> 精确授权，不是 `test_%` 通配符，不影响 Django 测试库 `test_hotel` 的既有授权与
> 生命周期。

### 3.1 前两次执行**未落到本机实例**（实测记录，供复现时避坑）

| 轮次 | 执行内容 | 实测结果 |
|---|---|---|
| 第 1 次 | `CREATE DATABASE ...` + `GRANT ... TO 'hotelhotel'@'localhost'` | 未落到本机实例：`information_schema.SCHEMATA` 中**不存在** `test_hotel_e2e`；应用身份 `CURRENT_USER=hotelhotel@127.0.0.1`（`skip_name_resolve=0`），`@localhost` 是**另一个账户**，对本应用不可见 |
| 第 2 次 | `GRANT ... TO 'hotelhotel'@'127.0.0.1'`（库已存在） | 仍未生效：同一条 `information_schema` 查询依旧看不到该库 |

判据（可自行复现）：

```sql
-- 以应用账号执行即可判定，无需 root
SELECT SCHEMA_NAME FROM information_schema.SCHEMATA WHERE SCHEMA_NAME='test_hotel_e2e';
```

> 排查提示：若执行后该查询仍为空，说明语句**没有到达本机实例**（连到了别的实例、
> 或在非 MySQL 客户端里执行）。先用
> `mysql -h 127.0.0.1 -P 3306 -u root -p -e "SELECT VERSION(), @@port, @@datadir;"`
> 自证连对了服务器（期望 `8.0.33` / `3306` / D 盘数据目录）。
>
> 另：第 1 次的 `GRANT ... @'localhost'` 若确实执行过，会留下一个
> `hotelhotel@localhost` 账户（空口令登录已被 MySQL 策略拒绝，实测 1045，
> **不构成空口令风险**），但它是「存在却用正确口令也登不进去」的僵尸账户，建议
> `DROP USER IF EXISTS 'hotelhotel'@'localhost';` 清理。

### 4.1 撞名护栏：告警而非拒绝（2026-11-27 复核订正）

护栏最初做成**硬拒绝**（`test_hotel` 一律 `sys.exit(2)`）。复核后订正为**告警 + 继续**，理由：

1. **撞名影响的是隔离库的「复用」，不是「本次 E2E 的正确性」。** 只要按
   `prepare_isolated_db.py` 在每次取证前重建隔离库、且不在「重建」与「使用」之间
   跑 `manage.py test`，本次 E2E 取证完全有效。
2. **硬拒绝会造成能力回退。** 在 DBA 授权落地之前，本机**没有任何一个可用隔离库名**
   ——`hotel` 是开发库（禁用作取证库）、`test_hotel` 被硬拒绝、`test_hotel_e2e`
   尚未授权。此时 E2E 全链与九岗位矩阵**完全无法运行**，等于把项目的验收能力
   整体堵死。纠错不应以「让验收跑不了」为代价。
3. **目标状态未变。** 默认库名、四个取证工具、`PMS_E2E_ALLOWED_DB_NAMES` 全部已
   切到 `test_hotel_e2e`；告警块同时打印需要 DBA 执行的授权语句，授权落地后旧名
   自然不再使用。

告警块实测：以 `test_hotel` + `--i-understand-reset` + 无服务端口触发，告警块先于
任何清库动作输出，随后因连不上数据库中止（**未触碰任何数据**）。
