## 一、现状（现取代码事实）

`apps/billing/models.py` 的 `ApprovalRecord` 现有字段：

`property`、`action_code`、`entity_type`、`entity_id`、`requested_by`、`approved_by`、`status`、`reason`、`payload_snapshot`、`idempotency_key`、`approved_at`、`expires_at`、`created_at`。

已具备：

- 状态机 PENDING → APPROVED / REJECTED / EXPIRED / CANCELLED；
- 追加写保护：`ImmutableFinancialFactQuerySet` 禁 `update`/`bulk_*`；`save()` 禁改申请事实、禁改已决策记录；
- 同人审批拒绝（模型层 + 服务层双重）；
- 动作白名单与动作级权限（`ApprovalActionRegistry`）；
- 跨物业 404、列表可见范围收敛。

**缺口一：无审批历史表。**
现状只能查单个审批单的「当前状态」。任务书 §11.4 要求可按「业务对象 / 申请人 / 审批人 / 时间 / 结果」检索历史，并要求记录转交、撤回、重新提交等动作。目前：

- 转交、撤回、重新提交**没有独立记录**（CANCELLED 只是终态，无操作者与原因链）；
- `payload_snapshot` 是申请时快照，不随审批过程演进；
- 历史检索只能靠 `AuditEvent` 的时间线拼接，字段口径与审批语义不对齐。

**缺口二：无附件/凭证模型。**
任务书 §11.4 要求记录「附件和凭证元数据」。当前模型无任何附件字段或关联表，审批依赖的是业务对象本身（如 Refund 的原支付）。

## 二、影响

| 受影响要求 | 当前是否可满足 |
|---|---|
| §11.4 按对象/申请人/审批人/时间/结果查询 | 部分（对象/状态可查；审批人与时间可查；转交撤回不可查） |
| §11.4 记录转交、撤回、重新提交 | **否** |
| §11.4 附件与凭证元数据 | **否** |
| §11.5 关键状态变更保留前后信息 | 部分（AuditEvent 有，但审批专用口径不足） |
| MC11 / G14 相关验收 | 未纳入本轮判定，不得据本缺口宣称通过或失败 |

风险等级：**中**。不影响当前资金正确性（退款三分离与审计已闭环），影响的是可追溯性与合规完备度。

## 三、选项

### 选项 A：新增 `ApprovalHistory`（只追加）+ `ApprovalAttachment` 两表

- 内容：历史表记录每次动作（REQUEST/APPROVE/REJECT/EXPIRE/CANCEL/TRANSFER/RESUBMIT），含操作者、时间、前后状态、原因、request_id；附件表存元数据（文件名、类型、大小、哈希、上传人、时间、关联审批），**文件本体不入库**。
- 成本：2 个模型 + 2 个迁移 + 服务写入点改造（约 6 处）+ 查询 API + 测试。
- 风险：审批服务是资金路径，改动需完整回归；附件涉及存储位置与访问权限（需同时决定文件存放与鉴权）。
- 好处：完整满足 §11.4，且后续对账/审计可复用。

### 选项 B：只新增 `ApprovalHistory`，附件延后

- 成本：减半。
- 代价：§11.4 附件项仍不满足，需在状态中保留 PARTIAL。

### 选项 C：不新增表，用 `AuditEvent` 扩展审批专用 action 码承载

- 成本：低（仅新增 action 常量与写入点）。
- 代价：`AuditEvent` 是通用审计表，按审批语义检索需靠 action 前缀约定，性能与可读性弱于专用表；附件仍无承载。**不建议**作为长期方案。

### 选项 D：本轮不实施，登记为 PARTIAL 并移交后续批次

- 成本：零。
- 代价：ARCH-11 保持 PARTIAL，需在 G14/MC11 材料中如实标注。

## 四、推荐

建议 **选项 B**（先建历史表，附件单列裁定）：历史表是 §11.4 的核心且不涉及文件存储与鉴权，风险可控；附件需要额外决定存储位置、访问控制与保留策略，宜单独评估。
