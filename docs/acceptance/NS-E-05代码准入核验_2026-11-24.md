## 3. 新发现缺陷：计划绑定校验与实现矛盾（阻断条件 4）

### 3.1 现象

```
apps/guests/test_retention.py:333
  plan_retention_cleanup(..., dry_run=False, approval_reference=str(approval.pk))
apps/guests/retention.py:194
  raise ValueError("审批记录与当前清理计划不一致，禁止执行。")

Ran 21 tests, FAILED (errors=1)
```

### 3.2 根因（设计与实现不一致）

**设计意图**（`retention.py:174-179` 注释）：

> 「审批记录必须绑定本次 dry-run 的 `RetentionExecution`，且…执行人≠审批人…」
> 「候选集（LegalHold、未结业务）在**执行时重新计算**，不允许 dry-run 结果直接复用」

**实际实现**：

| 行 | 行为 | 问题 |
|---|---|---|
| L126 | `exec_record = RetentionExecution(...)` **无条件新建** | 新实例 pk 必为 None |
| L191-194 | 校验 `approval.entity_id != str(exec_record.pk)` → 抛错 | 但 `exec_record.pk` 在 L126 时尚未落库 |

测试流程：
1. 先做一次 dry-run，得到 `execution`（pk=1），并为其申请+批准审批（`entity_id="1"`）；
2. 再调 `plan_retention_cleanup(dry_run=False, approval_reference=...)`；
3. 该调用在 L126 **新建另一个** `exec_record`（pk 待分配），L191 拿它与审批的 `entity_id="1"` 比对 → 不相等 → 抛错。

**两条逻辑互斥**：
- 若「执行时重新计算候选集、不复用 dry-run 结果」→ 就不可能与「审批绑定 dry-run 的 execution pk」同时成立；
- 若「审批绑定 dry-run execution」→ 正式执行就应当**加载**那个已存在的记录（按 `approval.entity_id` 取），而不是新建。

### 3.3 影响

| 维度 | 评估 |
|---|---|
| 功能 | **正式清理路径不可用**（`dry_run=False` 必抛错）——与 T02-1 修复前同类症状 |
| 条件 4 | 判定从 PASS 下调为 **未通过** |
| 条件 5 | 无法进行（测试红） |
| 阻断级别 | **P0**（阻断 Retention 三权限准入） |

### 3.4 建议修复方向（供责任方选择，本会话不代改）

| 方案 | 做法 | 影响面 |
|---|---|---|
| **A（推荐）** | 正式执行时按 `approval.entity_id` **加载**既有 `RetentionExecution`，复用其 `policy`/`as_of`，仅重算候选集 | 符合注释「重新计算候选集」+「绑定 dry-run 记录」两者 |
| B | 放宽校验：只校验 `approval` 的 `payload.retention_policy_id`/`as_of_date` 与入参一致，不校验 `entity_id` | 改动小，但失去「防 A 计划审批、B 计划执行」的部分保护 |
| C | 正式执行要求调用方传入 `execution_id` 而非 `approval_reference` | API 语义变化较大 |

> **本会话不实现任何一项**——该文件属并行会话在制范围，且方案涉及业务契约（审批与执行如何绑定），需责任方/负责人确认。
