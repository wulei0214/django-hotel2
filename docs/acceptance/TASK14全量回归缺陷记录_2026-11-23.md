## 1. 缺陷 A：`read_source_rows` 用不存在的 `id` 列排序（4 个 ERROR）

### 1.1 现象

4 个测试全部在 `setUpTestData` / 测试体中调用 `archive_table()` 时抛出：

```
django.core.exceptions.FieldError:
Cannot resolve keyword 'id' into field.
Choices are: accommodation, order, 备注, 身份证号, 客户id
```

受影响测试：

| 测试 | 触发位置 |
|---|---|
| `apps.billing.test_legacy_archive.ArchiveTableTests::test_all_four_tables_archive_and_verify` | `test_legacy_archive.py:167` |
| `apps.billing.test_legacy_archive_query.LegacyArchiveApiTests::setUpClass` | `test_legacy_archive_query.py:325` |
| `apps.billing.test_legacy_archive_query.LegacyArchiveQueryTests::setUpClass` | `test_legacy_archive_query.py:155` |
| `apps.billing.test_legacy_restore_drill.LegacyRestoreDrillTests::setUpClass` | `test_legacy_restore_drill.py:102` |

### 1.2 根因

`apps/billing/legacy_archive.py` 的 `read_source_rows()`（约 L232-249）：

```python
if spec.transform is not None:
    # 密钥 = column_map 首对源列（client="客户id"、vip="会员编号"）；
    # 可编辑面不含 "id"，但归档表需按源表主键排序
    pk_source = spec.column_map[0][1]
    source_fields = sorted({sf for _, sf in spec.column_map})
    rows: list[dict[str, Any]] = []
    for raw in _source_queryset(spec).values(*source_fields).order_by(pk_source):
        ...
```

**问题**：`spec.column_map[0][1]` 取的是 `column_map` **第一对的源字段名**。对于 `Client` / `Vip` 规格，若首对为 `("id", "id")`（从 Folio 等规格沿用），则 `pk_source = "id"`——但 **legacy `Client` 表的主键是 `客户id`，`Vip` 表的主键是 `会员编号`，二者都没有 `id` 字段**。

已实测 legacy 模型主键：

| 模型 | 真实主键字段 |
|---|---|
| `hotelapp.models.Client` | **`客户id`**（`AutoField(primary_key=True)`） |
| `hotelapp.models.Vip` | **`会员编号`**（`AutoField(primary_key=True)`） |

`FieldError` 的 `Choices are: accommodation, order, 备注, 身份证号, 客户id` 正是 `Client` 反向外键 + 自身字段集合，直接印证。

### 1.3 修复建议（供 TASK-04 责任人参考，本报告不代为修改）

**方案一（推荐）**：不从 `column_map` 推断主键，改用 Django 元数据：

```python
pk_source = _source_queryset(spec).model._meta.pk.name
```

**方案二**：在 `ArchiveSpec` 中显式增加 `source_pk` 字段，由各规格声明（`"客户id"` / `"会员编号"` / `"id"`），消除推断歧义。

**方案三**：`order_by()` 省略字段，依赖模型 `Meta.ordering`；但无法保证稳定顺序，**不建议**。

### 1.4 严重性

| 维度 | 评估 |
|---|---|
| 影响范围 | TASK-04 Client/Vip 归档全链（4 个测试类无法运行） |
| 生产风险 | **高**：归档功能对 Client/Vip 完全不可用 |
| 是否阻塞 TASK-14 | **是**：全量回归无法转绿 |
| 是否阻塞本会话任务 | 否（本会话 TASK-02/03 不涉及） |

## 2. 缺陷 B：测试断言未跟进实现（1 个 FAIL，**非实现缺失**）

### 2.1 现象

```
FAIL: test_archive_specs_cover_four_tables
  apps/billing/test_legacy_archive.py:101
AssertionError: Items in the first set but not the second:
  'legacy_vip_archive'
  'legacy_client_archive'
```

单独运行该测试**同样失败**（`Ran 1 test, FAILED`），与其它测试无关。

### 2.2 根因（已纠正初次误判）

**初次判断有误**：我曾判断「`ARCHIVE_SPECS` 缺 Client/Vip 两项，属实现未完成」。**核实后推翻**：

`ARCHIVE_SPECS` 实测有 **6 项**，Client/Vip **已包含**：

| # | archive_table |
|---|---|
| 1 | `legacy_folio_archive` |
| 2 | `legacy_finance_record_archive` |
| 3 | `legacy_night_audit_archive` |
| 4 | `legacy_accommodation_archive` |
| 5 | **`legacy_client_archive`** ← 存在（`legacy_archive.py:175`） |
| 6 | **`legacy_vip_archive`** ← 存在（`legacy_archive.py:190`） |

**真正原因**：测试断言写死了**旧的 4 项期望**（`test_legacy_archive.py:104-109`），而实现已扩展为 6 项。即**测试未跟进实现**，属测试维护滞后，不是代码缺陷。

```python
# test_legacy_archive.py:101-110（现状）
self.assertEqual(
    {spec.archive_table for spec in ARCHIVE_SPECS},
    {
        "legacy_folio_archive",
        "legacy_finance_record_archive",
        "legacy_night_audit_archive",
        "legacy_accommodation_archive",
        # ← 缺 legacy_client_archive / legacy_vip_archive
    },
)
```

### 2.3 修复建议

**唯一合理路径**：把测试期望补上 `legacy_client_archive` 与 `legacy_vip_archive`，使其与实现的 6 项一致。

> ⚠ **注意**：这**不是**「放宽断言」——是把断言**对齐到已扩展的实现**，属正常测试维护。与 §2.4 中「把 6 项减为 4 项」的性质完全相反。
>
> 初次报告中我把它误列为「需负责人裁定走补实现还是调测试」，现更正：**无需裁定，属明显测试滞后**，应由 TASK-04 责任方直接修正断言。
