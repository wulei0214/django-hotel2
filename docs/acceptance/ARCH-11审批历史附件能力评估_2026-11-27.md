| **请求链路信息** | ❌ `approval.request` 传 `request=getattr(requested_by, "_request", None)`（`apps/billing/services_v2.py:139`）——`requested_by` 是 User 实例，该属性恒为 `None`；`approve`/`reject`/`expire` 事件**根本未传 `request=`**（`:163-171,177-185,207-215`）→ `request_id`/`ip`/`user_agent` 全空，与 `ARCHITECTURE.md:168`「关键操作审计应包含操作者、物业、动作、目标对象、时间、原因和请求链路信息」不符 | ✅ 事件表可直接落 `request_id`/`ip`/`user_agent`（沿用 `apps/core/models.py:112,121-122` 字段型制） |
| **权限隔离** | ❌ 审计读取门禁是 `core.audit_view`（`apps/api/audit_center.py:322`、`apps/api/audit_governance.py:60`），审批读取门禁是 `billing.approval_view`（`apps/api/approval.py:91`），二者**权限码不同**；复用 AuditEvent 会把审批历史暴露给审计查看者，或需再加一层二次门禁 | ✅ 可沿用 `billing.approval_view` + 动作级 `approve_permission`（`apps/billing/approval_registry.py:315-318`）+ 物业过滤 + 可见范围收敛 |
| **迁移成本** | 低：仅新增 action 常量与写入点 | 中：1 模型 + 1 迁移 + 写入点改造（写入口集中在 `apps/billing/services_v2.py:29-216`）+ 查询 API + 页面 + 测试（MySQL/SQLite 双引擎） |
| **PMS3.0 扩展性** | ❌ 通用审计表无审批语义；转交/撤回/重新提交/执行等动作只能靠 action 前缀约定承载，长期可读性与可检索性弱（既有先例：`apps/api/audit_center.py:69-74` 已在为「幽灵条目」做人工订正） | ✅ 可扩展 `TRANSFER`/`RESUBMIT`/`REVOKE`/`EXECUTE` 等枚举与 `from_status`/`to_status` 字段，PMS3.0 直接继承 |

#### 2.3.2 结论与推荐

**结论**：

1. **不复用 `AuditEvent` 承载审批历史语义**（方案 A 否决）。核心理由不是「成本高」，而是**锚点错位**：审计事件以业务对象为锚点，无法反查审批单（`apps/billing/services_v2.py:133-135` 等 4 处），且请求链路字段恒空、`core.audit_view` 与 `billing.approval_view` 门禁不同。这会让「按业务对象追溯完整审批链」在数据结构层面**不可能实现**。
2. **建议新增专用表**，但形态应是**只追加事件表 `billing_approvalevent`（模型 `ApprovalEvent`）**，而不是「第三张状态表」。
3. **状态权威仍唯一留在 `ApprovalRecord`**：新表**只追加、不改状态**，`ApprovalRecord.status` 继续是审批当前状态的唯一权威（`apps/billing/models.py:64-66` + `save()` 守卫 `:85-137`）。这样既满足任务书「历史事件必须具备操作者、时间、动作、结果和关联对象」「支持按业务对象追溯完整审批链」「支持权限隔离」，又不制造第二权威（`AGENTS.md:23` 红线：不建第二权威）。
4. `AuditEvent` 侧**保留**审批动作的通用审计条目（用于跨域统一检索与既有 `audit.export` 口径），但**只写摘要**，避免同一事实双写全量载荷（详见 2.7）。

**推荐方案（待批准）**：

```
class ApprovalEvent（建议表名 billing_approvalevent，只追加）
  approval        FK -> billing.ApprovalRecord (PROTECT, related_name="events")
  property        FK -> core.Property (PROTECT)          # 物业隔离 + 索引
  event_code      CharField(32)   # REQUEST/APPROVE/REJECT/EXPIRE/CANCEL/TRANSFER/RESUBMIT/EXECUTE
  operator        FK -> AUTH_USER_MODEL (PROTECT)         # 操作者
  occurred_at     DateTimeField                             # 时间
  from_status     CharField(12, blank)                      # 前状态
  to_status       CharField(12, blank)                      # 后状态/结果
  action_code     CharField(64)                             # 冗余审批动作，便于直接筛
  entity_type     CharField(64)                             # 冗余目标类型，便于按业务对象追溯
  entity_id       CharField(64)                             # 冗余目标 ID
  reason          CharField(240, blank)
  request_id      CharField(64, blank)
  ip              GenericIPAddressField(null/blank)
  user_agent      CharField(240, blank)
  created_at      DateTimeField(auto_now_add=True)

  Meta:
    ordering = ("-occurred_at", "-id")
    indexes  = idx_appevent_approval(approval, -occurred_at)
               idx_appevent_entity(entity_type, entity_id, -occurred_at)
               idx_appevent_operator(operator, -occurred_at)
               idx_appevent_property_time(property, -occurred_at)
  不可变：save() 禁改（pk is not None 抛错）、delete() 抛错、QuerySet 禁 update/bulk_*
  数据库层：追加 trg_billing_approvalevent_no_update/no_delete（并入 apps/core/sql/audit_immutability.sql 同批脚本）
```

**关键设计取舍**：`entity_type`/`entity_id` 为**冗余列**，与 `ApprovalRecord` 同源（`apps/billing/models.py:48-49`）。冗余带来「按业务对象直接追审批链」的能力（不必先 JOIN），代价是必须由服务层保证与审批单一致——因写入点集中在唯一写入口 `apps/billing/services_v2.py:29-216`，可控。

**未获批准则不实施**——状态 `WAITING_OWNER`。

### 2.5 附件权限、存储、保留与删除设计（草案，未实施）

#### 2.5.1 上传校验

1. **鉴权前置**：认证 + `is_active` + 当前物业有效任职（复用 `apps/api/approval.py:38-54` `_require_membership`）+ `billing.approval_view`。
2. **状态校验**：仅 `status=PENDING` 的审批单允许挂附件（终态后补证需走新审批单），防止「审批完成后补附件」绕过证据链。
3. **类型白名单**：仅 `application/pdf`、`image/jpeg`、`image/png`、`text/csv` 等登记类型；拒 `application/x-msdownload`、可执行脚本、双扩展名（如 `x.pdf.exe`）。

5. **文件名安全化**：去目录前缀、禁控制字符、限 240 字符；存储键由服务端生成（`sha256` + 扩展名），**不使用用户原始文件名作路径**（防路径穿越）。

7. **病毒扫描**：PMS3.0 建议接入；本轮设计列为可选增强，不作为 PMS2.0 放行前置。

#### 2.5.2 下载鉴权

2. `billing.approval_view` **且** 持有该 `action_code` 的 `approve_permission`（权限码由注册表绑定 `apps/billing/approval_registry.py:85-86,115-116`；未登记历史码退回 `billing.refund_approve` 口径 `apps/api/approval.py:80-83`）；
3. `attachment.approval.property == request.property`，否则 404；

#### 2.5.3 保留期

- **既有留存口径可复用的部分**：审计事件最低留存 **10 年**，由负责人 2026-11-17 裁定认可（`apps/api/audit_governance.py:48-53` `AUDIT_RETENTION_YEARS = 10`）；到期销毁须走**独立审批与只读备份**（同上 `:51-52`）。附件**不适用**该年限（二进制体积大），但**审批凭证类附件建议对齐财务凭证最低留存口径**，具体年限**须负责人裁定**，本报告不代拍板。
- 附件默认保留期建议：与所属业务对象的 `RetentionPolicy.retention_days` 对齐（`apps/guests/models.py:487-577`，现有 `DataCategory` 仅 GUEST_PROFILE/GUEST_DOCUMENT/MARKETING_CONSENT，见 `:490-493`，**附件类别需新增**）。
- 到期不自动删除：到期仅标 `retention_until` 并生成待办，**删除必须走删除审批**（见 2.5.5）。

#### 2.5.4 Legal Hold 交互

- 现行 `LegalHold` 语义：冻结期内对应对象的**一切清理动作跳过（skipped），不得删除** — `apps/guests/models.py:579-585`。
- 现行冻结**只覆盖 GUEST 主档**：`target_type` 当前取值仅 GUEST（`apps/guests/models.py:582`），且 `LegalHold` 记录的是 `target_id`（`:598`），**没有附件维度**。
- 设计推荐：**不新增 `target_type=ATTACHMENT`**，改为**按审批单维度判定**——若 `attachment.approval.entity_type`/`entity_id` 命中任一 `ACTIVE` LegalHold 的 `target_type`/`target_id`（`apps/guests/models.py:597-598`），则该审批单的全部附件视为冻结中：`legal_hold=True`、删除请求返回 409、清理任务计入 `skipped_count`（对齐 `RetentionExecution.skipped_count` 语义 `apps/guests/models.py:734-736`）。改动面最小且与冻结的「对象级」语义一致。
- 冻结优先于保留期：**保留期到期但处于冻结 → 不删**。
- 解除冻结走 `release_legal_hold`（`apps/guests/retention.py:391-407`），附件随审批单解冻。

#### 2.5.5 删除审批

- 附件**不可物理直接删**。流程：申请删除 → 新增动作码 `privacy.attachment_delete` 登记进 `ApprovalActionRegistry._ACTIONS`（`apps/billing/approval_registry.py:223-294`），绑定申请权 `guests.attachment_delete_request` 与审批权 `guests.attachment_delete_approve`，申请/审批/执行**三人分离**（口径对齐 `privacy.retention_execute` 的 `sod_rule` `:292`）；
- 审批通过后由**执行人（≠申请人 ≠ 审批人）**执行：删除对象存储对象 → 元数据行 `status=DELETED` + `deleted_at`/`deleted_by`/`delete_reason` + `delete_approval_reference` → 写 `AuditEvent`；
- 元数据行**永不物理 DELETE**（与 `LegalHold.delete()` 抛错 `apps/guests/models.py:684-685`、`ApprovalRecord.delete()` 抛错 `apps/billing/models.py:139-140` 同制），保持追溯；
- 删除动作自身须留审计，且**导出清单不得含 `storage_key`**（避免凭键越权直取对象）。
