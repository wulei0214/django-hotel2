#### 2.2.2 结论：仓库无分级机制，以下为分析建议

**仓库无字段级敏感度分级机制**。建议负责人若要裁定薪酬可见性，先把「档位」定义在本裁定材料内固化（建议口径，供裁定时取舍）：

| 档位建议 | 定义 | 落在本项目的字段 | 建议读取门槛 |
|---|---|---|---|
| **L3 高敏（薪酬类）** | 可直接换算为个人经济利益；一旦泄露即涉劳动争议/商业秘密 | `月薪`、`工龄`（工龄与薪酬联动定薪） | 建议独立专项权限码 + 理由留痕 + 导出双审批 + 读审计；**默认不可见** |
| **L2 敏感（身份类）** | 自然人身份信息 | 姓名、手机号、身份证号 | 已有 `guests.retention_*`、`guest_document_reveal`/`guest_phone_reveal` 等专项码 + 理由强制 + 审计 | 
| **L1 一般（经营事实）** | 岗位、工号、任职状态 | `position_code`、`employee_no`、`employment_status` | 员工档案读取权限即可（当前 `identity.staff_manage`） |

按上述建议，**薪酬属 L3（最高档）**——依据有三：①历史讨论稿行业参考「薪酬是最敏感字段（连目录可见性都收紧）」（`docs/PMS2.0_当前版本/00_项目基线与决策/敏感字段权限边界设计_2026-11-10.md:15`）；②仓库自身把「导出含身份证号/薪酬/联系方式的数据」列为 `export_pii` 敏感导出对象（`hotelapp/migrations/0014_role_actions.py:19,37-38`；`apps/identity/registry.py:700-709`）；③旧实现对薪酬做的是**字段级遮罩**而非仅列隐藏（`templates/index.html` 历史行 108「受控字段」）。

#### 2.7.2 三方案对比

#### 2.7.3 复用通用员工查看权限的扩散后果（红线 2 的技术展开）

若把薪酬读取绑到通用员工查看类权限码（`identity.view_staffprofile` 或 `identity.staff_manage`），扩散路径为：

1. **静默生效**：`identity.view_staffprofile` 当前已被「财务」「店长」持有（§2.3.3），且**矩阵页上可见、迁移台账在册**（`apps/identity/legacy_permission_dispositions.py:493-499`）。一旦有端点以该码为门禁，财务**无需任何新授权动作**即获得访问——这正是「绕过」的定义。
2. **不可分级**：档案读取（姓名/工号/岗位/任职状态，L1）与薪酬读取（L3）共用一码后，**无法**表达「可读档案但不可读薪酬」，也无法做字段级遮罩（旧实现正是靠 `can_view_salary` 做遮罩：`templates/index.html` 历史行 108）。
3. **回收即误伤**：为切断薪酬访问而回收该码，会同时切断员工的档案访问（前端台/客房等岗位的正当需求）；为保留档案访问而保留该码，就无法切断薪酬访问。
4. **矩阵语义污染**：`SPECIAL_PERMISSIONS` 的 `risk`/`requires_reason`/`requires_confirm` 语义是为「高危动作」设计的；把「读一个字段」塞进通用 CRUD 码，**该码不会触发高危二次审批流**（`is_high_risk_diff` 只判定 `SPECIAL_PERMISSIONS` 集合内的码，`apps/identity/permission_center.py:159-162`），从而绕开矩阵页最严的一道闸。
5. **审计不可区分**：`AuditEvent` 的动作码按「域.动作」区分（`apps/api/audit_center.py:225-267`）；薪酬读取若挂在档案读取下，无法单独统计「谁看了薪酬」——若未来要求「薪酬读取必留审计 + 可导出访问记录」，将无法回溯。

### 2.10 可选方案与推荐

#### 方案 A：不授权（维持现状）——**推荐**

- **内容**：财务不获得任何薪酬读取能力；不新增权限码；不新增展示位；C12 裁定为「迁移/保留/退役」时，薪酬可见性在 PMS3.0 随薪酬模块启动时重新评估。
- **风险**：①若业务确有「财务核算人工成本」需求且长期无解，会积压为隐性需求；②历史决策 7-2（财务可见月薪）在文档层面「悬空」，需在裁定记录中写明「因 ARCH-02/03 退役而失效」。
- **代价**：零实现、零泄露面、零审计改造。

#### 方案 B：完全授权（财务可读全部薪酬，无限制）

- **内容**：财务岗位可读全部员工薪酬，无字段级/导出/审计限制。
- **风险**：**最高**。①L3 数据无差别放开；②无读取审计 → 泄露不可回溯（这正是 §2.4.2「生产访问记录取不到」的成因重演）；③可导出则绕过既有双人审批链的治理意图（`export_pii`/`export_approve` 的存在本身说明「导出比查看更严」）；④**直接违反任务书裁定前红线 1 与 2**。
- **代价**：需新增独立权限码 + 展示位 + 审计 + 导出链改造；且**在裁定前不得实施**。

#### 方案 C：有条件授权（限定岗位 + 字段 + 导出 + 审计）——若负责人确需业务能力时采用

- **内容**（建议参数）：
  1. **岗位**：仅「财务」（可选加「店长」，但店长已有 `identity.staff_manage` 员工中心全权）；
  2. **字段**：仅「月薪」「工龄」，**不含**身份证/联系方式等其他 L3 字段；
  3. **权限码**：**独立** `identity.staff_compensation_view`（或按 C12 落点选 `billing.*` 命名空间），登记 `SPECIAL_PERMISSIONS`（risk=high、requires_reason=True、requires_confirm=True）；
  4. **展示位**：**不放在财务中心**，放在员工中心的**独立只读视图**（与 `identity.staff_manage` 分离门禁），避免「进员工中心 = 看得见薪酬」的耦合；
  5. **导出**：**不可直接导出**；如需导出，必须并入既有 `privacy.export_staff` 双人审批链（申请需 `export_pii`、审批需 `export_approve`，财务不含审批权）；
  6. **审计**：每次读取写 `AuditEvent`（建议动作码 `staff.compensation_read`，含物业/操作人/对象/时间），保留期与既有审计一致；
  7. **前置依赖**：**必须先有 C12 裁定**（否则无字段可读）；若 C12 裁定为「保留旧表/退役」，本方案在 PMS2.0 内不成立。
- **风险**：①新增治理对象与二次审批流（高危码触发的矩阵审批会增加平台超管的审批负担）；②掩码/展示实现需要前端配合，且必须做到「无权限即列隐藏」而非「列可见但值遮罩」（旧实现是列遮罩，需评估是否保留）；③若 C12 未先行裁定，出现「授权了但无数据」的悬空授权。
- **代价**：中等（权限点 + 注册表登记 + 迁移 + 员工中心只读视图 + 审计埋点 + 定向测试 + 文档同步），且**必须**在负责人裁定后由开发单独立项。

#### 推荐结论

**推荐方案 A（不授权，维持现状）**，理由：

1. **现状即满足业务**：财务中心全部报表与流程都不依赖薪酬字段（§2.5.2 逐条比对），当前不存在「财务必须有薪酬才能完成的工作」；
2. **红线当前全部守住**，方案 A 是唯一「零新增泄露面」的选项（方案 B 违反红线 1、2；方案 C 在 C12 未决前是悬空授权）；
3. **数据前提缺失**：薪酬字段在新档案零承载，「授权」目前**无对象可授**——授权一个不存在的字段，只会制造「已授权但读不到」的假象，或诱导后续实现者把旧表重新拉回在线路径（那才是真正的风险）；
4. **C12 是前置**：把可见性裁定与 C12（薪酬落位）合并裁定，是唯一能避免返工的路径。

**若负责人确认业务确有需要**，则采用**方案 C**，且**必须**满足四条前置：D6 独立权限码、读必留审计、导出并入既有双人审批链、C12 先行裁定。
