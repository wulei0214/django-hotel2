## 三、缺陷与修复明细

### 3.1 提交成功后按钮永久 loading（前端 opt-in 接线自身）

- **现象**：抽屉内提交「调整每日房价」成功后，`resultBox` 显示「操作成功」、表单已复位，但提交按钮仍为
  `disabled=true` 且保留 `is-loading` 类。`static/css/pms-ux.css:68-77` 对 `button.is-loading` 设
  `color: transparent !important` + 旋转伪元素 → 按钮文字不可见且一直转圈，用户无法在同一抽屉内再次提交。
- **根因**：`templates/pms/management_center.html` 的 `submitAction()` 只在**失败**分支调用 `form.__uxRelease()`，
  成功分支没有；pms-ux 守卫在 submit 时把按钮置为 loading/disabled，成功后无人复位。
- **修复**：成功分支补 `form.__uxRelease()`；「缺少定位操作行所需的 ID 字段」早退分支同样补上
  （该分支不发请求，但守卫已禁用按钮，用户补齐字段后仍需能提交）。
- **回归**：浏览器验收新增 3 条断言——按钮已恢复可用（`disabled=false` 且无 `is-loading`）、按钮文字可见、
  **同一抽屉内二次提交成功并再次复位**。

### 3.2 R5 新增必填项未同步到 11 个浏览器脚本（证据链断裂）

- **现象**：`templates/force_password_change.html:35` 的 `current_password` 带 `required`，而
  `scripts/browser_tests/*.mjs` 的强制改密分支只填 `new_password1/2` → HTML5 校验阻断提交 →
  强制改密无法完成 → 后续业务断言连锁失败。
- **修复**：11 个脚本逐个补 `await page.fill('input[name="current_password"]', PASSWORD);`
  （逐行精确插入，保留原行尾与缩进；diff 为「11 文件 × 1 行」）。

### 3.3 R5 冷却计数是会话级读-改-写（防爆破可被并发绕过）

- **现象**：`apps/identity/services.py` 原实现把失败计数写在 session 里
  （`fails = int(session.get(fail_key) or 0) + 1; session[fail_key] = fails`），而 Django 的 DB session
  后端是**整行覆盖写**。并发请求各自读到同一个旧值、各自写 `fail+1`，最后写者胜出 → 每批只 +1；
  会话级计数还意味着换会话/清 cookie 即可清零。
- **实证**：新增并发回归用例（MySQL 上 5 线程共享同一 session cookie 并发提交错误当前密码），
  断言 DB 计数必须达到 5——旧实现下该断言不成立。
- **修复**：改用仓库既有的原子限流器 `apps/core/rate_limit.py`：
  - 新增限流动作 `identity.pwd_reauth`：`(ip, username)` 5 次/300 秒（与登录限流同口径）
    ＋ `(username,)` 20 次/300 秒（防分布式换 IP 爆破）；
  - 新增 `rate_limit.reset()` / `rate_limit.remaining_seconds()`（与 `check()` 共用同一套桶计算）；
  - `check_current_password()` 改为「先 peek（超限即冷却，即使密码正确也拒绝）→ 校验失败才 consume 计数
    → 校验通过清零」。
- **口径修正**：原注释声称「与登录限流同口径」，实现并非如此（会话级、不落库、非原子）；现已名副其实。

### 3.4 R5 失败无审计、强制改密审计缺请求链路信息

- **修复**：`check_current_password()` 失败时写 `auth.password_reauth_failure` 审计事件
  （reason 只取 `wrong_current_password` / `rate_limited`，**不落任何口令值**）；
  `hotelapp/views.py` 强制改密成功审计补 `request=request`（此前无 IP / request_id，与 `/system/` 路径不一致）。

### 3.5 ARCH-02/03：旧入口 302 把用户送进 403 死胡同

- **现象**：`/index/`、`/search_staff/` 的门禁是 `hotelapp.view_staff`（财务持有，见
  `hotelapp/migrations/0016_unify_authorization.py:69-71`、`0018_finance_view_staff_readonly.py`），
  而跳转目标 `/manage/staff/` 要求 `identity.staff_manage`（仅授店长，见
  `apps/identity/migrations/0004_staff_manage_and_d04.py`）→ 财务被 302 放行后落到 403 死胡同。
- **修复**：`hotel/urls.py` 的 `_legacy_center_redirect()` 增加 `target_permission_code` 参数：
  目标中心门禁更严时，旧入口**额外要求**该权限码，缺码直接 403，不做误导性跳转。
  「旧入口放行 ⇒ 新中心放行」不变式由此成立，且未新增任何授权。
- **回归**：新增 `RetiredRoutePermissionEquivalenceTests`（持旧码但不持目标码 → 403 且不得 302 到新中心）
  与 `test_redirect_target_is_reachable_for_permitted_user`（跟随重定向后不得落在 403、不得链式重定向）。

### 3.6 ARCH-04 C6：反向迁移在真实数据上必失败（本轮最重的一项）
- **方案承诺**：`docs/acceptance/ARCH-04LegacyStaff迁移方案_2026-11-26.md §5.2` 把
  「正向迁移 + **可用反向迁移（不可 noop）**」列为旧表退役的硬前置条件。
- **实证**：0022 把 `Room.负责人编号` / `Food.厨师id` / `Order.服务员编号` 从
  `ForeignKey('Staff')` 改成可空整数后，同批用例又把「悬空工号」「NULL 工号」断言为**合法数据**。
  而反向迁移在 MySQL 上先 `MODIFY ... NOT NULL`（遇 NULL → **1138 Invalid use of NULL value**），
  再 `ADD CONSTRAINT FOREIGN KEY`（遇悬空工号 → 1452）。在隔离 MySQL 库上真实跑反向：
  **失败**（1138）。原 docstring 的「可用反向迁移」承诺不成立。
- **修复**：0022 的操作列表末尾追加 `RunPython(_noop_forward, _repair_before_reverse)`
  （Django 反向时按操作倒序撤销 → 末尾的 RunPython **先于** schema 变更执行）：
  1. 为每列中指向不存在 staff 行的工号，补建**同 id** 的占位员工行（保留工号原值）；
  2. 为每列中的 NULL 工号，补建固定 id（-1，Django 拒绝 AutoField 取 0）的占位员工行并回填。
  占位行姓名以「占位员工」开头、`启用=False`，便于识别与清理；正向迁移不做任何数据搬运。
- **回归**：新增 `C6ReverseWithNullAndDanglingDataTests`——写入「真实工号 / 悬空工号 / NULL 工号」三行后
  执行真实反向迁移，断言：迁移成功、FK 约束复原、真实工号原值不丢、悬空工号被补建同 id 占位行（值不被改写）、
  NULL 工号被回填到真实存在的占位行；末态重新正向。

### 3.7 本轮自查发现并修正的自身缺陷（测试自身的顺序依赖）

第一次跑 MySQL 全量时，新增的并发回归用例**失败**（计数为 0）：并发请求根本没进到校验逻辑。
根因是本轮自己写的测试夹具复用了迁移种出的「店长」角色组——`TransactionTestCase` 的 flush 只重建
ContentType/Permission、**不重建 Group**；同批次里先跑的 `TransactionTestCase` 已把该组 flush 掉，
于是账号没有有效岗位授权 → `staff_required` 直接拦下 → 改密请求从未进入二次认证。
该用例单独跑时绿、全量里红，**正是「顺序依赖型假通过/假失败」的典型**。

修复：测试夹具改为**自建角色组**（不再依赖迁移种子），并按「先跑会 flush 的模块」的顺序复验通过。
这条同时印证了 §五 中「ARCH-04 M6」类问题在仓库里是系统性的，不是孤例。
