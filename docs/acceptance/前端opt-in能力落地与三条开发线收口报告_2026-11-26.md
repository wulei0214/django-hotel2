## 一、任务一：pms-ux opt-in 能力接到真实页面

### 1.1 结论

`static/js/pms-ux.js` 此前已具备但**没有任何页面启用**的三类声明式能力，已接到通用管理中心页面
（`templates/pms/management_center.html`，服务客人 360 / 房态与库存 / 会员 / 预订四个中心）：

| 能力 | 启用方式 | 落点 |
|---|---|---|
| URL 状态同步 | `data-ux-urlstate` + `data-ux-param`（q / page / page_size / order_by / direction） | 面板容器与受控控件 |
| 表单守卫 | `data-ux-form` / `data-ux-draft` / `data-ux-validate` / `data-ux-rule` / `data-ux-submit` | 抽屉内的房态操作表单 |
| 排序 | 新增服务端白名单排序（见 1.3） | 四个中心列表端点 |

### 1.2 URL 状态同步的实现要点

- **页面侧只做三件事**：URL→页面状态、页面状态→受控控件、`popstate` 还原。
  排序没有可见输入框，用两个隐藏参数（`order_by` / `direction`）承载，触发一次 `input` 事件
  让库内置的 `attachUrlState` 完成 `pushState`。
- **首次加载不产生多余历史记录**：写回前比对 URL 与页面状态，相同则不写。
- **非法参数收敛**：`page_size` 只认 20/50/100，`order_by` 只认白名单内的键，其余回落默认值。
- **页码与列表请求一致**：`page` 由「跳至」输入框承载，翻页/跳页后先落可见控件再写 URL，
  避免 URL 带上上一页的残留值。

### 1.3 排序必须落在服务端（关键设计决定）

浏览器内排序只作用于**当前页**，在服务端分页的前提下会给出「整表已排序」的错觉。
因此排序键由服务端执行，并新增**前后端唯一事实来源**：

- `apps/api/center_ordering.py`：`CENTER_ORDERING` 登记每个中心允许排序的键与 ORM 字段路径；
- `apps/core/api_contract.py`：新增 `apply_ordering()`，白名单制——
  键不在白名单内一律忽略（不 400、不改变默认排序），`direction` 只认 asc/desc，排序后追加主键保证分页稳定；
- `apps/api/pages.py`：可排序列声明 `sort` 键，前端只把白名单内的列渲染成可排序表头（三态循环：升序 → 降序 → 复位，并同步 `aria-sort`）；
- 端点接入：客人 360、房态与库存、会员、预订四个中心的列表端点。

### 1.4 房态操作表单守卫

- 抽屉内的业务操作表单启用：未保存提醒（`beforeunload`）、草稿（localStorage，按「动作 + 作用行」隔离）、
  失焦校验（必填/数字）、提交防重复（按钮 loading + disabled）、提交成功后表单复位并解除脏标记。
- **守卫与业务提交处理器的顺序**：守卫先挂载（它负责失焦校验并在不通过时 `preventDefault`），
  业务处理器据 `e.defaultPrevented` 放弃发请求。顺序写反会导致「校验失败也照发请求」。
- `pms-ux.js` 新增 `form.__uxDestroy`：抽屉内容替换/关闭时解除全局 `beforeunload` 监听，
  否则动态表单反复创建会让监听器随操作次数累积。

### 2.2 合并后审查发现并修复的三个缺陷

**① MySQL 迁移反向报 1553（真实阻断级）**
`identity/0015` 的唯一约束原以独立 `AddConstraint` 操作创建。MySQL 会把 `(group_id, ...)`
开头的唯一索引选作 `group_id` 外键的支撑索引，反向迁移先 `DROP INDEX` 时外键仍在 →
`Cannot drop index 'uq_legacy_permission_code_grant': needed in a foreign key constraint`。
**修复**：改为随建表内联创建（Django 4.1 的 `model._meta.constraints` 进 `CREATE TABLE` 定义，
外键先于唯一约束声明），反向迁移直接 `DROP TABLE`，回滚路径在 MySQL 上真实可用。
*SQLite 不复现——若只跑 SQLite 会漏掉。*

**② 迁移往返用例依赖会被 flush 清空的迁移种子角色组**
`TransactionTestCase` 的 flush 只重建 ContentType/Permission，不重建 Group，数据迁移种出的
「店长」等角色组会被清掉。该用例在 MySQL 全量中失败（`Group.DoesNotExist`），
而在 SQLite 全量中恰好通过——差异来自**引擎跳过项不同**（SQLite 跳过 31、MySQL 跳过 5），
跳过项越多→flush 次数越少→种子组存活越久。
**修复**：用例改为自建持有旧权限码的角色组，并补齐「再次反向精确撤销新增授权 + 不误删旧码 +
台账表撤下 + 末态再正向」的完整往返断言；结果不再取决于同批次其它用例的执行顺序与引擎跳过项。

**③ 旧表例外清单未随退役收敛**
`/index/` 与 `/search_staff/` 退役后，`hotelapp/views.py` 的 `Staff` 模块级 import 成为未使用导入，
且 C1 的例外清单还挂着 3 条「并行开发线在办」的条目。
**修复**：摘除该 import；例外清单从 7 条收敛到 4 条（只剩一次性归档/盘点命令），
并收紧自约束断言——在线业务路径再出现旧表引用即被测试拦下。
