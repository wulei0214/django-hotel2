## 一、ARCH-11 审批权限与审计闭环

### 1.1 已实现（有代码与负向测试证据）

| 能力 | 实现事实 | 证据 |
|---|---|---|
| 后端最终授权 | `_require_membership` 校验认证 + `is_active` + 当前物业有效任职；不依赖前端按钮 | `apps/api/approval.py:38-54` |
| 审批动作白名单 | `ApprovalActionRegistry._ACTIONS` 唯一注册表，未知动作 400 且零副作用 | `apps/billing/approval_registry.py:160-212` |
| 动作级权限 | 申请权限与审批权限由注册表按 action_code 绑定 | 同上 `request_permission` / `approve_permission` |
| 同人审批拒绝 | 模型层 `save()` 强校验 `approved_by != requested_by` | `apps/billing/models.py:133-134` |
| 列表数据范围 | 按物业过滤；无审批权者仅见自己发起 | `apps/api/approval.py:93-100` |
| 跨物业不可见 | 非本物业记录一律 404，不泄露存在性 | `apps/api/approval.py:72-77` |
| 追加写保护 | `ImmutableFinancialFactQuerySet` 禁 update/bulk；`save()` 禁改申请事实 | `apps/billing/models.py:13-26, 85-137` |
| 退款三分离 | 申请 → 审批 → 执行，三方不同账号；超时释放占用 | `apps/billing/services_v2.py:1247-1344, 1544-1810` |
| 敏感 payload 拒绝 | 身份证/卡号/密钥样式值写入审批快照被拒 | `approval_registry.py:248-278` |

负向测试（`apps/api/test_approval.py`，已实测覆盖）：匿名 401、无任职 403、停用 403、跨物业 403/404、无审批权 403、同人自批拒绝、未知动作 400、内部专用动作拒绝、错误 entity_type 400、跨物业 entity 404、他人退款申请 403、终态冲突 409、payload 越界/敏感值 400、过期审批 EXPIRED。

### 1.2 缺口（需裁定或后续批次）

| 编号 | 缺口 | 影响 | 处置 |
|---|---|---|---|
| A11-1 | **无独立审批历史表**：历史依赖 ApprovalRecord 当前态 + AuditEvent 时间线，无法按「申请人/审批人/结果」维度直接检索 | 审计查询需跨表拼接 | 新增模型属 L3；先登记，待负责人批准后建 `ApprovalHistory` 或等价只读视图 |
| A11-2 | **无附件/凭证模型**：审批附件元数据无独立承载 | 无法满足"附件凭证元数据"逐项要求 | 同上，需 L3 审批；当前不得宣称已具备 |
| A11-3 | 审批列表导出未提供专用端点 | 无越权面，但也无受控导出 | 与 A11-2 一并评估 |

## 二、ARCH-02 物业数据隔离

### 2.1 已实现

- 核心模型带 `property` 外键：Guest、Room、Reservation、ReservationRoom、Stay、Folio、Payment、LedgerEntry、AuditEvent、ApprovalRecord。
- `AuthorizationService.filter_queryset_for_property` 强制物业过滤，非物业模型直接报错（`apps/identity/authorization.py:72-82`）。
- `PropertyContextMiddleware` 按 `DEFAULT_PROPERTY_CODE` 解析；已认证但无有效任职 → 不提供上下文并审计（`apps/identity/middleware.py:42-79`）。
- 跨物业负向测试覆盖审批、访客、账单等多入口（`test_approval.py`、`test_whitebox_api.py`、`test_security.py`）。

### 2.2 冻结边界（非缺陷）

- 多物业运行时切换已移除（`middleware.py:23` 注释与实现一致），符合 PMS2 冻结决策，移交 PMS3。
- `Reservation.booking_no` 全局唯一而非物业内唯一：单物业下无影响，多物业需迁 PMS3。

### 2.3 待补（低风险）

- `ReservationRoom.property` 与 `Reservation.property` 一致性目前靠应用层校验，无数据库复合约束；建议在 MySQL 兼容前提下评估复合外键或触发器（L3）。

## 四、ARCH-05 日志与异常（本轮已整改）

整改前实测：`LOGGING` 仅 2 个 logger（`hotel.audit`、`django.request`），**`hotel.api` 无 handler**；formatter 为纯文本；`audit_middleware` 记录完整 query string。

本轮整改（`df6aef9`）：

| 项 | 实现 |
|---|---|
| RequestID 中间件 | 合法入站 `X-Request-ID` 复用（字符集白名单 + ≤64），缺失生成；响应回写 |
| JSON formatter | timestamp/level/logger/message/request_id/property_id/actor_id/event/error_code |
| 脱敏 | 手机号、18 位身份证、password/token 类键值 → `<redacted>` |
| logger 补全 | `hotel.api`、`hotel.core`、`hotel.billing` 均有 handler |
| 测试 | `apps/core/test_logging_contract.py` 7 项；core+auth+audit 回归 135 项 OK |

**未完成**：`hotelapp/audit_middleware.py` 仍记录完整 query string（历史模块）；接入前建议改为脱敏后的 path + 白名单参数。指标平台（Prometheus/Grafana）未部署，`PRODUCTION_PENDING`。

## 五、ARCH-14 性能

实测抽样：

- 前端核心查询普遍使用 `select_related`/`prefetch_related`（抽样 43 处）。
- 列表接口统一分页（默认 20，上限 100），并强制稳定排序追加主键。
- 报表/审计导出有行数上限（`MAX_EXPORT_ROWS`），避免无界内存。

**缺口**：无 benchmark 基线。任务书要求"优化前后可比较测试结果"，本轮**未建立**，标记 P2：需在 MySQL 环境以真实数据量测量后再优化，不得凭推测改查询。
