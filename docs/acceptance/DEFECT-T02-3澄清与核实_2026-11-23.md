## 2. 为什么这仍然是个问题（而非「已被测试覆盖解决」）

`ApprovalService.request_approval()` 的第一道门：

```python
spec = ApprovalActionRegistry.get(action_code)
if spec is None:
    raise ValueError(f"未知审批动作码：{action_code}。")
```

→ **任何试图通过正规服务层为数据清理申请审批的调用都会失败**。

提交信息也承认了绕行事实：

> 「审批夹具经**裸 QuerySet 置 APPROVED**（ApprovalRecord 只允许 PENDING 创建，与 test_legacy_archive 绕过模式一致）」

这说明：**连测试都必须绕过 `request_approval`** 才能构造出合格审批。生产/运维场景同样没有合法途径。

后果链条：

1. T02-2 的审批门已正确实现（要求 APPROVED 记录）；
2. 但**没有合法途径产生**合格的 `privacy.retention_execute` 审批；
3. 于是实际执行者只能绕过注册表直接在 DB 层改状态；
4. 绕行同时**跳过了** `action_code` 校验、`payload_fields` 校验、`validate_entity` 校验——**削弱了既有安全边界**。

## 4. 修复 T02-3 的前置条件（不可由开发方单方完成）

`ApprovalActionSpec` 必填 `request_permission` 与 `approve_permission` 两个**权限码**字段。

按 NS-E-05 硬约束：

> 「未逐项批准前，**不改** `apps/identity/registry.py` 与迁移」；
> 「任何权限码新增都不得合入 main」。

新增审批动作码若需要新的权限码（如 `privacy.retention_request` / `privacy.retention_approve`），属**权限码扩展**，必须先由负责人逐项批准。

**可行的低成本方案**（供负责人选择）：复用既有权限码，避免新增：

| 字段 | 建议复用 |
|---|---|
| `request_permission` | `hotelapp.finance_access`（现有，财务域） |
| `approve_permission` | `billing.refund_approve`（现有，高危审批） |

> 但「复用哪个码」属业务授权决策，**须负责人裁定**，开发方不得自行指派。
