## 2. 「finance_access 语义不贴切」——核实为**成立**

### 2.1 registry 中的定义

```python
"key": "finance_access",
"codename": "hotelapp.finance_access",
"module": "finance",
"risk": "medium",
"requires_reason": False,
"requires_confirm": False,
"note": "财务页入口/流水读（财务/值班经理/店长）",
```

### 2.2 实际使用面

- **非 registry 引用 162 处**；
- 主要集中在 `apps/api/billing_center.py`（财务中心各读取面）；
- 语义是「财务页入口 + 流水读」。

### 2.3 判定

我在此前的关联缺口报告中建议「优先复用 `hotelapp.finance_access`」。**该建议语义不贴切**，并行会话的质疑正确：

- `finance_access` 是**读权限**（`risk=medium`、`requires_reason=False`）；
- 用它作为「不可逆数据清理」的**申请**权限，等于让所有能看财务报表的人都能发起 PII 清理；
- 这与 NS-E-05「按具体业务动作逐项审批」的精细度要求相悖。

**→ 我撤回该建议。**

## 5. 「复用同一码给多动作」先例核查（重要补充）

### 5.1 现状：已注册仅 4 个动作（精确枚举）

| 动作码 | request_permission | approve_permission | api_requestable |
|---|---|---|---|
| `billing.refund` | `billing.refund_request` | `billing.refund_approve` | — |
| `billing.reversal` | `billing.reverse_entry` | `billing.reversal_approve` | — |
| `night_audit.reopen` | `hotelapp.business_date_reopen` | `hotelapp.business_date_reopen` | `False` |
| `privacy.export_staff` | `hotelapp.export_pii` | `hotelapp.export_approve` | `False` |

### 5.2 两项关键观察

**观察一：`request_permission` 无共用先例**

经精确枚举，**4 个动作的 `request_permission` 全部互不相同**——本项目**不存在「两个不同动作共用同一 request 码」的先例**。

**观察二：request 与 approve 同码有先例（但不适用于本场景）**

`night_audit.reopen` 的申请与审批用**同一个码**（`hotelapp.business_date_reopen`）。这说明「同码」形态存在，但它依赖 **SoD 约束（申请人≠审批人）**而非权限码分离来保证职责分离。

对 `privacy.retention_execute` 而言：清理是**不可逆**操作，风险高于夜审重开；**不宜采用同码形态**，应保持 request/approve 分离。

### 5.3 对方案 A 的影响

方案 A 若采用 `export_pii` / `export_approve`：

- `privacy.export_staff` **已占用**这两个码；
- 于是将出现「**两个不同动作共用同一 request 码**」的新形态——**无先例**；
- 且会让「员工薪资导出」与「PII 批量清理」在权限面**不可区分**（同一岗位要么都能做、要么都不能做）。

→ **这是方案 A 的额外缺陷，应纳入负责人裁量依据。**
