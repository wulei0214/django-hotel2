## 三、逐格说明

### 3.1 FIN-06 收款

| 岗位 | 格 | 说明 |
|---|---|---|
| 前台 | 允许 | 现状已隐式可收（change_accommodation）；候选方案将其显式化为 `payment_collect`，**能力不变、审计更清**；附带约束：仍不能读财务中心任何数据 |
| 值班经理 / 财务 / 店长 | 允许 | 现状 finance_access 可收；改造后需叠加 payment_collect，默认授权矩阵同步迁入 |
| 其余六岗 | 禁止 | 现状即禁止，改造后无变化 |

### 3.2 MB-11 暂停 / 恢复

| 岗位 | 格 | 说明 |
|---|---|---|
| 值班经理 / 店长 | 允许 | 现状 change_vip 可操作；候选专项码沿用现有授权面迁入 |
| 前台 / 财务 / 其余五岗 | 禁止 | 现状即禁止，改造后无变化 |

**不做的事**：不因"值班经理/店长可暂停"推导"前台也应可暂停"；不新增退款金额阈值；不新增审批层级（恢复是否需第二人审批单独交负责人裁定，见 MB-11 修订文档 §四表 4）。

## 四、数据范围矩阵

| 动作 | 物业范围 | 业务对象范围 |
|---|---|---|
| FIN-06 收款（入口一） | 仅 `request.property`（PropertyContextMiddleware 单店边界） | 本物业 Reservation 的 OPEN MASTER Folio |
| FIN-06 收款（入口二） | 同上（`front_desk_property` 强制 DEFAULT 物业） | 本物业本人可查预订（booking_no 路由参数） |
| MB-11 暂停/恢复 | 仅 `request.property` | 本物业 GuestMembership（`filter(pk=id, property=property)` 强制，他物业 404） |

跨物业拒绝策略：一律 404（不泄露存在性）或 403（物业上下文缺失），与现行 API 安全口径一致（P0-01）。

## 五、与九岗位矩阵既有专项码的关系

| 既有专项码 | 与本候选关系 |
|---|---|
| `billing.refund_request / refund_approve / refund_execute` | **SoD 链不改动**：收款（收钱）与退款执行（退钱）严格分离；同一人可同时持收款与退款执行不构成 SoD 冲突（现行规则：申请人 ≠ 审批人 ≠ 执行人，仅约束退款链内部） |
| `billing.cashier_shift_manage` | 现金收款守卫（本人 OPEN 班次）保留在服务层，与候选码正交 |
| `hotelapp.finance_access` | 保持为财务中心读门禁；**本候选不得借道扩大其授权面** |
| `hotelapp.change_vip` | MB-11 落地后建议从中**移除**暂停/恢复（权限收紧的另一半），等级变更保留——待负责人裁定 |
