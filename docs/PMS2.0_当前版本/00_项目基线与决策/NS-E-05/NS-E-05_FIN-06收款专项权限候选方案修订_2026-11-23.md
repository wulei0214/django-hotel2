## 三、授权方案修订（按入口分列）

### 3.1 设计原则

1. **收款 = 资金动作，应显式专项授权**，不应隐式搭在任何"修改权"上；
2. **不扩大 `finance_access`**：该码是财务中心**读**门禁（账单/流水/退款列表全可见），给前台扩此码等于开放全部财务明细——明确禁止；
3. 收款权限与财务流水**读取权限分离**：`payment_collect` 只放行收款写动作，不授予任何 `GET /billing/*` 列表/明细/汇总端点；
4. 退款执行（`billing.refund_execute`）与本候选**严格分离**——收款收钱、退款退钱是两个方向的独立资金动作，不得互相继承。

### 3.2 入口一（财务中心）改造方案

现门禁：`_require_finance_access(request)`（只要 finance_access 即可收款）。

**候选方案**：改为 `_require_finance_access(request, extra_permission="billing.payment_collect")`——与退款申请（`billing.refund_request`）同构。

效果：持有 `finance_access` 但无 `payment_collect` 的岗位（如仅报表查看型角色，若未来出现）只读不可收；财务/值班经理/店长默认授权矩阵内加入 `payment_collect`。

### 3.3 入口二（前台）改造方案

现门禁：`@_front_desk_write_required`（view+change accommodation 即可收款）。

**候选方案**：新增 `_front_desk_action_required("billing.payment_collect")` 叠加校验（该装饰器工厂已存在于 `front_desk.py`，模式现成，无需新造机制）。

效果：前台获得 `payment_collect` 后**仍不能**访问财务中心任何数据——因为财务中心全部门禁在 `finance_access`，专项码不携带读权限。这正面回答"前台获得收款权限后是否仍不能查看完整财务中心数据：**是，不能**"。

### 3.4 兼容性说明

| 现有权限 | 与候选关系 |
|---|---|
| `hotelapp.finance_access`（财务/值班经理/店长） | 保持为财务中心**读**门禁不变；收款改由 `payment_collect` 叠加控制 |
| `hotelapp.change_accommodation`（前台） | 收款**移出**其隐式能力；前台是否可收取决于是否单独授 `payment_collect` |
| `billing.cashier_shift_manage` | 不变。现金收款要求本人 OPEN 班次的守卫保留在服务层（`services_v2.py` L855-870），与专项码正交 |

| 岗位 | 建议 | 理由 |
|---|---|---|
| 前台 | 允许（候选授予 `payment_collect`） | 现状已隐式可收，显式化后能力不变、审计更清 |

现状与对照详见《NS-E-05权限入口与审计现状核查报告_2026-11-23.md》§二。获批后落地内容（**纯增量字段，不建第二套审计模型**）：

```python
# 候选落地形态（获批后才实施，本任务不写代码）
AuditEvent.record(
    action="billing.collect",
    entity_type="Payment",
    entity_id=payment.pk,
    actor=collected_by,
    property_obj=property_obj,
    before={"payment_status": None},                # 新增：创建场景无前态
    after={
        "payment_status": payment.status,           # 新增
        "method": method,
        "amount": str(amount),
        "currency": reservation.currency,           # 新增
        "reservation_id": reservation.pk,           # 新增
        "folio_id": folio.pk,                       # 新增
        "business_date": business_date,             # 新增
        "provider_ref": provider_ref,               # 新增
        "source_entry": source_entry,               # 新增：frontdesk / billing_center
    },
    request=request,                                # 修复：显式传 request（现 _request 属性失效）

```

**禁止项**：不记录银行卡号/CVV/有效期等支付敏感数据（现有 `method` 仅 CASH/CARD/TRANSFER 枚举，无敏感信息，保持不变）。

**关联缺陷（独立报告，不在本候选夹带）**：现 `request=getattr(collected_by, "_request", None)` 传的是 User 实例，恒为 None，request_id 链路失效——建议单独授权修复。
