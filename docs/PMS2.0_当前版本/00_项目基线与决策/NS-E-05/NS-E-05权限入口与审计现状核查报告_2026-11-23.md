## 一、FIN-06 收款：两个真实入口（均已核实）

### 1.1 入口一：财务中心收款

| 环节 | 实际代码（现取现核） |
|---|---|
| 路由 | `POST /api/v1/billing/payments`（`apps/api/urls.py`，`billing_payments` 分发） |
| 视图 | `apps/api/billing_center.py::collect_payment_api`（L662） |
| 权限门禁 | `_require_finance_access(request)`——要求 `hotelapp.finance_access`（**无** extra_permission 叠加） |
| 幂等 | `@idempotent` 装饰器 + body.reference 作为服务层 provider_ref 幂等键 |
| 服务层 | `apps/billing/services_v2.py::BillingService.collect_payment`（L771） |
| 写入 | `Payment`（SUCCEEDED）+ `LedgerEntry`（PAYMENT，负值贷方）同事务 |
| 现金约束 | method=CASH 时要求本人 OPEN 收银班次 |
| 超额守卫 | 收款金额不得超过当前应收余额（超出抛 ValueError） |

### 1.2 入口二：前台预订收款

| 环节 | 实际代码（现取现核） |
|---|---|
| 路由 | `POST /api/v1/front-desk/reservations/{booking_no}/payments`（`apps/api/urls.py`） |
| 视图 | `apps/api/front_desk.py::collect_payment`（L1347） |
| 权限门禁 | `@_front_desk_write_required`——要求 `hotelapp.view_accommodation` **且** `hotelapp.change_accommodation`（**不要求** finance_access） |
| 幂等 | `Idempotency-Key` 头（1-64 字符），拼为 `FD{property_pk}-{key}` 作 provider_ref |
| 服务层 | `apps/reservations/front_desk_services.py::collect_manual_payment`（L516）→ 委托 `BillingService.collect_payment`（同一唯一写入口） |
| 附带语义 | PENDING 订单收款成功即确认订单（CONFIRMED）+ 库存确认 + 取消开放支付意图 + 审计 `reservation.confirmed_at_frontdesk` |
| 状态守卫 | 仅 PENDING/CONFIRMED/CHECKED_IN 允许收款；过期 PENDING 拒绝（MC11-RES-02） |

### 1.3 关键结论

1. **两条入口共用同一服务层** `BillingService.collect_payment`——不存在第二套收款写入；权限差异只在 API 门禁层。
2. **当前权限不对称**：财务中心入口要求 `finance_access`（财务/值班经理/店长）；前台入口只要求 `view+change_accommodation`（前台即可收款）。候选权限 `billing.payment_collect` 若按单一权限码落地，必须同时覆盖两个入口的门禁改造，**且不得通过扩大 `finance_access` 授权面解决**。
3. **绕过路径核查**：全仓 `collect_payment` 调用点仅上述两处（`grep` 核实）；`BillingService.record_deposit`（押金）是独立业务事实，不属于本候选范围。

## 二、FIN-06 审计现状：`billing.collect` 字段对照

现有审计调用（`services_v2.py::collect_payment` 尾部，现取原样）：

```python
AuditEvent.record(
    action="billing.collect",
    entity_type="Payment",
    entity_id=payment.pk,
    actor=collected_by,
    property_obj=property_obj,
    after={"method": method, "amount": str(amount)},
    request=getattr(collected_by, "_request", None),
)
```

### 2.1 现有字段与建议字段对照表

| 字段 | 现有 | 建议 | 说明 |
|---|---|---|---|
| 操作人（actor） | ✅ | ✅ 保留 | `collected_by` |
| 物业范围 | ✅ | ✅ 保留 | `property_obj` |
| Reservation 标识 | ❌ | 建议补 `after["reservation_id"]` | 可经 Payment 实体回溯，但审计独立可读性差 |
| Folio 标识 | ❌ | 建议补 `after["folio_id"]` | 同上 |
| Payment 标识 | ✅ | ✅ 保留 | `entity_id` |
| 金额 | ✅ | ✅ 保留 | `after["amount"]` |
| 币种 | ❌ | 建议补 `after["currency"]` | 多币种口径必需 |
| 支付方式 | ✅ | ✅ 保留 | `after["method"]` |
| 营业日 | ❌ | 建议补 `after["business_date"]` | LedgerEntry 有，Payment 审计无 |
| 收款参考号 | ❌ | 建议补 `after["provider_ref"]` | 幂等键，对账关键 |
| 操作来源 | ❌ | 建议补 `after["source_entry"]`（`frontdesk` / `billing_center`） | 区分两个入口 |
| 业务原因 | ➖ | 不强制 | 收款是正常业务动作，非敏感揭示；如收错款走冲销链 |
| request_id | ➖ | 依赖 `request` 参数 | `request=getattr(collected_by, "_request", None)` 现状恒为 None（模型实例无该属性），**建议显式传入 request 对象** |
| 操作前后状态 | ➖ | 建议补 `before`/`after` 的 Payment.status | 收款创建即 SUCCEEDED；重放场景 changed=False 可记录 |

### 2.2 结论

- 现有审计**不重复建第二套模型**，仅建议在获批后**扩充 `after` 字段**（纯增量，向后兼容）；
- `request` 传参链路存在失效点（`_request` 属性不存在），属**独立低危缺陷**，建议单独授权修复，不在本候选内夹带。

### 3.2 权限命名空间核查（关键发现）

**`membership.status_manage` 按当前解析机制不可运行：**

| 核查项 | 结果 |
|---|---|
| 解析规则 | `AuthorizationService.has_permission()` 按**第一个 `.`** 拆分 → `app_label="membership"`、`codename="status_manage"` |
| Django Permission 表 | 无 `membership` 这个 app_label（guests 应用 `label = "guests"`，见 `apps/guests/apps.py::GuestsConfig`） |
| `registry.permission_exists()` | 对 `membership.status_manage` 恒返回 `False` → 权限无法创建/解析 |
| MODULE_REGISTRY_V2 模块编号 | `"memberships"` 模块（`route_prefix=/manage/memberships`）只是**页面注册编号**，与 Django `app_label` 是两套体系，不能混用 |
| 现有会员相关权限 | 无专项码；当前实际门禁 `hotelapp.change_vip`（module=accommodation 域） |

**结论**：候选权限码必须改名，建议 `guests.membership_status_manage`（app_label=guests 与模型归属一致）。

### 3.3 实际状态机（服务层实现，非文档推测）

| 操作 | 允许转换 | 其他状态 |
|---|---|---|
| `suspend` | ACTIVE → SUSPENDED、PENDING → SUSPENDED | EXPIRED/TERMINATED/SUSPENDED → **拒绝**（SUSPENDED 幂等返回 changed=False） |
| `restore` | 仅 SUSPENDED → ACTIVE | EXPIRED/TERMINATED/**其他一切状态 → 拒绝**（"仅暂停状态允许恢复"） |

**补充守卫**：`restore` 前复核同客人无其他 ACTIVE 会员（唯一有效键语义），冲突报业务错误而非数据库半途失败。

**审计现状（`membership.suspend` / `membership.restore`）**：

| 字段 | suspend | restore |
|---|---|---|
| actor / property_obj | ✅ | ✅ |
| entity_type / entity_id | ✅ GuestMembership | ✅ |
| before / after status | ✅ | ✅ |
| reason（1-240 必填） | ✅ | ✅ |
| request 关联 | ✅ | ✅ |

**结论：现有审计已完整覆盖任务书要求的 7 项字段，无需扩充。** 服务层已具备事务（`@transaction.atomic` + `select_for_update`）、幂等（同状态 changed=False）与状态冲突检查——**全部复用，不得重复开发**。
