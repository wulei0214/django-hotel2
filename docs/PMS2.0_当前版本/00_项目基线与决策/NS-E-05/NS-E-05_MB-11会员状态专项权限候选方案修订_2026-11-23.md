### 1.2 权限命名空间不可运行（已修正，关键）

**`membership.status_manage` 在当前解析机制下无法创建和解析：**

```
AuthorizationService.has_permission("membership.status_manage")
  → 按第一个 "." 拆分：app_label="membership", codename="status_manage"
  → registry.permission_exists() 查 Permission(content_type__app_label="membership", ...)
  → guests 应用 label = "guests"（apps/guests/apps.py：GuestsConfig.label = "guests"）
  → 不存在 app_label="membership" → 恒 False → 权限点无法创建、无法授权、无法校验
```

| 核查项 | 结果 |
|---|---|
| guests 应用 app_label | `guests`（GuestsConfig 显式声明） |
| `membership` app_label | **不存在**（无任何 Django app 使用该 label） |
| MODULE_REGISTRY_V2 模块编号 | `"memberships"`（`route_prefix=/manage/memberships`）——页面注册编号，**≠** Django app_label，两套体系不得混用 |
| 现有会员相关专项码 | **无**；当前会员暂停/恢复/等级变更共用 `hotelapp.change_vip` |
| 权限初始化机制 | `ensure_permissions` 按 `registry.permission_exists()` 校验后由矩阵保存同步——不可解析的码会被静默跳过或报错 |

**修订候选 codename：`guests.membership_status_manage`**（app_label=guests 与 `GuestMembership` 模型归属一致）。

### 1.3 现状澄清：该动作已有权限门禁

原候选文档假设会员状态管理"无权限码"。实际：

```python
# staff_center.py::membership_change_status (L404)
if not AuthorizationService.has_permission(request.user, property_obj, "hotelapp.change_vip"):
    raise ApiError("PERMISSION_DENIED", "缺少会员修改权限。")
```

即：**当前由 `hotelapp.change_vip`（与会员等级变更同权）控制暂停/恢复**。候选专项码的本质是"从 change_vip 中**拆分出**状态管理"，而非"给无门禁动作加门禁"。这一点必须向负责人明确——**引入专项码是权限收紧（change_vip 持有者不再自动可暂停/恢复），不是能力新增**。

## 二、真实调用链（现取现核）

```
POST /api/v1/memberships/{id}/status
  → apps/api/staff_center.py::membership_change_status (L404)
  → 门禁：AuthorizationService.has_permission(user, property, "hotelapp.change_vip")
  → body: {action: "suspend"|"restore", reason: "1-240 必填"}
  → GuestMembershipService.suspend_membership / restore_membership
      （@transaction.atomic + select_for_update，状态机唯一写入口）
  → 审计 membership.suspend / membership.restore（before/after/reason/actor/property/request 全齐）
  → 幂等：同状态重放返回 changed=false，不重复审计
```

跨物业：`GuestMembership.objects.filter(pk=id, property=property_obj)` 强制过滤，他物业会员 404。

## 三、实际状态机（服务层实现，非文档推测）

`GuestMembership.Status`：`PENDING`（待生效）/ `ACTIVE`（有效）/ `SUSPENDED`（暂停）/ `EXPIRED`（已过期）/ `TERMINATED`（已终止）。

| 操作 | 允许转换 | 非法状态处理 |
|---|---|---|
| **suspend** | `ACTIVE → SUSPENDED`、`PENDING → SUSPENDED` | EXPIRED / TERMINATED → 抛业务错误拒绝；SUSPENDED → 幂等返回 changed=False |
| **restore** | **仅** `SUSPENDED → ACTIVE` | EXPIRED / TERMINATED / PENDING / ACTIVE → **拒绝**（"仅暂停状态允许恢复"）；ACTIVE → 幂等 changed=False |

**附加守卫（restore 专属）**：恢复前复核同物业同客人不存在其他 `ACTIVE` 会员（唯一有效键语义），冲突抛 `GuestServiceError` 而非数据库约束半途失败。

**明确纠正**：EXPIRED 与 TERMINATED **均不是**可恢复状态——过期会员走续期/重建链路（P3-MB 条目），终止会员走重新入会，二者都不经 restore。候选文档若将二者列为"可恢复"即与代码不符，本文档已纠正。

**暂停的业务语义**：暂停释放"有效会员唯一键"（`active_guest_key` 由模型 save 维护），允许同客人在暂停期间不占唯一有效约束；历史等级不变。

## 四、暂停与恢复动作拆分评估

| 评估项 | 分析 | 建议 |
|---|---|---|
| 1. 暂停权限 | 风险较低：可逆（可恢复）、不产生资金/权益损失 | 与恢复合并管理 |
| 2. 恢复权限 | **风险较高**：恢复即重获会员权益（折扣/积分资格），且需复核唯一有效键 | 恢复是权益授予动作 |
| 3. 是否共用权限码 | 暂停与恢复同属"会员生命周期状态管理"业务动作；服务层同一入口（action 参数区分）；拆成两码会使注册表膨胀且授权矩阵复杂化（恢复风险高可由**审批**补偿而非权限拆分） | **建议共用一个权限码** |
| 4. 是否需第二人审批 | 当前均无审批；恢复涉及权益重新授予 | 建议恢复增加"操作人 ≠ 等级最近变更人"软约束复核或二次确认；**是否强制第二人审批属负责人裁定**（不擅自增加审批层级） |
| 5. 前台是否应有权限 | 前台无 `change_vip`，日常也不承担会员生命周期管理 | 建议不授 |
| 6. 值班经理/店长 | 当前 `change_vip` 实际授权面（与等级变更同权） | 建议沿用现有 change_vip 授权面迁入专项码 |
| 7. 其他岗位 | 财务/客房/夜审/餐饮/餐饮主管/停车安保 | **明确禁止** |
| 8. 恢复的权益风险 | 恢复后会员立即重获等级权益，且唯一键复核已防"双有效" | 已由服务层守卫；残余风险为"暂停理由未消除即恢复"——由 reason 审计留痕追责 |

**共用权限码不造成权限扩大的论证**：suspend 与 restore 均为"在既有状态机合法转移内切换会员状态"，二者能力集合对称（一个暂停一个恢复，互为逆操作）；风险差异（恢复授权益）由 `reason` 必填 + 审计 before/after + 唯一键复核守卫，而非靠拆分权限码——拆码只改变"谁能点按钮"，不改变"操作本身的风险"，且会使"暂停者无法恢复自己暂停的会员"这类 SoD 变得难以表达（拆码后反而需要额外规则绑定）。若负责人认为恢复必须独立管控，可选方案是仅拆出 `guests.membership_restore`，暂停沿用 change_vip——**此为备选，交负责人裁定**。
