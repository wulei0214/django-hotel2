## 1. 目标与执行边界

本任务清单把六项已确认业务规则及本轮代码审查发现的高风险缺口拆成可开发、可测试、可验收的 P0 工作包。目标是先消除可能导致个人信息泄露、重复账务、错误收费、员工权限残留和库存/入住不一致的风险。

### 1.1 本轮范围

| 编号 | 工作包 | 优先级 | 主要风险 |
|---|---|---:|---|
| P0-01 | 手机号加密存储与 HMAC 查询索引 | P0 | 住客手机号明文泄露 |
| P0-02 | 证件 PII 密钥隔离、加密迁移与旧明文清理 | P0 | 证件信息泄露、密钥耦合 |
| P0-03 | 幂等 PROCESSING 并发安全 | P0 | 重复收款/退款/业务写入 |
| P0-04 | 押金 30% 服务端计算与统一收取 | P0 | 押金金额可被客户端篡改 |
| P0-05 | 提前离店按实际入住晚数结算 | P0 | 多收房费、罚金错误、库存不释放 |
| P0-06 | 员工离职后重新入职及有效任职约束 | P0 | 历史任职覆盖、重复有效任职 |
| P0-07 | 员工工号服务端自动生成 | P0 | 工号重复、人工伪造、并发冲突 |
| P0-08 | Walk-in 完整入住闭环 | P0 | 孤儿入住/账务记录、绕过库存 |

### 1.2 统一约束

- 本轮先更新文档，不代表代码已经修改；每个工作包须单独提交代码和测试证据。
- 所有开发开始前重新获取 main 最新 SHA，并复核对应代码；本文件中的路径/现状仅代表所列基线。
- 继续遵循九角色 RBAC、DEC-02-A1/B2、D1—D6、Q1—Q7 及现行 API 契约。
- 任何前端金额、身份、物业、权限、房态、库存和政策值均不作为最终可信来源；后端必须重新读取并校验。
- 涉及支付渠道的外部副作用必须使用现有支付状态机和持久化补偿机制，不得在数据库事务中伪造外部成功。
- SQLite 通过不等于 MySQL 通过；所有并发、锁、条件更新、唯一性和迁移兼容测试必须在 MySQL 8.0 验证。
- 不得把本任务中的建议 API 路径视为现有接口；实施前应核对路由命名，优先扩展现有契约，避免重复入口。

## 2. P0-01 手机号加密存储与 HMAC 查询索引

### 2.1 当前差距

代码审查基线中，Guest.phone、Guest.phone_normalized、GuestPhone.phone、GuestPhone.phone_normalized 仍存在明文持久化路径。手机号不能作为自然人身份主键；共享手机号也不能把多个住客错误合并。

### 2.2 目标数据设计

建议统一由住客 PII 服务封装读写，底层字段可按现有模型兼容演进：

- phone_ciphertext：手机号密文。
- phone_hmac：规范化手机号的 HMAC 查询索引。
- phone_key_version：加密密钥版本。
- phone_hmac_key_version：HMAC 密钥版本。
- phone_last4：仅在确有业务展示需要时保存末四位；不能反向替代完整手机号。
- verified_at / verification_source：仅在真实验证流程存在时记录；不得把录入视为已验证。
- 旧 phone / phone_normalized 字段在迁移期只读或兼容，最终停止写入并清理明文。

加密密钥和 HMAC 密钥必须相互独立，并与 Django SECRET_KEY 分离。密钥材料不得进入数据库、代码仓库、日志或异常信息。

### 2.3 服务与 API 任务

- 建立统一 PII 服务：规范化、加密、解密、HMAC 计算、密钥版本选择、轮换读取。
- 所有手机号创建/更新统一调用服务；禁止模型之外的 API、后台、导入脚本直接写明文。
- 精确检索通过 HMAC 等值匹配；不得对密文做 LIKE 或使用明文 normalized 字段兜底。
- 前台查看完整号码必须遵循现行敏感字段权限和查看原因要求；财务按既定规则遮罩，客房服务岗位不得查看完整号码。
- 订单查询仍按 booking_no + phone 的既有安全方向处理，必须限流、审计和遮罩；共享手机号不得当作唯一身份验证。
- 对 HMAC 密钥轮换提供双版本过渡/重建索引方案，保证轮换期间可检索。

### 2.4 迁移步骤

1. 盘点所有 Guest/GuestPhone 字段写入点：API、模板表单、后台、导入脚本、测试工厂、旧 hotelapp.Client 兼容路径。
2. 生成迁移前统计：总记录数、空值、重复手机号、共享手机号、格式异常；报告不输出手机号明文。
3. 新增密文/HMAC 字段和索引，先部署双写。
4. 对历史记录分批加密和计算 HMAC；记录成功/失败数量与可重跑游标。
5. 抽样验证：密文可解密、HMAC 可命中、共享号码关系不被合并、空值保持空值。
6. 切换所有读取到 PII 服务，停止明文写入。
7. 完成备份恢复和回滚演练后，清理旧明文字段/值；若字段需保留兼容，必须确保不再存储明文。
8. 迁移结果、异常清单、操作人、时间和 commit SHA 留档。

### 2.5 验收标准

- 数据库中不再存在可直接读取的住客手机号明文或明文规范化索引。
- 相同规范化号码可通过 HMAC 精确查询；格式不同但语义相同的号码按统一规则处理。
- 两位住客共享手机号时仍是两个独立 Guest/身份记录。
- 密钥缺失/错误时不回退 SECRET_KEY，不允许相关敏感操作静默降级。
- 手机号查看权限、遮罩、查看原因、导出审计符合现行 RBAC。
- SQLite 和 MySQL 迁移、回滚/补偿、轮换测试通过。

## 3. P0-02 证件 PII 密钥隔离、加密迁移与旧明文清理

### 3.1 当前差距

GuestDocument 已有 doc_no_ciphertext、doc_no_hash 等字段，但不能据此认定所有证件读写路径已加密。证件服务中存在 DJANGO_PII_KEY 缺失时回退 SECRET_KEY 的实现路径；旧 hotelapp.Client 等历史模型/模板/导出路径仍需完整盘点。

### 3.2 目标约束

- 证件号码等必要字段使用独立 PII 密钥加密；查询索引使用独立 HMAC。
- DJANGO_PII_KEY 不得回退 SECRET_KEY；生产环境必须校验密钥存在、长度/格式正确、版本可识别。
- 证件照片/扫描件默认不长期保存；只有法律依据和期限明确时才允许启用。
- 经营辖区、证件类型、法定登记字段和保留期限尚未确定，故本轮可做加密/元数据框架，但禁止启用自动到期删除。
- legal hold 生效期间必须阻止清理；清理不能删除订单、入住、账务或审计事实。

### 3.3 服务与数据任务

- 统一 PII 加密服务，不允许各模块自行实现加密/解密。
- 证件记录保存加密算法/密钥版本、HMAC 版本、创建时间和数据来源。
- 建立 RetentionPolicy 版本化元数据、retention_until、清理状态和 LegalHold 关联；不得在辖区/期限未确认时写入伪造期限。
- 提供 dry-run 清理预览，输出记录数、对象类型和阻止原因，不输出明文。
- 清理执行需要独立权限、审批、原因、法律依据、批次号、结果校验和审计。
- 密钥轮换必须覆盖在线数据、备份、恢复和灾备流程。

### 3.4 迁移步骤

1. 盘点新旧模型、API、模板、管理后台、导出、日志、异常追踪、测试数据和脚本。
2. 先修复密钥强校验和回退逻辑。
3. 新增/确认密文字段及版本字段，实施双读/双写过渡。
4. 历史证件数据分批加密，逐条校验可解密及哈希查询。
5. 切换所有读写路径至统一服务。
6. 检查日志、缓存、导出和备份中的明文副本。
7. 在完成备份恢复演练、审批和核对后清理旧明文；保留不可逆清理证据。
8. 在辖区与期限确认之前，清理任务只能 dry-run，不得执行删除。

### 3.5 验收标准

- PII 密钥缺失或无效时启动/敏感操作按安全策略失败，不发生 SECRET_KEY 回退。
- 旧证件明文读写路径全部被关闭或有明确受控迁移豁免。
- 证件号码密文可恢复，HMAC 可精确检索；日志和导出无明文泄漏。
- legal hold 可以阻止清理，解除需授权且有审计。
- 未配置辖区/期限时，自动删除任务不能执行。
- 业务账务、入住、审计事实在 PII 清理后仍完整。

## 4. P0-03 幂等 PROCESSING 并发安全

### 4.1 当前差距

api_contract 幂等实现中，相同幂等键处于 PROCESSING 的并发请求仍需验证是否可能继续进入业务 view。若两个请求同时执行，可能重复创建收款、退款或其他不可逆业务事实。

### 4.2 目标状态机

建议状态：PROCESSING、SUCCEEDED、FAILED_RETRYABLE、FAILED_FINAL（具体枚举可复用现有模型）。

- 首个请求原子创建 PROCESSING 记录并取得执行权。
- 同键并发请求不得同时进入业务写逻辑；应返回处理中冲突/可重试响应，或等待后读取最终结果。
- SUCCEEDED 重放必须返回原业务结果，不重新执行。
- 失败状态是否允许重试必须按错误类型分类；不能对已发生外部副作用的 UNKNOWN 状态盲目重放。
- 幂等键作用域至少包含物业、操作者/客户端身份、接口动作和业务场景，防止跨物业碰撞。
- 请求体摘要必须绑定幂等键，防止同键不同参数被当作同一请求。

### 4.3 实施任务

- 核对 IdempotencyRecord 当前唯一约束、事务、状态转换和响应保存字段。
- 对 PROCESSING 获取执行权采用数据库原子机制：唯一插入、行锁或条件更新；不得使用“先查询后插入”的非原子流程。
- 为长任务增加处理租约/超时恢复机制；租约超时后先核对业务事实，再决定恢复，不得直接重复执行。
- 对 Payment、Refund、Deposit、LedgerEntry 等关键业务对象增加业务级唯一性或来源幂等约束，避免只依赖 API 幂等表。
- 外部支付结果 UNKNOWN 时先查询渠道/对账，不得把 UNKNOWN 当失败释放库存或重新扣款。
- 记录请求摘要、状态、响应摘要、执行者、时间和失败类别；不得记录敏感原文。

### 4.4 测试场景

- 同一幂等键、相同请求体，10/20 个并发请求：只能产生一份业务结果。
- 同一幂等键、不同请求体：拒绝并审计。
- 首次请求成功后重复请求：返回原结果，不增加 Payment/Refund/LedgerEntry。
- 首次请求在事务中异常：业务数据回滚，幂等记录状态可安全恢复。
- 进程在业务提交后、响应保存前崩溃：恢复流程能够识别业务事实，不重复执行。
- 不同物业使用相同外部幂等字符串：互不冲突。
- MySQL 8.0 多连接真实并发执行；SQLite 仅做基础回归。

### 4.5 验收标准

以 MySQL 8.0 并发测试为准：同键最多一个执行者；业务对象、支付、退款和账本凭证无重复；失败恢复不丢失外部成功事实；所有重放均可审计。

## 5. P0-04 押金 30% 服务端计算与统一收取

### 5.1 正式规则

- 计算基数：整单 Reservation.total_amount。
- 比例：30%；本阶段无最低/最高金额。
- 普通预订确认时收取；Walk-in 办理入住时收取。
- 押金是预收款/客人资金，不直接计入营业收入。
- 押金可退性遵循适用 DepositPolicy 的 refundable 配置。
- 旧的“入住前 48 小时”规则和历史最低/最高金额讨论不得覆盖本次决策。

### 5.2 当前差距

DepositPolicy 已存在，但 RatePlan 仍有文本 deposit_policy 字段；BillingService.record_deposit() 由调用方传 amount，未由服务端统一按 30% 计算。

### 5.3 实施任务

- 以结构化 DepositPolicy 作为唯一政策源，梳理并迁移 RatePlan 文本字段。
- 在 Reservation 上保存押金政策快照：政策标识/版本、计算基数、比例、应收金额、币种、计算时间和收取触发点。
- 建立统一 DepositService（或等价领域服务）：根据 Reservation.total_amount 计算 30%，减去已有效收取金额得到本次应收差额。
- 前端不传最终金额；如为兼容传入 amount，服务端必须忽略或仅用于一致性核对，不能据此入账。
- 普通预订确认与 Walk-in 入住调用同一计算服务。
- 通过现有 BillingService/Payment/LedgerEntry 完成真实收款记录；押金科目与收入科目分离。
- 检查重复确认、并发确认、支付失败/UNKNOWN、部分支付和退款的幂等边界。
- 押金退款必须关联真实原 Payment，并遵循 D1 与既有退款审批/执行流程。

### 5.4 验收标准

- Reservation.total_amount=1,000.00 时，应收押金 300.00。
- 客户端传 1.00、999.00 或负数均不能改变服务端应收金额。
- 普通预订确认和 Walk-in 入住计算结果一致。
- 已确认订单的政策快照不因 RatePlan 后续修改而变化。
- 并发/重复确认不重复收款；部分已收款只收差额。
- 押金不进入房费营业收入统计；退款关联真实 Payment。
- MySQL 并发与事务回滚测试通过。

## 6. P0-05 提前离店按实际入住晚数结算

### 6.1 正式规则

- 多房预订按实际提前离店的 ReservationRoom 分别计算。
- 实际住宿房费按该房间预订时逐晚价格快照计算。
- 未住晚数不作为住宿房费；只有预订时适用的独立 EarlyDeparturePolicy 可产生违约金。
- 灵活房价默认 NONE；无政策或无快照时按 NONE，不产生非零罚金。
- 退款、负余额、异常放行继续遵循 DEC-02-A1/B2 和正式退款链路。
- 未住日期库存由库存领域服务逐日释放。

### 6.2 当前差距

check_out_stay() 仍以 ReservationRoom.amount 减已过账金额作为补记目标，没有完整的实际入住晚数重算、独立提前离店罚金和未来库存释放闭环。

### 6.3 实施任务

- 新增独立 EarlyDeparturePolicy 结构（或等价结构化配置），不得复用 CancellationPolicy。
- 在预订确认时保存适用政策版本快照和逐晚价格快照。
- 明确酒店当地时间、入住日/离店日边界、跨日夜审和提前退房时刻处理。
- 实际住宿金额按实际入住晚数逐晚汇总；提前离店违约金独立计算、独立记账。
- 已夜审过账的金额按差额处理；不能再次入账同一晚房费。
- 罚金类型允许 NONE、FIRST_NIGHT、FIXED、PERCENT_UNUSED、REMAINING_NIGHTS；各 RatePlan 具体类型和值须受控配置。未配置按 NONE。
- 未来库存逐日调用库存服务，检查停售、已售、已分配、维修、房态和其他预订；不能直接修改 sold 数。
- 库存释放与退房事务的失败策略必须明确；使用幂等键避免重复释放。
- 最终应收低于已收款时，走 RefundLiability/Refund 正式链路；不能在退房接口伪造退款成功。

### 6.4 验收标准

- 预订 4 晚、实际入住 2 晚，NONE 政策只收 2 晚实际住宿费。
- 多房预订仅提前离店房间重算，其他仍入住的房间不被计罚。
- 四种非 NONE 政策按订单时快照计算；修改 RatePlan 不影响历史订单。
- 缺失政策快照按 NONE。
- 夜审已过账金额不重复收费。
- 库存只释放可释放的未住日期，不影响其他预订。
- 重复退房请求不重复收费、退款或释放库存。
- MySQL 事务、并发和失败恢复测试通过。

## 7. P0-06 员工离职后重新入职及有效任职约束

### 7.1 正式规则

- 同一自然人继续使用原 StaffProfile 和登录身份。
- 每次重新入职创建新的 PropertyStaffMembership；旧 Membership 保留，不复活、不覆盖。
- 新任职重新分配岗位和角色，不继承旧任职权限。
- 同一员工同一物业可有多条历史任职，但同一时点最多一条有效任职。
- 不同物业任职相互独立；不得用全局 StaffProfile 状态错误表示单物业任职状态。

### 7.2 当前差距

PropertyStaffMembership 的 uq_membership_property_staff 对 property + staff_profile 永久唯一，阻止创建历史任职；StaffProfile.employment_status 的全局语义也需复核。

### 7.3 实施任务

- 盘点 Membership、StaffRoleAssignment、User 登录状态、会话校验和全局 StaffProfile 状态的依赖。

### 13.4 P0-06 员工重新入职任务补充：MySQL 8 兼容

已发现不能仅将永久唯一约束改成 `UniqueConstraint(condition=Q(status="ACTIVE"))`：Django 4.1 项目使用的 MySQL backend 不支持 partial unique indexes，SQLite 测试通过不能证明 MySQL 约束实际存在。

实施约束：
- 不得以条件唯一索引作为 MySQL 生产唯一性保证。
- 设计 MySQL 8 可真实执行的有效任职唯一机制。优先评估独立有效任职槽/当前任职占位表，或经 MySQL 8 实测的生成列+唯一索引方案。
- 项目固定 Django 4.1；不得直接使用 Django 5.0 才提供的 GeneratedField API。
- 如使用 MySQL 生成列，必须设计 Django 4.1 兼容的 ORM 写入方式，确保 INSERT/UPDATE 不会向数据库生成列写值；迁移需正确维护 Django migration state。
- MySQL 验收必须检查 information_schema.STATISTICS，限定 TABLE_SCHEMA=DATABASE()、TABLE_NAME、INDEX_NAME，并验证 NON_UNIQUE=0、索引列及列顺序；随后实际插入两条冲突有效任职记录，确认数据库拒绝第二条。
- 业务必须明确 ACTIVE/SUSPENDED 等状态是否占用当前任职槽，不能把“只约束 ACTIVE”未经决策直接写成业务定义。
- 同一自然人同一物业允许多条历史 Membership，但同一时点只允许一条有效任职；并发重新入职必须以 MySQL 多连接测试证明。

### 13.5 P0-07 工号生成任务补充：序列行与部门目录
