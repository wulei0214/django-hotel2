## NS-E-01 ｜ MC11-HK-07：维修工单取消与库存/房态语义

### 原始问题

`cancel_maintenance_ticket` 只把工单置 `CANCELLED`，**不回滚房间维修停用状态与库存影响**（`apps/inventory/services_housekeeping_tasks.py`，取消已停用工单后房间保持停用，需人工走"维修恢复"）。

### 业务风险

- 误报修后取消工单，房间可能被长期错误停用，造成可售库存虚减；
- 反向的"取消即自动恢复"又会让未实际修复的房间被售卖，产生超卖与客诉；
- 若无审计衔接，事后无法判断停用是"工单遗留"还是"真实维修中"。

### 推荐方案（开发团队建议，非裁定）

1. **取消工单 ≠ 自动恢复可售**。停用状态是房态事实，工单取消只是流程终止；
2. 取消后房间保持当前维修状态，并明确提示"需另行执行维修恢复/验收"；
3. 恢复必须走既有维修解除链路（`change_maintenance_status` → NORMAL），保留操作人与原因；
4. 工单、房间状态、库存变化三者审计必须可相互追溯；
5. 若业务确认"未派工、未开始的误报工单取消应同时解除停用"，则该分支需显式二次确认 + 单独审计，而不是静默恢复。

### 当前状态

`WAITING_OWNER` —— 需负责人明确"取消是否解除停用"以及是否只对 `OPEN`（未开始）分支开放联动。

### 是否需代码整改

| 分支 | 整改内容 |
|---|---|
| 若批准方案 1-4（保持停用） | **无需改代码**；仅补页面提示文案与审计可追溯性核对 |
| 若批准"未开始工单取消联动解除" | 需改 `cancel_maintenance_ticket` + 测试 + 页面二次确认 |

## NS-E-02 ｜ MC11-NTF-05：预订四类任务的确认入口

### 原始问题

待办中心（`/manage/notifications/`）可派生预订相关 WorkItem，但部分任务缺少直达业务权威入口的跳转；存在"从待办误以为能直接改预订状态"的产品风险。

### 业务风险

- WorkItem 若成为第二套预订状态写入口，破坏"业务事实单一权威归属"；
- 前台/管理者在待办里"标记完成"可能被误读为"预订已处理"。

### 推荐方案

1. **WorkItem 是业务待办投影，不是预订事实源**（与既有纪律一致：通知已读 ≠ 待办完成 ≠ 业务完成）；
2. 通知中心只提供任务提示与**跳转到权威入口**（`/checkin/` 履约写入口）；
3. 预订确认、取消、收款一律走前台权威入口；
4. 严禁 WorkItem 直接写 `Reservation` 状态。

### 当前状态

`WAITING_OWNER` —— 需负责人确认"四类任务"的具体清单与各自跳转目标。

### 是否需代码整改

若当前已无 WorkItem 直写预订（需现取现核），**仅补页面跳转链接与文案**，不新增写服务。

## NS-E-03 ｜ MC11-AUD-04：审计链式哈希

### 原始问题

`integrity_check` 目前只做按日计数摘要，`gaps` 恒空，不具备真正的链式哈希防篡改能力。

### 业务风险

审计事件可被有数据库权限者定向修改而不易察觉；但 PMS 2.0 阶段已有"只追加"三层防护（模型 save/delete + QuerySet + MySQL 触发器），风险部分缓释。

### 推荐方案

1. **PMS 2.0 暂不新增完整链式哈希系统**——避免为安全演进改写/重算历史审计记录；
2. 保留现有追加式审计 + 数据库保护；
3. 链式哈希列入 **PMS 3.0 审计增强候选**（新事件从启用点起算，历史段只登记不重写）；
4. 严禁为"补齐哈希"而重写历史 `AuditEvent`。

### 当前状态

`WAITING_OWNER`（建议裁定为 `DEFERRED_TO_PMS3`）。

### 是否需代码整改

**无需**（PMS 2.0 范围内）。PMS 3.0 启动后单独立项。

## NS-E-04 ｜ MC11-NA-09 / NA-10：调度停摆探测与失败告警

### 原始问题

缺少 `SchedulerRun` 级别的调度运行记录、调度器停摆探测、夜审 FAILED 站内告警与自动夜审提醒。

### 业务风险

夜审/补偿等后台任务静默停摆会导致营业日不推进、收款不补偿，且无人知晓。

### 推荐方案

1. **PMS 2.0 不建设完整调度监控平台**；
2. PMS 3.0 规划 Worker 心跳、任务超时、失败告警（与 Outbox/后台任务机制一并设计）；
3. **严禁自动重跑夜审、账务关账等不可逆操作**——监控与业务执行必须分离，重跑一律人工确认；
4. PMS 2.0 现有 `recover_stale_night_audits` 陈旧 RUNNING 恢复保持不变。

### 当前状态

`WAITING_OWNER`（建议裁定为 `DEFERRED_TO_PMS3`）。

### 是否需代码整改

**无需**（PMS 2.0 范围内）。

## NS-E-05 ｜ MC11-FIN-06 / MB-11：权限码扩展（L3 架构变更）

### 原始问题

财务与会员域存在拟扩展的细分权限码需求，但缺乏"权限码 ↔ 业务动作 ↔ 岗位 ↔ 数据范围 ↔ 审批关系"的一一映射。

### 业务风险

批量增加权限码会稀释职责分离（SoD）强度，可能让同一人既申请又审批；权限矩阵膨胀后九岗位口径难维护。

### 推荐方案

1. **暂不批量增加权限码**；
2. 每个拟增权限码必须先明确：对应业务动作、授予岗位、数据范围（物业级/全局）、与既有审批的关系、是否影响 SoD；
3. 不得以新增权限码的方式绕过既有职责分离（如退款申请/审批/执行三方分离）；
4. 具体扩展由负责人**逐项批准**，并在 `apps/identity/registry.py` 与九岗位矩阵同步登记。

### 当前状态

`WAITING_OWNER` —— 需负责人逐项决定是否新增、新增哪些。

### 是否需代码整改

取决于逐项批准结果；未批准前**不改** `registry.py` 与迁移。
