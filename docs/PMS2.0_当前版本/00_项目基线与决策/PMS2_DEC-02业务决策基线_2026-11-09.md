## 1. 决策范围

本决策记录覆盖 DEC-02-A1、DEC-02-B2 与多笔原支付退款分配规则。支付、库存、账务其余专项决策见《PMS2支付库存账务专项业务决策基线_2026-11-09.md》。

当前代码事实基线：
- `RefundLiability.amount` 保存原始负债金额，原始业务关联及来源字段受不可变约束。
- `RefundLiability.remaining_amount` 只允许随成功退款执行而减少，不允许通过普通更新回增。
- 最后一间房退房时，在同一业务事务中登记待退款负债；正常登记失败则退房回滚。
- 找不到有效原支付及账本凭证，或候选支付可退余额不足时，当前流程阻止最后退房并回滚。
- 退款申请、审批和执行分离；只有退款执行成功并形成 REFUND 账本凭证后，才减少负债余额。
- 候选 Payment 关系仅表示可能的原支付来源，不表示已经分配退款金额。

以上是当前实现事实，不应将本文件中的目标流程误读为已经上线的功能。

## 2. DEC-02-A：待退款负债登记后的 Folio 账务调整

### 2.1 已确认决策

**采用 A1：冻结原负债，账务调整独立记录。**

1. 原始 `RefundLiability.amount` 是负债登记时的财务事实，登记后不得覆盖、重算或直接修改。
2. `RefundLiability.remaining_amount` 不得通过普通编辑增加；成功退款仍是减少该余额的既有唯一常规路径。
3. Folio 关闭后发现漏记消费、错记费用、冲销或其他账务差异，必须产生独立、可追溯的账务调整凭证/记录，并关联原 Folio、Reservation、Property；如与待退款负债有关，还必须关联原 RefundLiability。
4. 调整记录应保留调整类型、金额、币种、原因、证据/备注、创建人、审批人、执行人、时间、幂等标识和审计历史；不得物理删除或改写已生效的历史记录。
5. 经批准的新增应收费用可形成独立抵扣/冲抵事项，减少客人最终应收回的净额；经批准的费用冲销或新增应退款事项可形成独立增加应退金额的事项。两者均不得伪装成退款成功，也不得直接修改原负债。
6. 任何抵扣必须由财务发起，并由值班经理或具有明确授权的审批角色批准；生成独立抵扣凭证。抵扣不属于 Refund，不得生成 REFUND 类型账本凭证，也不得绕过退款申请、审批、执行职责分离。
7. 实际可退净额必须能够从原始负债、已批准调整/抵扣、已成功退款及其账本凭证完整重建。未经批准的调整不得影响可退款金额；不得出现负数余额或超额退款。
8. 在独立调整模型、凭证语义、审批权限、事务边界、审计和财务页面闭环开发完成前，系统不得允许退房后通过直接改写 Folio 或 RefundLiability 来修正负债。现阶段保持原负债冻结，差异进入人工财务核查。

### 2.2 必须实现的控制

- 调整记录和审批状态机；状态变化须校验权限和合法迁移。
- 调整/抵扣与 Folio、Reservation、Property、RefundLiability 的一致性校验。
- 金额使用 Decimal 和明确币种；禁止跨物业、跨预订、跨账单、跨币种关联。
- 同一业务请求幂等；并发审批/执行不得重复抵扣。
- 抵扣凭证、调整状态、负债净额视图及审计事件必须处于同一数据库事务。
- 退款执行与抵扣执行不得重复占用同一负债余额；应使用行锁或等效并发保护。
- 财务中心可分别查看原始负债、已执行退款、已批准抵扣、已批准增加应退调整、剩余可退款净额和未处理调整。
- 未经审批、审批拒绝、执行失败或事务回滚的调整，不得改变有效净额。

### 2.3 明确禁止

- 修改原始 `RefundLiability.amount`。
- 通过普通模型更新将 `remaining_amount` 调大。
- 把新增消费直接伪装成退款，或把抵扣伪装成退款成功。
- 将未审批调整计入可退款净额。
- 物理删除或覆盖历史调整、抵扣和账本凭证。

## 3. DEC-02-B：无法追溯原支付或可退余额不足时的退房处理

### 3.1 已确认决策

**采用 B2：允许经授权异常放行，但建立“待财务核查”记录，不创建正式退款负债。**

触发条件包括但不限于：
- 找不到与待退款金额相匹配的成功 Payment；
- 找不到可追溯的 PAYMENT/DEPOSIT 账本凭证；
- 候选原支付可退余额不足；
- 原支付、账本凭证、物业、预订、Folio 或币种关系不一致；
- 其他导致系统无法可靠证明退款资金来源的情况。

异常处理规则：

1. 正常退房路径仍按原规则执行：有效支付来源和账本凭证可验证、候选可退余额充足、负债登记成功，才形成正式 RefundLiability。
2. 正常条件不满足时，不得自动创建 RefundLiability，不得创建 Refund，不得伪造 Payment 或账本凭证。
3. 前台可发起异常放行申请，必须填写结构化异常原因及必要说明。
4. 由值班经理或更高明确授权岗位审批；申请人和审批人不得相同。审批与实际退房操作应留有独立审计记录。
5. 审批通过后，允许完成客人离店，但必须创建独立的“待财务核查”异常记录，并与 Reservation、Folio、Property 关联。
6. 待财务核查记录不是退款负债，不得进入正式退款申请入口，不得被当作可退款余额。
7. 财务负责核查真实支付来源、账本凭证及可退余额。只有证据补齐且金额核验通过后，才可通过受控的财务纠正/负债登记流程转入正式退款处理。
8. 若核查证明无需退款，应按审批流程关闭异常记录并保留证据；不得删除记录。
9. 异常未解决前，应持续出现在财务待办/异常列表中，并可按物业隔离查看。

### 3.2 必须实现的控制

- 独立异常放行记录及状态机：待审批、已批准待核查、核查中、已解决、已驳回等状态（最终枚举需与实现统一）。
- 原因代码、补充说明、相关金额、币种、支付核查结果、账本核查结果、申请人、审批人、实际操作人、财务处理人及时间戳。
- 申请、审批、退房执行和异常记录创建应具备事务一致性；不得出现放行成功但异常记录丢失。
- 异常放行必须按当前物业权限校验；不能跨物业读取或处理。
- 申请人不得审批自己的异常申请；高权限不能绕过审计。
- 同一 Stay/Folio 的异常放行申请必须幂等并防止并发重复审批/重复放行。
- 财务核查完成后，转正式退款负债必须重新验证支付、账本、金额、币种及物业归属；不能仅凭人工点击将异常记录直接变成退款负债。
- 前台和财务页面明确区分“正式待退款负债”与“待财务核查异常”。

### 3.3 明确禁止

- 无支付来源或可退余额不足时，直接创建正式 RefundLiability。
- 无来源创建 Refund 或 REFUND 账本凭证。
- 将异常放行视为退款审批、退款执行或财务结算完成。
- 前台自行批准自己的异常放行。
- 异常记录跨物业查询、修改或审批。

## 4. DEC-02 多笔原支付规则仍待确认

本次确认**不自动等于**确认多笔原支付的正式分配政策。

当前代码沿用 Refund 的 `payment_id` 必填语义：财务逐笔选择候选 Payment，每笔 Refund 关联一笔 Payment，并可关联同一 RefundLiability；系统不自动拆分、不按顺序分配、不生成虚构分配金额。已执行退款按负债聚合冲减。

该规则仍需负责人单独确认后，才能将 DEC-02 全部业务政策标记为正式确认。
