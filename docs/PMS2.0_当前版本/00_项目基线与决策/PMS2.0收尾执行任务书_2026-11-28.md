## 0. 用法与边界

### 0.1 三条执行线

| 线 | 定义 | 是否改业务代码 | 启动条件 |
|---|---|---|---|
| **A 线** | 立即可执行：证据复跑、签署代录、文档订正、门禁与提交 | 否 | 本文件生效即可执行 |
| **B 线** | 已获 2026-11-28 裁定授权的代码/配置改动 | 是 | 逐卡授权；一卡一提交；双引擎回归 |
| **C 线** | 冻结或依赖外部资源：生产、DBA、负责人书面审批、PMS3 立项 | 原则上否 | 外部条件具备；不得以本地结果冒充 |

### 0.2 每张任务卡的读法

每张卡固定七项：**目标、输入、步骤、DoD、证据、依赖、责任方**。

1. **DoD 全部满足**才算 `DONE`；任一项缺失只能记 `NOT_STARTED` / `WAITING_ENVIRONMENT` / `WAITING_OWNER` / `FAIL`。
2. 证据头必须含：被测树 SHA、环境（OS/Python/Django/DB）、完整命令、开始与结束时间、执行人、退出码。缺一项即视为证据不合格。
3. 证据绑定 SHA 必须是**实际被测树**；文档提交 SHA 不得冒充测试代码基线。
4. 本文件只登记状态与证据指针，不复制大段日志；日志落 `docs/acceptance/evidence/` 对应目录。

### 0.3 状态词（OWNER-07 裁定，8 词）

| 状态 | 含义 | 使用约束 |
|---|---|---|
| `DONE` | 已完成且有合格证据 | 必须能指向证据 |
| `PASS` | 验收通过，无保留 | 仅 C-01 在六项证据同树全绿后可标 |
| `PASS_WITH_RESERVATIONS` | 通过但有书面保留 | 保留项必须逐条列明 |
| `WAITING_OWNER` | 等负责人书面决定/签字 | 不得由开发代拍板 |
| `WAITING_ENVIRONMENT` | 等环境/资源/授权 | 生产、DBA、Redis、SUPER 等 |
| `DEFERRED_TO_PMS3` | 已裁定移交 PMS3 | 不计入 PMS2 已实现功能 |
| `NOT_STARTED` | 未开始 | 需有任务卡或登记项 |
| `FAIL` | 已执行但不通过 | 必须附失败证据与根因 |
