## 2. D1 多笔原支付退款

1. 一笔 Refund 只能指向一笔真实 Payment；不得创建没有原支付依据的退款。
2. 一笔 RefundLiability 可以通过多笔 Refund 分批结清；每笔退款分别校验 Payment 可退余额和负债可退款净额。
3. 默认分配顺序为原支付发生时间升序；同一时间戳以稳定的 Payment 主键作为次级排序键，保证重放结果确定。
4. 财务可在权限允许时人工指定候选原支付；必须填写原因代码和说明，记录操作人、时间及原始候选顺序。
5. 人工指定不得绕过 Property、Reservation、Folio、币种、成功状态、账本凭证和可退余额校验。
6. 系统不得静默拆分一笔 Refund 到多个 Payment。需要跨多个 Payment 退款时，创建多笔独立 Refund。
7. 退款申请阶段应锁定/占用申请金额，防止多个待审批申请共同超额；拒绝、撤销、过期应幂等释放占用；只有退款实际成功并形成 REFUND 凭证才减少已退款负债。
8. 退款申请、审批、执行必须继续遵守职责分离；申请人不得审批自己的申请。

## 3. D2 按渠道配置支付窗口与 Hold

1. 每个支付渠道适配器/配置项提供支付等待窗口参数；参数必须有单位、有效范围、默认值策略、版本和审计。
2. 不允许客户端提交或修改支付窗口、Hold 延长上限。
3. Hold 延长仅在支付仍处于 PENDING/PROCESSING 且渠道查询/回调证据支持继续等待时允许；UNKNOWN 必须先查询渠道，不得以超时直接视为失败。
4. 延长必须有最大累计等待时长、最大延长次数和明确的截止时间；达到上限后转入人工/补偿核查，不可无限延长。
5. 渠道明确失败、明确取消或经查询确认未支付且达到策略终点，方可按规则释放 Hold。
6. 渠道确认成功时，订单支付确认与库存 Hold 转 CONFIRMED 必须通过幂等事务/可恢复流程完成；不得出现支付成功订单却释放库存。
7. 每次创建、延长、释放、确认均记录原因、支付意图、Hold、操作者/任务和时间。

## 4. D3 持久化支付补偿（P0）

补偿任务是资金正确性的一部分，不是可选运维优化。必须包含持久化任务记录、任务类型、幂等键、关联 PaymentIntent/ProviderTransaction/Payment、状态、尝试次数、下次执行时间、最后错误、租约/抢占信息、完成时间及审计。

自动重试采用有上限的指数退避与抖动；超过上限进入死信/人工核查。人工重放不得新建第二笔支付事实，必须重用原业务幂等标识并再次查询渠道。补偿消费者允许多 worker，但同一任务必须有数据库级抢占/租约和幂等保护。队列不能只存在内存、Redis TTL 或浏览器请求中。

## 5. D4 库存差异人工审批修复

1. 系统按 Property、RoomType、业务日期扫描库存权威数据与订单/Hold/停房事实。
2. 差异报告保存计算时间、输入版本/快照、期望值、当前值、差额、影响日期、关联订单/Hold、差异原因候选。
3. 系统可自动分类和建议修复，但不得直接覆盖库存权威计数。
4. 修复申请需说明原因、证据和影响范围；审批人与申请人分离。
5. 执行前重新计算并检查版本；数据已变化则拒绝旧方案并要求重新生成差异。
6. 修复使用唯一领域服务、事务、乐观锁/行锁和审计；修复后再次对账。
7. 仅允许授权岗位审批和执行，权限按物业隔离。

## 6. D5 CLOSED 营业日特殊财务操作

1. CLOSED 是写入保护边界。普通业务写入不得直接写入已关闭营业日。
2. 退款、冲账、历史补记、财务调整等特殊操作必须提交独立申请，提供原因、证据、原业务日期、实际操作日期及关联凭证。
3. 由有明确授权的审批人审批；申请人和审批人分离。审批通过后由专用服务执行，不允许普通 API 增加绕过参数。
4. 任何批准的跨日操作必须保留交易发生时间、渠道确认时间、PMS 接收时间、入账时间、业务日期、物业时区和操作时间。
5. 不得为方便入账而篡改原业务日期；也不得仅因渠道次日回调而将业务日期自动改成回调日期。
6. 重新开启营业日仍是独立高风险操作，不替代特殊财务审批；重开、操作、再次关闭均需完整审计。

## 7. D6 本轮支付渠道边界

本轮交付渠道无关的支付领域模型、Provider Adapter 接口、模拟渠道、回调验签接口契约、状态查询、超时、重复/乱序回调、补偿和对账能力。模拟渠道不得被描述为真实收款，不得在生产配置中伪装成已接入渠道。

真实渠道 SDK、商户密钥、真实沙箱联调、清结算文件格式和生产切流不属于本轮交付；后续单独提交渠道接入决策、凭证管理、安全评估和沙箱验收计划。

## 8. 通用不可妥协约束

- 物业隔离、角色权限、职责分离、字段脱敏和审计不可绕过。
- 金额使用 Decimal，所有金额带明确币种；不得使用浮点数。
- 历史 Payment、Refund、LedgerEntry、审计事实不可改写或删除；通过追加事实更正。
- 所有跨模块写操作必须明确事务边界、幂等键、状态迁移和失败恢复。
- SQLite 与 MySQL 必须针对同一最新 main SHA 验证；MySQL 专项验证行锁、条件更新、唯一约束、死锁与触发器。
- 文档决策确认不等于开发完成；“代码存在”不等于验收通过。

## 9. 实施门禁

P0 顺序：DEC-02 A1/B2、支付意图/渠道交易/补偿/支付账本一致性、Hold 与支付竞态、库存并发防超卖、账本与 Folio 对账、CLOSED 写保护。P1 顺序：支付渠道对账、库存差异治理、夜审恢复、全局锁序及运维可观测性。

每项任务必须交付：现状代码证据、字段字典、迁移、领域服务、API 契约、权限矩阵、页面/待办、审计、SQLite 测试、MySQL 测试、故障注入、运维说明和验收记录。

- **D1 已冻结**：默认按原支付发生时间升序分配，时间相同按 Payment 主键稳定排序；财务可人工指定，但必须记录原因代码、说明、操作者、时间和候选顺序。每笔 Refund 只对应一笔真实 Payment；一笔 RefundLiability 可由多笔 Refund 分批完成。人工指定不绕过归属、币种、成功状态、原始账本凭证和可退余额校验。申请阶段的金额占用、拒绝/撤销释放和退款执行后负债减少必须分别建模，不能混淆。
- **D2 已冻结**：支付窗口由服务端按渠道配置；Hold 仅可在渠道仍处于可等待状态时按上限延长；UNKNOWN 必须主动查询并进入补偿/核查，不可当作失败释放。客户端不得决定窗口和延长上限。

- **D4 已冻结**：自动发现和报告差异；修复权威库存前必须授权审批、执行前重新计算/核对版本、修复后再对账；禁止扫描任务自动覆盖库存事实。
- **D5 已冻结**：CLOSED 后特殊财务操作必须独立申请和审批；保留原业务日期、渠道发生/确认时间、PMS 接收时间、实际入账时间及实际操作日期；重开营业日是另一项独立高风险权限，不得代替特殊操作审批。
- **D6 已冻结**：本轮交付渠道无关架构、模拟 Provider、回调/查询/超时/重复乱序/补偿/恢复测试；真实渠道 SDK、商户凭证、真实沙箱联调、清结算和生产切流单独排期。模拟渠道不得在生产中冒充真实收款。
