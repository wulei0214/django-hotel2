## 一、已落地

|---|---|---|

> 缓存失效/写入失败只记录日志，不得把已经完成的数据库业务操作伪装成 500。

## 一点五、MySQL 不可变审计/账务事实保护（生产必做）

MySQL 触发器是数据库层保护，不是 Django 模型约定，也不是 Migration 自动安装。
当前仓库提供两个管理命令：

- `python manage.py install_mysql_append_only_guards`：在当前连接的 MySQL 数据库安装 6 条只追加保护触发器，以及 1 条现金流水必须属于本人 OPEN 收银班次的 INSERT 保护触发器。
- `python manage.py check_mysql_append_only_guards`：读取当前数据库的 `information_schema.TRIGGERS`，核对触发器名称、表、事件、时机和关键 SQL 定义。

**每个环境的首次部署、数据库重建或迁移到新 MySQL 实例后，都必须显式执行并留存结果：**

```bash
python manage.py migrate --noinput
python manage.py install_mysql_append_only_guards
python manage.py check_mysql_append_only_guards
```

注意事项：

1. 以上命令必须连接目标环境实际使用的 MySQL 数据库；SQLite 检查不能替代生产验收。
2. 安装账号必须拥有目标 schema 的 TRIGGER 权限；应用运行账号不应因此获得任意 DDL 权限。
3. 安装命令会按固定名称重建本项目管理的触发器；应在受控部署窗口执行。
4. CI 的 MySQL 工作流会在测试数据库迁移后安装并校验触发器，但 CI 通过不代表开发、预发布或生产数据库已安装。
5. 发布验收必须保存 `check_mysql_append_only_guards` 的成功输出，并在目标库再次执行校验；不能仅凭代码文件或 CI 记录认定目标环境已受保护。

## 一点六、性能基准测量（ARCH-14）

优化前必须先有量化基线，否则「变快了」无法验证。仓库提供可重复执行的测量脚本：

```bash
# MySQL（权威）：dev 库真实数据
DJANGO_ENV=test python scripts/perf_baseline.py

# 可选：SQLite（仅作参考，不代表 MySQL 行为）
DJANGO_ENV=test DJANGO_DB_ENGINE=sqlite DJANGO_DB_NAME=:memory: python scripts/perf_baseline.py
```

输出 JSON：每个接口的 `median_ms`、`p95_ms`、`queries_median`、`queries_max`，
可直接存档做前后对比（`PERF_SAMPLES` 环境变量可调采样数，默认 12）。

**2026-11-25 首次基线（MySQL 8.0.33，dev 库 68 条预订，每接口 12 样本）**：

| 接口 | 中位数 | p95 | SQL 条数(中位/最大) |
|---|---:|---:|---:|
| `/api/v1/front-desk/overview` | 22.52 ms | 24.49 ms | 15 / 15 |
| `/api/v1/front-desk/reservations` | 36.31 ms | 59.05 ms | 11 / 11 |
| `/api/v1/front-desk/arrivals` | 16.75 ms | 17.88 ms | 7 / 7 |
| `/api/v1/front-desk/rooms` | 14.24 ms | 14.51 ms | 6 / 6 |

判读要点：

1. **SQL 条数中位=最大**说明查询数不随数据量波动，无 N+1；该性质另由
   `apps/api/test_query_budget.py` 自动断言（数据量翻倍时查询数不得线性增长）。
2. 本表为**本机测量**，不是生产容量证明；p95 在 12 样本下代表性有限，仅用于同环境对比。
3. 改动任何列表接口后，重跑本脚本并对比；若 `queries_median` 上升或 p95 劣化超过 50%，
   须在提交说明中给出原因。
4. 生产环境接入后，应在预发布环境用同一脚本复测并替换本节基线
   （`PRODUCTION_PENDING`，需真实数据量与目标服务器）。

## 二、生产部署升级路线（按需实施）

### 负载均衡（Nginx）

本项目为单进程 Django 开发服务器，上生产时建议 `gunicorn`/`waitress`（Windows 用 waitress）+ Nginx：

```nginx
# nginx_hotel.conf —— Nginx 反向代理 + 静态文件
upstream hotel_app {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;   # 多实例即实现负载均衡
}
server {
    listen 80;
    location /static/ {
        alias /path/to/django-hotel/static/;
    }
    location / {
        proxy_pass http://hotel_app;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

### 异步处理（Celery）

项目暂无邮件发送、报表生成类任务。后续加入时：

1. `pip install celery redis`，新增 `hotel/celery.py` 配置 broker 为 Redis；
2. 耗时任务写成 `@shared_task`，视图里 `task.delay()` 异步执行；
3. Windows 本地调试可用 `celery -A hotel worker -P solo`。

### 多因素登录 / 第三方登录

当前为用户名密码登录（Django 内置哈希存储）。接入验证码/第三方登录建议使用
`django-allauth` 或 `django-otp`，在 `/admin/login/` 的登录流程上叠加。

## 三、定时任务（基线 2.0 §4.2 自动调度：Windows Task Scheduler / cron）

现有维护类管理命令共 10 个（本节只做文档化，不新增任务队列依赖；M4-3 增补
`run_inventory_reconciliation` 与 `check_inventory_calendar_coverage` 两条调度任务）。
所有命令支持重复执行（幂等），可安全挂调度；失败重试=按原计划再次执行。

| 命令 | 作用 | 建议频率 | 幂等性 |
|---|---|---|---|
| `python manage.py expire_reservation_holds` | 释放超 15 分钟未支付预订的库存 hold（PENDING + expires_at 已过） | 每 5 分钟 | 是（仅处理过期 PENDING） |
| `python manage.py sync_inventory_calendar --property-code DEFAULT --all-room-types --start-date YYYY-MM-DD --end-date YYYY-MM-DD` | 按物理房间主数据初始化/同步房型日库存（M4-3：`--all-room-types` 滚动全部启用房型；单一房型失败跳过告警不中断） | 每日凌晨 + 房型变更后手动 | 是（按日期区间重算） |
| `python manage.py expire_invitations` | 员工邀请超期扫描（PENDING → EXPIRED，AUTH-20） | 每 15 分钟 | 是 |
| `python manage.py bind_staff_user ...` | 员工账号绑定修复（按需手动执行） | 按需 | 按入参 |
| `python manage.py platform_superadmin_check ...` | 平台超管账号核查（按需手动执行） | 按需 | 按入参 |
| `python manage.py run_billing_maintenance` | 支付意图到期过期、卡住的渠道成功回调重试、账务对账差异转补偿任务 | 每 10 分钟 | 是（意图只处理到期项；任务按稳定幂等键去重） |
| `python manage.py payment_compensation_worker` | 消费持久化补偿任务（渠道查询/回调确认/账本修复/Hold 协调/对账差异） | 每 5 分钟 | 是（数据库租约 + 退避 + 死信） |
| `python manage.py recover_stale_night_audits` | 把超时残留的夜审 RUNNING 标记 FAILED，恢复该营业日可重跑 | 每 15 分钟 | 是（仅处理超阈值记录） |
| `python manage.py run_inventory_reconciliation --property-code DEFAULT` | 库存对账差异扫描（D4：只报告不修复；OPEN 差异经 MC-007 inventory.discrepancy_open 派生待办；M4-4 并入排房冲突日检测，OPEN 冲突经 inventory.room_conflict_open 派生待办，复核走 review_room_conflict） | 每 60 分钟 | 是（同一〔物业, 房型, 住宿日〕只一条 OPEN 差异报告；同一〔物业, 物理房, 住宿日〕只一条 OPEN 冲突报告） |
| `python manage.py check_inventory_calendar_coverage --property-code DEFAULT` | 库存日历滚动覆盖检测（MAX(stay_date) < 今天+7 告警并经 MC-007 inventory.calendar_coverage 派生待办；补齐走 sync_inventory_calendar） | 每日 03:00（晚于 02:30 滚动同步） | 是（只读检测 + 待办对账幂等） |

> 调度闭环：`run_billing_maintenance` 是补偿任务的**创建方**，
> `payment_compensation_worker` 是**消费方**。此前两者都未列入调度清单，
> 导致意图过期、账务对账扫描与四类补偿执行器在生产中完全不可达。

### 夜审（Night Audit）调度口径

- 夜审执行入口是 `POST /api/v1/night-audit/run`（Session 认证 +
  `hotelapp.night_audit_execute` 权限 + CSRF），**不存在也不允许匿名/公开 URL
  触发**（§4.2：任务执行必须校验物业、当前营业日、幂等键和系统身份）。
- 首期由值班经理在「营业日与夜审中心」`/manage/night-audit/` 人工执行
  （预览 → 确认 → 执行两步）；`NightAuditService.run` 自带并发锁、同营业日
  幂等重放与失败记录（NightAuditRun.FAILED + error_message），重复触发安全。
- 自动夜审触发属二期（需系统身份凭证设计），本期不新增管理命令。

### Windows Task Scheduler（开发/单机部署）

**唯一安装入口：`scripts/install_scheduler_tasks.ps1`**（ScheduledTasks API，显式
WorkingDirectory=仓库根，避免 `schtasks` 无「起始于」导致 .env 载入失败）。

```powershell
# 安装并启用（等价于明确声明「本机承担调度部署」）
powershell -ExecutionPolicy Bypass -File scripts\install_scheduler_tasks.ps1

# 停用 / 重新启用（只切换计划任务 State，不重写任务定义）
powershell -ExecutionPolicy Bypass -File scripts\install_scheduler_tasks.ps1 -Disable
powershell -ExecutionPolicy Bypass -File scripts\install_scheduler_tasks.ps1 -Enable

# 彻底移除
powershell -ExecutionPolicy Bypass -File scripts\install_scheduler_tasks.ps1 -Uninstall
```

> **本地开发默认停用。** 「安装」表达的是部署意图，不等于「装机即长期在跑」：
> 只做功能开发时应保持 `-Disable`，八个任务不触发、不写调度日志、不占用任何
> 进程；需要验证调度链路或真正部署时再 `-Enable`。停用是计划任务的持久状态，
> 重启或重新登录都不会自行恢复触发，只有显式 `-Enable` 或重新安装才会恢复。
>
> 判定是否真正停用**以 `State=Disabled` 为准**，不要看 `NextRunTime`——任务被
> 停用后该字段仍保留上次计算值，属正常现象。

> 脚本路径必须指向仓库内文件：在仓库根之外执行时用绝对路径
> （`-File "F:\...\django-hotel\scripts\install_scheduler_tasks.ps1"`），
> 否则 PowerShell 按当前目录解析相对路径并报「实际参数不存在」。

安装器固化的四条硬约束（不要退回手工 `schtasks` 写法）：

1. **动作必须用 `pythonw.exe`**，不能用 `python.exe` 或 `cmd /c`。后两者是控制台
   子系统程序，以交互会话运行时由 Windows Terminal 托管出可见窗口（标题显示
   可执行文件路径），并发触发时还会因控制台创建失败返回 `0x800710E0`；`pythonw`
   不分配控制台，任务完全静默。
2. **`payment_compensation_worker` 必须带 `--once`**。该命令默认 `while True`
   循环，不带 `--once` 的任务永不退出，会长期占用实例并使后续触发全部被拒。
3. **`sync_inventory_calendar` 必须传日期区间**（命令强制要求）。Windows 计划任务
   没有 shell 日期运算，用 `scheduler_runner.py` 的占位符表达滚动窗口：
   `--start-date={today} --end-date={today+30}`（等价下方 cron 的 `$(date ...)`）；
   M4-3 起调度任务固定带 `--all-room-types` 滚动全部启用房型。
4. **每类任务独立日志** `logs/scheduler/<slug>.log`，由
   `scheduler_runner.py --log=` 写入（含完整命令、时间戳、退出码）。多类任务并发
   追加同一文件会互相穿插，证据不可用。

触发重复期按 10 年设置（等效长期有效）；`MultipleInstances=IgnoreNew` 且执行时限
15 分钟，单轮卡死不会堆积实例。核对方式：

```powershell
Get-ScheduledTaskInfo -TaskName 'PMS2 *'    # LastTaskResult 应为 0
Get-Content logs/scheduler/*.log -Tail 5     # 单任务独立日志
```

> 注意：命令重复执行安全（幂等）；并发场景由 `select_for_update` 串行化。
> 营业日切换时间由 `Property.timezone`（IANA 时区）驱动营业日本地日期，
> 调度器的服务器自然日不得直接当作营业日。
