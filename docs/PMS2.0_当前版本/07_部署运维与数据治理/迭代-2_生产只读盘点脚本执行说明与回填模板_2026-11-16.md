## 1. 这份产物解决什么

裁定 5 要求"生产盘点必须执行只读 SQL 并回填"，裁定 3 要求"DEFAULT 归属须依据生产数据逐条核验"。此前盘点 SQL 只以片段形式散落在《历史账务数据迁移与对账方案》§2 与《现状盘点》§6，**没有一份可直接交给运维执行、带只读纪律兜底、且经真实 MySQL 验证的脚本**。本产物补齐这一缺口：

- 脚本 `scripts/legacy_finance_readonly_audit.sql`：把八项统计 + R4-01 六态归属 + R6-01 双轨候选 + R6-02 逐条分类整合为单一可执行 SQL。
- 本文档：执行前置、字段口径、空白回填模板与责任边界。

## 2. 责任边界（必读）

- **本脚本已通过本地 MySQL 只读验证**（14 条 SELECT 全部 EXPLAIN 通过 + 只读事务内冒烟实跑），但本地库为开发环境、旧表为空，**不构成生产盘点结果**。
- **生产执行必须由具备生产库只读权限的运维/财务人员完成**；开发方不接触生产库、不代填结果、不代签。
- 回填后的结果仅用于裁定 3 逐记录核验与 GOV-03 准入证据，**不构成阶段 D 实施授权**；阶段 D 代码开发已由《五主线开发授权与代签边界记录》解冻；生产迁移执行仍受生产盘点数据、生产权限与独立验收等客观门禁约束。

## 3. 执行前置

1. 使用**只读账号**，禁止应用写账号；确认账号无 DDL/DML 权限。
2. 在执行库按脚本 §0.1 跑前置校验：应返回 31 行列清单；缺表/缺列即停止并记录差异，不得凭脚本推定 schema。
3. `START TRANSACTION READ ONLY` 作为辅助保护，阻止当前事务对非临时表的 DML；MySQL DDL 会隐式结束当前事务，不能依赖该事务拦截。必须使用无 DML/DDL 权限的 SELECT-only 账号，禁止应用写账号、管理员账号；结束用 `COMMIT`（无数据变更）。
4. 脚本输出必要的业务记录 ID、金额/日期原值、COUNT/SUM/MIN/MAX、物业 code 与分类；**不返回手机号、证件号、顾客姓名等 PII 字段值**。

## 5. 本地实测发现（可执行性适配，非裁定变更）

对设计文档 SQL 做真实 MySQL 8 EXPLAIN 时发现：房号 JOIN `nr.number = CAST(r.房间号 AS CHAR)` 报 **1267 Illegal mix of collations**。根因：`room.房间号` / `accommodation.客房编号` 为整数字段，`CAST(... AS CHAR)` 后继承库默认 `utf8mb4_general_ci`，而新表 `inventory_room.number` 为 `utf8mb4_0900_ai_ci`。

脚本中 4 处房号 JOIN 已改为两侧显式 `COLLATE utf8mb4_unicode_ci`（R4-01 六态、R6-01 双轨两处、R6-02 分类）。此为**只读盘点脚本的可执行性适配，语义不变、不触及任何裁定**，已在脚本头部注明。

## 8. 只读盘点 SQL 与归档写入命令的边界

本文件关联的 legacy_finance_readonly_audit.sql 是只读盘点脚本，不执行归档写入。不得把“只读 SQL 盘点完成”理解为“可以执行归档命令”。

archive_legacy_finance 命令当前安全行为：

- 不带执行模式参数：默认 dry-run，只读盘点，不写任何表。
- --dry-run：只读盘点；--verify：只读重算归档摘要。
- --execute：唯一写入模式，且必须同时提供 --batch-uid、--operator、--approval-ref；执行模式与 --dry-run / --verify 互斥。
- --approval-ref 会进入归档审计事件，作为负责人书面批准/GOV-03 签署记录的引用。它只是审计引用，不验证签名，也不替代审批流程。
- --operator 是自报标签，不是已认证的 Django 身份；当前 AuditEvent.actor 为空，也不校验它与 OS 登录账号一致。生产执行必须使用获批运维账号，并保留 shell/作业平台执行日志。
- 即使命令参数齐全，也不代表 D3 已获生产执行许可。生产归档仍须满足 D1/D2/D3 的真实准入证据、生产备份/恢复要求、财务负责人批准和独立验收。

本轮开发只在 CI 测试数据库验证命令行为；没有执行生产归档、没有连接生产数据库、没有停写、切换读路径或物理删除。
