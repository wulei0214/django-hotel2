## 1. 对账核验规则（修订版：按分类分列守恒，消除重复计数）

> 修订（2026-11-13，负责人评审意见 A）：原"行数守恒"公式把一条 C1 记录迁移后同时产生的 LedgerEntry 与 LegacyRecordLink 相加，存在重复计数。修订后**按 C1-C5 分类分别核验**，每类各自守恒，且**按 来源模型 × 分类 × 批次 三个维度分组核验**，不只看总数。

### 1.1 分类守恒公式（修订版）

| 分类 | 应满足的关系（源记录数 = ？） | 新建 LedgerEntry 数 |
| --- | --- | --- |
| C1 可迁移 | **C1 源记录数 = 新建凭证数 = 对应 LINKED 映射数** | 恰等于 C1 源记录数 |
| C2 已覆盖 | **C2 源记录数 = 已核验映射数**（LINKED 指向新侧既有凭证） | **必须为 0** |
| C3 重复确认 | **C3 源记录数 = 已核验映射数**（LINKED + review_note 记重复来源） | **必须为 0** |
| C4 无法确认 | **C4 源记录数 = CONFLICT/待人工处置记录数** | **必须为 0** |
| C5 仅归档 | **C5 源记录数 = 归档记录数** | **必须为 0** |

任一维度（来源模型 Folio/FinanceRecord × 分类 C1-C5 × 批次号）的守恒破坏 → 差异清单（阻断批次收口）。C2/C3/C4/C5 任何"新建凭证数 > 0"均为**阻断级缺陷**（分类泄漏：本不该迁移的记录被迁移了）。

**D-08 补充（映射状态唯一性）**：每条源记录在 LegacyRecordLink 中**至多一行**（`uq_legacy_link_source` 约束保证），即至多一个有效映射状态（UNREVIEWED/MATCH_CANDIDATE/LINKED/CONFLICT/IGNORED 五态之一）——状态流转在该唯一行上进行，不存在"一条记录同时处于 CONFLICT 和 LINKED"的中间态。

### 1.2 金额守恒（修订：分维度，不跨币种求和）

| 规则 | 说明 |
| --- | --- |
| 分组维度 | **按 来源模型 × 新凭证类型 × 币种 × 物业 × 批次** 分别核对，禁止跨币种/跨类型求和 |
| 房费 | Σ(旧 Folio 房费，正) = Σ(新 ROOM_CHARGE，正) |
| 押金 | Σ(旧 Folio 押金，正) = Σ(|新 DEPOSIT|，取绝对值) |
| 收款 | Σ(旧 Folio 收款，正) = Σ(|新 PAYMENT|，取绝对值) |
| 精度 | 差额 = 0.00（逐条 Decimal 换算后无舍入；出现舍入需求即归 C4 复核） |

### 1.3 两类配对（不变）+ 订单关联守恒

| 配对 | 规则 | 失败处置 |
| --- | --- | --- |
| 冲销配对 | 旧"冲账"行与其被冲销原凭证：同订单+同类型+金额绝对值相等+日期≥原凭证日期 → 候选对；**人工确认后**经受控迁移服务入口建 void_of 链（§5） | 无法配对 → C4 归档（不伪造 void_of） |
| 订单归属配对 | FinanceRecord.关联订单（字符串）→ Accommodation.id 数值匹配 + 订单存在性 | 不匹配 → C4 |

### 1.4 核验维度清单（每条迁移凭证的验收字段）

行数 / 金额（分类型合计与逐条）/ 订单关联（LegacyRecordLink 双向）/ 营业日期（解析成功且 ≥ 系统最早营业日）/ 凭证类型（映射表 §2）/ 冲销关系（void_of 链或归档标记）/ reference 唯一性 / property 归属（**裁定 3：DEFAULT 逐记录核验通过后生效，不以默认值自动赋值**）。

## 1.5 关联预检模型（第三轮重做，P0-1：关系记录结构，可表达多目标）

> 第二轮评审指正成立：原"逐旧订单一行 + 单 Reservation/Folio 字段"设计与一对多关系、`uq_legacy_link_source` 单目标约束**三者互相冲突**；且 `master_reservation_key` 是新 Folio 的 MASTER 唯一键（约束每个 Reservation 的 MASTER 账单，billing/models.py:148-170），**不能替代旧 Accommodation 到多个新 Reservation 的关系映射**。本节重做为**关系记录结构**。

### 1.5.1 关系基数声明（业务事实，非数据异常）

| 基数 | 真实业务情形 | 处置 |
| --- | --- | --- |
| 1:1（旧订单↔新预订） | 常规 | 逐对确认后映射 |
| 1:N（旧订单→多条新预订） | 同客人多次入住拆单 / 分段入住 | **逐对建立映射**（每对新预订一条关系记录），凭证按归属依据逐条归入对应新账单 |
| N:1（多旧订单→同一新预订） | 合并场景 | 同上，关系记录逐对建立 |
| N:M | 上述组合 | 同上，关系记录表达全部合法配对 |
| 无法对应 | 悬空/证据不足/人工无法确认 | 该订单名下凭证降 C4 归档（原因码），**不丢弃原始数据** |

### 1.5.2 关系记录结构（独立关系表设计，阶段 D 创建；不改 LegacyRecordLink 约束）

**订单-预订关系表**（设计名 `legacy_order_reservation_map`）：一行 = 一对（旧订单, 新预订）确认关系——**关系基数由行数表达**：

| 字段 | 说明 |
| --- | --- |
| 旧订单 ID | Accommodation.id |
| 新 Reservation ID | 确认的新预订 |
| relation_type | ONE_TO_ONE / SPLIT_SOURCE（1:N 的 N 行）/ MERGED_TARGET（N:1 的行）/ OTHER（附说明） |
| match_basis | 匹配依据（客人+日期+房型 等） |
| confirmed_by / confirmed_at | 人工确认留痕 |
| status | CONFIRMED / REJECTED / SUPERSEDED |

约束设计：`UniqueConstraint(旧订单 ID, 新 Reservation ID)`（同一配对仅一行）；旧订单可出现多行（表达 1:N）。

**映射职责拆分（LegacyRecordLink 保持单目标约束）**：

| 关系 | 承载结构 | 说明 |
| --- | --- | --- |
| 旧 Accommodation ↔ 新 Reservation | **`legacy_order_reservation_map`（本节新表）** | 多目标关系在此表达；LegacyRecordLink 不承载 |
| 旧 Folio ↔ 新 LedgerEntry | LegacyRecordLink（source_model="Folio", target_model="LedgerEntry"） | 单目标：一条旧凭证 ↔ 一条迁移凭证（迁移凭证的 folio FK 已含新账单归属） |
| 旧 FinanceRecord ↔ 新 LedgerEntry | LegacyRecordLink（source_model="FinanceRecord"） | 同上 |
| 新 Folio ↔ 新 Reservation | **billing.Folio.reservation FK（既有业务字段）** | 新业务模型自身维护，不进映射表 |

**凭证归属规则（1:N/N:1 场景）**：旧凭证归入哪张新账单，由关系记录 + 凭证日期/类型在**人工确认时逐条判定**并记入该凭证的 LegacyRecordLink（target=迁移凭证）；无法逐条归属的凭证 → C4。

### 1.5.3 样例与约束测试设计（阶段 D TDD）

| 场景 | 预检数据 | 断言 |
| --- | --- | --- |
| 1:1 | 旧#100→新#201 一行 | 迁移凭证挂 #201 的账单；LegacyRecordLink 单行 |
| 1:N | 旧#100→新#201、新#202 两行（SPLIT_SOURCE） | 两行关系均须人工确认；凭证按归属依据分别迁移；无确认归属依据的凭证 → C4 |
| N:1 | 旧#100、旧#101→新#201 两行（MERGED_TARGET） | 两订单凭证均可迁移至同一预订的账单 |
| N:M | 拆分+合并组合 | 关系行表达全部合法配对；无配对的凭证不迁移 |
| 约束 | 同一 (旧订单,新预订) 配对重复插入 | IntegrityError |
| 约束 | 同一旧 Folio 第二条 LegacyRecordLink | IntegrityError（uq_legacy_link_source 保持） |



## 2. 阶段 A 补充：生产盘点命令清单（运维只读执行，结果回填现状盘点 §6）

```sql
-- 规模与时间窗
SELECT COUNT(*), MIN(日期), MAX(日期) FROM finance_record;
SELECT 类型, COUNT(*), SUM(CAST(金额 AS DECIMAL(12,2))), MIN(日期), MAX(日期)
  FROM folio GROUP BY 类型;
SELECT 状态, COUNT(*), SUM(CAST(收款金额 AS DECIMAL(12,2))), SUM(CAST(押金 AS DECIMAL(12,2)))
  FROM accommodation GROUP BY 状态;
SELECT COUNT(*), MIN(营业日期), MAX(营业日期) FROM night_audit;
-- 数据质量预检（决定 C4 规模）
SELECT COUNT(*) FROM folio WHERE 金额 NOT REGEXP '^-?[0-9]+(\\.[0-9]{1,2})?$';
SELECT COUNT(*) FROM folio WHERE 日期 NOT REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$';
SELECT COUNT(*) FROM folio f LEFT JOIN accommodation a ON f.order_id=a.id
  WHERE f.order_id IS NOT NULL AND a.id IS NULL;                          -- 孤儿凭证
SELECT COUNT(*) FROM finance_record WHERE 类型='支出';                      -- 无法映射类规模
-- 新账本覆盖预检（C2 判定输入）
SELECT COUNT(*) FROM ledger_entry WHERE reference LIKE 'legacy:%';          -- 应为 0（未迁移）
-- D-09 补充：FinanceRecord 解析失败预检
SELECT COUNT(*) FROM finance_record WHERE 金额 NOT REGEXP '^-?[0-9]+(\\.[0-9]{1,2})?$';
SELECT COUNT(*) FROM finance_record WHERE 日期 NOT REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$';
-- D-09 重写（第三轮 P0-3）：非 DEFAULT 物业归属证据——真实关联路径
-- 主路径：旧订单 → 旧 Room.房间号 → 新 inventory Room.number（按房号匹配）→ 新 Room.property
-- 说明：旧 Room 无 property 维度；归属证据 = 旧房号能否在新侧对应唯一物业的房间。
--   若新侧存在非 DEFAULT 物业且房号与其匹配 → 归属证据冲突；否则归 DEFAULT 证据。
-- 表名按 Django 默认（inventory_room/core_property）；列名以实际 db_column 为准，执行前运维核对。
SELECT r.房间号,
       COUNT(DISTINCT nr.property_id) AS matched_properties,
       GROUP_CONCAT(DISTINCT p.code)  AS matched_property_codes
  FROM accommodation a
  JOIN room r             ON r.房间号 = a.客房编号
  JOIN inventory_room nr  ON nr.number = CAST(r.房间号 AS CHAR)
  JOIN core_property p    ON p.id = nr.property_id
 GROUP BY r.房间号
HAVING matched_properties > 1;                       -- 同号多物业 = 归属冲突证据
SELECT COUNT(DISTINCT a.客房编号) AS orders_no_room_match
  FROM accommodation a
  LEFT JOIN room r ON r.房间号 = a.客房编号
 WHERE r.房间号 IS NULL;                             -- 旧房号在新侧无对应（证据不足类）

-- D-09 重写：新旧重复事实交叉核验（C2/C3 判定输入）
-- 口径：旧 Folio 收款（金额/日期）与新 LedgerEntry PAYMENT（|amount|/business_date）
-- 逐笔匹配重合度——只输出候选对清单供人工核验，不构成 C2/C3 判定本身。
SELECT f.id AS legacy_folio_id, f.金额, f.日期,
       le.id AS new_entry_id, le.amount, le.business_date
  FROM folio f
  JOIN ledger_entry le
    ON le.entry_type = 'PAYMENT'
   AND le.amount = CAST(-CAST(f.金额 AS DECIMAL(12,2)) AS CHAR)  -- 新侧收款为负
   AND DATE(le.business_date) = STR_TO_DATE(f.日期, '%Y-%m-%d')
 ORDER BY f.id
 LIMIT 200;                                                          -- 候选对采样（人工核验入口）
```

## 3. 差异处理流程（原则 5：只报告，不自动修账）

1. 对账工具输出三类清单：**差异清单**（守恒破坏，逐条带两侧证据）/ **C4 清单**（无法确认）/ **配对候选清单**（冲销/订单，待人工确认）；
2. 差异由财务负责人指派核对：核对依据 = 历史页面（legacy_reservations 端点原样展示）+ Admin 只读记录 + 原始凭证影像（如有）；
3. 处置动作仅两种：**修正分类**（改 LegacyRecordLink mapping_status + review_note）或**维持归档**；
4. 任何"改数"行为（旧表或新账本）都超出本迭代权限——新账本纠错走既有红字冲销 + ApprovalRecord 流程，旧表纠错属历史档案，不改。

## 4. 迁移机制设计（阶段 D 实施蓝图，本轮不写代码）

- **形态**：Django management command（`migrate_legacy_finance`，设计稿），**只读旧表 + 只写新账本/LegacyRecordLink/归档表**；
- **事务边界**：按订单分批（每批一个 atomic：校验→建凭证→LegacyRecordLink→计数器），批间可断点续跑（reference 幂等保证重跑零新增）；
- **冲销建链**：仅处理"配对候选清单"中**人工确认**的条目，经 **§5 受控历史迁移服务入口** 建 `legacy_workflow=True` 凭证（不得经 ORM 绕过 BillingService，不补造审批人）；
- **LegacyRecordLink 写入通道**：source_system="hotelapp"、source_model="Folio"/"FinanceRecord"、mapping_status 按 §3 分类矩阵流转（UNREVIEWED→MATCH_CANDIDATE→LINKED/CONFLICT/IGNORED），reviewed_by 记录核验人；

## 5. 受控历史迁移服务入口（第二轮复审阻断项 2：创建链路重构设计）

> 核实结论（2026-11-13 复核 @ fe579479）：`BillingService.post_entry`（services_v2.py:334）签名**不含** `legacy_workflow` 参数，创建凭证的 facts 字典也不传该键（models.py:301 字段存在，`ck_ledger_reversal_approval_link` 约束允许 REVERSAL + legacy_workflow=True + approval_record=NULL）——评审断言属实。**禁止以 ORM `LedgerEntry.objects.create` 绕过领域服务**（将绕过幂等/币种/关账/审计守卫），也**不得**把该入口变成普通员工可调用的审批旁路。

### 5.0 首轮设计的缺陷确认（评审意见成立）

首轮 §5.2"委托 post_entry 后追加 legacy_workflow 字段赋值"**不可执行**，四条路径均被否：
1. post_entry 先创建 REVERSAL 而无 legacy_workflow=True → DB 约束（approval_record=NULL + legacy_workflow=False）拒绝创建；
2. 先建普通凭证再改 legacy_workflow → 违反账本不可变原则（ImmutableLedgerEntryQuerySet + save 守卫）；
3. 直接 objects.create → 绕过幂等/币种/关账/五重校验守卫；
4. post_entry 后改字段 → 触发模型不可变保护。

### 5.1 修订设计：共享凭证创建流 + 显式迁移授权（legacy_workflow 首次创建时确定）

**核心重构**：从 `BillingService.post_entry` 中抽出**共享凭证创建流程** `_create_entry_record(*facts, legacy_workflow=False)`（私有方法，包含既有全部守卫：幂等重放判定/币种一致/关账豁免五重校验/金额校验），`post_entry` 与受控历史迁移入口共同委托它：

```
BillingService
├── post_entry(...)                    # 公共入口：签名不变（无 legacy_workflow 参数），
│     └── _create_entry_record(facts, legacy_workflow=False)
└── post_legacy_migration_entry(...)   # 受控历史迁移入口（新增，仅迁移命令可及），
      └── _create_entry_record(facts, legacy_workflow=True)   # 首次创建即定值
```

- `legacy_workflow` 在**首次创建凭证时确定**（经 `_create_entry_record` 参数传入），创建后不可修改（不可变守卫不变）；
- 普通业务入口签名不变、无该参数 → **普通业务调用不能设置历史迁移标识**；
- 常规 REVERSAL 无 approval_record 仍被 DB 约束拒绝 → **普通业务调用不能创建无审批的 REVERSAL**（守卫行为不变）。

### 5.2 可验证的调用授权（第三轮修订 P0-4：完整权限闭环）

受控入口的调用授权以**数据库登记的迁移批次记录（`LegacyMigrationBatch`，阶段 D 新增模型）**为凭证，并验证**执行上下文与批次授权的匹配**——"存在一个 ACTIVE 批次"不是全部权限判断。

**批次记录字段（授权信息全量）**：

| 字段 | 说明 |
| --- | --- |
| batch_uid（唯一） | 批次身份 |
| approved_by / approved_at / approval_basis | 审批事实：批准人、批准时间、审批依据（文档/Issue 链接） |
| scope_property | 授权处理的物业（FK） |
| scope_source_models | 授权处理的来源模型清单（Folio/FinanceRecord） |
| scope_record_range | 授权处理的记录范围（pk 区间或 id 清单快照） |
| executed_by | 实际执行人（迁移命令操作者，须与批准人分离——批准人≠执行人） |
| status | PENDING → ACTIVE → CLOSED（含 REJECTED）；合法转换：PENDING→ACTIVE/CLOSED/REJECTED，ACTIVE→CLOSED；其余转换拒绝 |

**授权闭环流程**：
1. 批次登记（PENDING）：由迁移计划批准时创建，登记审批事实与范围；
2. 负责人批准 → status=ACTIVE（批准人记录在案）；
3. 迁移命令以 `batch_uid + 操作者身份` 调用受控入口；
4. 受控入口校验（全部通过才执行）：批次存在且 ACTIVE；**操作者 = batch.executed_by**（执行身份匹配）；处理对象的 property/来源模型/记录范围 ∈ 批次 scope；
5. 每次调用（成功/拒绝）均写 AuditEvent（billing.legacy_migration：批次/调用者/动作/结果）；
6. 批次 CLOSED 后入口永久拒绝（防止关闭后继续执行）；批次处理完成或终止时关闭。

**执行上下文验证**：受控入口除校验批次外，还校验每次调用传入的记录集合 ⊆ batch.scope_record_range——越范围记录一律拒绝并审计。
