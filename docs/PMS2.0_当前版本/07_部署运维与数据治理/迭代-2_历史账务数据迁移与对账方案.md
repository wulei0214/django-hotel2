## 1. 对账核验规则（修订版：按分类分列守恒，消除重复计数）

> 修订（2026-11-13，负责人评审意见 A）：原"行数守恒"公式把一条 C1 记录迁移后同时产生的 LedgerEntry 与 LegacyRecordLink 相加，存在重复计数。修订后**按 C1-C5 分类分别核验**，每类各自守恒，且**按 来源模型 × 分类 × 批次 三个维度分组核验**，不只看总数。

### 1.1 分类守恒公式（修订版）

| 分类 | 应满足的关系（源记录数 = ？） | 新建 LedgerEntry 数 |
| --- | --- | --- |
| C1 可迁移 | **C1 源记录数 = 新建凭证数 = 对应 LINKED 映射数** | 恰等于 C1 源记录数 |
| C2 已覆盖 | **C2 源记录数 = 已核验映射数**（LINKED 指向新侧既有凭证） | **必须为 0** |
| C3 重复确认 | **C3 源记录数 = 已核验映射数**（LINKED + review_note 记重复来源） | **必须为 0** |
| C4 无法确认 | **C4 源记录数 = CONFLICT/待人工处置记录数** | **必须为 0** |
| C5 仅归档 | **C5 源记录数 = 归档记录数** | **必须为 0** |

任一维度（来源模型 Folio/FinanceRecord × 分类 C1-C5 × 批次号）的守恒破坏 → 差异清单（阻断批次收口）。C2/C3/C4/C5 任何"新建凭证数 > 0"均为**阻断级缺陷**（分类泄漏：本不该迁移的记录被迁移了）。

**D-08 补充（映射状态唯一性）**：每条源记录在 LegacyRecordLink 中**至多一行**（`uq_legacy_link_source` 约束保证），即至多一个有效映射状态（UNREVIEWED/MATCH_CANDIDATE/LINKED/CONFLICT/IGNORED 五态之一）——状态流转在该唯一行上进行，不存在"一条记录同时处于 CONFLICT 和 LINKED"的中间态。

### 1.2 金额守恒（修订：分维度，不跨币种求和）

| 规则 | 说明 |
| --- | --- |
| 分组维度 | **按 来源模型 × 新凭证类型 × 币种 × 物业 × 批次** 分别核对，禁止跨币种/跨类型求和 |
| 房费 | Σ(旧 Folio 房费，正) = Σ(新 ROOM_CHARGE，正) |
| 押金 | Σ(旧 Folio 押金，正) = Σ(|新 DEPOSIT|，取绝对值) |
| 收款 | Σ(旧 Folio 收款，正) = Σ(|新 PAYMENT|，取绝对值) |
| 精度 | 差额 = 0.00（逐条 Decimal 换算后无舍入；出现舍入需求即归 C4 复核） |

### 1.3 两类配对（不变）+ 订单关联守恒

| 配对 | 规则 | 失败处置 |
| --- | --- | --- |
| 冲销配对 | 旧"冲账"行与其被冲销原凭证：同订单+同类型+金额绝对值相等+日期≥原凭证日期 → 候选对；**人工确认后**经受控迁移服务入口建 void_of 链（§5） | 无法配对 → C4 归档（不伪造 void_of） |
| 订单归属配对 | FinanceRecord.关联订单（字符串）→ Accommodation.id 数值匹配 + 订单存在性 | 不匹配 → C4 |

### 1.4 核验维度清单（每条迁移凭证的验收字段）

行数 / 金额（分类型合计与逐条）/ 订单关联（LegacyRecordLink 双向）/ 营业日期（解析成功且 ≥ 系统最早营业日）/ 凭证类型（映射表 §2）/ 冲销关系（void_of 链或归档标记）/ reference 唯一性 / property 归属（**裁定 3：DEFAULT 逐记录核验通过后生效，不以默认值自动赋值**）。

## 1.5 关联预检表（评审意见 B：迁移目标对象闭环）

**迁移不是"旧 Folio → 新 LedgerEntry"的直映射**——新 LedgerEntry 必须挂在 property → 新 Folio → （新 Reservation）的归属链上，而旧 Accommodation 与新 Reservation 之间**当前无任何映射数据**。因此阶段 D 迁移前必须建立**关联预检表**（逐旧订单一行），字段：

| 字段 | 说明 |
| --- | --- |
| 旧订单 ID（Accommodation.id） | 源主键 |
| 新 Reservation ID | 关联判定结果（一对一 / 一对多 / 多对一 / 无法对应 / 订单取消态） |
| 新 Folio ID | 目标账单（迁移凭证挂载点） |
| 物业 ID | 裁定 3 核验结果（DEFAULT 或 CONFLICT） |
| 对应关系判定结果 | 一致 / 冲突 / 无法对应（含原因码） |
| 人工确认人 / 确认时间 | 核验留痕 |

**预检规则（修订，D-06）**：
- **一对多/多对一 ≠ 数据异常**：旧订单可能有合法的多次预订历史（如同客人多次入住拆单）——按业务事实判定迁移资格，不为了让工具简单而丢弃真实业务关系；
- **判定分两类**：① 真实业务关系（如一次入住拆多张新 Folio）→ 记入预检表 relation_type="one_to_many"/"many_to_one"，逐对人工确认后**分别建立映射**；② 无法确认（悬空/状态冲突/证据不足）→ 该订单名下旧凭证不得迁移（降 C4 归档，原因码记录）；
- **映射结构（阻断 1 闭环）**：`uq_legacy_link_source` 约束保持不动（一条源记录仅一行映射）。映射按**来源-目标模型对**拆分为三条独立链路，一条旧记录只产生**一条** LegacyRecordLink：
  | 来源模型 | 目标模型 | 链路含义 | 产物 |
  | --- | --- | --- | --- |
  | Accommodation | Reservation | 旧订单↔新预订（预检表产物） | LINKED |
  | Folio | LedgerEntry | 旧凭证↔迁移产生的新凭证（新 Folio 归属经凭证自身 folio FK 自洽） | LINKED |
  | FinanceRecord | LedgerEntry | 有资格迁移的旧财务记录↔新凭证 | LINKED |
  - **不建立 Folio→Folio 映射**（新 Folio 与新 Reservation 的对应关系由新业务模型自身字段 master_reservation_key 维护，不塞进 LegacyRecordLink）；如确有独立账单映射需求，另行设计关联模型及约束（不修改现有唯一约束）；
  - C2/C3（已覆盖/重复确认）同样走 Folio→LedgerEntry 单链（target 指向新侧既有凭证）；
- 迁移工具只消费预检表与分类判定，不自行推断关联。

## 3. 差异处理流程（原则 5：只报告，不自动修账）

1. 对账工具输出三类清单：**差异清单**（守恒破坏，逐条带两侧证据）/ **C4 清单**（无法确认）/ **配对候选清单**（冲销/订单，待人工确认）；
2. 差异由财务负责人指派核对：核对依据 = 历史页面（legacy_reservations 端点原样展示）+ Admin 只读记录 + 原始凭证影像（如有）；
3. 处置动作仅两种：**修正分类**（改 LegacyRecordLink mapping_status + review_note）或**维持归档**；
4. 任何"改数"行为（旧表或新账本）都超出本迭代权限——新账本纠错走既有红字冲销 + ApprovalRecord 流程，旧表纠错属历史档案，不改。

## 4. 迁移机制设计（阶段 D 实施蓝图，本轮不写代码）

- **形态**：Django management command（`migrate_legacy_finance`，设计稿），**只读旧表 + 只写新账本/LegacyRecordLink/归档表**；
- **事务边界**：按订单分批（每批一个 atomic：校验→建凭证→LegacyRecordLink→计数器），批间可断点续跑（reference 幂等保证重跑零新增）；
- **冲销建链**：仅处理"配对候选清单"中**人工确认**的条目，经 **§5 受控历史迁移服务入口** 建 `legacy_workflow=True` 凭证（不得经 ORM 绕过 BillingService，不补造审批人）；
- **LegacyRecordLink 写入通道**：source_system="hotelapp"、source_model="Folio"/"FinanceRecord"、mapping_status 按 §3 分类矩阵流转（UNREVIEWED→MATCH_CANDIDATE→LINKED/CONFLICT/IGNORED），reviewed_by 记录核验人；
- **干跑模式**：`--dry-run` 输出分类统计与差异清单，不写任何表；
- **归档表设计**：`legacy_folio_archive` 等**新建归档表**（含全列快照+归档时间+批次号），旧表本身在 E 阶段前不删不改；
- **凭证挂载**：迁移凭证仅挂载到**关联预检表（§1.5）人工确认**的新 Folio；预检表无法对应的订单名下凭证一律不迁移。

## 5. 受控历史迁移服务入口（第二轮复审阻断项 2：创建链路重构设计）

> 核实结论（2026-11-13 复核 @ fe579479）：`BillingService.post_entry`（services_v2.py:334）签名**不含** `legacy_workflow` 参数，创建凭证的 facts 字典也不传该键（models.py:301 字段存在，`ck_ledger_reversal_approval_link` 约束允许 REVERSAL + legacy_workflow=True + approval_record=NULL）——评审断言属实。**禁止以 ORM `LedgerEntry.objects.create` 绕过领域服务**（将绕过幂等/币种/关账/审计守卫），也**不得**把该入口变成普通员工可调用的审批旁路。

### 5.0 首轮设计的缺陷确认（评审意见成立）

首轮 §5.2"委托 post_entry 后追加 legacy_workflow 字段赋值"**不可执行**，四条路径均被否：
1. post_entry 先创建 REVERSAL 而无 legacy_workflow=True → DB 约束（approval_record=NULL + legacy_workflow=False）拒绝创建；
2. 先建普通凭证再改 legacy_workflow → 违反账本不可变原则（ImmutableLedgerEntryQuerySet + save 守卫）；
3. 直接 objects.create → 绕过幂等/币种/关账/五重校验守卫；
4. post_entry 后改字段 → 触发模型不可变保护。

### 5.1 修订设计：共享凭证创建流 + 显式迁移授权（legacy_workflow 首次创建时确定）

**核心重构**：从 `BillingService.post_entry` 中抽出**共享凭证创建流程** `_create_entry_record(*facts, legacy_workflow=False)`（私有方法，包含既有全部守卫：幂等重放判定/币种一致/关账豁免五重校验/金额校验），`post_entry` 与受控历史迁移入口共同委托它：

```
BillingService
├── post_entry(...)                    # 公共入口：签名不变（无 legacy_workflow 参数），
│     └── _create_entry_record(facts, legacy_workflow=False)
└── post_legacy_migration_entry(...)   # 受控历史迁移入口（新增，仅迁移命令可及），
      └── _create_entry_record(facts, legacy_workflow=True)   # 首次创建即定值
```

- `legacy_workflow` 在**首次创建凭证时确定**（经 `_create_entry_record` 参数传入），创建后不可修改（不可变守卫不变）；
- 普通业务入口签名不变、无该参数 → **普通业务调用不能设置历史迁移标识**；
- 常规 REVERSAL 无 approval_record 仍被 DB 约束拒绝 → **普通业务调用不能创建无审批的 REVERSAL**（守卫行为不变）。

### 5.2 可验证的调用授权（不做纯字符串约定）

受控入口的调用授权以**数据库登记的迁移批次记录**为凭证（字符串参数可伪造，DB 记录须经批准流程产生）：

| 授权要素 | 实现 |
| --- | --- |
| 迁移批次登记 | 阶段 D 新增迁移批次登记机制（批次号+批准人+批准依据+状态 ACTIVE/CLOSED，登记记录由负责人批准迁移计划时创建） |
| 入口校验 | `post_legacy_migration_entry` 首行校验批次记录存在且 status=ACTIVE；不存在/已关闭 → 拒绝（拒绝与审计同事务） |
| 人工确认校验 | REVERSAL 仅消费配对候选清单中人工确认（LegacyRecordLink LINKED）的记录；无确认 → 拒绝 |
| 审计 | 每次受控创建写 AuditEvent（billing.legacy_migration：批次/来源/核验人），与凭证同事务 |
