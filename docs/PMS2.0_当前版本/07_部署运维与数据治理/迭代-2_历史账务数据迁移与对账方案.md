## 1. 对账核验规则（修订版：按分类分列守恒，消除重复计数）

> 修订（2026-11-13，负责人评审意见 A）：原"行数守恒"公式把一条 C1 记录迁移后同时产生的 LedgerEntry 与 LegacyRecordLink 相加，存在重复计数。修订后**按 C1-C5 分类分别核验**，每类各自守恒，且**按 来源模型 × 分类 × 批次 三个维度分组核验**，不只看总数。

### 1.1 分类守恒公式（修订版）

| 分类 | 应满足的关系（源记录数 = ？） | 新建 LedgerEntry 数 |
| --- | --- | --- |
| C1 可迁移 | **C1 源记录数 = 新建凭证数 = 对应 LINKED 映射数** | 恰等于 C1 源记录数 |
| C2 已覆盖 | **C2 源记录数 = 已核验映射数**（LINKED 指向新侧既有凭证） | **必须为 0** |
| C3 重复确认 | **C3 源记录数 = 已核验映射数**（LINKED + review_note 记重复来源） | **必须为 0** |
| C4 无法确认 | **C4 源记录数 = CONFLICT/待人工处置记录数** | **必须为 0** |
| C5 仅归档 | **C5 源记录数 = 归档记录数** | **必须为 0** |

任一维度（来源模型 Folio/FinanceRecord × 分类 C1-C5 × 批次号）的守恒破坏 → 差异清单（阻断批次收口）。C2/C3/C4/C5 任何"新建凭证数 > 0"均为**阻断级缺陷**（分类泄漏：本不该迁移的记录被迁移了）。

**D-08 补充（映射状态唯一性）**：每条源记录在 LegacyRecordLink 中**至多一行**（`uq_legacy_link_source` 约束保证），即至多一个有效映射状态（UNREVIEWED/MATCH_CANDIDATE/LINKED/CONFLICT/IGNORED 五态之一）——状态流转在该唯一行上进行，不存在"一条记录同时处于 CONFLICT 和 LINKED"的中间态。

### 1.2 金额守恒（修订：分维度，不跨币种求和）

| 规则 | 说明 |
| --- | --- |
| 分组维度 | **按 来源模型 × 新凭证类型 × 币种 × 物业 × 批次** 分别核对，禁止跨币种/跨类型求和 |
| 房费 | Σ(旧 Folio 房费，正) = Σ(新 ROOM_CHARGE，正) |
| 押金 | Σ(旧 Folio 押金，正) = Σ(|新 DEPOSIT|，取绝对值) |
| 收款 | Σ(旧 Folio 收款，正) = Σ(|新 PAYMENT|，取绝对值) |
| 精度 | 差额 = 0.00（逐条 Decimal 换算后无舍入；出现舍入需求即归 C4 复核） |

### 1.3 两类配对（不变）+ 订单关联守恒

| 配对 | 规则 | 失败处置 |
| --- | --- | --- |
| 冲销配对 | 旧"冲账"行与其被冲销原凭证：同订单+同类型+金额绝对值相等+日期≥原凭证日期 → 候选对；**人工确认后**经受控迁移服务入口建 void_of 链（§5） | 无法配对 → C4 归档（不伪造 void_of） |
| 订单归属配对 | FinanceRecord.关联订单（字符串）→ Accommodation.id 数值匹配 + 订单存在性 | 不匹配 → C4 |

### 1.4 核验维度清单（每条迁移凭证的验收字段）

行数 / 金额（分类型合计与逐条）/ 订单关联（LegacyRecordLink 双向）/ 营业日期（解析成功且 ≥ 系统最早营业日）/ 凭证类型（映射表 §2）/ 冲销关系（void_of 链或归档标记）/ reference 唯一性 / property 归属（**裁定 3：DEFAULT 逐记录核验通过后生效，不以默认值自动赋值**）。

## 1.5 关联预检模型（第三轮重做，P0-1：关系记录结构，可表达多目标）

> 第二轮评审指正成立：原"逐旧订单一行 + 单 Reservation/Folio 字段"设计与一对多关系、`uq_legacy_link_source` 单目标约束**三者互相冲突**；且 `master_reservation_key` 是新 Folio 的 MASTER 唯一键（约束每个 Reservation 的 MASTER 账单，billing/models.py:148-170），**不能替代旧 Accommodation 到多个新 Reservation 的关系映射**。本节重做为**关系记录结构**。

### 1.5.1 关系基数声明（业务事实，非数据异常）

| 基数 | 真实业务情形 | 处置 |
| --- | --- | --- |
| 1:1（旧订单↔新预订） | 常规 | 逐对确认后映射 |
| 1:N（旧订单→多条新预订） | 同客人多次入住拆单 / 分段入住 | **逐对建立映射**（每对新预订一条关系记录），凭证按归属依据逐条归入对应新账单 |
| N:1（多旧订单→同一新预订） | 合并场景 | 同上，关系记录逐对建立 |
| N:M | 上述组合 | 同上，关系记录表达全部合法配对 |
| 无法对应 | 悬空/证据不足/人工无法确认 | 该订单名下凭证降 C4 归档（原因码），**不丢弃原始数据** |

### 1.5.2 关系记录结构（独立关系表设计，阶段 D 创建；不改 LegacyRecordLink 约束）

**订单-预订关系表**（设计名 `legacy_order_reservation_map`）：一行 = 一对（旧订单, 新预订）确认关系——**关系基数由行数表达**：

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| legacy_order | FK → hotelapp.Accommodation，`on_delete=PROTECT`，**`db_constraint=False`** | 旧订单：E 阶段旧表物理退役时 DB 外键不阻断归档下线（ORM 关系保留）；评审 R4-05 要求明确外键与归档的交互，此为设计答案 |
| reservation | FK → reservations.Reservation，`on_delete=PROTECT`（DB 约束保留） | 新预订：PMS2 侧长期存在，用强约束保护 |
| property | FK → core.Property，`on_delete=PROTECT` | **物业一致性**：关系记录显式登记物业；应用层校验"新 Reservation.property 必须等于关系记录 property"（跨物业关系禁止；跨表一致性无法用 CheckConstraint 表达，由确认时点应用校验 + 迁移工具复核双重保障） |
| relation_type | CharField | ONE_TO_ONE / SPLIT_SOURCE / MERGED_TARGET / OTHER(附说明)——**描述该行配对在整个旧订单-新预订集合中的角色**；集合完整性（如 SPLIT_SOURCE 的行数与对端 MERGED_TARGET 行数对齐）由人工确认时点核验 + 对账清单核验，不做 DB 级约束 |
| match_basis | CharField | 匹配依据（客人+日期+房型 等） |
| confirmed_by / confirmed_at | 人工确认留痕（**CONFIRMED 态两者均强制非空**，见下方 CheckConstraint） | |
| status | CharField | CONFIRMED / REJECTED / SUPERSEDED |

**状态与并发约束（R5-04 修订：确认时间、事务锁、确认后不可随意改写）**：

| 约束/规则 | 说明 |
| --- | --- |
| `UniqueConstraint(legacy_order, reservation, status)` | 同一 (旧订单, 新预订, 状态) 组合仅一行——**同一配对同时至多一条 CONFIRMED**（并发确认竞态被 DB 拒绝）；REJECTED 后可重新提交（新 CONFIRMED 行，旧 REJECTED 行留作历史）；非条件唯一索引，SQLite/MySQL 行为一致 |
| `CheckConstraint(status='CONFIRMED' → confirmed_by 非空 **且 confirmed_at 非空**)` | **R5-04 修订**：CONFIRMED 必须同时留核验人与核验时间（审计证据完整，不得有核验人无时间） |
| `CheckConstraint(status='CONFIRMED' → property 非空)` | CONFIRMED 必须显式登记物业 |
| 旧订单多条 CONFIRMED | **允许**（即 1:N 业务关系）；每行独立人工确认 |
| 同一新 Reservation 被多条旧订单关联 | **允许**（即 N:1 合并场景）；relation_type=MERGED_TARGET 逐行标注 |
| REJECTED / SUPERSEDED 重新提交 | 允许：新状态行插入（旧行留作历史）；SUPERSEDED 由取代它的 CONFIRMED 行建立时自动标注旧行 |

**确认事务与 CONFIRMED 不可改写（R5-04 修订）**：

| 规则 | 实现 |
| --- | --- |
| 确认事务 | 确认动作在单事务内完成：`Reservation.objects.select_for_update()` 锁定新预订行 → **事务内复核 property 一致性**（关系记录 property == Reservation.property，防止确认过程与 Reservation 物业调整并发冲突）→ 写入 CONFIRMED 行 | 
| CONFIRMED 不可改写 | save() 守卫：**status=CONFIRMED 的行拒绝任何字段修改**（不可变业务事实——对照 billing 退款凭证不可变模式）；改映射 = 新增 SUPERSEDED/新 CONFIRMED 行表达，不修改已确认行 |
| 允许的字段变更 | 仅限非 CONFIRMED 行：REJECTED/SUPERSEDED 行留作历史亦不可改（不可变）；只有**未确认草稿态**（若引入）允许编辑——本设计默认无草稿态，创建即待确认 |
| 不可删除 | delete() 拒绝（同 LegacyRecordLink 模式） |

**映射职责拆分（LegacyRecordLink 保持单目标约束）**：

| 关系 | 承载结构 | 说明 |
| --- | --- | --- |
| 旧 Accommodation ↔ 新 Reservation | **`legacy_order_reservation_map`（本节新表）** | 多目标关系在此表达；LegacyRecordLink 不承载 |
| 旧 Folio ↔ 新 LedgerEntry | LegacyRecordLink（source_model="Folio", target_model="LedgerEntry"） | 单目标：一条旧凭证 ↔ 一条迁移凭证（迁移凭证的 folio FK 已含新账单归属） |
| 旧 FinanceRecord ↔ 新 LedgerEntry | LegacyRecordLink（source_model="FinanceRecord"） | 同上 |
| 新 Folio ↔ 新 Reservation | **billing.Folio.reservation FK（既有业务字段）** | 新业务模型自身维护，不进映射表 |

**凭证归属规则（1:N/N:1 场景）**：旧凭证归入哪张新账单，由关系记录 + 凭证日期/类型在**人工确认时逐条判定**并记入该凭证的 LegacyRecordLink（target=迁移凭证）；无法逐条归属的凭证 → C4。

### 1.5.3 样例与约束测试设计（阶段 D TDD）

| 场景 | 预检数据 | 断言 |
| --- | --- | --- |
| 1:1 | 旧#100→新#201 一行 | 迁移凭证挂 #201 的账单；LegacyRecordLink 单行 |
| 1:N | 旧#100→新#201、新#202 两行（SPLIT_SOURCE） | 两行关系均须人工确认；凭证按归属依据分别迁移；无确认归属依据的凭证 → C4 |

## 2. 阶段 A 补充：生产盘点命令清单（运维只读执行，结果回填现状盘点 §6）

```sql
-- 规模与时间窗
SELECT COUNT(*), MIN(日期), MAX(日期) FROM finance_record;
SELECT 类型, COUNT(*), SUM(CAST(金额 AS DECIMAL(12,2))), MIN(日期), MAX(日期)
  FROM folio GROUP BY 类型;
SELECT 状态, COUNT(*), SUM(CAST(收款金额 AS DECIMAL(12,2))), SUM(CAST(押金 AS DECIMAL(12,2)))
  FROM accommodation GROUP BY 状态;
SELECT COUNT(*), MIN(营业日期), MAX(营业日期) FROM night_audit;
-- 数据质量预检（决定 C4 规模）
SELECT COUNT(*) FROM folio WHERE 金额 NOT REGEXP '^-?[0-9]+(\\.[0-9]{1,2})?$';
SELECT COUNT(*) FROM folio WHERE 日期 NOT REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$';
SELECT COUNT(*) FROM folio f LEFT JOIN accommodation a ON f.order_id=a.id
  WHERE f.order_id IS NOT NULL AND a.id IS NULL;                          -- 孤儿凭证
SELECT COUNT(*) FROM finance_record WHERE 类型='支出';                      -- 无法映射类规模
-- 新账本覆盖预检（C2 判定输入）
SELECT COUNT(*) FROM ledger_entry WHERE reference LIKE 'legacy:%';          -- 应为 0（未迁移）
-- D-09 补充：FinanceRecord 解析失败预检
SELECT COUNT(*) FROM finance_record WHERE 金额 NOT REGEXP '^-?[0-9]+(\\.[0-9]{1,2})?$';
SELECT COUNT(*) FROM finance_record WHERE 日期 NOT REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$';
-- R4-01 重写（第三轮 P0-3→R4-01）：逐订单物业归属判定——六态结果，Accommodation 粒度
-- 表名/列名均经 Django introspection 核实（基线 fe579479；执行前仍须在生产 MySQL 复验）：
--   accommodation(客房编号 FK→room) / room(房间号 主键) / inventory_room(number+property_id)
--   / core_property(code)。房号相同仅为辅助证据；历史调房/跨物业复用号需人工确认。
SELECT a.id                            AS accommodation_id,
       r.房间号                         AS legacy_room_no,
       COUNT(DISTINCT nr.property_id)  AS matched_property_count,
       GROUP_CONCAT(DISTINCT p.code)   AS matched_property_codes,
       CASE
         WHEN r.房间号 IS NULL THEN '旧数据关系异常（订单未关联旧房间）'
         WHEN COUNT(DISTINCT nr.property_id) = 0 THEN '证据不足（新侧无匹配房间）'
         WHEN COUNT(DISTINCT nr.property_id) = 1
              AND MAX(p.code) = 'DEFAULT' THEN '唯一匹配 DEFAULT（候选证据，须人工确认）'
         WHEN COUNT(DISTINCT nr.property_id) = 1 THEN '唯一匹配非 DEFAULT（其他物业证据）'
         ELSE '同号多物业冲突（需人工核验）'
       END                             AS attribution_verdict
  FROM accommodation a
  LEFT JOIN room r            ON r.房间号 = a.客房编号
  LEFT JOIN inventory_room nr ON nr.number = CAST(r.房间号 AS CHAR)
  LEFT JOIN core_property p   ON p.id = nr.property_id
 GROUP BY a.id, r.房间号
 ORDER BY a.id;

-- R5-01 重写（第四轮 P0）：新旧重复事实候选核验——纳入订单关联状态，禁止仅凭物业+金额+日期判定覆盖
-- 关联链：旧凭证 → 旧订单 → （订单-预订关系映射【阶段 D 交付，尚未实施】）→ 新预订 → 新账单 → 新凭证
-- 当前关系映射未实施：所有候选对的 订单关联状态 一律输出 '未建立（禁止判定 C2/C3）'，
--   不得仅凭物业+金额+日期标记为已覆盖；同物业同金额同日期出现多个候选时逐对输出并标注 多候选。
-- 阶段 D 关系映射落地后，本查询升级为 JOIN legacy_order_reservation_map 关联核验版（设计见 §1.5.2）。
SELECT f.id                        AS legacy_folio_id,
       f.order_id                  AS legacy_order_id,
       f.类型                       AS legacy_entry_type,
       f.金额                       AS legacy_amount_raw,
       f.日期                       AS legacy_date,
       p.code                      AS matched_property_code,
       bf.id                       AS candidate_new_folio_id,
       bf.reservation_id           AS candidate_new_reservation_id,
       le.id                       AS candidate_new_entry_id,
       le.amount                   AS candidate_new_amount,
       le.business_date            AS candidate_new_business_date,
       '未建立（禁止判定 C2/C3；关系映射属阶段 D 交付）' AS order_association_status
  FROM folio f
  JOIN accommodation a         ON a.id = f.order_id
  JOIN room r                  ON r.房间号 = a.客房编号
  JOIN inventory_room nr       ON nr.number = CAST(r.房间号 AS CHAR)
  JOIN core_property p         ON p.id = nr.property_id
  JOIN billing_folio bf        ON bf.property_id = nr.property_id
  JOIN billing_ledgerentry le  ON le.folio_id = bf.id
                              AND le.entry_type = 'PAYMENT'
                              AND le.amount = -CAST(f.金额 AS DECIMAL(12, 2))
                              AND le.business_date = STR_TO_DATE(f.日期, '%Y-%m-%d')
 ORDER BY f.id, bf.id, le.id
 LIMIT 200;                                   -- 候选对输出（人工核验入口；禁止自动判定）

-- R5-02 重写（第四轮 P0）：FinanceRecord 收入记录逐条分类输出——异常记录独立呈现，不静默消失
-- 分类口径（每条收入记录恰好一个 classification）：
--   金额解析失败 / 日期解析失败 / 订单ID格式非法 / 订单不存在 / 无关联订单（C5 候选）
--   / 订单关联已建立→候选匹配（列出新侧候选）/ 订单关联已建立→无对应（C1 候选或 C4）
-- 关联订单 为 CharField：先 REGEXP 校验数字格式，仅格式合法时才 CAST 比较（不依赖隐式转换）。
-- 仅有"收入"标签、无押金/收款资金性质证据的记录：classification 附注"资金性质待人工判定"，
--   不得直接归入 PAYMENT 已覆盖（映射矩阵 §2.2 证据分级规则）。
SELECT fr.id                          AS legacy_finance_id,
       fr.关联订单                     AS legacy_order_ref_raw,
       fr.金额                         AS legacy_amount_raw,
       fr.日期                         AS legacy_date_raw,
       CASE
         WHEN fr.金额 NOT REGEXP '^-?[0-9]+(\\.[0-9]{1,2})?$' THEN '金额解析失败（C4）'
         WHEN fr.日期 NOT REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$' THEN '日期解析失败（C4）'
         WHEN fr.关联订单 IS NULL OR TRIM(fr.关联订单) = '' THEN '无关联订单（C5 候选，资金性质待人工判定）'
         WHEN TRIM(fr.关联订单) NOT REGEXP '^[0-9]+$' THEN '订单ID格式非法（C4）'
         WHEN NOT EXISTS (SELECT 1 FROM accommodation ax
                           WHERE ax.id = CAST(TRIM(fr.关联订单) AS UNSIGNED)) THEN '订单不存在（C4）'
         ELSE '订单关联已建立（进入候选匹配）'
       END                             AS classification,
       p.code                          AS matched_property_code,
       le.id                           AS candidate_new_entry_id,
       le.amount                       AS candidate_new_amount,
       le.business_date                AS candidate_new_business_date
  FROM finance_record fr
  LEFT JOIN accommodation a
         ON TRIM(fr.关联订单) REGEXP '^[0-9]+$'
        AND a.id = CAST(TRIM(fr.关联订单) AS UNSIGNED)
  LEFT JOIN room r                ON r.房间号 = a.客房编号
  LEFT JOIN inventory_room nr     ON nr.number = CAST(r.房间号 AS CHAR)
  LEFT JOIN core_property p       ON p.id = nr.property_id
  LEFT JOIN billing_ledgerentry le
         ON le.entry_type = 'PAYMENT'
        AND le.property_id = nr.property_id
        AND le.amount = -CAST(fr.金额 AS DECIMAL(12, 2))
        AND le.business_date = STR_TO_DATE(fr.日期, '%Y-%m-%d')
 WHERE fr.类型 = '收入'
 ORDER BY fr.id;
-- 解读：classification='订单关联已建立' 且 candidate_new_entry_id 非空 = C2 候选（人工核验）；
--       classification='订单关联已建立' 且 candidate_new_entry_id 为空 = 无对应（C1 候选或 C4）；
--       其余 classification = 按 C4/C5 归档。全部记录可见，无静默消失。

-- R4-03 新增：FinanceRecord 收入与新账本重复事实候选核验（评审指出仅覆盖 Folio 收款不足）
-- 口径：FinanceRecord.类型='收入' 且 关联订单可解析 → 同上归属链 → 与新 PAYMENT 按
-- 金额(负)/营业日 匹配；无法解析关联订单（C4/C5 类）不参与本查询。
SELECT fr.id                       AS legacy_finance_id,
       fr.关联订单                   AS legacy_order_ref,
       fr.金额                       AS legacy_amount_raw,
       fr.日期                       AS legacy_date,
       p.code                      AS matched_property_code,
       le.id                       AS new_entry_id,
       le.amount                   AS new_amount
  FROM finance_record fr
  LEFT JOIN accommodation a  ON a.id = CAST(fr.关联订单 AS UNSIGNED)
  JOIN room r                ON r.房间号 = a.客房编号
  JOIN inventory_room nr     ON nr.number = CAST(r.房间号 AS CHAR)
  JOIN core_property p       ON p.id = nr.property_id
  LEFT JOIN billing_ledgerentry le
         ON le.entry_type = 'PAYMENT'
        AND le.property_id = nr.property_id
        AND le.amount = -CAST(fr.金额 AS DECIMAL(12, 2))
        AND le.business_date = STR_TO_DATE(fr.日期, '%Y-%m-%d')
 WHERE fr.类型 = '收入'
 ORDER BY fr.id
 LIMIT 200;
-- 解读：new_entry_id 非空 = 新账本已存在对应事实（C2 候选）；为空 = 无对应（C1 候选或 C4）。
```

## 3. 差异处理流程（原则 5：只报告，不自动修账）

1. 对账工具输出三类清单：**差异清单**（守恒破坏，逐条带两侧证据）/ **C4 清单**（无法确认）/ **配对候选清单**（冲销/订单，待人工确认）；
2. 差异由财务负责人指派核对：核对依据 = 历史页面（legacy_reservations 端点原样展示）+ Admin 只读记录 + 原始凭证影像（如有）；
3. 处置动作仅两种：**修正分类**（改 LegacyRecordLink mapping_status + review_note）或**维持归档**；
4. 任何"改数"行为（旧表或新账本）都超出本迭代权限——新账本纠错走既有红字冲销 + ApprovalRecord 流程，旧表纠错属历史档案，不改。

## 4. 迁移机制设计（阶段 D 实施蓝图，本轮不写代码）

- **形态**：Django management command（`migrate_legacy_finance`，设计稿），**只读旧表 + 只写新账本/LegacyRecordLink/归档表**；
- **事务边界**：按订单分批（每批一个 atomic：校验→建凭证→LegacyRecordLink→计数器），批间可断点续跑（reference 幂等保证重跑零新增）；
- **冲销建链**：仅处理"配对候选清单"中**人工确认**的条目，经 **§5 受控历史迁移服务入口** 建 `legacy_workflow=True` 凭证（不得经 ORM 绕过 BillingService，不补造审批人）；
- **LegacyRecordLink 写入通道**：source_system="hotelapp"、source_model="Folio"/"FinanceRecord"、mapping_status 按 §3 分类矩阵流转（UNREVIEWED→MATCH_CANDIDATE→LINKED/CONFLICT/IGNORED），reviewed_by 记录核验人；
- **干跑模式**：`--dry-run` 输出分类统计与差异清单，不写任何表；
- **归档表设计**：`legacy_folio_archive` 等**新建归档表**（含全列快照+归档时间+批次号），旧表本身在 E 阶段前不删不改；
- **凭证挂载**：迁移凭证仅挂载到**关联预检表（§1.5）人工确认**的新 Folio；预检表无法对应的订单名下凭证一律不迁移。

## 5. 受控历史迁移服务入口（第二轮复审阻断项 2：创建链路重构设计）

> 核实结论（2026-11-13 复核 @ fe579479）：`BillingService.post_entry`（services_v2.py:334）签名**不含** `legacy_workflow` 参数，创建凭证的 facts 字典也不传该键（models.py:301 字段存在，`ck_ledger_reversal_approval_link` 约束允许 REVERSAL + legacy_workflow=True + approval_record=NULL）——评审断言属实。**禁止以 ORM `LedgerEntry.objects.create` 绕过领域服务**（将绕过幂等/币种/关账/审计守卫），也**不得**把该入口变成普通员工可调用的审批旁路。

### 5.0 首轮设计的缺陷确认（评审意见成立）

首轮 §5.2"委托 post_entry 后追加 legacy_workflow 字段赋值"**不可执行**，四条路径均被否：
1. post_entry 先创建 REVERSAL 而无 legacy_workflow=True → DB 约束（approval_record=NULL + legacy_workflow=False）拒绝创建；
2. 先建普通凭证再改 legacy_workflow → 违反账本不可变原则（ImmutableLedgerEntryQuerySet + save 守卫）；
3. 直接 objects.create → 绕过幂等/币种/关账/五重校验守卫；
4. post_entry 后改字段 → 触发模型不可变保护。

### 5.1 修订设计：共享凭证创建流 + 显式迁移授权（legacy_workflow 首次创建时确定）

**核心重构**：从 `BillingService.post_entry` 中抽出**共享凭证创建流程** `_create_entry_record(*facts, legacy_workflow=False)`（私有方法，包含既有全部守卫：幂等重放判定/币种一致/关账豁免五重校验/金额校验），`post_entry` 与受控历史迁移入口共同委托它：

```
BillingService
├── post_entry(...)                    # 公共入口：签名不变（无 legacy_workflow 参数），
│     └── _create_entry_record(facts, legacy_workflow=False)
└── post_legacy_migration_entry(...)   # 受控历史迁移入口（新增，仅迁移命令可及），
      └── _create_entry_record(facts, legacy_workflow=True)   # 首次创建即定值
```

- `legacy_workflow` 在**首次创建凭证时确定**（经 `_create_entry_record` 参数传入），创建后不可修改（不可变守卫不变）；
- 普通业务入口签名不变、无该参数 → **普通业务调用不能设置历史迁移标识**；
- 常规 REVERSAL 无 approval_record 仍被 DB 约束拒绝 → **普通业务调用不能创建无审批的 REVERSAL**（守卫行为不变）。

### 5.2 可验证的调用授权（第四轮修订 P0-4/R4-04：完整权限闭环 + 可信执行身份）

受控入口的调用授权以**数据库登记的迁移批次记录（`LegacyMigrationBatch`，阶段 D 新增模型）**为凭证，并验证**执行上下文与批次授权的匹配**——"存在一个 ACTIVE 批次"不是全部权限判断。

**批次记录字段（授权信息全量）**：

| 字段 | 说明 |
| --- | --- |
| batch_uid（唯一） | 批次身份 |
| approved_by / approved_at / approval_basis | 审批事实：批准人、批准时间、审批依据（文档/Issue 链接） |
| scope_property | 授权处理的物业（FK） |
| scope_source_models | 授权处理的来源模型清单（Folio/FinanceRecord） |
| scope_record_range | 授权处理的记录范围（pk 区间或 id 清单快照，JSON 落库） |
| executed_by | 实际执行人（FK → 平台账号；须与批准人分离——批准人≠执行人，DB CheckConstraint 强制） |
| status | PENDING → ACTIVE → CLOSED（含 REJECTED）；合法转换：PENDING→ACTIVE/CLOSED/REJECTED，ACTIVE→CLOSED；其余转换拒绝 |

**授权闭环流程与主体**（评审要求逐项明确"谁能做什么"）：

| 步骤 | 主体 | 动作 | 权限依据 |
| --- | --- | --- | --- |
| 1. 批次登记（PENDING） | 迁移负责人（开发/运维侧） | 提交批次登记：审批依据+scope+拟执行人 | 阶段 D 迁移计划获批（文档） |
| 2. 批次批准（ACTIVE） | **项目负责人** | 将 PENDING 置 ACTIVE，approved_by=负责人；**校验 approved_by ≠ executed_by**（SoD） | L4 审批权限 |
| 3. 批次关闭（CLOSED） | 负责人（完成/终止） | CLOSED 为**终态且不可重新激活**（模型 save 守卫拒绝 CLOSED→任何状态） | L3 |
| 4. 受控入口执行 | **batch.executed_by 登记的运维账号** | 调用受控入口；入口逐条校验（下表） | 批次授权 + 交互式身份认证 |

**可信执行身份（R4-04 核心缺口修复）**：management command 不天然携带登录身份——**伪造 `--operator` 参数不可接受**。设计为**交互式密码认证建立执行上下文**：

1. 迁移命令启动时提示输入**执行人账号 + 密码**，经 Django `authenticate()`（ModelBackend，与 Admin 登录同一可信认证链）验证；
2. 认证通过后校验该账号：`is_active=True`、`is_staff=True`（平台身份）、`user.pk == batch.executed_by_id`（与批次登记执行人一致）、`user != batch.approved_by`（SoD）；
3. 任一校验失败 → 拒绝执行并写 `billing.legacy_migration_denied` 审计（含尝试账号）；
4. 认证通过的账号身份即为**本次执行的 AuditEvent.actor**——审计里的执行身份来自密码认证，非自报参数；
5. 批次 scope 不可篡改：`LegacyMigrationBatch` 模型 save 守卫在 status=ACTIVE 后**冻结 scope 字段**（修改即 ValidationError）；CLOSED 为终态不可重新激活。

**受控入口自身的服务级强制（不依赖调用者约定）**：`post_legacy_migration_entry` 方法体首行执行批次授权校验（§上表步骤 4）+ 执行上下文验证（记录集合 ⊆ scope_record_range），任何不满足直接抛 `LegacyMigrationDenied`——服务边界即权限边界，无文档约定式豁免。

**授权闭环流程**：
1. 批次登记（PENDING）：由迁移计划批准时创建，登记审批事实与范围；
2. 负责人批准 → status=ACTIVE（批准人记录在案）；
3. 迁移命令以**交互式认证的执行人身份** + `batch_uid` 调用受控入口；
4. 受控入口校验（全部通过才执行）：批次存在且 ACTIVE；**操作者 = batch.executed_by**（经密码认证证实）；处理对象的 property/来源模型/记录范围 ∈ 批次 scope；
5. 每次调用（成功/拒绝）均写 AuditEvent（billing.legacy_migration：批次/调用者/动作/结果）；
6. 批次 CLOSED 后入口永久拒绝（防止关闭后继续执行）；批次处理完成或终止时关闭。

**执行上下文验证**：受控入口除校验批次外，还校验每次调用传入的记录集合 ⊆ batch.scope_record_range——越范围记录一律拒绝并审计。
