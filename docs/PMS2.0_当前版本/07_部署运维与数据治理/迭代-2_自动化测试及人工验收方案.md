> 阶段 C/D/E 交付物（测试与验收设计）。原则：迁移/对账工具的每一层守卫都要有自动化测试先行；人工验收只做机器不能证明的事（抽凭、追溯演示、签署）。

### 3.1 阶段 D 批准条件（评审明确：五项裁定批准 ≠ 立即批准阶段 D 开发）

阶段 D 实施必须同时满足以下八项，缺一不可：

1. 六份文档完成本轮修订并统一引用同一代码基线（23bd575 及其后续评审基线）；
2. 五项裁定正式记录（映射矩阵修订版 §3.1，开发方已确认）——其中裁定 3（DEFAULT 归属）须附生产盘点数据证据；
3. 迁移服务设计与既有 BillingService/LedgerEntry 约束完全一致（受控入口 §5 设计已按评审意见补齐）；
4. **测试先行**：M1-M18/R1-R7/Q1-Q5 用例先于迁移命令交付；
5. SQLite + MySQL 双库验证，MySQL 必须覆盖真实事务、唯一约束（pending_diff_key 结构）与并发场景；
6. 先测试数据与 dry-run，未经批准不得批量迁移生产数据；
7. 不删除旧表、不停止旧查询（裁定 4：方案甲）、不对 Accommodation 整表撤销写权限；
8. D1-D5 各阶段独立验收与回滚条件，不得合并为一次操作。

## 4. 硬性限制重申（阶段 D 实施时的红线）

1. 不删除旧表（D5 两步法单独审批前）；
2. 不批量迁移生产数据（先 dry-run 报告 → 负责人批准 → 分批执行）；
3. 不改变新账本写入规则（迁移凭证走既有 BillingService/凭证创建通道，不绕过 ImmutableLedgerEntryQuerySet；历史 REVERSAL 走受控迁移服务入口 §5 设计，同样不绕过守卫链）；
4. 不绕过财务审批与不可变约束（冲销 legacy_workflow 是既有合规通道，不是新建旁路；**受控入口仅供迁移命令使用**）；
5. 全部迁移/对账代码走 TDD（§1 矩阵用例先行）+ 双库验证 + CI 门禁；
6. Accommodation 整表 DML 权限不动（财务字段退役不连带订单业务停写）。
