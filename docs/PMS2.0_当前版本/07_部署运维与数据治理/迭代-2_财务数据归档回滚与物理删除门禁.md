## 4.1 归档数据的隐私、备份与审计要求（评审新增五项）

Accommodation 含顾客个人信息（姓名/联系电话/身份证号），旧 Folio/FinanceRecord 含经手人与客户关联——归档不是"全列快照永久保留"一句话，必须满足：

| --- | --- | --- |
| 1 | **敏感字段访问权限** | 归档表查询通道仅开放给**现有 RBAC 体系内的两类主体**（D-11：不新造角色）——平台超管（Admin 现行通道）+ 持 `hotelapp.finance_access` 权限码的财务负责人（AuthorizationService 现行校验）；身份证/电话完整值不得出现在任何报表输出 |

| 3 | **校验和算法与字段规范化** | **定稿算法见 §4.1**（逐字段规范化序列化 → 逐行 SHA-256 → 按主键序聚合整表摘要）；金额保原字符串（不做类型转换） |

| 5 | **归档访问审计** | 归档查询通道的所有访问记审计（who/when/what）；归档备份的取用同样登记 |

### 4.1 归档校验和算法定稿（第三轮修订 P1-1：长度前缀编码，消除分隔符碰撞假设）

原 CONCAT_WS 方案与 checksum-v1 初版（`\x1f` 分隔 + 四元组）均**废弃**——初版假设"字段值内不出现 `\x1f`"不成立（文本字段可含任意控制字符），且 `\|` 四元组分隔无转义规则。**定稿算法（checksum-v2，长度前缀二进制编码）**：

**逐字段编码**（对归档表每一行，按表定义列序；全部输出为 UTF-8 字节流，字段间无分隔符歧义）：
1. 每字段依序输出：`len(字段名 UTF-8 字节) + 字段名字节 + len(数据类型标识字节) + 类型标识字节 + NULL 标志字节(0/1) + len(值字节) + 值字节`——所有 len 为 4 字节大端整数；长度前缀使任意字节内容（含控制字符/分隔符样字符）无歧义；
2. NULL 与空串严格区分：NULL 标志=1 且值字节为空；空串 NULL 标志=0 且值字节为空；
3. 字符串值统一 UTF-8 原样（金额保原字符串，**不做类型转换**）；
4. 时间字段：原始值 + 统一转换规则（UTC ISO8601 `YYYY-MM-DDTHH:MM:SSZ`）**两者都纳入编码**（原始值保历史事实，转换值保可比性）；
5. Decimal/整数：标准十进制文本（无科学计数法、无千分位）。

**行摘要与整表聚合**：
6. 行摘要 = `SHA-256(该行全部字段编码拼接)`；
7. 行摘要按**主键升序**排列，以同样长度前缀编码（`len(行摘要字节)+行摘要字节`）拼接为表规范化串；
8. 整表摘要 = `SHA-256(表规范化串)`；
9. 登记元数据：**算法版本（checksum-v2）、源表行数、min/max 主键、计算时间、执行人**——随归档批次元数据落盘。

**跨库一致性验证**：同一归档数据从 SQLite 与 MySQL 导出/恢复后，按同规则计算必须得到相同整表摘要（阶段 D 恢复演练的双库验证项之一；差异即导出序列化缺陷，阻断归档收口）。

**实现约束**：校验和计算由归档命令内置实现（Python 侧逐行计算，不依赖 DB 方言函数——避免 SQLite/MySQL SHA2 实现差异）；行摘要与整表摘要均落盘于归档批次元数据。

## 5. 归档表设计要点（D3 实施蓝图）

- 命名：`legacy_folio_archive` / `legacy_finance_record_archive` / `legacy_night_audit_archive` / `legacy_accommodation_archive`；
- 结构：**源表全列快照**（类型保真：CharField 原样）+ `archived_at` + `archive_batch`（批次号）+ `verified_checksum`；
- 归档表**无唯一约束保留价值**（历史只读），仅保留主键与索引；
- 归档表自身的生命周期：**不设过期**（历史账务凭证永久保留，符合账务档案要求）；
- 查询通道：保留一个只读 Django Admin（或只读端点）供审计追溯，随 E 阶段评估。
