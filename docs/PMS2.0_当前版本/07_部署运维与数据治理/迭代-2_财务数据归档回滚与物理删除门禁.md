# 迭代-2 财务数据归档、回滚与物理删除门禁

> 阶段 D/E 交付物（门禁设计）。退役原则 6：**停止写入、停止读取、归档、验证、物理删除是五个独立阶段，各自有准入/准出门禁与独立审批，不得合并为一次迁移。**

## 1. 五阶段门禁总表

| 阶段 | 动作 | 准入条件 | 准出条件（验收） | 审批等级 | 可逆性 |
| --- | --- | --- | --- | --- | --- |
| D1 停止写入 | 确认写入口收口（活跃写=0 已实证）+ 可选 DB 只读授权（运维：REVOKE INSERT/UPDATE/DELETE ON folio/finance_record/night_audit/accommodation） | 迭代-1 写收口证据 + 本清单 §1 全景复核 | 只读授权生效证明（尝试写入被拒的截图/日志） | L2（运维操作） | ✅ 完全可逆（GRANT 恢复） |
| D2 停止读取 | E1-E4 读入口下线或切读归档表（改造方案另行 L2 审批）；前端确认 folio_api 零调用 | D1 完成 + 替代查询路径可用（legacy 端点或归档查询） | 全域 grep 零活跃读引用 + 冒烟测试 | L2（含前端确认） | ✅ 可逆（恢复端点） |
| D3 归档 | 建 `legacy_*_archive` 归档表 → 全量快照迁移（含行数/校验和）→ LegacyRecordLink 分类标注完成 | D2 完成 + C1-C5 分类矩阵定稿 + 迁移工具 dry-run 通过 | 归档行数=源表行数（逐表）+ 校验和一致 + 抽样 100 条人工比对 | L3（数据结构变更 + 批处理） | ✅ 可逆（归档表独立，源表未动） |
| D4 验证 | 归档恢复演练（归档表 → 临时库 → 关键查询复现）+ 对账差异清零（或全部差异有人工处置记录）+ 财务抽凭 | D3 完成 | 恢复演练报告（从归档重建历史账单页面的演示）+ 差异清单全部 CLOSED/ARCHIVED | L3 | ✅ 可逆 |
| D5 物理删除（单独审批） | DROP 旧表（folio/finance_record/night_audit + accommodation 财务列处置） | **五项准入全满足（§2）+ 项目负责人专项审批** | 删除前最终备份存档 + 审批记录归档 | **L4 专项** | ❌ 不可逆（仅靠 D4 前备份） |

## 2. D5 物理删除的五项准入（缺一不可）

1. **归档完整性**：三张表全量快照在归档表，行数/校验和比对通过，且归档表已在生产库验证可查询；
2. **恢复演练通过**：从归档数据在隔离库重建"历史账单查询"完整演示（订单→凭证→聚合余额），财务负责人签字；
3. **零引用检查**：`grep -rn "Folio.objects|FinanceRecord|Accommodation.objects|NightAudit" apps/ hotelapp/ templates/` 全域仅命中归档模块与测试；代码中无任何对旧表的 ORM/原生引用；
4. **零写入检查**：DB 只读授权已生效一个观察周期（≥30 天），期间零写入尝试日志；
5. **双库一致**：SQLite/MySQL 迁移链在 D3/D4 均执行验证（迁移 0010-0012+归档迁移），MySQL CI 全绿。

## 3. 回滚设计（每阶段的回退路径）

| 阶段 | 回滚动作 | 数据损失 |
| --- | --- | --- |
| D1 | GRANT 恢复写权限 | 无 |
| D2 | 恢复读端点（代码 revert 或重新挂载） | 无 |
| D3 | 归档表 DROP（源表未动，旧数据原样在位） | 无 |
| D4 | 无状态变更，无回滚需要 | 无 |
| D5 | **不可逆**——唯一保护 = D4 前的最终备份（mysqldump 全表 + 归档表双份 + 异机存放） | D5 后依赖备份恢复 |

**回滚纪律**：D5 执行前必须完成"最终备份校验和归档 + 恢复演练重放一次"；D5 执行采用先 RENAME（`RENAME TABLE folio TO folio_removed_YYYYMMDD`）观察 30 天、再 DROP 的两步法（RENAME 可逆，DROP 不可逆——两步各自审批）。

## 4. Accommodation 的特殊处理（非财务专用表）

- Accommodation 是**订单主表**（含非财务字段：顾客 FK、客房 FK、状态机），不能整表随财务退役——只有其**财务冗余列**（收款金额/押金/冲账人/冲账时间）进入处置范围；
- 列处置门禁：随 E 阶段，四列以"标注废弃→停止读取（legacy 端点退役后自然达成）→ 列删除迁移（单独审批）"执行；
- Folio.order FK（DO_NOTHING）随 Folio 表退役自然消除。

## 5. 归档表设计要点（D3 实施蓝图）

- 命名：`legacy_folio_archive` / `legacy_finance_record_archive` / `legacy_night_audit_archive` / `legacy_accommodation_archive`；
- 结构：**源表全列快照**（类型保真：CharField 原样）+ `archived_at` + `archive_batch`（批次号）+ `verified_checksum`；
- 归档表**无唯一约束保留价值**（历史只读），仅保留主键与索引；
- 归档表自身的生命周期：**不设过期**（历史账务凭证永久保留，符合账务档案要求）；
- 查询通道：保留一个只读 Django Admin（或只读端点）供审计追溯，随 E 阶段评估。

## 6. 剩余风险

| 风险 | 缓解 |
| --- | --- |
| 生产库可能有本盘点未发现的外部系统直连旧表（如报表工具/导出脚本） | D1 前运维核查 DB 连接审计（`information_schema.PROCESSLIST` 历史与账号清单） |
| Long-lived 只读授权的误操作 | DB 只读授权仅限旧表四张，新账本表权限不变 |
| 归档表查询性能（历史数据量大时） | 归档表索引按查询通道设计；必要时归档库独立实例 |
| MySQL 条件索引陷阱复现 | 归档表无条件约束需求（全量快照）；迁移 0011 教训已入记忆库 |
