# PMS2 员工中心最终 UI 规范与权限管理、入住管理一致性审查

> 文档性质：PMS2 后台 UI 规范基线（V1.0）
> 
> 基准模块：员工中心
> 
> 审查模块：权限管理中心、入住管理 / 前台接待工作台
> 
> 审查基线：GitHub `main`，审查时树 SHA：`b75df27eee842d824fa3a650c24f11236dc0eb87`
> 
> 本文只冻结 UI 结构、视觉、交互和一致性要求，不授权修改业务代码、接口、数据库、权限规则或业务流程。

---

## 1. 目的与适用范围

以当前员工中心页面为基础，建立 PMS2 后台可复用的页面设计规范。后续权限管理、入住管理及其他 PMS2 管理工作台，应在不改变各自业务职责的前提下复用统一的视觉语言、表单规则、列表规则、状态表达和交互反馈。

本规范不要求所有页面长得完全一样。员工中心、权限管理中心、入住管理分别属于员工生命周期工作台、平台治理工作台、前台运营工作台，信息结构应服从业务任务；统一的是设计系统和交互原则，不是把不同业务强行改造成同一模板。

### 1.1 非目标

- 不新增业务功能、页面、字段或流程。
- 不调整员工生命周期服务、RBAC 授权规则、入住状态机、财务规则。
- 不修改 API 契约、数据库模型、迁移、权限码、审计语义。
- 不因 UI 审查结论推断后端功能已经可用；页面行为仍需独立功能测试。
- 不以截图代替运行态验收。

## 2. 员工中心作为基准的页面结构

员工中心基准页面为 `/manage/staff/`，模板为 `templates/pms/staff_center.html`。当前实现采用员工列表 + 可折叠新增表单 + 右侧员工生命周期操作抽屉。该结构保留，不推倒重做。

页面从上到下固定为：

1. **页面标题区**：标题“员工中心”；副标题简述员工建档、账号开通、角色授权、任职管理；右侧放置低强调度的返回/导航链接。
2. **新增员工卡片**：默认收起；展开后按员工身份信息、登录账号开通、初始角色授权分组；表单底部统一放置主操作和说明/反馈。
3. **员工列表卡片**：搜索区、结果总数、数据表格、空/错/加载状态、分页区。
4. **员工操作抽屉**：员工身份概览、账号安全、任职管理、角色授权、授权历史分区；抽屉内部独立滚动，标题栏和关闭操作保持可见。

### 2.1 新增员工表单字段布局

表单分为三个语义区，不把所有字段混成一行：

**A. 员工身份信息**
- 姓名（必填）
- 物业工号（必填；统一术语，替代“店内工号”）
- 岗位代码（按现有业务契约）
- 手机号（选填）
- 关联旧员工记录（选填）

桌面宽屏优先采用两列网格；姓名可在较宽屏占据独立行或较宽列。窄屏单列。不得通过视觉优化擅自改变字段必填性、长度、格式或校验规则。

**B. 登录账号**
- “同时开通登录账号”作为独立开关。
- 仅在启用时展示当前接口支持的登录账号字段。
- 初始密码如由系统生成，必须清楚标记“仅本次显示”，并提示安全交付；不得将明文密码长期留在页面、日志或审计详情中。
- 员工档案与登录账号是不同概念，页面文案不得混为“创建账号即创建员工”。

**C. 初始角色授权**
- 角色选择独立分区，允许多选的前提以当前服务端契约为准。
- 岗位代码与系统角色必须视觉和语义分离：岗位描述工作岗位，角色决定系统授权。
- 角色展示使用统一的名称、间距和可选状态；窄屏换行，不横向挤压。

### 2.2 员工列表规范

- 搜索输入与查询操作放在列表卡片顶部；支持回车查询（若现有交互具备）。
- 结果数量放右侧；加载中、无结果、请求失败必须有明确状态。
- 列表列名使用统一术语：姓名、物业工号、岗位、联系电话、任职状态、账号、有效角色、操作。
- “账号状态”与“任职状态”是两个独立维度，不能用单个“有效”覆盖二者。账号未开通、启用、停用等状态与任职有效、暂停、离职等状态分别表达。
- 联系电话遵循当前敏感字段展示策略，默认使用掩码；不得为视觉完整而显示完整号码。
- 操作列使用轻量次级按钮（如“管理”），不要把每行操作做成高饱和主按钮。
- 表格允许横向滚动，但桌面端应优先保证姓名、工号、岗位、状态、操作等关键列可见。
- 分页区统一显示当前页、总页数或下一页状态，以及总记录数；分页参数行为服从 API 契约，不由前端自行截断或伪造。

### 2.3 员工操作抽屉规范

固定分区：
1. 员工身份概览；
2. 账号安全（重置登录密码）；
3. 任职管理（暂停任职、办理离职等当前已有操作）；
4. 角色授权（角色、结束时间、授权原因）；
5. 角色授权历史（历史保留，不提供删除）。

规则：
- 抽屉宽度桌面建议 560–640px，窄屏最大宽度 100vw；主体滚动，标题栏固定。
- 同一业务操作的原因输入、字段和按钮必须放在同一视觉分区。
- 原因字段是否必填由业务规则决定；既定要求必填时明确标注“必填”，不得仅用“选填”占位提示。
- 临时授权与长期授权的区别必须可读；长期有效不得伪装成缺失数据。
- 危险操作（离职、结束授权等）使用危险色次级按钮并二次确认；普通操作使用主按钮或次级按钮。
- 成功、失败、处理中反馈在抽屉内就地呈现，不依赖浏览器 alert。
- 抽屉应支持关闭按钮、遮罩关闭（若业务确认无未提交内容）、Esc 关闭；打开后焦点进入抽屉，关闭后焦点返回触发按钮；避免键盘焦点逃逸。
- 审计历史只读展示，不出现删除入口。

## 3. 全局视觉与组件规范

### 3.1 页面容器与间距

- PMS 业务工作台沿用现有左侧 PMS 导航与主内容区，不另造一套全屏壳。
- 主内容最大宽度建议 1440–1500px；桌面内边距 24–30px，窄屏 12–16px。
- 页面标题区与首张卡片间距 16–22px；卡片之间 16–18px。
- 卡片内边距桌面 18–20px，窄屏 12–14px。
- 卡片圆角统一 8–12px；边框使用浅灰；阴影仅轻微辅助层级，不做重阴影。
- 不用大量空白制造“高级感”，也不把多个业务分区挤在一个大表单内。

### 3.2 色彩

- 页面背景：浅灰蓝/中性浅灰。
- 内容卡片：白色。
- 正文：深蓝灰/深灰；辅助说明：中灰。
- 主色：统一 PMS 蓝，用于主操作、链接、焦点和选中态。
- 成功：绿色；警告/待处理：琥珀色；危险/拒绝/离职等：红色；停用/不可用：中性灰。
- 颜色必须同时配合文字标签，不允许只靠颜色传达状态。
- 平台治理页面可以保留平台域独立导航与强调色，但不得另造冲突的状态含义和按钮语义。

### 3.3 字体与尺寸

- 页面主标题 22–26px；卡片标题 15–17px；正文 13–14px；辅助说明 11–12px。
- 表格正文 12–13px；表头 11–12px。
- 表单控件高度统一 36–40px；按钮高度 34–40px。
- 数字、金额、编号、日期时间使用适当的等宽数字或 tabular numerals；长编号允许换行或复制，不得撑坏布局。

### 3.4 表单规范

- 标签置于控件上方；标签与控件间距 5–7px；字段组间距 12–16px。
- 必填星号和必填规则一致；必填校验在提交前和服务端错误反馈中均有清晰提示。
- 同一表单同类控件宽高一致；不要出现输入框、选择框、日期框高度不一。
- 桌面 2–4 列按字段长度和语义分组；窄屏单列；不能为了凑齐网格把短字段拉得过宽。
- 占位符只举例，不替代标签，不用“选填”作为唯一标签。
- 错误信息就近显示，成功信息放在表单操作区附近。
- 表单提交中禁用重复提交，并明确显示处理中状态。

### 3.5 表格规范

- 表头浅灰背景、正文白底、行分隔线轻量；行高建议 44–52px，数据密集型列表可略低但不低于可读性要求。
- 表格操作列统一放末列；状态使用短文本标签；列名、字段术语跨模块一致。
- 列表必须具备加载、空结果、错误三种状态；不能将请求失败显示成“暂无数据”。
- 横向滚动容器不能导致整页宽度溢出；移动端优先保证关键字段。
- 不在前端重排服务端分页数据；排序和分页以 API 契约为准。

### 3.6 按钮层级

- 主按钮：当前卡片/表单的唯一主要提交动作。
- 次级按钮：查看、管理、刷新、取消等辅助操作。
- 危险按钮：离职、删除（如业务允许）、撤销/冲销等风险操作，使用危险色并二次确认。
- 文字链接：返回、跳转等低频导航。
- 同一操作区避免多个同等视觉权重的主按钮；按钮文案使用动宾结构，如“保存员工”“重置密码”“结束授权”。

### 3.7 响应式与可访问性

- 1440px 及以上：使用完整桌面网格。
- 1024–1439px：适当压缩列间距；多栏工作台允许改为两栏。
- 720px 以下：表单单列；三栏区域改为纵向；表格在独立容器横向滚动；抽屉接近全屏。
- 控件有可见键盘焦点；按钮有 disabled/loading 状态；颜色对比满足可读性；图标按钮必须有可访问名称。
- 尊重 `prefers-reduced-motion`，动画仅作辅助。

## 4. 权限管理中心一致性审查

### 4.1 页面定位

代码路径：
- 页面模板：`templates/platform/permissions.html`
- 样式：`static/css/permission_center.css`
- 页面脚本：`static/js/permission_center.js`
- API：`apps/identity/permission_center.py`
- 平台布局：`templates/platform/base.html`

权限管理中心属于**平台治理门户**，不是员工中心内的员工岗位授权页面。平台导航与 PMS 业务导航、会话域均有独立边界，因此不应强行改成员工中心的页面壳。

### 4.2 已符合的方面

- 角色目录、模块动作矩阵、影响范围、专项权限、变更摘要和保存确认区分区清晰。
- 平台业务权限边界提示明确，符合“PMS 业务权限仍以员工任职和岗位授权为准”的责任区分。
- 高危专项权限二次确认、变更理由、保存结果反馈有明确界面承载。
- 角色状态、模块状态和风险级别已有标签表达。
- 角色列表/矩阵/影响面采用卡片化布局，与员工中心的卡片语言基本兼容。
- 1100px 以下三栏切为单列，已有基础响应式处理。

### 4.3 UI 一致性差异与建议

| 编号 | 观察 | 建议 | 优先级 |
|---|---|---|---|
| PC-UI-01 | 平台页主标题 22px，员工中心 24px；字号与标题间距略有差异 | 统一标题层级和间距，保留平台导航外壳 | P2 |
| PC-UI-02 | 平台页卡片圆角 8px、员工中心使用设计变量默认 12px | 统一到 10–12px 范围 | P2 |
| PC-UI-03 | 平台页使用金色选中/焦点色，员工中心主色为蓝色 | 平台可保留平台身份强调色，但普通按钮、输入焦点、状态语义应统一；避免金色与风险颜色混淆 | P2 |
| PC-UI-04 | 矩阵列密集，专项权限说明文字与标签较多 | 保持矩阵信息密度；小屏改为矩阵容器横向滚动或模块分组，不应强行压成单列超长表单 | P1 |
| PC-UI-05 | 角色项以可点击 `li` 承担按钮行为 | 使用语义化按钮或补齐键盘可操作、焦点和选中语义 | P1 |
| PC-UI-06 | 变更理由、保存按钮与变更摘要集中在底部确认区 | 保留业务顺序；窄屏确保确认区不与矩阵内容混淆，提交结果就地可见 | P2 |
| PC-UI-07 | 高危确认流程的按钮文案会变化 | 保持两步确认提示、令牌有效期和变更内容说明始终可见；不得只靠按钮颜色表达风险 | P1 |

**结论：** 权限管理中心的信息架构不需要重做。主要工作是组件细节、可访问性和窄屏矩阵呈现；平台域独立身份与导航必须保留。

## 5. 入住管理 / 前台接待一致性审查

当前仓库存在两套明显不同的入住相关页面，需要先区分，不能把它们当作同一个页面：

1. `/checkin/` 路由指向 `hotelapp.views.checkin_workspace`；对应模板 `templates/checkin.html`。该模板仍使用旧式多张长表格和内联操作，且视口标签缺少 viewport 设置。
2. `templates/frontdesk.html` 与 `static/css/frontdesk.css` 是较新的“前台接待工作台”界面，采用 KPI、搜索栏、Tabs、数据面板和抽屉式详情/操作布局。
3. 员工中心及通用 PMS2 管理中心的返回链接仍指向 `/checkin/`。因此必须先由产品/路由负责人确认：`/checkin/` 是否仍是唯一正式入口，`/frontdesk/` 或其他前台工作台路由如何承接，旧模板是否仅作兼容。本文不擅自决定路由迁移或旧页面退役。

### 5.1 旧 `templates/checkin.html` 的主要差异

| 编号 | 观察 | 建议 | 优先级 |
|---|---|---|---|
| CK-UI-01 | 页面采用多张卡片，但标题、搜索、统计、表格样式沿用旧版 `card/data-table` | 按统一页面标题、卡片、表格、状态组件重整视觉层级 | P1 |
| CK-UI-02 | 散客直入表单多个字段以内联方式挤在段落中 | 按字段标签上置、网格布局、操作区统一排列 | P1 |
| CK-UI-03 | 待确认、已确认、预抵、在住、已退房分散为多张长表格 | 保留业务分区，但采用清晰的区块标题、数量、筛选/空状态和一致表格 | P1 |
| CK-UI-04 | 多种高风险操作均使用同一 `btn-primary` 视觉样式 | 仅按现有业务风险区分按钮视觉；取消、快捷离店、冲账/反结账等风险操作应有清晰危险等级与确认反馈 | P1 |
| CK-UI-05 | 同一行内包含多个输入、选择框和动作按钮，容易误触 | 复杂操作改为行内明确操作区或详情抽屉承载；不得改变现有操作步骤和权限 | P1 |
| CK-UI-06 | 表格列多，缺少统一的响应式表格容器策略 | 小屏独立横向滚动；关键字段优先；避免整页横向溢出 | P1 |
| CK-UI-07 | 身份证号、联系电话等敏感信息在模板中直接输出旧对象字段 | 需与敏感字段权限基线核对；UI 默认掩码，完整值仅在已授权揭示流程中显示。此项是敏感信息展示审查提示，须结合实际 view/API 和权限测试确认 | P0（先核实） |
| CK-UI-08 | 页面没有 viewport meta | 增加响应式视口配置 | P1 |

### 5.2 新版 `frontdesk.html` / `frontdesk.css` 的现状

- 页面标题、物业/岗位/营业日上下文、搜索与日期过滤、运营 KPI、Tab、主列表与侧边状态区、详情抽屉等结构较成熟。
- 卡片、按钮、状态标签、表格和抽屉有独立命名空间，视觉风格更接近现代 PMS 工作台。
- 其蓝灰色、圆角、卡片间距与员工中心方向基本一致。
- 仍需检查各操作区的按钮风险等级、状态颜色与文字映射、窄屏 KPI/侧栏布局、键盘焦点与抽屉可访问性。
- 该页面比旧 `checkin.html` 更适合作为入住业务的视觉优化参考，但不能仅凭模板存在就认定它是当前正式路由。

**结论：** 入住管理的 UI 一致性问题比权限管理更明显。应优先核清正式入口，再以新版前台工作台为视觉参考，分阶段整理旧页面；在路由归属未确认前，不删除旧模板、不改跳转。

## 6. 三个模块统一与差异化原则

| 维度 | 员工中心 | 权限管理中心 | 入住管理/前台接待 |
|---|---|---|---|
| 身份域 | PMS 员工会话 | 平台治理会话 | PMS 员工会话 |
| 页面职责 | 员工档案、账号、任职、岗位授权 | 平台角色权限矩阵治理 | 预订接待、排房、入住、在住、退房 |
| 主布局 | 列表 + 新增表单 + 员工抽屉 | 角色目录 + 权限矩阵 + 影响面 + 确认区 | KPI + 搜索/筛选 + Tabs + 运营列表 + 详情/操作抽屉 |
| 共同规范 | 统一标题层级、卡片、间距、字体、按钮、表单、状态、表格、空/错/加载状态、响应式与可访问性 | 同左 | 同左 |
| 不应统一的部分 | 员工生命周期分区 | 不得并入员工角色授权；保留平台域壳 | 保留前台高频操作和运营指标，不套用员工列表结构 |

## 7. 建议实施顺序

| 顺序 | 工作 | 交付 |
|---|---|---|
| 1 | 员工中心规范落地 | 员工中心 UI 对照规范修订清单 |
| 2 | 权限管理中心 UI 一致性修订 | 仅样式、响应式、键盘可操作性与状态呈现 |
| 3 | 核对入住正式入口与路由归属 | 路由/模板现状表和保留/兼容/退役建议，需产品确认 |
| 4 | 入住管理页面一致性修订 | 以正式页面为对象修订布局和组件 |
| 5 | 跨页面视觉与交互回归 | 桌面/平板/窄屏截图、键盘、空/错/加载态验收 |

建议优先级：
- P0：核对身份证/电话等敏感字段在旧入住模板的展示边界；未确认前不进行视觉上线。
- P1：入住管理复杂表格/表单/操作风险样式；权限矩阵小屏与键盘可操作性。
- P2：标题字号、卡片圆角、强调色和间距细节统一。

## 8. 验收标准

### 8.1 员工中心
- 新增员工表单分为身份、账号、角色三个区域；窄屏单列。
- “物业工号”术语统一；岗位代码与角色授权分开呈现。
- 账号状态和任职状态明确区分。
- 员工抽屉按五个固定分区组织；危险操作有明确确认；授权历史无删除操作。
- 列表具备加载、空、错状态和分页。
- 不改变任何服务端业务规则、接口字段和权限。

### 8.2 权限管理中心
- 保留平台域导航和权限范围提示。
- 角色列表可用键盘操作，焦点和选中状态可见。
- 权限矩阵在窄屏不发生整页溢出；高危权限的风险、两步确认和理由要求明确。
- 保存成功/失败、版本冲突等反馈明确。
- 不改变权限注册表、授权面、并发版本、token 和审计规则。

### 8.3 入住管理
- 正式入口与模板映射明确，旧/新页面职责无重复入口冲突。
- 表单标签、输入高度、按钮、表格、状态标签与员工中心规范一致。
- 高风险操作不与普通操作使用相同视觉等级；二次确认遵循现有业务规则。
- 敏感字段默认掩码，完整值仅按已批准的揭示权限展示。
- 桌面、平板、窄屏无整页横向溢出。
- 不改变预订、排房、入住、退房、账单和审批业务流程。
