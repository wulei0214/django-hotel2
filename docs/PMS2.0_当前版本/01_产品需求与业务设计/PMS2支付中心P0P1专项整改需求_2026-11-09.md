# PMS2 支付中心 P0/P1 专项整改需求（2026-11-09）

> 本轮范围：渠道无关支付架构、模拟渠道和恢复/对账基础；不接入真实生产渠道。需求以最新 main 代码盘点为起点，先复用现有 Payment、BillingService、Refund、LedgerEntry 和回调实现，禁止重复建模。

## 1. 现状判断原则

现有项目具备 Payment、账务服务、支付/退款状态处理及部分模拟支付流程。当前需求不能把这些既有能力描述成完全不存在，也不能把它们等同于完整支付生命周期。PMS3 设计已指出 PaymentIntent、ProviderTransaction、支付补偿与真实渠道边界需要补齐；本轮按此方向收口。

实施前必须逐项盘点：Payment 创建入口、渠道字段、外部交易号约束、回调入口、签名/来源验证、状态迁移、账本入账事务、Hold 关联、任务调度方式、当前测试覆盖。若现有字段/服务已满足，保留并补测试；只有缺失时才迁移新增。

## 2. P0 数据与领域边界

### 2.1 PaymentIntent（支付意图）

职责：记录 PMS 发起的一次支付请求，不代表渠道已扣款。建议字段：
- property、reservation、folio；
- intent_no / idempotency_key（唯一且有作用域）；
- amount、currency、purpose（房费/押金/其他明确类型）；
- provider_code、provider_config_version；
- status、expires_at、max_expires_at、extension_count；
- created_by、created_at、updated_at；
- confirmed_payment（如关系需要，需保证一意性）。

状态建议：CREATED、PENDING、PROCESSING、SUCCEEDED、FAILED、EXPIRED、CANCELLED、UNKNOWN。UNKNOWN 是需要查询/核查的非终态，不得当作 FAILED。状态只能经领域服务合法迁移。

### 2.2 ProviderTransaction（渠道交易事实）

职责：保存渠道返回或查询到的交易事实，与 PaymentIntent 分离。字段建议：
- provider_code、provider_transaction_id（渠道范围唯一）；
- intent、交易金额、币种、渠道状态；
- event_id / notification_id（渠道事件幂等）；
- occurred_at、provider_confirmed_at、received_at；
- sanitized_payload / payload_hash、signature_verified；
- query_count、last_queried_at；
- 原始敏感报文按最小必要原则保存，禁止存储卡号、安全码、密钥或超范围个人信息。

同一渠道交易号只能归属于一个意图；同一成功渠道交易最多形成一笔有效 Payment。重复或乱序通知必须先记录事件，再由状态机判断是否允许推进。

### 2.3 Payment 与账本

Payment 是 PMS 已确认的收款事实，不是支付请求或未经验证的回调。支付确认必须校验物业、预订、Folio、币种、金额和渠道交易唯一性。创建 Payment、写 PAYMENT/DEPOSIT LedgerEntry、更新 Folio/押金累计、确认库存 Hold 的跨域一致性必须有明确事务/恢复设计。

如果数据库事务可以覆盖所有本地事实，则本地 Payment 与 LedgerEntry 同事务提交；库存确认也在同一数据库事务时一起提交。若跨进程或外部渠道无法纳入同一事务，必须用持久化 Outbox/补偿状态保证最终一致，不得声称外部渠道调用与本地 DB 原子事务。

## 3. P0 持久化补偿任务

建立持久化任务记录（可复用现有可靠任务框架；不得只靠内存任务/Redis TTL）。至少有：
- task_type、aggregate_type/id、idempotency_key；
- status、attempt_count、max_attempts、next_attempt_at；
- lease_owner、lease_expires_at、locked_at；
- last_error_code、last_error_summary；
- created_at、started_at、completed_at；
- 人工重放/取消的 operator、reason、audit reference。

任务类型至少覆盖：渠道查询、回调后本地确认重试、Payment/账本修复、Hold 状态协调、渠道对账差异处理。任务执行必须幂等，使用数据库租约/条件更新抢占；多 worker 不得重复执行有效任务。退避上限和重试次数配置化并有安全默认值；超过上限进入 DEAD_LETTER，生成财务/运营待办和告警。

人工重放必须再次查询渠道状态并复用原意图和幂等键；不得重新发起扣款，不得直接手工插入 Payment 或 LedgerEntry。任何人工修复均通过受控领域服务。

## 4. P0 支付与库存联动

- 创建支付意图时关联有效 InventoryHold。
- Hold 的有效期与渠道支付窗口联动；渠道可分别配置等待时长。
- PENDING/PROCESSING 可以在策略内有限延长；UNKNOWN 先主动查询，不直接释放。
- 明确失败/取消或查询确认未支付并达到窗口上限，才允许释放。
- 渠道成功时必须保证 Payment 与账本事实最终生成，Hold 转 CONFIRMED；回调和过期任务竞争时以数据库条件迁移/锁保证单一结果。
- 若支付已成功但房间库存已无法确认，不得丢弃支付事实或虚构订单成功；进入高优先级异常处理，保留资金事实并触发退款/人工履约策略，不得静默释放或超卖。

## 5. P1 状态机、超时和渠道对账

- 定义每个状态的允许迁移、触发来源、超时规则、终态和补偿动作。
- FAILED/EXPIRED/CANCELLED 后重新支付必须创建新 PaymentIntent，不能复活旧意图。
- SUCCEEDED 不允许回退；后续退款是独立 Refund 状态机。
- 渠道查询结果和回调冲突时，以经验证的渠道事实和明确规则处理，冲突进入人工核查。
- 渠道对账导入需有批次、文件摘要、渠道日期、币种、交易号、金额、差异类型和处理状态；同一对账文件/行重复导入幂等。
- 对账差异包括渠道有成功但 PMS 无 Payment、PMS 有 Payment 但渠道无成功、金额/币种不一致、重复交易、退款差异、手续费/净结算差异。
- 本轮渠道无关架构和模拟渠道交付；真实渠道协议、沙箱、清结算与生产接入单独排期。

## 6. API 与安全

API 路径按现有版本路由盘点后扩展，不在文档中预设未核实路径。接口至少支持创建意图、查询状态、接收渠道事件、主动查询、取消/超时、补偿任务诊断、对账批次和差异处理。回调必须验签、校验时间窗/重放、渠道事件唯一性、金额币种和商户配置；拒绝伪造来源。模拟渠道只允许在明确的测试/开发配置启用，生产环境 fail closed。

敏感配置放环境变量/密钥管理，不写数据库明文日志或仓库；支付日志脱敏。对象级物业权限和财务敏感操作原因必填。

## 7. 验收测试

P0：重复点击、重复回调、乱序回调、伪造签名、回调重放、渠道成功但本地事务失败、账本写入失败、Payment 已建账本失败、任务重复抢占、任务进程中断、死信重放、支付成功与 Hold 过期并发、未知状态不释放库存、金额/币种/物业不匹配。

P1：窗口边界、最大延长次数、渠道主动查询、对账重复导入、渠道/PMS 金额差异、失败任务告警、状态迁移非法请求、跨日回调及物业时区。

SQLite 覆盖业务逻辑与回滚；MySQL 必须验证唯一约束、行锁/条件更新、多 worker 任务抢占和并发竞争。全部针对同一最新 main SHA。

## 9. 六项决策落地补充与任务拆分

本需求受《PMS2支付库存账务专项业务决策基线_2026-11-09.md》D1、D2、D3、D6 约束，负责人已确认全部采用推荐方案。

### 9.1 P0 必须完成

1. **PAY-P0-01 支付意图与渠道交易事实分离**：核实现有 Payment 和回调代码后再决定是否新增 PaymentIntent、ProviderTransaction；若现有结构不能分别表达“PMS 请求”与“渠道事实”，才新增模型。不得重复造表。补齐唯一约束、物业/订单/Folio/币种金额校验、事件幂等和状态机。
2. **PAY-P0-02 回调与本地入账一致性**：渠道成功必须可恢复地产生唯一 Payment 和 PAYMENT/DEPOSIT LedgerEntry；本地失败不得丢失渠道成功事实。回调重复、乱序、伪造、重放均需测试。UNKNOWN 不能转 FAILED。
3. **PAY-P0-03 持久化补偿队列**：任务持久化、数据库租约/条件更新抢占、幂等、退避、最大重试、死信、人工重放和审计全部纳入 P0。重放先查渠道并复用原意图，不重新扣款。
4. **PAY-P0-04 支付-Hold 竞态**：支付成功与 Hold 过期/释放必须有唯一仲裁结果。渠道成功后即使本地库存确认失败，也必须保留资金事实并创建高优先级异常处理，不得伪造支付失败或订单确认。
5. **PAY-P0-05 D2 渠道窗口策略**：配置只由服务端控制；有限延长次数、最大累计等待时长和最终核查策略均需明确、可审计。渠道明确失败或查询确认未支付且达到策略终点后方可释放库存。

### 9.2 P1 必须完成

- 渠道对账批次、文件/行幂等、金额/币种/交易号核对、差异待办与处理审计。
- 支付状态迁移诊断、渠道查询频率/超时/错误告警和死信运营视图。
- 真实渠道接入单独排期；本轮只验收模拟 Provider 和渠道无关契约。

### 9.3 验收新增硬门槛

- 模拟渠道成功、失败、超时、未知、重复通知、乱序通知、回调丢失、查询补偿、进程中断和本地 DB 故障均可恢复。
- 两个 worker 同时抢占同一补偿任务，最多一个有效执行者；死信人工重放不得生成第二笔 Payment。
- 支付成功与 Hold 到期并发，不能出现“成功支付但库存已无声释放”。
- 测试必须运行在 SQLite 和 MySQL；MySQL 验证真实行锁、唯一约束和多 worker 抢占。所有证据对应同一最新 main SHA。
