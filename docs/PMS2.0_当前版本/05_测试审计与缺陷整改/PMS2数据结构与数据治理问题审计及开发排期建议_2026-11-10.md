## 2. P0：审批 API 认证与权限风险

### 2.1 审计发现

本轮静态读取 `apps/api/approval.py` 发现：

- `approval_list` 获取 `request.property` 并按物业查询审批记录，但当前函数内未见显式 `request.user.is_authenticated` 或 `AuthorizationService` 权限检查。
- `approval_request` 当前也未见显式认证与业务权限检查，后续将 `request.user` 作为申请人传入服务。
- 项目物业上下文中间件可能为匿名请求解析默认物业上下文，因此“property 不为空”不能替代用户认证和权限校验。
- API 统一包装装饰器不应被视为认证授权门禁。

**风险判断：** 存在匿名读取审批数据或匿名提交审批申请的潜在风险。当前结论来自静态代码观察，尚未通过隔离环境匿名 HTTP 请求证明实际可利用，必须标记为“待复测”，不得在复测前宣称已确认发生数据泄露。

### 2.2 必须拆分的任务

| 任务编号 | 任务 | 实施要求 | 验收要求 |
|---|---|---|---|
| AUTH-P0-01 | 审批列表认证与权限门禁 | 在服务端显式验证登录状态和审批列表权限；拒绝逻辑不得依赖物业上下文存在 | 匿名请求 401/项目统一未认证响应；无审批查询/数据返回；无跨物业数据 |
| AUTH-P0-02 | 审批申请认证与权限门禁 | 显式认证；校验申请动作权限、申请人身份和业务数据范围 | 匿名请求被拒绝；无数据库异常堆栈；无审批记录写入 |
| AUTH-P0-03 | 默认物业匿名访问封堵 | 匿名请求不得因 DEFAULT 物业上下文而访问审批资源 | 匿名访问 DEFAULT 和其他物业均被拒绝 |
| AUTH-P0-04 | 审批物业与角色隔离 | 查询必须先认证、授权、生成物业数据范围，再访问记录 | 无权角色拒绝；跨物业 ID 不可读；合法角色仅见授权范围 |
| AUTH-P0-05 | 同文件其他审批入口检查 | 复核审批详情、批准、拒绝、撤回等同域路由 | 每个入口均有服务端认证、权限、物业范围和审计测试 |

### 2.3 必须执行的隔离测试矩阵

| 身份 | 审批列表 | 审批申请 | 审批详情/处理 |
|---|---|---|---|
| 匿名用户 | 拒绝 | 拒绝 | 拒绝 |
| 已登录但无审批权限员工 | 拒绝 | 拒绝 | 拒绝 |
| 当前物业具备申请权限员工 | 按授权范围读取 | 允许合法申请 | 不得自动获得审批权 |
| 当前物业具备审批权限员工 | 按授权范围读取 | 依业务矩阵决定 | 仅允许授权动作 |
| 其他物业员工 | 不得读取本物业之外记录 | 不得向其他物业提交 | 不得跨物业处理 |
| 已停用/无有效任职员工 | 拒绝 | 拒绝 | 拒绝 |

测试还需检查：
- 被拒绝请求不执行敏感列表查询或写入；

## 3. PAG：分页与数据访问契约整改

分页是 API 数据访问契约，不只是页面组件。每个列表必须登记分页模式、参数边界、排序、权限范围、统计策略和 OpenAPI 行为。

### 3.1 PAG-F01：分页参数统一

冻结规则：

- 缺省参数使用接口登记的默认值；普通列表默认 `page_size=20`。
- `page_size` 合法范围为 1–100。
- 0、负数、非整数、空字符串、重复参数、超过 100 一律返回 HTTP 400，错误码 `VALIDATION_ERROR`。
- 禁止将超限值静默截断为 100。
- 非法 `page` 参数统一返回 400；缺省按默认页处理。
- 校验必须发生在权限通过之后、列表查询和 COUNT 之前；非法参数不得执行列表查询、COUNT 或返回数据。
- 超出末页返回 200、空数组、`has_next=false`。
- 错误体统一包含 `error.code`、`error.message`、`field_errors`、`retryable`。

重点复核：`apps/core/api_contract.py` 既有实现曾对 page_size 做 min/max 截断，与 F01 不一致；`front_desk` 分页参数错误处理与其不一致。实施时必须以最新 main 复核。

### 3.2 PAG-F02：offset 与 cursor 分流

分页登记表必须增加 `pagination_mode`，仅允许 `offset` / `cursor`。

**Offset：** 适用于中小规模、需要页码跳转的列表，例如员工、住客、会员、房态、房型、审批和有限权限字典。提供 page/page_size，稳定排序必须有唯一键兜底，并设置合理深页上限。

**Cursor：** 适用于高增长列表，例如审计日志、财务流水、支付/退款、夜审记录、预订历史。必须支持日期筛选和不透明签名游标；游标绑定物业、权限范围/版本、筛选条件、排序和分页模式；设置过期时间，防止篡改和跨范围复用。默认不返回精确 total，优先使用 has_next/lookahead。

兼容规则：
- cursor 接口传入 `page>1`：400 `PAGINATION_MODE_UNSUPPORTED`。
- cursor 接口传入 `page=1`：允许兼容共享前端组件。
- 不得静默忽略 `page=500`。
- offset 前端可显示页码跳转；cursor 前端仅显示上一页/下一页/加载更多。
- 筛选条件变化必须重置游标；筛选条件应进入 URL。

日期规则（财务/审计等高增长列表）：
- 未传日期时，默认最近 31 天，响应 `range_defaulted=true`。
- 最大日期跨度 366 天。
- 业务日期边界均包含，使用物业业务时区。
- 响应返回实际生效的 start/end。
- 仅传一个边界、start>end、跨度超过 366 天均返回 400。
- 日期过滤必须先于统计、游标生成和分页。

### 3.3 PAG-F03：认证、物业和权限范围优先

固定查询流水线：

认证 → 解析物业上下文 → 权限校验/生成数据范围 → 强制物业过滤 → 业务筛选 → 稳定排序 → COUNT/游标生成 → LIMIT/OFFSET 或游标条件 → 序列化。

禁止：
- 先查全量再 Python 过滤；
- 全表 COUNT 后再做权限过滤；
- 未授权数据参与游标生成；
- 财务汇总后才做物业过滤；
- 客户端传入 property_id 覆盖服务端授权范围；
- 通过 total 泄露其他物业数据规模。

游标签名至少绑定 property_id、权限范围标识/版本、筛选条件哈希、排序方式和分页模式。切换物业、角色、筛选、排序或权限撤销后，旧游标不得继续跨范围使用。

- 详情嵌套集合有明确上限或独立分页契约。

## 4. DATA-F01：查询场景排序治理

### 4.1 原则

统一的是“查询场景”的排序契约，而不是要求同一张表的所有页面只有一种排序。API、页面、测试和导出在同一查询场景中必须使用同一排序规则；不同场景可以有不同合法排序，但必须登记。

每个排序场景登记：
- 场景 ID、所属列表/API/页面/导出；
- 默认排序字段和明确 ORM 表达式；
- 唯一键兜底；
- 空值规则（NULLS FIRST/LAST）；
- 大小写、空格和字符规范；
- 是否允许用户切换排序；
- 对应索引；
- 是否参与 cursor；
- MySQL/SQLite 等数据库兼容说明。

API 响应 meta 应返回实际生效的 ordering；前端只展示服务端排序，不得拿当前页数据自行重排。

### 4.2 本轮观察到的问题

| 对象/场景 | 当前观察 | 需要处理 |
|---|---|---|
| Reservation 列表 | 默认 `-created_at` | 增加稳定唯一键兜底并检查筛选索引 |
| Guest 列表 | 部分查询按 `-created_at` | 全量核对 API、页面、导出 |
| Staff 列表 | 部分查询按 `-created_at` | 员工中心工号排序与稳定排序统一 |
| ApprovalRecord | 创建时间排序缺 id 兜底 | 结合权限过滤、时间和 id 排序 |
| Payment / Refund | 创建时间排序缺 id 兜底 | 财务流水按业务日期/创建时间的场景规则登记 |
| AuditEvent | 模型默认 `-created_at,-id`，API 显式 `-created_at` | API 显式排序覆盖唯一键兜底 |
| LedgerEntry | 模型默认 `created_at,id` 升序 | 确认财务查询场景方向和业务日期排序 |
| NightAuditRun | 模型按 `-started_at` | 夜审历史列表应评估营业日期排序 |
| Stay | `actual_check_in` 可空 | 明确 NULL 排序和入住历史语义 |
| Room | `number`、`floor` 为字符串 | 房号自然排序、楼层数值排序、楼栋字段需求评估 |
| RoomType | 缺少 `sort_order` | 评估是否增加业务排序字段 |
| employee_no | 字符串字段 | 工号规范化与自然排序键评估 |

以上是本轮观察到的候选问题清单，不是全量排序路由审计结果。

### 4.3 排序模型决策要求

- Room 当前没有楼栋字段；floor/number 为字符串，可能出现 1、10、2 的字典序问题。
- RoomType 当前缺少业务排序号。
- employee_no 是字符串，不能直接假设自然数字排序。
- 混合房号如 `A-101`、`101A`、`101` 必须定义业务排序规则，不能依赖数据库默认 collation。
- 明确大小写、尾随空格、strip、NULL 和数据库 collation 差异。
- 需要索引的排序字段必须结合筛选条件与 ORDER BY 联合评估，避免盲目增加索引。
- 跨页边界必须测试同时间多条记录、相同房号跨物业、空入住时间和并发插入。

### 4.4 验收标准

- DATA-A01：同一查询场景 API/页面/测试/导出排序一致且稳定。
- DATA-A02：楼层和房号符合确认的自然/业务排序规则。
- DATA-A03：工号排序符合已冻结的规范化规则。
- DATA-A08：排序字段和组合索引有 MySQL EXPLAIN 证据。
- 相同排序值跨页时不重不漏；任何分页查询均有确定性排序。

## 5. DATA-F02：员工工号与物业任职治理

### 5.1 当前模型关系

当前模型职责方向合理：

- `User`：登录认证账号。
- `StaffProfile`：员工自然人档案。
- `PropertyStaffMembership`：员工在某物业的任职关系，工号归属该模型。
- `StaffRoleAssignment`：物业任职期间的岗位授权历史。

工号不是登录账号，也不是 StaffProfile 的全局属性。同一员工在不同物业可以有不同物业工号。

### 5.2 已观察到的缺口

- 工号字段位于 `PropertyStaffMembership.employee_no`，最大长度 32。
- 当前有物业内工号唯一约束，以及同物业员工档案唯一约束。
- `EmployeeLifecycleService.create_employee()` 目前主要校验非空和同物业重复，没有完整格式规范与统一自动生成服务。
- 员工中心新增员工要求管理员输入工号。
- 历史迁移曾使用 `str(legacy.pk)` 回填员工工号，与新员工手工填写的格式不一致。
- 没有完整工号不可变保护和纠错专用审计服务。
- 数据库大小写和尾随空格比较行为可能因数据库类型/collation 不同而异。
- 同一 StaffProfile 在同一 Property 只能有一条 Membership 的唯一约束，使多次独立任职周期无法直接建模。

### 5.3 DATA-F02A：格式与原子生成

建议提交评审的候选规则：
- 仅允许大写字母、数字和连字符；
- 长度 4–32；
- 写入前统一 strip 和大写；
- 生成过程必须原子化，不能使用 `max()+1`；
- 生成序列不得依赖可修改的 property.code；
- 必须预留物业前缀和序号长度预算；
- 数据库唯一约束作为最终并发保护，服务层处理冲突重试。

以上格式属于待冻结建议，正式编码前需项目负责人确认。

### 5.4 DATA-F02B：工号生命周期

建议规则：
- 工号分配后不可随意修改；
- 离职、停用、调岗不释放工号；
- 工号永久保留，不复用；
- 纠错通过独立服务执行，必须记录修改前后值、原因、操作人、物业和时间；
- 普通员工编辑页面不得直接修改工号。

### 5.5 DATA-F02C：再入职模型决策（未决）

当前唯一约束是一人一物业一条 Membership。需在以下两种方向中评审，不能由开发人员自行选择：

**方案 A：一人一物业保留一条 Membership**
- 再入职复用 Membership；
- 增加任职周期实体/历史记录，例如 StaffEmploymentPeriod；
- 角色授权、离职、再入职按周期留痕；
- 对现有外键和历史审计的影响相对集中，但必须证明历史周期可完整还原。

**方案 B：一人同一物业允许多条 Membership**
- 每次入职创建独立 Membership；
- 对“当前有效任职”建立受控唯一约束；
- 另设工号历史注册/保留机制，防止工号复用；
- 外键、审批、审计、薪酬/门禁等历史引用需要全面迁移评估。

评审前必须盘点：
- Membership 被哪些模型作为外键引用；
- StaffRoleAssignment、审批、审计和业务记录如何关联；
- 当前状态字段是否表达“任职周期”还是“当前人员状态”；
- 历史数据是否已有重复/离职/再入职样例。

### 5.6 DATA-F02D：存量工号映射

执行任何改号前必须只读盘点：
- 工号格式分布；
- 纯数字、前缀、空格、大小写、超长值；
- 规范化后重复；
- Membership 缺失、无 StaffProfile/User 的记录；
- 离职工号占用情况；
- 历史员工 ID 与 PMS2 员工档案映射关系。

必须生成旧工号 → 新工号映射清单，并保留 legacy_staff 关联。不得直接批量改号；不得因格式不统一破坏审批、审计、工资、门禁或纸质档案关联。

### 5.7 DATA-F02E：工号展示规则

- 员工中心、员工详情、审批列表、审计时间线应有统一身份展示规则。
- 当前业务页面展示当前物业的工号，不得从其他物业任意取工号。
- 历史审批/审计建议保存事件发生时的物业工号快照，避免员工后来离职、调岗或再次入职后历史记录显示变化。
- “历史记录展示当时工号还是当前工号”需正式确认后实施。
- 工号快照不得替代 actor 的稳定主键关联。

### 5.8 验收标准

- DATA-A03：格式、规范化、唯一性、原子生成、不可变和离职不复用。
- DATA-A04：再入职、跨物业任职和历史映射符合批准的模型决策。
- DATA-A05：员工中心、详情、审批和审计展示一致；历史身份快照可追溯。
- DATA-A07：存量盘点无未处置重复、孤立或未映射记录；无法自动处理的记录进入人工核验清单。

## 6. DATA-F03：测试数据治理

### 6.1 当前观察

测试代码存在多种工号、房间号和物业编码风格，例如：
- 员工工号：`A001`、`LIFE-001`、`ADMIN-READ-001`、`RBAC-000`、`FD-API-001`、`SEC-001`、`E2E-...`。
- 房间号：`FD101`、`FD-W801`、`E2E-8201` 等。
- 物业编码：`TEST-A`、`TEST-B`、`OTHER` 等。

测试直接调用 `PropertyStaffMembership.objects.create()` 等 ORM 的情况较多。直接 ORM 造数并非一概禁止：针对历史脏数据、数据库约束和异常场景可以使用专用 helper；但正常业务流程测试应优先通过正式 Service 创建数据。

### 6.2 DATA-F03A：统一测试命名空间与工厂

建议统一保留测试命名空间，例如：
- 物业：`TST-*`；
- 员工：`TST-*-0001`；
- 房间：保留测试号段 9001–9999；
- 订单、会员、账单等由统一工厂生成唯一编号。

建议工厂接口（名称为设计示例，实施前需检查现有工具避免重复）：

```python
make_property(code="TST-A")
make_employee(property, employee_no="TST-A-0001")
make_room(property, room_type, number="9001", floor="9")
make_reservation(...)
```

员工创建业务测试尽量调用 `EmployeeLifecycleService.create_employee()`。只有专门测试历史脏数据或绕过业务约束的测试，才允许通过明确命名的 `legacy_fixture` / `unsafe_fixture` helper 直接 ORM 造数，并在测试中说明原因。

### 6.3 DATA-F03B：种子命令安全治理

当前存在多个种子命令，保护能力不一致。特别需要复核 `seed_hotel_data` 对 DEFAULT 物业的操作行为和生产环境门禁。

目标要求：
- 支持显式 `--namespace TST`；
- 支持 `--dry-run`；
- `--reset` 只能删除指定命名空间创建的数据；
- 生产环境默认拒绝；
- 若确有生产演练需求，必须显式 `--confirm-production` 并二次确认，且原则上不建议在生产执行；
- 幂等运行；
- 不允许 flush 全库或删除非测试数据；
- 清理前核对对象关联和外键；
- 命令执行结果输出创建/跳过/清理数量，不输出敏感信息。

### 6.4 DATA-F03C：测试数据遵循业务规则

- 正常业务测试通过领域服务创建员工、预订、入住、账务等对象。
- 直接 ORM 造数必须限定为模型约束测试、历史脏数据测试或故障注入。
- 测试初始化后检查关键关联：员工有物业任职、房间有房型、订单有关联住客/房间/入住关系、账单关联订单和物业。
- 单元测试使用事务回滚；开发/测试环境按命名空间清理。
- 禁止使用全库 flush 作为常规清理方案。

### 6.5 验收标准

- DATA-A06：测试工厂覆盖常用业务实体，编号格式与正式规则兼容。
- 测试不再散落自定义编号生成逻辑；特殊历史数据有明确 helper 和注释。
- 种子命令生产环境默认拒绝，dry-run、幂等和按命名空间清理有测试。
- 测试数据关联完整，不产生无物业员工、无房型房间或无关联订单等意外孤立数据。
