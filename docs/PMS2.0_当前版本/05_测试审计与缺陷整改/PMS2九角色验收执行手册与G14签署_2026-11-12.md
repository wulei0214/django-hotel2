## 执行边界声明（必读）

1. **本手册是执行指引与记录模板，不是验收结论**。手册中所有"预期结果"均为按代码注册表与验收标准推导的预期，必须以真实执行结果为准；实测结果与预期不一致时，以实测为准并登记缺陷。
2. **G14（独立签署）必须由人类签署人独立执行后签署**。第一至第四部分的任何准备材料——包括本手册、AI 生成的执行记录、脚本输出、自动化报告——都只是签署人复核的输入，**不能替代签署**。独立验收人必须亲自执行或逐项复核证据后，才能在第五部分签署栏签字。
3. **开发人员不得代签**。《验收标准》§18 明确：G14 签署栏必须由独立验收人填写，开发人员不得代签；开发与验收分离（§1 原则 6），关键安全、财务和数据完整性项目不得仅由开发人员自证。
4. **凭据纪律**：本手册所有密码/口令一律使用占位符（如 `<九角色统一测试口令>`）。任何真实密码不得写入文档、脚本、CI 变量、日志、截图或 Git。seed 命令通过终端隐藏输入收集密码且**从不输出**密码——凡见到"输出密码"的流程即为违规。
5. **CI 与自动化不能替代本手册**：CI 1178 项通过不等于九角色真实口令登录、浏览器 E2E、Apifox 手工执行或 G14 签署已完成（《角色权限验证指南》§6/复核节、《验收标准》2026-11-12 附录）。
6. **PLANNED 角色不得临时授权**：夜审员、餐饮服务员、餐饮主管、停车安保四个角色为 PLANNED 空组，验收预期是"认证可用、无业务授权"；不得为了让其业务页面可访问而临时授予权限。
7. 本手册不修改任何代码；执行中发现的缺陷走缺陷流程（登记 → 修复 → 复测），不得为通过验收放宽断言或调整门槛（《验收标准》§9.2）。

### 1.2 播种命令与流程

账号播种的唯一方式为 `seed_role_test_accounts` 管理命令（位于 `hotelapp/management/commands/seed_role_test_accounts.py`）：

```powershell
# 1) 设置测试环境
$env:DJANGO_ENV='test'

# 2)（可选）安全收敛测试环境历史账号授权残留
python manage.py reconcile_test_users

# 3) 播种九角色测试账号（交互式输入统一口令，两次确认，不回显、不输出）
python manage.py seed_role_test_accounts
```

命令行为要点（源自命令源码，验收人应现场核对）：

1. 环境与数据库安全门禁：仅允许本机 DEBUG dev 库或明确的 test 库；生产命名库拒绝。
2. 密码通过 `getpass` 两次输入确认，调用 `validate_password` 校验；不提供默认密码、不写入命令行参数。
3. 对每个 `test_*` 账号：创建/激活 User（强制 `is_staff=False`）；清除历史遗留直授 Group 并写 `identity.test_direct_groups_cleared` 审计；创建 StaffProfile（`测试-<角色名>`，ACTIVE）；在第一个 ACTIVE 物业创建 PropertyStaffMembership（工号 `T-TEST_*`）；岗位授权统一由 StaffRoleAssignment 承载，非目标岗位的历史授权只结束不物理删除（写 `identity.test_role_assignment_closed` 审计）。
4. 已具有 superuser/is_staff 身份的 test_* 账号会被拒绝（不自动降权或覆盖）。
5. 存在未来生效岗位授权时命令回滚，要求人工核对。
6. 命令只管理 `test_*` 专用账号，不重置历史演示账号。

## 第三部分：浏览器 E2E 走查脚本（主链路）

### 3.1 两种执行方式说明

**方式 A：真实浏览器手工走查（验收口径，必做）**

1. 启动隔离环境服务（test 库），浏览器访问 `http://127.0.0.1:8000/`。
2. 按 3.2 步骤表逐步执行；每步在浏览器 DevTools（Network 面板）核对请求/响应状态码与封套，截图保存至 `docs/acceptance/evidence/`（命名建议：`2026-MM-DD_e2e_step-<n>_<角色>.png`）。
3. 涉及角色切换时，**必须退出登录后用对应 test_* 账号重新登录**，禁止同一会话连续冒充多角色。
4. 每步实测结果记入 3.2 表"实测/证据"列；任何一步失败即登记缺陷，修复后在新 SHA 上重跑全链路。

**方式 B：Playwright 辅助执行（录制与回归辅助，不能替代人工记录用于 G14）**

- 当前仓库没有已提交的 Playwright 用例；`scripts/e2e_full_chain.py` 存在导入缺失、硬编码凭据、清库护栏不足等问题，**不可作为验收脚本**（《角色权限验证指南》§8）。
- 如需编写辅助脚本（建议路径 `scripts/e2e_nine_roles_browser.py`），必须遵守：凭据一律从环境变量读取（如 `PMS_E2E_BASE_URL`、`PMS_E2E_PASSWORD`），**严禁硬编码**；断言包含界面反馈与响应码，不得把 HTTP 200 一律视为通过；失败截图落 `docs/acceptance/evidence/`。骨架示例（仅示意，非可直接运行脚本）：

```python
import os
from playwright.sync_api import sync_playwright

BASE = os.environ["PMS_E2E_BASE_URL"]          # 例：http://127.0.0.1:8000
PASSWORD = os.environ["PMS_E2E_PASSWORD"]      # 统一测试口令，仅进程内使用

def login(page, username):
    page.goto(f"{BASE}/login/")
    page.fill('input[name="username"]', username)
    page.fill('input[name="password"]', PASSWORD)
    page.click('button[type="submit"]')        # 以真实表单结构为准

# 步骤函数按 3.2 表逐个实现；每个函数内同时断言：URL、界面元素、关键 API 响应码。
# PLANNED 账号步骤只断言"可登录 + 业务 403"，不得临时授权。
```

|---|---|---|

| `sessionid` | 浏览器完成 `POST /login/` 登录后，从 DevTools → Application → Cookies 复制（**无 JSON 登录接口**；也可在 Apifox 用 HTML Form 方式先 GET `/login/` 取 `csrftoken` 再 POST 登录，Form 数据含 `csrfmiddlewaretoken`） | 员工端全部受保护端点 |
| `csrftoken` | 同上，从 Cookie `csrftoken` 复制 | 请求头 `X-CSRFToken: {{csrftoken}}`（写操作必需） |
| `bookingToken` | 公开预订 `POST /api/v1/reservations` 响应返回；存量预订可用 `python manage.py issue_booking_tokens` 补签 | 请求头 `X-Booking-Token: {{bookingToken}}`（预订查询/取消/公开支付） |
| `idemKey` | 每个写用例自拟唯一键（如 `apifox-20261112-refund-01`） | 请求头 `Idempotency-Key`（幂等验证用） |

纪律：cookie/token 属临时会话凭据，录入 Apifox 环境后不得导出共享、不得截图外发、不得入库 Git；执行结束清除环境变量。
