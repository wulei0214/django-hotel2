## 3. 关键实现判断（与设计原文的差异与理由）

1. **`legacy_workflow=True` 只可能出现在 REVERSAL**：数据库约束 `ck_ledger_reversal_approval_link`
   对非冲销凭证只允许 `legacy_workflow=False`。受控入口因此按 `entry_type == REVERSAL` 决定该值，
   非冲销的迁移凭证靠 `LegacyRecordLink` + 批次审计表达来源，**不靠该布尔位**。设计 §5.1 的
   "迁移凭证 legacy_workflow=True" 应读作冲销场景，本批按库约束的可行口径实现并在测试中锁定。
2. **执行凭证逐条重新铸造**：nonce 为单次消费制，同一凭证第二次使用判重放。`migrate_legacy_finance`
   在认证通过后持有可信执行人身份，**每建一条 C1 凭证铸一次新凭证**（TTL 900s 不构成批量瓶颈，
   长批次天然"按需重新铸造"，与 §5.2 一致）。
3. **订单-预订关系映射以"人工确认映射文件"作为等价输入**：设计 §1.5.2 的 `legacy_order_reservation_map`
   关系表属阶段 D 后续交付（含版本链、触发器、并发确认测试）。本批不半成品化该表，改为要求
   `--mapping-file` 提供逐订单人工确认结果（`orders[旧订单] = {reservation, basis, confirmed_by}`），
   未提供映射的订单一律 C4——**不猜测、不自动配对**。关系表落地后仅替换映射输入层，分类与执行逻辑不变。
4. **归档表只读由模型层保证**：四张归档表 + 归档元数据均拒绝 `save` 二次写入与 QuerySet 批量改删；
   生产 MySQL 侧不另建归档表触发器（设计未要求），由"归档命令只在 D3 执行 + 表权限"共同保障，
   此处不做超出设计的声明。

## 9. 后续安全补丁记录（2026-11-17）

批次 3 原交付时，archive_legacy_finance 通过 --dry-run 进入只读模式，但未传 --dry-run 会执行归档写入。该默认行为与后续治理门禁不一致，已在 FIN-02 后续补丁中修正：

1. 默认不带模式参数即只读盘点；显式 --dry-run 仍只读；--verify 只读核验。
2. 只有显式 --execute 才写归档表；--execute 与 --dry-run / --verify 互斥。
3. 执行必须提供 --batch-uid、--operator 和 --approval-ref；审批引用写入 billing.legacy_archive 审计事件。
4. approval_ref 仅为可追溯的审批记录引用，不代替真实签署，也不由命令验证其签名。
5. apps/billing/test_legacy_archive.py 扩展为 21 条，增加默认只读、模式互斥和审批引用缺失拒绝测试。

本补丁没有执行生产归档；D3 生产准入仍以本文件第 7 节责任边界及现行 GOV-03 门禁为准。
