## 1. R6-01 · Folio 候选核验双轨化 —— 通过（设计层）

**第五轮批评**：Folio 收款候选查询单轨 LIMIT 抽样，生产盘点可能遗漏多候选，无法作为完整性核对入口。

**复审核验**：迁移方案 `:178–239` 已落双轨形态——
- ① 完整统计（无 LIMIT）：逐旧收款 `GROUP BY` 输出 `candidate_count`，`candidate_match_status` 区分多候选/单候选/无候选，明确"完整性核对入口，不遗漏"（`:183–208`）；
- ② 逐对明细（LIMIT 200）：`COUNT(*) OVER (PARTITION BY f.id)` 窗口函数逐对标注，注释明确"人工抽样；完整性以查询 ① 为准"（`:210–239`）。

**结论**：两轨职责分离、完整性口径单一（以①为准），"禁止自动判定 C2/C3"约束在两轨均保留（`:180、:193、:224`）。**通过**。SQL 为设计稿，执行需运维只读盘点回填（属 GOV-02 裁定 5，非本轮）。

## 2. R6-02 · FinanceRecord 收入分类化查询 —— 通过（设计层）

**第五轮批评**：日期格式/存在性未严格校验、JOIN 隐式转换可能静默丢行、"订单存在"被误标为"关联已建立"。

**复审核验**：迁移方案 `:241–297` 已落四项修订——
- ① 日期三重校验：`REGEXP` 格式 + `STR_TO_DATE ... IS NULL`（不存在，如 2026-02-30）+ `DATE_FORMAT` roundtrip 回写比对（`:255–258`）；
- ② JOIN 分类保护：全部解析谓词前置到 `LEFT JOIN ... ON`（`:271–276`），解析失败记录不参与候选匹配，消除隐式转换；
- ③ 状态分离：`ELSE '旧订单存在，待新预订关联核验'`（`:263`）不再误标关联已建立，解读段明确 C2/C3 判定必须等阶段 D 关系映射（`:288–289`）；
- ④ 全记录可见：`LEFT JOIN` + 逐条 `classification`（8 类，每记录恰一分类），已被 R4-03 旧 INNER JOIN 静默丢行的对照说明替换（`:295–297`）。

**结论**：批评点逐条对应、分类互斥完备、无静默丢行。**通过**。

## 3. R6-03 · 可信执行身份与不可伪造凭证 —— 通过（设计层）

**第五轮批评（R5-03 未通过，P0）**：交互式密码认证只建立进程内存上下文，任何 Python 路径可自行构造上下文对象绕过认证；ACTIVE scope 可被 `QuerySet.update` 绕过 save 守卫。

**复审核验**：迁移方案 `:345–425` 已落三层重构——
- ① 动机补充（`:349`）：明确指出内存上下文的伪造面；
- ② 签名凭证（`:379–389`）：`django.core.signing` HMAC-SHA256 + 专用 salt 隔离 + `max_age=900` TTL + nonce 写 `AuditEvent` 唯一约束消费 + 三重绑定校验（batch_uid/executor/status）；
- ③ 服务级验签（`:389`）：`post_legacy_migration_entry` 方法体首行验签→nonce 消费→绑定→scope 校验，执行身份只来自凭证，不接受裸 User/自报 operator；
- ④ 三层防绕过（`:391–397`）：`ImmutableBatchQuerySet` 拒四批量方法 + save 守卫白名单/ACTIVE 冻结 + MySQL BEFORE UPDATE 触发器（明确标注"阶段 D D3 部署，SQLite 无触发器，模型层为唯一防线"的诚实边界）；
- ⑤ 负向测试 N9–N13（`:421–425`）：无凭证/篡改载荷/过期重放/QuerySet.update 改 scope/批准人冒充执行人，均拒绝并审计。

**结论**：P0 批评点已由"内存上下文"升级为"密码学凭证 + 服务级验签 + 三层防绕过"，且对 SQLite 边界作诚实声明，不夸大保护范围。**通过（设计层）**。凭证类、批次模型、触发器均为阶段 D 待实现，代码零实现属正常冻结，不在本次判定范围。

**复审人附加提示（不阻断通过）**：设计 `:384` 声明"签名密钥服务端持有、不落日志/不入库"——阶段 D 实施时须在 GOV-03 准入中核验密钥来源（应复用既有 `DJANGO_*` 密钥管理机制，不新造硬编码），否则该约束无法落地。

## 4. R6-04 · 关系表追加式版本链 —— 通过（设计层）

**第五轮批评（R5-04 部分通过待收口）**：CONFIRMED 不可变与 SUPERSEDED 改写相互矛盾，缺乏演进路径与 DB 级防绕过。

**复审核验**：迁移方案 `:58–130` 已落状态模型重构——
- ① 追加式版本链（`:72–82`）：关系行创建即 CONFIRMED 且永不可变，无状态字段、无改写路径；演进 = 追加新行 + `supersedes` 自引用 FK（可空 UNIQUE），旧行原样保留；
- ② 当前有效关系派生口径（`:79`）：`NOT EXISTS (被其他行 supersedes 引用)` 的派生查询，无存储态翻转，消除矛盾根源；
- ③ 分层不可变（`:83–89`）：`ImmutableMapQuerySet` 拒四批量方法 + save 创建后拒改 + MySQL 触发器（阶段 D 部署，诚实边界声明）；
- ④ 确认事务（`:91–96`）：`select_for_update` 锁新预订 + 事务内物业一致性复核 + 版本演进校验目标为当前有效关系；
- ⑤ 版本链测试（`:122–130`）：改字段拒/批量拒/追加版本行/重复取代拒/触发器兜底，5 项与设计一一对应。

**结论**：不可变 vs 演进的矛盾以"追加版本链 + 派生有效性"根本性化解，非打补丁；字段级、事务级、测试级均闭环。**通过（设计层）**。关系表与触发器为阶段 D 待实现。
