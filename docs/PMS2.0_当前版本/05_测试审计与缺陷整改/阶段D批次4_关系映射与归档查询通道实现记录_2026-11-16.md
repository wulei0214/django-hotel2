## 3. 关键实现判断（与设计原文的差异与理由）

### 3.1 归档行显式主键必须 `force_insert`（批次 3 遗留缺陷路径）

`LegacyArchiveRecord` 以**源表主键显式写入**，`pk` 一开始就非空。Django 的 `save()` 在 pk 已存在且
未指定 `force_insert` 时会先试 `UPDATE`（命中 0 行）再 `INSERT`，而 `auto_now_add` 只在插入态填充
→ `archived_at` 以 NULL 落库，触发 `NOT NULL` 失败。本批在 `save()` 里 `kwargs.setdefault("force_insert", True)`
显式声明「创建即插入」语义。该路径在批次 3 的既有用例未触发（其夹具未走显式主键插入），
本批新增归档查询夹具时暴露并修正。

### 3.2 归档查询的物业隔离：按批次登记判定，不自动推定物业

归档行本身**不含物业列**（源表快照未自动推定归属，符合裁定 3「DEFAULT 逐记录核验，不以默认值自动赋值」）。
若在查询层按 `room_id → inventory_room.property_id` 反推，就会把「同号多物业冲突」的历史数据
静默归到某个物业——这正是裁定 3 禁止的自动推定。

本批口径：`LegacyArchiveRun.batch_uid` → 已登记 `LegacyMigrationBatch.scope_property` → 校验调用者在该物业
的 `finance_access`；找不到登记批次的归档批次属「未登记来源」，**仅平台超管可查**。跨物业与未登记来源
一律 404（不泄露存在性）。此口径的代价与边界已在服务层文档字符串与契约 notes 中明示。

### 3.3 组合唯一约束与「回退到已取代配对」的张力（设计边界，未擅自放宽）

设计 §1.5.3 要求「同一 (旧订单, 新预订) 重复插入 → IntegrityError」以拒绝并发第二行；而版本链在
「改映射后又改回原预订」时会尝试插入**第二条**同配对行。两者不可同时成立。本批按设计实现组合唯一
（并发安全优先），并在测试中锁定「重复确认被拒」；**未擅自放宽为部分唯一**——MySQL 8 也不支持条件唯一约束
（`models.W036`）。该边界需设计方在下一轮裁定：可选方向为「组合唯一改为 (legacy_order, reservation, supersedes)」
或「回退场景以 OTHER 关系角色表达」。本记录只登记，不改设计。

### 3.4 关系映射与映射文件并存期的冲突处理

阶段 D 关系表尚未铺满时，`--mapping-file` 仍是有效的确认输入。`build_plan` 因此同时接受两个来源：
关系表为权威、文件为兼容；**同一旧订单指向不同预订即拒绝迁移**（不静默选一边）。
`--mapping-file` 已改为可选：不传时只用关系表。

### 3.5 格式化器分歧的处理（black 与 ruff-format）

`apps/api/openapi_schema.py` 前台只读端点处有一段三层嵌套条件表达式，black（CI 门禁）与 ruff-format
（pre-commit 钩子）对该处的续行规则不一致，二者无法同时满足。本批把该段重构为辅助函数
`_front_desk_read_path_params(path)`（顺序 `if` 返回），**语义等价**（`booking_no` → `legacy_id` → `stay_id` 优先级不变），
使两个格式化器重新一致；未用 `# noqa` 或格式化豁免绕过。

### 3.6 D4 演练的引擎边界

隔离库用独立 SQLite 文件，属**可用性演练**（验证「归档数据能重建历史查询」），不是生产 MySQL 恢复。
生产恢复须按运维方案用备份集在独立实例执行，并由运维与财务负责人共同确认；本工具只产出可归档报告，
不代签。报告默认落 `.work/`（不污染仓库、不入库）。
