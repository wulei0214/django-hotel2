## 0. 审查结论与边界

### 0.1 核心结论

当前仓库已经具备 11 个业务管理中心的大量模型、领域服务、API 和专项测试，不是“没有开发”。但“代码存在”与“员工能从工作台完成业务”之间仍有明显断层。

本轮静态核对确认的核心问题不是页面数量，而是：

1. **页面能力与后端能力没有逐项对齐**：部分中心的 API 已有写操作，当前工作台仍使用只读通用模板；另一些中心只有房间状态写入口，没有任务级业务操作。
2. **任务编排层缺位**：清洁/维修需求已经定义任务领取、派工、完成、验收；当前接口主要操作 Room 状态，不能完整承载任务负责人、任务时限、任务认领和任务结果。
3. **通知与业务任务概念未闭合**：当前 Notification 是源业务状态的只读投影，个人已读不是业务完成；需求基线却要求 WorkItem 领取、指派、完成并回调源领域服务。当前代码没有对应 WorkItem 模型和任务 API。
4. **文档当前值存在冲突和滞后**：当前状态总览的 OpenAPI 现值与遗留表互相矛盾；代码事实锚点及远端状态段落仍引用较早时间点，开发人员可能误判重复开发。
5. **自动化测试不能替代页面/角色验收**：五大中心测试覆盖了若干关键服务和 API 链，但当前没有本轮真实浏览器、全角色操作、页面按钮与完整任务链的独立验收证据。

### 0.3 闭环定义（统一验收口径）

一个管理中心只有同时满足以下条件才可称为业务闭环：

1. 有唯一明确的业务对象和权威数据模型；
2. 页面列表、详情、搜索、筛选、空态、错误态与 API 契约一致；
3. 每个写操作经过授权、参数校验和领域服务，不由模板/视图直接改模型；
4. 状态迁移有合法状态机、事务、幂等和并发控制；
5. 关联中心能读取到同一业务事实，不复制第二份权威状态；
6. 业务操作产生必要审计；敏感字段按最小权限展示；
7. 待办/通知只提示和编排，不替代源业务状态；
8. 异常、失败、重试、补偿有可见入口和最终处理结果；
9. 有正向、反向、越权、跨物业、并发、幂等、异常回滚测试；
10. 需求、API、数据字典、测试和当前状态文档同步更新。

页面可访问、API 返回 200、OpenAPI 标记 verified、单元测试通过，均不能单独作为业务闭环通过依据。

## 4. 通知与业务状态联动的强制设计规则

本节为 MC-007 的实施约束，所有开发人员必须遵守：

1. Reservation、Stay、Room、HousekeepingTask、MaintenanceTicket、Refund、ApprovalRecord、BusinessDate、CashierShift、Invitation 等源模型是业务事实权威。
2. WorkItem 是“工作分配/执行过程”的编排记录，不是源业务状态副本；Notification 是提示投影；NotificationRead 是个人阅读回执。
3. 用户点击“已读”只能创建 NotificationRead，不得关闭 WorkItem，不得修改 Reservation/Refund/Room 等源状态。
4. 用户点击“完成任务”必须经过源领域服务；领域服务校验状态、权限、对象归属、幂等、并发和审批分离后，才可将 WorkItem 标记完成。
5. 源业务因其他入口完成时，WorkItem 应在同一事务或可靠的事务后处理机制中自动关闭；失败必须保留待处理状态并可重试。
6. 业务失败、审批驳回、执行失败不能误销项；已关闭任务再次因源业务重新打开时，必须按规则重开或生成新版本任务。
7. 待办按当前物业有效任职和角色动态可见；员工调岗/离职后，待办重新分派或从其可见范围撤回，不能继续授予旧岗位权限。
8. dedupe_key 必须稳定且与源业务对象、任务类型、目标角色/员工范围一致；并发创建由数据库唯一约束兜底。
9. 所有待办来源必须登记：source event、domain service、WorkItem 生成/销项条件、Notification 模板、跳转 URL、权限、测试。
10. 不允许通过定时刷新把“源业务未完成”误判为“任务完成”；refresh 只负责对账投影。
