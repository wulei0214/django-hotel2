**建议（未在本轮实施）**：后续可将约束改为
`(billing_type='NIGHT_STAY' AND check_out > check_in) OR (billing_type='DAY_USE' AND check_out = check_in)`，

## 四、TASK-02：手机号规范化统一（PASS，代码 SHA `5731e8a`）

### 4.1 问题与根因

改造前存在**两套并存实现**，且口径相反：

| 位置 | 原实现 | 效果 |
|---|---|---|
| `apps/guests/services.py::normalize_phone` | `re.sub(r"[^\d+]", "", ...)` | **保留 `+`**，不校验长度 |
| `apps/reservations/services.py::normalize_phone` | `"".join(ch ... if ch.isdigit())` + 6–20 位校验 | **只保留数字** |

同一号码（如 `+86 138 0000 1111`）因此产生两个不同哈希：

```
档案侧：HMAC(PII_KEY, "+8613800001111")
预订侧：HMAC(PII_KEY, "8613800001111")
```

三类业务后果：

1. **共享号码判定失真**（M-03 规则 2）：同一自然人前后台建档形态不同 → `shared_review_required` 不触发，重复档案产生。
2. **同手机号 PENDING 上限失效**（§6.4）：`Reservation.objects.filter(guest__phone_hash=gate_key)` 查不到另一种形态的存量单，暗示可超限下单。
3. **待确认锁行粒度分裂**（`PendingBookingGate.gate_key`）：并发仲裁按哈希分行，同一号码可绕过串行化。
4. 附带：公开预订限流电话维度按**原始字符串**指纹化（`rate_limit.fingerprint(phone)`），同一号码换写法即可各拿 3 次/10 分钟配额。

### 4.2 口径裁定（工程基线，变更需评审）

| 维度 | 裁定 | 理由 |
|---|---|---|
| 存储/哈希形态 | **纯数字**，不含 `+` | 预订/待确认锁行/账务检索历来按纯数字，向既有数据靠拢 |
| `+` 的角色 | 仅作可接受的输入分隔符 | 不进入规范形态，避免同一号码两套哈希 |
| 国际号码 | 保留国家码数字（`+86 138...` → `8613800001111`） | 剥离前缀可能把不同号码误并成同一人，属业务判断，不自动化 |
| 位数约束 | 6 ≤ 位数 ≤ 20 | 沿用预订侧既有规则，拦截明显残缺与超长输入 |
| 必填性 | 预订/入住必填；客人档案允许为空 | 由调用方选择 `require_phone` 或直接规范化，**不把业务允许性写进规范化函数** |
| 历史数据 | **不改写** | 见 §4.4 |

分层职责（`apps/core/phone.py`，无业务依赖、可被任意层引用）：

| 函数 | 职责 | 失败行为 |
|---|---|---|
| `normalize_phone(raw)` | 格式规范化：仅保留数字 | 不抛异常，空值返回 `""` |
| `digit_count` / `is_valid_phone` | 有效性判定 | 返回 bool/int |
| `validate_phone(raw)` | 校验并返回规范形态 | 抛 `ValueError("请输入有效联系电话。")`（与改造前文案、400 契约一致） |
| `require_phone(raw)` | 业务场景必填 | 空值或无效均抛 `ValueError` |
| `legacy_phone_variants(normalized)` | 历史形态枚举（`数字`、`+数字`） | 仅读侧使用 |

### 5.3 退款状态机（唯一口径）

```text
                 ┌────────────── 审批超时（ApprovalRecord.EXPIRED）──────────────┐
                 │                                                              ▼
create ──▶ PENDING ──approve──▶ APPROVED ──execute──▶ SUCCEEDED              EXPIRED
              │                     │
              └──reject──▶ REJECTED └──（不可 reject / 不可重复审批他人）
```

| 迁移 | 触发点 | 同事务副作用 | 审计动作 |
|---|---|---|---|
| `→ PENDING` | `request_refund` | 创建 `Refund` + `ApprovalRecord(PENDING)` + 占用可退余额校验 | `billing.refund_request` |
| `PENDING → APPROVED` | `approve_refund` | `ApprovalRecord → APPROVED`；申请人≠审批人 | `billing.refund_approved` |
| `PENDING → REJECTED` | `reject_refund` | `ApprovalRecord → REJECTED`；释放占款 | `billing.refund_rejected` |
| `PENDING → EXPIRED` | 审批超时 | `ApprovalRecord → EXPIRED`；无待处理退款时重算支付状态 | `billing.refund_expired` |
| `APPROVED → SUCCEEDED` | `execute_refund` | 写 REFUND 账本、执行班次/参考号、负债回减、支付状态重算 | `billing.refund_executed` |

不变量：同一 `payment` 下 `PENDING + APPROVED + SUCCEEDED` 金额之和不得超过原支付金额；锁顺序统一为 `Shift → Payment → Refund → ApprovalRecord`（非现金退款从 `Payment` 开始）；`SUCCEEDED` 后审批/驳回/再执行均不得迁移状态。

### 10.3 体积根因：一个可修的日志缺陷放大了 70% 输出

对 `test-mysql-wb-round30-final.log`（19.55 MB / 160,283 行）逐行分类：

| 行类型 | 行数 | 占比 |
|---|---|---|
| `--- Logging error ---` 及其 `PermissionError` 栈、`Arguments/Call/Message/argv/command_line` 调试块 | 113,448 | **70.8%** |
| 真实测试输出 | 46,767 | 29.2% |

根因（`hotel/settings.py:252-267`）：

```python
"audit_file": {"class": "logging.handlers.RotatingFileHandler",
               "filename": str(LOG_DIR / "audit.log"),
               "maxBytes": 1024 * 1024, "backupCount": 5, ...}
```

全量回归期间 `hotel.audit` 以 INFO 级持续写入，每次越过 1 MB 触发 `doRollover()` 重命名 `audit.log` → `audit.log.1`；该文件正被并行进程（runserver/waitress）或另一 handler 持有，Windows 下抛 `PermissionError`，标准 `logging` 把完整栈打到 stderr，被 `2>&1` 收进验收日志。`logs/` 目录现存 `audit.log.1`、`audit.log.5`、`request.log.1`、`request.log.5`，与该机制一致。

**这意味着：8 份大日志里约 142 MB 不是测试信息，是日志轮转失败的栈回溯。** 修好 handler 后同类全量回归日志从 19.55 MB 降到约 5.7 MB（仅去噪），再收敛 `-v` 输出可降到 1 MB 以下。

### 11.2 `_body`：六处两份口径，只有四份可并

| 模块 | 实现口径 | 处理 |
|---|---|---|
| `guest_subresources`、`housekeeping_workflow_center`、`inventory_admin_center`、`task_center` | 空体→`{}`；非法 JSON→400「请求体必须是合法 JSON 对象。」；非对象→400「请求体必须是 JSON 对象。」 | **四个文件逐字相同**，收敛到 `apps/core/api_contract.parse_json_object` |

### 11.3 `_money`：四份三义，合并即破坏错误契约

| 定义 | 语义 | 不可合并的原因 |
|---|---|---|
| `billing/dec02.py:30` | `Decimal(str(v)).quantize(0.01, ROUND_HALF_UP)`，**不做任何校验** | 唯一做四舍五入的一处；入参是内部计算结果（负余额绝对值），若加正数校验会直接抛错 |
| `billing/services_v2.py:256` | 严格校验：格式非法 / 非有限 / 超两位小数 → `ValueError`；**允许 0 与负数** | 入账与冲正需要负数；错误类型是 `ValueError`，由视图层统一映射 409/400 |
| `reservations/front_desk_services.py:139` | 严格校验 + **必须 > 0**，错误类型 `FrontDeskOperationError` | 错误类型决定 API 错误码映射，换类型即改契约 |
| `reservations/lifecycle_services.py:31` | 严格校验 + > 0，错误类型 `LifecycleOperationError`，文案为合并句式 | 同上 |

抽取「校验内核 + 传入 error 工厂」在技术上可行，但会让四处调用都变成
`_money(v, error=FrontDeskOperationError, positive=True)` 这类参数化调用，**可读性下降、diff 覆盖全部资金入参校验**，收益（少 40 行）与风险不成比例。按任务书第 4 条禁止事项，**不做**。

### 11.4 `_context`：八处八文案，抽取等于改写对客提示

| 模块 | 返回 | `PERMISSION_DENIED` 文案 |
|---|---|---|
| `audit_center` | `property_obj` | （安全审计域专用文案） |
| `housekeeping_center` | `property_obj` | 当前岗位没有清洁与维修工作台权限。 |
| `night_audit` | `property_obj` | 当前岗位没有该项夜审权限。 |
| `report_center` | `property_obj` | 当前岗位无权查看该报表。 |
| `guest_subresources` | `(property_obj, user)` | 当前岗位无权维护客人档案。 |
| `housekeeping_workflow_center` | `(property_obj, user)` | 当前岗位无权访问清洁维修任务。 |
| `inventory_admin_center` | `(property_obj, user)` | 当前岗位无权维护房态库存。 |
| `notification_center` | `(property_obj, staff_profile, group_ids)` | （任职失效兜底复核分支） |

返回元数三种、文案八种。抽取方案只能是 `_context(request, permission, message)`，等于把「安全提示」降级为一个可随意传入的字符串参数——**权限边界会从「模块内写死」变成「调用方决定」**，正是任务书第 4 条点名禁止的形态。**不合并。**
