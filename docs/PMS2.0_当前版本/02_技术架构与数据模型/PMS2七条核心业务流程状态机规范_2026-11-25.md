## 0. 阅读前提与边界

1. 七条流程**不是一条线性状态链**。它们分别落在 Reservation、Stay、Room、Folio、Payment、Refund、ApprovalRecord、OutboxEvent 八个独立模型上，各有自己的枚举与守卫。
2. 状态推进只能经领域服务完成；View/API 层直接赋值 status 视为缺陷。
3. 本文不重复价格、押金比例、退款政策等业务口径——这些以 `00_项目基线与决策/` 下正式决策为准。
4. 文中「允许边」均附代码落点；无代码落点的迁移一律记为**未实现**，不按设计意图补写。

## 1. Reservation（预约）

状态枚举（`apps/reservations/models.py:15`）：`PENDING` / `CONFIRMED` / `CANCELLED` / `EXPIRED` / `CHECKED_IN` / `CHECKED_OUT` / `NO_SHOW`。

| 前置 | 目标 | 触发服务 | 关键条件 | 代码落点 |
|---|---|---|---|---|
| — | PENDING | `create_reservation` | 库存 Hold、RatePlan 选取、金额服务端计算 | `apps/reservations/services.py` |
| PENDING | CONFIRMED | 支付回调确认 / 前台收款确认 | 验签成功且库存确认成功 | `apps/billing/services.py`（`process_mock_payment_callback`）、`apps/reservations/front_desk_services.py` |
| PENDING | EXPIRED | 过期维护任务 | `expires_at` 已过 | 维护命令 `expire_reservation_holds` |
| PENDING/CONFIRMED | CANCELLED | 前台取消 / 客人自助取消 | Booking Access Token、原因必填、已收款须走退款 | `apps/api/front_desk.py`、`apps/api/views.py` |
| CONFIRMED | CHECKED_IN | `check_in_stay` | 已排房、房间可售、当日营业日未关账 | `apps/reservations/front_desk_services.py:374` |
| CHECKED_IN | CHECKED_OUT | `check_out_stay` | 账单结清或登记退款负债 | `apps/reservations/front_desk_services.py:616` |
| CONFIRMED/CHECKED_IN | NO_SHOW | `mark_reservation_room_no_show` | 按 ReservationRoom 逐间处理 | `apps/reservations/lifecycle_services.py` |

- 押金/预付：目前由「确认时应收取」的既有决策约束，`Reservation` 本身不存押金状态，押金体现为 Payment/DEPOSIT 账本事实。
- 重复提交：`create_reservation` 幂等键 + 库存行锁；重复入住由 `Stay` 一明细一记录的唯一性拦截。

**验证状态：PARTIAL** — 主路径与幂等有回归；并发占房证据在 MySQL 并发用例（`apps/reservations/test_mysql_concurrency.py`）。

## 2. 入住（Stay）

状态枚举（`apps/reservations/models.py:267`）：`IN_HOUSE` / `CHECKED_OUT` / `VOIDED`。

| 前置 | 目标 | 服务 | 关键条件 |
|---|---|---|---|
| — | IN_HOUSE | `check_in_stay` | 预订已确认、房间可售、无其他在住、主账单已建 |
| IN_HOUSE | CHECKED_OUT | `check_out_stay` | 余额结清或登记负债/异常放行 |

- `Stay.reservation_room` 为 OneToOne：同一明细不可能存在第二条入住记录（重复入住被数据库拒绝）。
- 房态联动：入住置 `Room.occupancy_status=OCCUPIED`，与 Stay、Reservation 同事务。
- 失败回滚：`check_in_stay` 整体 `transaction.atomic`；半完成状态在既有回归中被覆盖。

**验证状态：IMPLEMENTED** — `apps/reservations/tests.py` 覆盖未授权、房间不可用、重复入住、回滚。

## 3. 退房（含提前离店）

涉及 Fact：`Stay`、`Reservation`、`Room`、`Folio`、`HousekeepingTask`、`RefundLiability`。

| 步骤 | 服务 | 同事务内动作 |
|---|---|---|
| 房费结算 | `check_out_stay` | 按逐晚快照重算、差额 ADJUSTMENT、提前离店罚金独立凭证 |
| 账务校验 | 同上 | OPEN 且余额 > 0 拒绝退房；余额 < 0 且最后一间登记负债 |
| 房态 | 同上 | `VACANT` + `DIRTY` |
| 清洁任务 | 同上 | 生成 DEPARTURE 任务（幂等，不重复） |
| 状态 | 同上 | Stay→CHECKED_OUT；最后一间时 Reservation→CHECKED_OUT、Folio→CLOSED |

- DEC-01：按实际入住晚数 + RatePlan 提前离店政策快照；缺快照拒绝自动结算。
- DEC-02：负余额先登记 `RefundLiability`；无可靠来源时走 B2 异常放行，不伪造退款。
- 重复退房：`Stay` 已是 CHECKED_OUT 时直接返回 `changed=False`，不重复结算。

**验证状态：IMPLEMENTED** — 提前离店、日租、负债登记、异常放行、清洁任务幂等均有回归；MySQL 侧并发用例覆盖。

## 4. 换房

服务：`change_stay_room`（`apps/reservations/lifecycle_services.py`）。

| 校验 | 实现事实 |
|---|---|
| 当前入住 | Stay 必须 IN_HOUSE |
| 目标房间可用 | `is_sellable_now`（空闲净房、非维修停用） |
| 目标冲突 | 剩余住宿区间内不得有其他有效预订/在住 |
| 并发 | 源与目标房间按主键升序一次性 `select_for_update`，规避 ABBA 死锁 |
| 历史 | `StayRoomSegment` 记录前后房段，旧段写 `ended_at` |
| 房态 | 旧房 VACANT+DIRTY，新房 OCCUPIED，同一事务 |
| 差额 | 跨房型差价目前**拒绝**（需独立价格审批规则） |

**验证状态：PARTIAL** — 现有实现只支持同房型换房；跨房型差价属**未裁定**（M4-4 相关语义保持原状，本文不作裁定）。

## 5. 续住

服务：`extend_stay`（`apps/reservations/lifecycle_services.py:61`）。

| 校验 | 实现事实 |
|---|---|
| 原入住 | Stay IN_HOUSE，预订 CHECKED_IN |
| 日期 | 新离店日期不得早于当前；原离店日已过须走异常入住 |
| 房价计划 | 必须覆盖续住日期，否则拒绝 |
| 房价 | 逐晚 DailyRate 全部存在且未关房；币种须与预订一致 |
| 库存 | 逐日 RoomTypeInventory 未停售且可售 |
| 并发 | READ COMMITTED + 房间/库存行锁，防止与排房、退房并发重叠 |
| 账务 | 续住房费凭证 `stay-extension:{stay}:{date}`，退房结算时归集，防重复计费 |

**验证状态：IMPLEMENTED** — `test_mysql_concurrency.py` 覆盖续住 vs 排房、续住 vs 退房两场景。

## 6. 付款

模型：`Payment`（8 态，`apps/billing/models.py:444`）、`PaymentIntent`（8 态，:1901）、`ProviderTransaction`。

Payment 允许边（依代码守卫）：

| 前置 | 目标 | 条件 |
|---|---|---|
| CREATED | PENDING | 建单 |
| PENDING | SUCCEEDED | 已验签渠道成功 + 金额一致 |
| PENDING | FAILED | 渠道失败 |
| PENDING/CREATED | CANCELLED | 预订取消/过期时关闭未成功意图 |
| SUCCEEDED | REFUND_PENDING / PARTIALLY_REFUNDED / REFUNDED | 由 Refund 执行结果汇总 |

- 三模式：MOCK（开发测试，生产由 `IS_PRODUCTION` 在服务层硬拒绝）、MANUAL（前台人工收款，需操作人）、PROVIDER（真实渠道，未接入，`PRODUCTION_PENDING`）。
- 幂等：`ProviderTransaction` 事件级唯一键（provider+event_id）；重复回调返回 `duplicate=True` 且不重复入账。
- 验签：未验签 SUCCESS 在写入任何资金事实前拒绝。
- 事务边界：外部渠道调用不放在长事务内；迟到成功进入 `PaymentCompensationTask` 补偿。

**验证状态：PARTIAL** — 本地 mock/manual 链路与幂等有回归；**真实渠道未接入**（`PRODUCTION_PENDING`），不得宣称已满足真实支付验收。

## 7. 退款

模型：`Refund`（5 态，`apps/billing/models.py:659`）、`RefundLiability`（3 态，:1073）、`ApprovalRecord`（5 态，:34）。

| 前置 | 目标 | 角色 | 条件 |
|---|---|---|---|
| — | PENDING | 前台/财务发起 | 金额 ≤ 原支付可退余额；必须生成 ApprovalRecord |
| PENDING | APPROVED | 值班经理/店长审批 | 申请人 ≠ 审批人 |
| PENDING | REJECTED | 审批人驳回 | 原因必填 |
| PENDING | EXPIRED | 过期任务 | 审批超时释放占用 |
| APPROVED | SUCCEEDED | 财务执行 | 申请/审批/执行三方不同账号；现金需本人班次；冲减负债 |

- DEC-02：负余额走既定退款流程 B；闭账后退款按 `next_day` 规则。
- 幂等：`execution_idempotency_key` 全局唯一；重复执行返回 `changed=False`。
- 超额：`reserved + refund.amount > payment.amount` 直接拒绝。

**验证状态：IMPLEMENTED（本地）** — 三分离、同人拒绝、超额拒绝、并发、负债冲减均有回归；生产真实原路退款 `PRODUCTION_PENDING`。

## 8. 审批与 Outbox 的支撑状态

- `ApprovalRecord`：PENDING → APPROVED/REJECTED/EXPIRED/CANCELLED；APPROVED/REJECTED 为终态，模型层禁止回退（`ImmutableFinancialFactQuerySet`）。
- `OutboxEvent`：PENDING → PROCESSING → SUCCEEDED / RETRY / DEAD；`RETRY` 到期可再被认领，`DEAD` 仅人工重放。
- Outbox 入队硬拒绝高风险事件（`billing.*`、`night_audit.*`、`business_date.reopen`、`reservation.checkout`），确保 Worker 不会自动重跑账务/夜审动作（`2604b19`）。
