### 2.3 R2-04 退役准备（本批不执行 410，仅登记触发条件与步骤清单）

**触发条件（两者同时满足方可进入退役执行）：**

1. 调用方=0：观察统计中连续 ≥1 个营业日无 `frontdesk.legacy_walk_in_called` 事件新增（查 apps_core_auditevent，action=frontdesk.legacy_walk_in_called；观察起点=本批部署日 2026-11-19）。因已核实前端/内部零调用，该条件预期在首个营业日后即满足；若出现事件，须先定位调用方并完成迁移再观察。
2. 契约基线就绪：9 项兼容端点契约测试（test_walk_in_api.py）语义已转化为 410 退役行为测试（见步骤 3）。

**退役执行步骤清单（届时按序执行，每步独立可回滚）：**

1. `apps/api/front_desk.py` walk_in_create：观测埋点保留，视图体替换为直接返回 410（`{"error": {"code": "GONE", "message": "该端点已退役，请改用 POST /api/v1/front-desk/walk-ins。"}}`，沿用 `_response` 封套），删除业务参数解析与 create_walk_in 调用；docstring 同步改为"已退役（410）"。
2. `apps/api/openapi_schema.py`：`/front-desk/walk-in` 条目 responses 改 410、x-contract-status 改 `retired`（如无该枚举则按契约治理流程新增）、description 去掉"观察期后"改为"已于 YYYY-MM-DD 退役"；重生成双快照并 cmp 逐字节一致。
3. `apps/api/test_walk_in_api.py`：9 项行为契约测试转化为 410 断言（每项保留原场景入参，断言 410 + GONE + 无业务写入），观测审计断言保留（410 路径仍记 legacy_walk_in_called，用于退役后残留调用监控）。
4. `apps/api/urls.py`：路由暂保留（410 也需路由承载），登记至僵尸路由清单随下一批次清理。
5. 全量回归：`DJANGO_DB_ENGINE=sqlite DJANGO_ENV=test .venv/Scripts/python.exe manage.py test apps.api` 全绿 + 双快照 cmp 一致后，方可部署。
6. 部署后连续 1 个营业日监控 `frontdesk.legacy_walk_in_called`：持续为 0 → 退役完成登记；非 0 → 回溯定位调用方（事件含 request_id/ip/user_agent）。

**回滚方案**：恢复 walk_in_create 视图体与契约条目（git revert 单提交即可），观测事件为追加式审计事实、无需清理。
