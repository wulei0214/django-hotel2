## 1. 任务目标

在不改变现有业务行为、不迁移权限数据、不重写权限矩阵的前提下，对指定 Git 基线进行可复核的静态代码审计、配置审计、只读数据核验和测试基线采集，形成 Phase 1–5 可以直接使用的事实输入。

必须回答：

1. 仓库中有哪些 URL、HTTP 方法、视图、认证域、权限检查、模块状态和下游处理？
2. 所有 `app_label.codename` 权限分别在哪里定义、授予、读取和执行？
3. 九个现役业务角色的实际授权、矩阵展示、迁移授予和有效任职使用情况是否一致？
4. 预约、入住、收款、退款、夜审和异常操作的真实数据流、写表、事务和审计路径是什么？
5. 平台、PMS 员工、住客三类身份的认证入口、Session、授权与登出边界是否一致？
6. 哪些关键动作有数据库审计，哪些仅有文件日志或完全没有审计？
7. 当前 OpenAPI 是否准确反映真实接口；哪些路由尚无契约、字段或测试证据？

## 2. 审计边界与禁止事项

### 2.1 允许事项

- 读取 Git 历史、源代码、路由、模板、迁移、配置样例、测试和文档。
- 在隔离环境执行静态扫描、Django URL 解析、测试套件和只读核验。
- 在明确批准的开发/测试/脱敏数据库上执行只读 SELECT、只读事务和只读一致性统计。
- 编写仅输出审计报告的脚本；脚本默认不执行写操作。
- 为审计建立独立输出目录，保存命令、环境信息、报告和校验值。

### 2.2 明确禁止

- 不修改业务视图、服务、模型、权限判断、模板交互和 API 行为。
- 不修改或新增业务 migration，不改 Group/Permission/StaffRoleAssignment 数据。
- 不重写权限矩阵 UI，不提前实现 ModuleRegistry/RoleRegistry。
- 不删除、合并、停用或修复任何 User、StaffProfile、Membership、Group、Permission 或业务记录。
- 不运行 seed、初始化、修复、重置密码、数据回填或迁移命令。
- 不执行真实收款、退款、反结账、夜审执行、重开营业日、入住/退房等有业务副作用的动作。
- 不在生产数据库执行本任务书中的审计脚本。
- 不将密码、Cookie、Session、访问令牌、证件号、手机号等敏感值写入报告。

### 2.3 发现问题时的处理

发现可能造成资金损失、越权、PII 泄露或数据破坏的 P0 风险时：
1. 立即停止可能触发该风险的动态验证；
2. 保存脱敏证据、文件位置、请求条件和影响范围；
3. 登记为阻塞缺陷并通知负责人；
4. 不得在 Phase 0 中自行修复，除非负责人另行批准紧急安全修复并单独建立变更记录。

### 3.2 Tag 与回滚节点

- 只有负责人确认审计 SHA 且工作区状态可解释后，才创建 `phase0-baseline-YYYYMMDD` tag。
- Tag 必须指向被审计 commit，不得指向包含未审核业务改动的临时工作区。
- Phase 0 是只读审计，不需要为了审计修改业务代码。
- 本任务书不代替执行人创建 tag；tag 创建、权限和命名由仓库负责人确认。
- 后续每个实施阶段使用独立提交批次和阶段 tag；不得把 Phase 0 审计文档与后续业务改造混成一个不可独立回滚的提交。

### 3.3 环境选择与数据库访问

默认顺序：
1. 静态代码审计；
2. 隔离测试库或脱敏副本的只读数据核验；
3. 本地开发库只读核验（需明确批准）；
4. 不使用生产库。

只读数据库访问必须同时满足：
- 负责人明确批准数据库环境、主机范围和审计账号；
- 使用只读账号，数据库权限层面拒绝 INSERT/UPDATE/DELETE/DDL；
- 连接串和凭据只通过环境变量或本地安全配置提供，不写入仓库、命令历史或报告；
- 动态核验前确认备份/快照和恢复责任人；
- SQL 使用只读事务；输出仅保留计数、脱敏 ID 或哈希，不导出敏感明文。

如果没有批准的数据库或只读账号，Phase 0 仍可完成静态审计，但所有依赖数据库事实的项目必须标记为“未核验/阻塞”，不得用代码推断代替实际数据结论。

### C. 全量权限点与执行位置清单

扫描范围：
- Django `Permission` 模型和所有已安装 app；
- migration 中创建/改名/删除权限的操作；
- 代码注册、常量、装饰器、服务层权限判断；
- `has_perm`、`user_permissions`、`Group.permissions`、`User.groups`；
- 自定义权限字符串、角色枚举和特殊操作 gate。

每个权限点填写：

| 字段 | 含义 |
|---|---|
| permission_key | `app_label.codename` |
| definition_source | 模型默认 / migration / 手工创建 / 代码常量 |
| display_label | 中文语义 |
| grant_source | migration / matrix / admin / command / manual / unknown |
| runtime_check | 实际执行的检查函数/服务/装饰器 |
| execution_points | 视图、API、服务、任务等调用点 |
| protected_operation | 该权限实际保护的动作 |
| risk_level | LOW / MEDIUM / HIGH / CRITICAL |
| sensitive_class | PII / FINANCIAL / APPROVAL / IRREVERSIBLE / NONE |
| roles_granted | 实际拥有该权限的 Group |
| matrix_visible | YES / NO / PARTIAL |
| active_assignments | 使用相关角色的有效任职统计 |
| evidence | 代码/数据库/测试证据 |
| finding_id | 缺口编号 |

权限点模板：

| permission_key | 定义来源 | 授予来源 | 执行点 | 保护动作 | 风险/敏感级别 | 角色 | 矩阵可见 | 证据 | finding_id |
|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |

必须明确区分：
- “Permission 存在”不等于“执行点有检查”；
- “视图被登录保护”不等于“业务权限已校验”；
- “前端按钮隐藏/disabled”不等于“服务端拒绝”；
- “角色拥有 codename”不等于“AuthorizationService 实际授予”；
- “权限矩阵显示”不等于“矩阵能管理并控制它”。

找不到执行点的权限标记 `NO_RUNTIME_CHECK`；执行点存在但矩阵不可管理的标记 `NOT_MATRIX_MANAGED`；只依赖模板控制的标记 `CLIENT_ONLY_GUARD`。

核验对象：
- 九个现役 Group（以数据库和代码实际注册为准，不把历史名称预设为现役）；
- 预留角色；
- `StaffRoleAssignment` 的有效、过期、未来生效、停用和无效关联；
- 角色授予迁移、seed、管理命令和人工管理入口。

角色差异表：

| role/group | Group.permissions | migration/seed grants | matrix displayed | active assignments | unmapped grants | missing grants | planned grants | conclusion |
|---|---|---|---|---:|---|---|---|---|
|  |  |  |  |  |  |  |  |  |

对每个角色导出排序后的 codename 快照；数据库结果必须脱敏。报告记录快照生成时间、数据库快照标识和哈希，不能把哈希当作版本模型已经存在的证据。

## 5. 只读审计脚本与命令清单

### 5.1 脚本设计原则

- 脚本只读取仓库和数据库，不执行写操作。
- 默认输出 JSON/CSV/Markdown 到审计输出目录，不覆盖源文件。
- 数据库脚本使用只读账号和只读事务；连接失败时退出并明确标记 BLOCKED。
- 不输出密码、Session、Token、PII 原文或环境变量全量内容。
- 每个脚本有单元测试，至少验证不会执行 INSERT/UPDATE/DELETE/DDL。
- 脚本不应自动推断权限效果；只收集候选点，最终执行点需人工核对代码上下文。

## 6. Phase 0 测试要求

### 6.1 静态检查

- 全量 URL resolver 清单与 URLConf 文件对照。
- 权限定义、迁移、授予和运行时检查点扫描。
- 扫描 `User.groups`、`Group.permissions`、`has_perm`、`is_superuser`、`is_staff`、`csrf_exempt`、自定义装饰器和模块 gate。
- 扫描 AuditEvent action、调用点、文件日志和敏感字段 reveal/export。
- OpenAPI path/method 与实际路由/view 对照。
- 每个静态扫描结果必须人工复核误报和漏报风险。

### 6.2 自动化测试基线

- 运行现有 Django 测试套件；
- 分 app 记录测试数量、通过、失败、错误、跳过；
- 记录数据库依赖、外部服务依赖、环境变量缺失；
- 不因测试失败而在 Phase 0 修改业务逻辑；
- 对不能运行的测试记录阻塞原因和建议恢复步骤。

### 6.3 真实 HTTP / 数据库验证

只有在隔离测试环境、测试账号和数据重置方案可用时执行：
- 公开预约创建后，用员工身份从预订中心/前台查询同一预约；
- 记录 request_id、脱敏业务主键、相关表状态变化和审计事件；
- 不调用真实支付渠道，不执行真实退款；
- 对收款/退款/夜审/反向操作优先使用现有测试模式、事务回滚测试或服务层测试；如测试模式仍有持久副作用，停止执行并登记；
- 不允许仅凭页面出现订单卡片就认定数据链路完成。

### 6.4 Session 与权限验证

使用专用测试账号，不使用生产管理员凭据：
- 仅 PMS Session、仅 Admin Session、双 Session 三种状态；
- 未登录、已登录非超管、平台超管、有效 PMS 员工、无任职员工；
- 分别测试页面 GET、只读 API、写 API；
- 分别测试 PMS logout、Admin logout；
- 所有拒绝响应必须记录状态码、重定向目标和审计行为，不记录 Cookie 值。

## 7. Phase 0 退出标准与评审门禁

以下九项全部满足，Phase 0 才能标记 PASS：

1. **路由完整**：所有 URLConf 路由、API、导出、后台任务入口均有清单；每条记录认证域、HTTP 方法、权限、模块状态和证据；未知项明确标 UNKNOWN。
2. **权限完整**：覆盖所有已安装 app 的 `app_label.codename`；每个权限有定义来源、授予来源、执行点或明确标记无执行点。
3. **角色差异明确**：九个现役角色的 Group 实际权限、迁移/seed 授权、矩阵显示和有效 StaffRoleAssignment 使用数有差异表。
4. **P0 链路有证据**：预约/入住/账单收款/退款/夜审/异常路径的真实调用链、写表、权限、事务、审计和失败回滚均有记录；未获准动态执行的链路标 BLOCKED，不得算通过。
5. **身份边界明确**：平台、PMS、住客的入口、Session、授权、登出和账号关联情况有证据；所有未解释项有 finding。
6. **审计覆盖明确**：关键动作成功、拒绝、失败三类审计均已核对，缺失项登记。
7. **缺口有归属**：所有 P0/P1/P2 finding 有证据、影响、责任人、目标阶段和状态；P0 风险有处置决定。
8. **环境可复现**：审计 SHA、工作区状态、环境、数据库类型、命令和测试结果齐全；批准的基线 tag 已建立或记录未建立原因。
9. **负责人签字**：项目负责人/业务代表确认权限点基线和角色基线；技术负责人确认代码证据；测试负责人确认测试基线与复现性。

### 7.1 阻塞规则

- 任一 P0 finding 未经负责人书面接受风险或明确进入紧急修复计划，不得进入 Phase 1/3 的权限写入实施。
- 权限点清单或角色基线未签字，不得开始矩阵 UI 重写。
- 没有可复现测试环境时，可以完成静态审计，但 P0 数据流验收为 BLOCKED。
- 只读数据库未获批准，不得尝试连接其他环境绕过审批。
- 发现工作区有未提交修改但归属不明，不得打基线 tag。
