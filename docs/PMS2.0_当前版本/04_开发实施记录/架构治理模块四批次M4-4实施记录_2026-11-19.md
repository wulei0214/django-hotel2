## 二、交付清单与实施说明

### 2.1 RoomAssignmentConflict 模型 + 迁移 0010

文件：`apps/inventory/models.py`（:711 起）、`apps/inventory/migrations/0010_inventoryreconciliationrun_room_conflict_count_and_more.py`（新增）

- `RoomAssignmentConflict`：run（首报运行，PROTECT，重扫描原位更新归属不变——M4-3 幂等化同款）/ room / room_type / stay_date / conflict_count（当日活跃明细数）/ details（JSON 快照：line_id+booking_no+check_in+check_out，确定性排序，供人工修复定位）/ status（OPEN/DISMISSED）/ dismiss_reason/dismissed_by/dismissed_at。
- 约束与索引：`UniqueConstraint(run, room, stay_date)`（库级 per-run 去重，与 M4-3 `uq_inv_disc_run_type_date` 同构；跨运行去重由应用层 OPEN 查找承担）+ `Index(property, status, stay_date)`（OPEN 报告查询路径）。三字段均非空，无 MySQL 可空列唯一失防问题。
- `InventoryReconciliationRun.room_conflict_count`（PositiveIntegerField default 0）：本批扫描检出冲突日数，与既有 `diff_count` 并列。
- 判定口径模型 docstring 固化：某（物理房, 住宿日）≥2 条活跃排房明细即冲突日（物理房可售容量=1 间/晚）。

### 2.2 判定式唯一实现 + 扫描并入（D4-2 B 主体）

文件：`apps/inventory/reconciliation.py`（:125 起）

- `_room_occupancy_counts(property, start, end)`：判定式**唯一实现**（扫描端与复核端共用，不设第二套口径）。只统计已排房明细（`assigned_room` 非空）；合同区间半开覆盖 `check_in ≤ 日 < check_out`（与 WB-085 闸门同款）；活跃状态 PENDING/CONFIRMED/CHECKED_IN（与 WB-085/assignable_rooms 同款常量口径）；排除带 NoShowRecord 的明细与提前离店已释放夜晚（RSV-03 `inventory_released_from`，与库存 sold 重算同一释放语义）。**只读**：不锁行、不写任何业务表（门禁项②）。
- `_scan_room_assignment_conflicts(property, run, start, end)`：并入 `scan_inventory_discrepancies` 同一运行/同一扫描窗口（[today-days_back, today+30)）。幂等化与 M4-3 差异扫描同款：同一（物业, 物理房, 住宿日）只保留一条 OPEN 报告——重复扫描命中已有 OPEN 行时占用计数/明细快照变化则**原位更新**（首报运行归属不变），无变化不写库，不重复建行。返回（检出冲突日数, 新建行数）记入审计 `inventory.reconciliation_scanned` meta（`room_conflicts`/`new_room_conflicts`）。

### 2.3 复核与关闭服务（人工修复闭环）

文件：`apps/inventory/reconciliation.py`（:719/:754 起）

- `dismiss_room_conflict(property, conflict_id, dismissed_by, reason)`：终态关闭（OPEN→DISMISSED），审计 `inventory.room_conflict_dismissed`；重复扫描按判定式重判，冲突消除即不再报。
- `review_room_conflict(property, conflict_id, reviewed_by)`：`inventory.room_conflict_open` 待办的唯一完成复核服务——与扫描端共用 `_room_occupancy_counts` 同一判定式对该冲突日重算核对：
  * 冲突仍在（≥2 条活跃明细）→ 审计 `inventory.room_conflict_review_rejected` + 拒绝闭环（ValueError），WorkItem 保持待处理可重试（经 `complete_work_item` 失败记 `last_error_code=SOURCE_SERVICE_FAILED`）；
  * 冲突已消除/误报 → 经 `dismiss_room_conflict`（源领域服务）关闭，审计 `inventory.room_conflict_reviewed`；
  * **只报告不自动改派（负责人约束）**：本服务从不改写 ReservationRoom/排房明细，也不改预订状态——改派只能经唯一前台履约工作流执行。`select_for_update` 真锁（MySQL 权威口径）。

### 2.4 MC-007 任务源登记 + 待办来源扩展（复用，零新体系）

文件：`apps/core/task_registry.py`、`apps/core/services_notifications.py`

- task_registry 新增 `inventory.room_conflict_open`（source_type=RoomAssignmentConflict，复用既有权限码 `inventory.maintenance_manage` 不新增权限码；executor=`_room_conflict_review_executor` → `review_room_conflict`，经 `execute_source_service` 唯一完成入口）。
- services_notifications 待办来源清单第 11 项：OPEN 排房冲突逐条（AUDIT/WARNING，广播 `AUDIENCE_INVENTORY`＝值班经理+店长，与差异待办同口径），正文含房型/物理房/住宿日/占用计数/冲突明细 booking_no 与修复指引（前台换房或取消多余明细后复核）。全部走既有 `refresh_operational_todos`/`sync_work_items` upsert 对账机制——**零新表、零新待办体系**。
