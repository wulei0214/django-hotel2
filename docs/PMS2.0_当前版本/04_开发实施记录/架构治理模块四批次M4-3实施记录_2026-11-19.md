## 二、交付清单与实施说明

### 2.1 `sync_inventory_calendar` 滚动调度口径改造（D4-3 B）

文件：`apps/inventory/management/commands/sync_inventory_calendar.py`

- 原单房型同步逻辑（容量校验 + `select_for_update().get_or_create` + 版本推进）整体提取为模块级唯一实现 `_sync_room_type_calendar(property, room_type, start, end)`——**复用而非复制**（门禁项①：单房型模式与 `--all-room-types` 模式调用同一函数，容量校验同口径：`total ≥ held+sold+oos` 才允许覆写总量）。
- 新增 `--all-room-types`（与 `--room-type-code` 互斥，二者必选其一）：遍历该物业全部启用房型滚动；**单一房型失败（无启用房间/容量校验未过）跳过并告警，不中断其他房型**（调度滚动不因个别房型主数据残缺而整体失效），失败房型列入"未完成房型"汇总行；单房型模式保持既有显式失败语义（CommandError 非零退出）。
- 幂等语义不变：已存在行按房间主数据重推总量/停用数并推进 version；重复执行安全挂调度（门禁项②）。

### 2.2 日历覆盖检测命令 + 共用口径服务（D4-3 B 探测面）

文件：`apps/inventory/services.py`、`apps/inventory/management/commands/check_inventory_calendar_coverage.py`（新增）

- `services.calendar_coverage_gaps(property, *, horizon_days=7, today=None)`：对每个启用房型取 `MAX(stay_date)`（无库存行视为未覆盖），小于物业时区"今天"+horizon 即覆盖不足；**只读**，返回 `[{room_type, max_stay, horizon}]`。该函数是覆盖检测命令（§2.2）与待办派生服务（§2.4 来源 10）的**共用口径**——不设第二套阈值定义。
- `check_inventory_calendar_coverage` 命令：输出告警行（scheduler_runner 落 logs/scheduler/ 留痕）→ 调 `refresh_operational_todos` 对账待办；只读检测不写库存；`--horizon-days` 限 1-365。

### 2.3 对账扫描调度化 + 复核服务（D4-4 B）

文件：`apps/inventory/reconciliation.py`、`apps/inventory/management/commands/run_inventory_reconciliation.py`（新增）

- `scan_inventory_discrepancies` 调度幂等化（门禁项②）：同一（物业, 房型, 住宿日）只保留一条 OPEN 差异报告——重复扫描命中已有 OPEN 行时，重算值变化则**原位更新**（首报运行归属不变），无变化不写库；不重复建差异行（差异风暴根治）。审计事件 `inventory.reconciliation_scanned` 增记 `new_discrepancies`。
- 新增 `review_discrepancy(property, discrepancy_id, reviewed_by)`：`inventory.discrepancy_open` 待办的唯一完成复核服务——与扫描/执行端共用 `_recompute_inventory_day` 同一重算口径；差异已消除/误报 → 经 `dismiss_discrepancy`（源领域服务）关闭；差异仍在 → 拒绝闭环并指向唯一修复工作流（申请→审批→执行，职责分离），WorkItem 保持待处理可重试（`last_error_code=SOURCE_SERVICE_FAILED`）。**从不改写库存权威计数（held/sold），不触碰排房明细**（§四 第 2 条）。
- `run_inventory_reconciliation` 命令（每小时）：`--days-back` 限 1-180，调唯一扫描服务 → 打印 OPEN 差异清单 → `refresh_operational_todos` 对账待办；只报告不修复。

### 2.4 MC-007 任务源登记 + 待办派生扩展
