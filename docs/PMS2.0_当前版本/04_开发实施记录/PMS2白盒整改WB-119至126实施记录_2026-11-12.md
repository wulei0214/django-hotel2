## 二、逐项整改说明

### WB-119 渠道交易事件模型拆分（P1）

**根因**：ProviderTransaction 同时承担「渠道交易」与「渠道事件」两个概念，`uq_pt_provider_txn` 唯一约束导致同一交易号的第二个事件 ID 无法作为独立事实保存。

**修改**：
- `apps/billing/migrations/0030_providerevent_history.py`：新增 `ProviderTransactionEvent` 事件历史表（transaction 外键 + `provider_event_key` 可空唯一键实现 (provider_code, event_id) 真实唯一），并把每条存量主记录当前事实回填为首条事件；主记录 `uq_pt_provider_txn` 保持不变（同一交易号只归属一个意图）。
- `apps/billing/payment_intents.py::record_provider_event()`：同交易号新事件 ID → 追加不可变事件 + 受控状态机推进主记录（SUCCESS 终态不可倒退）；同 event_id 事实完全一致 → 幂等返回；任何事实不一致（物业/意图/交易号/金额/币种/状态/验签）→ 拒绝重放，并在**独立事务**写 `billing.provider_event_replay_conflict` 安全审计（主原子块回滚不吞审计证据）。

**数据兼容**：存量 ProviderTransaction 全量回填为首条事件，主记录与关联关系不动；重复执行迁移回填按 transaction 已有事件跳过（幂等）。

### WB-120 对账差异与补偿执行器映射（P1）

**根因**：维护命令把账本修复任务创建为 `aggregate_type="Folio"`（执行器要求 Payment），对账任务聚合 `FolioReconciliationRun` 无解析分支，且 REFUND/ADJUSTMENT 差异误用 Payment 修复器。

**修改**：
- `run_billing_maintenance.py`：`LEDGER_REPAIR_DIFF_TYPES` 收窄为 `PAYMENT_REPAIR_DIFF_TYPES = (PAYMENT_NO_ENTRY, DEPOSIT_NO_ENTRY)`，且要求 `diff.entity_type == "Payment"` 时才创建 `PAYMENT_LEDGER_REPAIR`（聚合为 Payment、`aggregate_id=diff.entity_id`）；退款/调整/余额/负债差异一律 `RECONCILIATION_DIFF` 只读核对转人工，绝不自动改账。
- `payment_compensation_worker.py::resolve_reconciliation_property()`：补齐 `FolioReconciliationRun` 解析分支（run 自带 property），创建方与执行方契约一致。

**验收对应**：REFUND_NO_ENTRY/ADJUSTMENT_NO_ENTRY 按报告要求不自动补造凭证——核实条件无法自动满足时进入只读对账 + 人工处理，符合「不能安全修复的任务进入人工处理或死信」。

### WB-121 过期任务异常分类（P2）

**根因**：`_expire_intents()` 把 `expire_intent()` 抛的所有 ValueError 都计入 unknown 统计，掩盖真实程序异常。

**修改**：`payment_intents.py` 新增 `ChannelStateUnknownError(ValueError)` 专用信号；`_expire_intent_atomic` 仅在渠道 UNKNOWN 时抛出；`expire_intent` 捕获该异常后原子块回滚、意图保持原状态，随后**独立事务**创建 CHANNEL_QUERY 补偿任务再抛业务错误。命令层其余 ValueError 归入 errors 分类统计，UNKNOWN 指标不再失真；UNKNOWN 不释放库存。

### WB-122 手机号回填遗漏（P1）

**根因**：迁移 0007 回填扫描条件 `exclude(phone__isnull=True).exclude(phone__exact="")` 漏掉 phone 为空但 phone_normalized 有值的记录，随后清明文步骤会清空全部记录，造成该类数据永久丢失。

**修改**：`apps/guests/migrations/0007_phone_pii_ciphertext_and_document_index.py`
- 扫描条件改为 `exclude(phone__isnull=True, phone_normalized__isnull=True)`（Guest 与 GuestPhone 均覆盖）；
- 标准化优先取 `phone_normalized`，为空再从 `phone` 标准化；两者均空不伪造号码；
- 原始值无法标准化、同客人重复号码哈希冲突 → 显式失败，保留原值不清明文；
- 清明文前完整守卫：任一明文非空记录缺少密文/HMAC → RuntimeError 阻断清理。

### WB-123 PII 密钥接入 Setting（P1）

**根因**：settings 生产检查只读环境变量，未赋值 `settings.DJANGO_PII_KEY`，业务加密函数 `getattr(settings, "DJANGO_PII_KEY", None) or settings.SECRET_KEY` 静默回退到 SECRET_KEY。

**修改**：`hotel/settings.py` 显式定义 `DJANGO_PII_KEY = os.environ.get("DJANGO_PII_KEY", "").strip()` 与 `IS_PRODUCTION`；生产环境缺失或长度 <32 直接 `ImproperlyConfigured` 启动失败，不允许回退。`apps/guests/services.py` 密钥派生统一，迁移与业务服务共用同一实现；密钥错误时明确失败，不静默返回空手机号。

**密钥切换约束**：既有密文按旧密钥派生算法可解密（迁移守卫测试含密钥轮换隔离场景）；生产换钥必须走「识别旧钥 → 保留只读解密 → 配置新独立密钥 → 受控重加密 → 重算 HMAC → 对账 → 切换」流程，禁止直接换钥上线。

### WB-124 迁移不可逆与恢复预案（P1）

**根因**：清明文 RunPython 反向为 noop，结构回滚不等于数据恢复，运维可能误以为反向迁移可恢复明文。

**修改**：清明文步骤改为 `migrations.RunPython(clear_phone_plaintext)`（不提供 reverse_code）——反向迁移显式报 "irreversible"，杜绝静默丢弃；配合 WB-122 的清明文前守卫，明文清理只会在回填完整且可解密核验通过后发生。

**恢复预案**：正式恢复流程为「停写 → 确认迁移阶段 → 迁移前备份恢复数据库 → 恢复匹配的 PII 密钥 → 核对 Guest/GuestPhone 数量 → 验证解密与 HMAC → 验证业务 → 恢复服务」。迁移前必须完成全库备份（含 Guest/GuestPhone/密钥/迁移状态，加密保存）。专项测试 `apps/guests/test_phone_migration_guard.py`（8 项）覆盖四组合回填、守卫阻断与密钥轮换隔离。

### WB-125 ProviderTransaction 只追加保护（P1）

**根因**：QuerySet 层已有 ImmutableFinancialFactQuerySet，但实例 `save()` 未阻止对已存在记录改写交易号/金额/币种/验签/状态。

**修改**：`apps/billing/models.py::ProviderTransaction.save()` 对已存在记录（pk 已持久化）拒绝普通更新，唯一放行口是 `payment_intents._record_provider_event_atomic` 内经 `select_for_update` 锁定的受控状态机推进（`_transition_provider_transaction`）；后续状态变化全部落 `ProviderTransactionEvent` 事件表，不修改旧事实。`last_queried_at`/`query_count` 等查询统计仅经受控方法维护。数据库层 MySQL 只追加触发器现状（AuditEvent/LedgerEntry/CashierShiftMovement）在部署说明中已明确 ProviderTransaction 保护由应用层状态机承担，已在文档与注释中声明边界。

### WB-126 补偿任务并发幂等（P1）

**根因**：`create_compensation_task()` 先查后写，并发插入第二个调用撞 `idempotency_key` 唯一键直接失败，未实现完整并发幂等语义。

**修改**：`payment_intents.py::create_compensation_task()` 预查询 → 嵌套保存点 INSERT → 捕获 IntegrityError 后退出保存点按幂等键回查 → 找到则幂等返回 `(existing, False)`，找不到则重抛原始异常（不伪装未知数据库错误）；回查时按 `_find_compensation_task` 核对 task_type/aggregate_type/aggregate_id，同一幂等键不同业务参数判为幂等键冲突拒绝。MySQL 独立连接 + Barrier 真实并发测试通过（`apps/billing/test_payment_dec02.py` WB-126 用例）。

### WB-092 补齐：ENTRY_NO_PAYMENT 反向扫描（凭证 → Payment 方向）

前 32 轮的对账扫描只有**正向**（Payment → 凭证：`PAYMENT_NO_ENTRY` / `DEPOSIT_NO_ENTRY`），`ENTRY_NO_PAYMENT` 差异类型在 models 与迁移 0031 中已定义但无实现。本轮补齐：

- **位置**：`apps/billing/reconciliation.py::scan_folio_reconciliation`（每 Folio 主循环内，紧跟正向收款核对之后）；
- **规则**：每张 `PAYMENT`/`DEPOSIT` 凭证必须能精确追回到一笔 `PAYMENT_ENTRY_CHECK_STATUSES` 白名单状态内的 `Payment`：
  - 引用必须符合 `payment:{provider_ref}` / `deposit:{provider_ref}` 命名，否则报"无法追溯"；
  - `deposit:` 前缀凭证要求来源 Payment 的 `provider == frontdesk_deposit`，`payment:` 前缀反之（渠道类别不符报差异）；
  - 同 Folio 内按 `provider_ref` 精确匹配；本 Folio 无候选时跨 Folio 复查（同物业），命中则报"Payment 挂在账单 Folio X，与凭证归属不一致"；
  - 追溯到来源 Payment 后仍核对金额方向（`凭证金额 == -payment.amount`）、币种、物业归属；
- **与正向互补**：正向兜"收款无凭证"，反向兜"凭证孤立/伪造/重复入账/状态失配"；两方向独立报差异（如引用存在但金额不符时，正向报 `PAYMENT_NO_ENTRY`、反向报 `ENTRY_NO_PAYMENT`，entity_type 分别为 `Payment` / `LedgerEntry`）。
