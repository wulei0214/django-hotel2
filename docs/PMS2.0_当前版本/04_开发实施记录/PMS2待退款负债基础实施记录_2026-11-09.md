## 2. 已实施内容

### 2.1 数据模型

新增 `billing.RefundLiability`：
- 物业、预订、Folio 关联；
- 原始负债金额、待处理余额、币种；
- OPEN / PARTIALLY_SETTLED / SETTLED 状态；
- 全局唯一幂等键；
- 登记人、登记时间、结清时间；
- 与多个候选原支付 Payment 的多对多关系。

数据库约束：
- 原始负债金额必须大于零；
- 待处理余额必须在 0 与原始金额之间；
- 状态、余额、结清时间必须匹配。

负债原始金额、物业、预订、Folio、币种、幂等键和登记人不可修改；待处理余额禁止回增；已结清负债不可重新打开；QuerySet 批量 update/delete 被禁止。

### 2.2 原支付追踪

`source_payments` 只保存同一 Folio 下具有成功支付事实及对应 PAYMENT 账本凭证、且仍有候选可退款余额的 Payment。

候选关联不等于自动金额分配。财务人员在现有退款申请中明确选择候选 Payment 并填写本次退款金额；系统验证 Payment 候选关系、原支付剩余可退款金额及负债剩余金额。系统不按时间、支付顺序或其他规则自动分配。

### 2.3 退房行为

修改 `check_out_stay()`：
- 最后一间房退房后若 Folio 余额为负，先在同一事务内登记待退款负债；
- 负债登记成功后允许客人离店；
- 没有可追溯的原支付及对应 PAYMENT 账本凭证、币种/物业/账单不一致、候选支付可退款余额不足时，退房仍失败并回滚；
- 登记负债失败，退房不会部分提交；
- 负余额不会被清零，Folio 结账后仍可查询 RefundLiability；
- 不自动创建 Refund，不自动审批或执行退款。

### 2.4 退款申请与执行关联

- Refund 增加可选 `refund_liability` 外键。
- `BillingService.request_refund()` 增加可选 `refund_liability_id`；财务显式选择候选 Payment。
- 同一负债下 PENDING/APPROVED 退款金额会预占待处理余额，避免并发申请超过负债金额。
- 退款实际执行成功并追加 REFUND 账本凭证后，才扣减 `remaining_amount`；部分退款保留余额，全部处理完转 SETTLED 并记录结清时间。
- 退款申请幂等重放校验包含负债关联，不能用同一幂等键切换负债。
- 执行成功审计事件记录负债 ID 和剩余金额。
- 退款模型校验退款、负债、原支付属于同一物业、预订、Folio 和币种，且 Payment 必须在负债候选集合中。

### 2.5 API 与后台

- 新增 `GET /api/v1/billing/refund-liabilities`，仅财务权限可查询负债及候选原支付。
- `POST /api/v1/billing/refunds` 可选传入 `refund_liability_id`，沿用现有申请、审批、执行流程。
- RefundLiability Django Admin 为只读查询；不允许后台直接新增、编辑或删除负债事实。
- 退款列表返回负债关联 ID。

### 2.6 财务中心 UI

- 财务中心新增“待退款负债”列表，展示预订编号、原始负债、待处理余额、候选原支付和状态。
- 财务人员选择候选原支付后，在现有退款表单中提交金额和原因；请求携带 `refund_liability_id`。
- 申请、审批、驳回、执行后刷新负债列表；执行成功后显示最新待处理余额。
- 没有退款申请权限的员工只读查看，不显示发起操作。
- UI 明确提示候选支付仅供财务核对，不代表自动分配。

## 4. 自动化测试

- 最后一间房负余额退房，登记负债后离店；
- 退房重复调用不重复生成负债；

- API 财务查询负债及候选支付、关联发起退款；

## 5. 尚未完成的事项与门禁

1. 需要在真实浏览器中使用不同申请人、审批人、执行人完成一次待退款负债全流程；当前尚无浏览器 E2E 证据。
2. 需要补充专门的 MySQL 并发测试：同一负债不同 Payment 并发申请/执行、部分退款重放、超额申请和锁顺序。
3. 当前采用财务手工选择候选 Payment 并填写金额，不自动分配。若将来要求系统自动分配，必须另行确认分配规则。
4. 已登记负债后若发生新的 Folio 冲账、费用补记或其他账务调整，负债如何同步调整尚未定义；当前原始负债金额冻结，不静默重算。
5. 如果存在无法关联原支付的负余额或候选支付可退款余额不足，当前会阻止最后退房并回滚；异常人工处理流程仍需业务确认。
6. 渠道退款对账/未知状态自动 reconcile 不属于本次实现范围。

## 6. 安全与数据保护

- 不清理、不覆盖 Payment、Refund、LedgerEntry 历史事实。
- 不将负余额视为已退款或已结清。
- 不自动创建 Guest Wallet。
- 不绕过退款申请、审批、财务执行职责分离。
- 不执行 E2E 清库脚本。
- 不更改已确认的其他业务政策。
