## 1. 项目概述

### 1.1 项目定位

建设一套面向单体酒店日常运营的酒店管理系统（Property Management System，简称 PMS），以酒店物业、员工身份、住客档案、房型房间、房价库存、预订、实际入住、账单和账务为核心。

系统从历史 Django CRUD 原型逐步演进为按业务域组织的模块化单体。新业务采用 API-First 思路，业务规则集中在后端领域服务中，页面负责交互和展示。

### 1.2 建设目标

1. 建立统一的酒店物业、员工身份和岗位授权基础。
2. 建立以“房型 + 住宿日期”为核心的房价与库存管理能力。
3. 建立预订、实际入住和账务相互分离的核心业务模型。
4. 保证预订过程中的库存一致性、价格快照和请求幂等。
5. 建立可追溯的账单、支付流水和账本凭证。
6. 逐步将历史员工后台业务迁移到新领域模型，避免一次性推翻旧系统。
7. 为未来多物业和第三方集成保留清晰边界，但不提前开发未经确认的业务。

### 1.3 设计原则

- **单体酒店优先：** 当前业务按一家酒店落地，物业字段为后续隔离预留。
- **模块化单体：** 一个 Django 项目内按业务域划分 App，不拆微服务。
- **业务规则后端统一：** 前端不得自行决定库存、价格、支付结果或账务余额。
- **数据一致性优先：** 关键业务操作使用数据库事务、约束和幂等控制。
- **账务可审计：** 财务凭证保留历史，不通过直接修改或物理删除掩盖差错。
- **渐进式迁移：** 新旧页面并存，按完整业务流程逐步替换。
- **真实状态透明：** 不得将规划功能描述为已经交付的功能。

## 3. 用户角色与权限需求

### 3.1 身份模型

登录身份与员工业务档案分离：

- Django User：账号、密码、Session 和认证状态。
- StaffProfile：员工自然人档案。
- PropertyStaffMembership：员工在某个物业中的任职关系、店内工号、岗位和任职状态。
- StaffRoleAssignment：某次物业任职获得的岗位授权及有效期。
- Django Group / Permission：岗位权限模板和底层权限定义。

当前物业范围、任职有效状态和岗位授权必须共同参与权限判断。不能仅依靠菜单隐藏、前端按钮隐藏或 is_staff 判断业务权限。

### 3.2 目标岗位职责

以下为权限设计目标；岗位权限矩阵和全部业务接口接入需以实际实施状态为准。

| 岗位/角色 | 主要职责 | 典型权限边界 |
|---|---|---|
| 系统管理员 | 系统配置、账号和基础数据维护 | 系统级管理；敏感操作需审计 |
| 店长/经理 | 经营管理、业务审核和异常处理 | 查看经营数据、审核授权范围内的操作 |
| 前台接待 | 预订查询、入住接待、退房办理 | 仅操作所属物业和授权业务 |
| 值班经理 | 前台异常、房态和业务授权处理 | 按岗位授权处理特殊业务 |
| 财务人员 | 账单、收款、退款和财务核对 | 财务权限独立，冲销需授权和原因 |
| 客房人员 | 清洁任务和清洁状态维护 | 不应拥有支付和财务写入权限 |
| 夜审人员 | 营业日结算和夜审核对 | 夜审执行及结果查看权限 |
| 顾客 | 查询可订房型、提交和查询本人预订 | 仅访问本人可验证的订单信息 |

### 3.3 权限要求

1. 服务端每个敏感读写接口都必须进行认证和授权。
2. 员工只能访问当前物业且任职有效的业务数据。
3. 前台、客房、财务、夜审等岗位按业务动作授权，不能仅按页面授权。
4. 财务冲销、退款、人工调整等敏感操作必须记录操作者、时间、原因和关联凭证。
5. 顾客查询订单时，预订编号必须配合联系电话核验。
6. 账号停用或任职失效后，应阻止对应业务访问。

## 4. 功能需求

### 4.1 物业与基础配置

目标：为单体酒店建立统一的物业上下文和基础数据归属。

- 建立物业编码、名称、启用状态等基础信息。
- 当前使用默认物业编码 DEFAULT。
- 核心业务数据关联物业，服务端按当前物业上下文隔离。
- 默认物业通过 DEFAULT_PROPERTY_CODE 配置。
- 不在本版本实现集团组织、跨店运营或集团级权限。

### 4.2 员工身份与岗位授权

目标：支持员工账号与员工档案分离，并建立物业任职和岗位授权基础。

- 支持员工档案与 Django User 关联。
- 员工可拥有不同物业任职记录的数据结构。
- 任职信息记录物业、工号、岗位、状态和有效期。
- 角色授权绑定具体物业任职。
- 后续将历史员工后台逐步迁移到统一身份与权限服务。

### 4.3 住客档案

目标：建立跨预订复用的住客档案。

- 记录住客姓名、联系电话及必要联系信息。
- 同一物业内按规范化联系电话进行去重。
- 顾客端当前不要求采集身份证号码。
- 身份证件加密、脱敏、留存和公安旅业系统适配属于后续合规专项，不在本版本假设已完成。

### 4.4 房型、客房和房态

目标：将销售房型与实际物理房间分离管理。

核心实体：RoomType（销售房型）、Room（物理客房）。

Room 的三个状态维度独立维护：

| 维度 | 状态示例 | 含义 |
|---|---|---|
| 占用状态 | VACANT / OCCUPIED | 是否有实际住客占用 |
| 清洁状态 | CLEAN / DIRTY / CLEANING / INSPECTING | 客房清洁与检查进度 |
| 维修状态 | NORMAL / OUT_OF_ORDER / OUT_OF_SERVICE | 是否可正常投入使用 |

需求：
- 房间必须归属物业和房型。
- 可售判断不能只依赖一个“房态”字段。
- 物理房间当前可售基础条件为启用、空闲、净房且维修状态正常。
- 未来日期销售库存以按日库存模型为准，不可用当前物理房态简单替代。

### 4.5 房价计划与每日价格

核心实体：RatePlan、DailyRate。

- 每晚价格按住宿日期维护。
- 查询区间内每一住宿晚必须存在有效价格。
- 预订创建时保存每晚成交价快照。
- 后续调整 DailyRate 不得改变已创建订单的历史成交价格。
- 入住日计价，离店日不计价。

### 4.6 按日库存

核心实体：RoomTypeInventory。

库存字段包括 total_rooms、held、sold、out_of_service 和停售状态。

可售库存口径：

available = total_rooms - held - sold - out_of_service

需求：
1. 每个住宿日单独检查库存。
2. 创建预订时，在数据库事务中锁定涉及的库存日期记录。
3. 任意一晚库存不足，整个预订事务回滚。
4. 不允许只扣减部分住宿日库存。
5. Hold 默认期限为 15 分钟。
6. 过期 Hold 由管理命令释放；后续可由系统调度器触发，但当前不强制引入 Celery。
7. 库存日历同步根据启用的物理房间主数据更新总量和停用量，不覆盖已有 Hold/Sold。

### 4.7 预订管理

核心实体：Reservation、ReservationRoom、Stay。

- 支持入住日期、离店日期、房型、房间数、入住人数、联系人和联系电话。
- 支持一张订单多间房，每间房独立明细。
- 入住日期包含，离店日期不包含。
- 预订金额根据每晚价格明细汇总。
- 保存每间房的逐晚成交价格快照。
- 创建预订必须带 Idempotency-Key。
- 同一 Key 和相同请求内容应返回同一预订结果。
- 同一 Key 对应不同请求内容应返回冲突。
- 默认创建 15 分钟库存 Hold。
- 当前顾客自助取消仅适用于待支付预订。
- 已确认订单的自助取消/退款规则未定义前不得开放。

### 4.8 在住与履约

Stay 用于记录实际入住和退房履约信息。后续既定迁移工作包括：

- 前台核验预订与住客信息。
- 分配符合条件的物理客房。
- 办理实际入住并创建 Stay。
- 记录实际入住、退房时间。
- 支持既定范围内的换房、续住和退房流程。
- 将住中消费、收款和退款关联到 Folio。
- 退房后更新房间占用和清洁状态。

**当前状态：** Stay 数据模型已建立，完整前台入住、换房、续住、退房流程尚未全面接入新模型。

### 4.9 账单、支付和账本

核心实体：Folio、Payment、LedgerEntry。

余额口径：
- 房费/消费为正数。
- 押金/收款/退款抵减为负数。
- 正数余额表示客人仍需支付。

需求：
1. Payment 与预订和 Folio 关联。
2. 支付渠道流水号应具备唯一性约束。
3. LedgerEntry 使用唯一业务 reference。
4. LedgerEntry 不允许常规物理删除或直接更新。
5. 财务纠错通过红字反向凭证处理，记录原因并关联原始凭证。
6. 收款/退款必须保留 Payment 与 LedgerEntry 的对应关系。
7. 当前 Mock 支付只用于开发/测试环境验证订单和账本状态流转，不产生真实资金交易。
8. 生产环境不得展示模拟支付入口或开放模拟回调。

### 4.10 顾客端预订页面

当前新页面：/reserve/。技术方式：Django Template + 原生 JavaScript。

- 选择入住日、离店日、房型和房间数量。
- 查询可订房型、逐晚价格和库存结果。
- 提交预订并显示订单编号。
- 通过预订编号和联系电话查询订单。
- 允许取消待支付订单。
- 仅在 dev/test 环境展示 Mock 支付演示。
- 加载、无房、价格缺失、参数错误、网络错误和重复提交都应有明确反馈。
- 前端金额和库存仅用于展示，最终结果以服务端计算为准。

历史页面 /booking/ 暂时保留，不应与新页面混为一谈。

### 4.11 员工端与管理后台

- 当前员工登录和历史员工页面仍然存在。
- Django Admin + django-simpleui 用于后台基础数据管理。
- 历史员工管理、入住/退房、财务、夜审等页面尚未全部迁移到新领域模型。
- 页面迁移必须调用领域服务，不能在模板或视图中直接散落库存扣减和账务写入逻辑。
- 页面交互变更必须同步 UI 文档；无实际功能的控件不得作为已交付功能展示。

## 5. 核心业务规则

### 5.1 日期规则

- 入住日包含在住宿区间内。
- 离店日不包含在住宿区间内。
- 住宿晚数为离店日期减入住日期。
- 价格和库存必须覆盖每一住宿日。

### 5.2 预订价格规则

- 每晚价格由后端读取 DailyRate。
- 订单总价由每间房逐晚价格汇总。
- 创建订单时固化成交价格快照。
- 历史订单不得因房价计划调整而变化。

### 5.3 库存规则

- 库存以物业、房型、住宿日为维度。
- 可售库存按 total - held - sold - out_of_service 计算。
- 创建订单必须在事务中锁定涉及的库存记录。
- 任一住宿日失败必须整体回滚。
- Hold 只能被确认一次或释放一次，不能重复转销售。

### 5.4 幂等规则

- 创建预订使用 Idempotency-Key 和请求指纹。
- 相同 Key + 相同 payload：返回原有结果。
- 相同 Key + 不同 payload：返回冲突。
- 支付回调必须校验签名、金额、状态和幂等条件。

### 5.5 账务规则

- Folio 是账务容器，不等同于支付流水。
- Payment 记录渠道交易。
- LedgerEntry 记录业务账务凭证。
- 账本差错通过反向凭证处理，不直接覆盖历史。
- 正负方向必须遵循统一余额口径。

## 6. 技术架构

### 6.1 总体架构

采用模块化单体（Modular Monolith）+ Django B/S + API-First。

访问端：
- 顾客浏览器。
- 员工浏览器。
- 系统管理员。

表现层：
- Django Template + 原生 JavaScript。
- Django View + JsonResponse（API v1）。
- Django Admin + django-simpleui。
- 历史 Django 模板页面（渐进迁移兼容）。

应用/领域层：
- 按业务域划分 Django App。
- 业务写操作通过领域服务组织。
- 数据库事务负责关键库存和账务一致性。

数据层：
- 默认 MySQL。
- 配置支持 PostgreSQL 和 SQLite。
- 当前默认缓存为 LocMemCache。

### 6.2 技术栈

| 层次 | 当前技术 | 说明 |
|---|---|---|
| 开发语言 | Python | 后端语言 |
| Web 框架 | Django 4.1 | 当前依赖锁定版本 |
| 页面 | Django Template + 原生 JavaScript | 无独立前端构建工程 |
| API | Django View + JsonResponse | API v1 |
| 管理后台 | Django Admin + django-simpleui | 管理与基础配置 |
| 认证授权 | Django User / Session / Group / Permission + 员工任职授权模型 | 新旧身份渐进迁移 |
| 数据库 | MySQL 默认 | 支持 PostgreSQL / SQLite 配置 |
| 缓存 | LocMemCache | 当前默认本地内存缓存 |
| 静态资源 | Django staticfiles | 当前使用项目静态目录 |
| 测试 | Django TestCase / GitHub Actions | CI 结果以实际运行记录为准 |

当前没有引入 Django REST Framework、Next.js、React、Vue、Celery、Redis、消息队列或微服务。不得将这些技术写成当前架构组成。

### 6.3 Django App 模块划分

| 模块 | 职责 | 关键实体/内容 |
|---|---|---|
| apps.core | 物业主数据和请求物业上下文 | Property |
| apps.identity | 员工档案、物业任职和岗位授权 | StaffProfile、PropertyStaffMembership、StaffRoleAssignment |
| apps.guests | 住客档案 | Guest |
| apps.inventory | 房型、客房、房价计划、每日价格、日库存 | RoomType、Room、RatePlan、DailyRate、RoomTypeInventory |
| apps.reservations | 预订合同、预订明细和实际履约 | Reservation、ReservationRoom、Stay |
| apps.billing | 账单、支付流水和账本 | Folio、Payment、LedgerEntry |
| apps.api | API 路由、参数校验和 JSON 响应 | API v1、OpenAPI JSON |
| hotelapp | 历史系统与兼容层 | 尚未迁移的历史页面和模型 |
| hotel | Django 项目配置和根路由 | settings、urls、ASGI/WSGI |

### 6.4 依赖方向

推荐依赖方向：表现层 → API/应用服务 → 领域模块 → ORM/数据库。

约束：
- 模板不得直接执行关键业务写操作。
- 跨模块写操作调用领域服务。
- 库存锁定、预订创建和账本写入必须在服务层统一处理。
- API 只负责输入校验、调用服务和组织响应，不复制业务规则。
- 历史兼容层逐步迁移，不在单次改动中推翻全部旧代码。

## 7. 核心数据模型与关系

### 7.1 物业和员工

- Property：酒店物业。
- StaffProfile：员工自然人档案。
- PropertyStaffMembership：员工与物业之间的任职关系。
- StaffRoleAssignment：任职对应的岗位授权。
- Django User：登录身份。

### 7.2 住客、房型和库存

- Guest：住客档案，按物业和规范化联系电话去重。
- RoomType：销售房型。
- Room：物理客房，分别记录占用、清洁和维修状态。
- RatePlan：房价计划。
- DailyRate：房型/房价计划/住宿日期的每日价格。
- RoomTypeInventory：房型/住宿日期的销售库存。

### 7.3 预订和履约

- Reservation：预订主单，记录预订意图、日期、房间数、金额、幂等信息和 Hold 截止时间。
- ReservationRoom：每间房的预订明细和逐晚价格快照。
- Stay：实际入住履约记录。

### 7.4 账务

- Folio：账单容器。
- Payment：支付渠道流水。
- LedgerEntry：账本凭证，记录金额方向、业务日期、唯一 reference 和冲销关联信息。

### 7.5 关键关系（逻辑关系）

- 一个 Property 拥有多种 RoomType、Room、Guest、Reservation 和日库存记录。
- 一个 StaffProfile 可对应多个物业任职记录。
- 一个任职记录可拥有多个岗位授权。
- 一个 Reservation 包含一条或多条 ReservationRoom。
- ReservationRoom 可对应实际 Stay。
- Reservation 对应 Folio。
- Folio 关联多个 LedgerEntry 和 Payment。

具体字段、索引、唯一约束和外键以 Django Model 与数据库迁移文件为准；本文不替代模型定义。

## 9. 核心业务流程

### 9.1 顾客预订流程

1. 顾客打开 /reserve/。
2. 选择入住日期、离店日期、房型和房间数量。
3. 页面请求可订查询 API。
4. 后端逐住宿日检查价格和库存。
5. 顾客提交预订。
6. 后端在事务中锁定每日库存并创建 Reservation、ReservationRoom 和 Folio。
7. 库存进入 Hold 状态，默认 15 分钟。
8. dev/test 环境可创建 Mock Payment 并演示签名回调。
9. 回调通过验签和幂等检查后，Held 转 Sold，预订确认。
10. 顾客通过预订编号和联系电话查询订单。

### 9.2 预订取消与 Hold 释放

- 当前自助取消只针对待支付预订。
- 取消操作必须释放对应住宿日的 Hold。
- 过期 Hold 通过管理命令释放。
- 支付失败后暂不立即释放，等待支付期限到期，降低迟到回调与库存重新售卖之间的竞态风险。
- 已确认订单取消和退款需先定义政策及账务冲销流程，不在当前开放。

### 9.3 未来入住到退房流程（待完成迁移）

已确认预订 → 前台核验 → 分配物理客房 → 创建 Stay → 住中消费进入 Folio/LedgerEntry → 退房结算 → 收款/退款/结清 → 结束 Stay → 房间转脏房 → 清洁检查 → 恢复净房。

该流程是后续既定迁移目标，不代表当前页面和全部节点已经接入新模型。

## 11. 非功能需求

### 11.1 安全

- 生产环境必须关闭 DEBUG。
- 生产环境必须显式配置高强度 Django Secret Key。
- ALLOWED_HOSTS 应限制为实际域名。
- 使用 HTTPS，并按部署拓扑配置安全 Cookie、CSRF 和反向代理。
- 数据库账号遵循最小权限原则。
- 不得将真实密码、Token、证书和密钥提交到代码仓库。
- 顾客订单查询必须做身份信息核验。
- 敏感员工操作和财务操作需要审计记录。
- 身份证件信息如未来采集，必须另行完成加密、脱敏、访问控制和留存策略评审。

### 11.2 数据一致性

- 预订、库存、支付状态和账本写入应具备事务边界。
- 关键唯一性和关联完整性尽量由数据库约束兜底。
- 并发预订必须锁定库存行。
- 账本凭证禁止常规更新/删除。
- SQLite 测试不能替代 MySQL/PostgreSQL 的事务锁和并发验证。

### 11.3 可维护性

- 按业务域组织 Django App。
- 领域服务集中封装关键业务写操作。
- 页面、API、领域服务和模型职责分离。
- 新旧系统迁移保持小步、可回归。
- 文档与代码同一 PR 更新。

### 11.4 可用性与易用性

- 页面应明确展示加载中、无数据、无房、提交成功和失败原因。
- 所有可见按钮和控件必须具备真实行为。
- 防止重复提交。
- 桌面和窄屏页面均应可操作。
- 表单错误应指向具体字段或业务原因。

### 11.5 性能与扩展

- 当前按单体应用和单物业规模设计。
- 查询应使用必要索引，避免无边界扫描。
- 预订库存操作应尽量缩短事务时间。
- 当前 LocMemCache 适用于本地开发，不作为多实例共享缓存方案。
- 未来部署拓扑发生变化时，再评估共享缓存、任务调度和横向扩展方案；不得将尚未引入的 Redis/Celery 描述为现有依赖。

## 13. 测试与验收标准

### 13.1 基础质量门禁

~~~powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
~~~

### 13.2 业务验收

| 编号 | 验收场景 | 预期结果 |
|---|---|---|
| AC-01 | 跨多晚查询价格 | 每个住宿日晚价格正确汇总，离店日不计价 |
| AC-02 | 价格缺失 | 不允许创建缺少任一晚价格的预订 |
| AC-03 | 任一晚库存不足 | 整个预订事务回滚，不遗留部分 Hold |
| AC-04 | 并发预订 | 库存行锁保证不会超卖；需在真实 MySQL/PostgreSQL 环境验证 |
| AC-05 | 相同幂等键和相同请求 | 返回同一预订结果，不重复占用库存 |
| AC-06 | 相同幂等键和不同请求 | 返回冲突，不覆盖原请求 |
| AC-07 | 重复支付回调 | 只发生一次状态转换和 PAYMENT 账本入账 |
| AC-08 | HMAC 或金额不匹配 | 拒绝回调，不确认订单、不写成功账本 |
| AC-09 | Hold 超时 | 释放全部住宿日对应 Hold |
| AC-10 | 住客手机号复用 | 同一物业复用既有 Guest 档案 |
| AC-11 | 订单查询 | 预订编号与联系电话必须匹配 |
| AC-12 | 账本纠错 | 使用反向凭证，不直接覆盖或删除原凭证 |
| AC-13 | 生产环境 Mock | 不展示模拟支付，不允许模拟回调 |
| AC-14 | 静态资源 | 页面 CSS/JS 返回成功，页面布局和交互正常 |
| AC-15 | 权限边界 | 未授权岗位、失效任职或跨物业访问被拒绝 |

### 13.3 测试环境说明

- Django TestCase 和 SQLite CI 可用于快速回归。
- 真实 MySQL/PostgreSQL 需要补充事务锁、并发、隔离级别验证。
- UI 变更必须在真实运行环境验收，不得使用旧截图冒充新页面。
- 测试结果应记录实际命令、结果和未覆盖风险。

## 16. 风险与注意事项

1. **新旧模型并存：** 历史 hotelapp 页面可能仍读写旧模型，迁移时必须识别数据来源，避免双写和状态不一致。
2. **数据库差异：** SQLite 的锁行为与 MySQL/PostgreSQL 不同，不能替代真实数据库并发验收。
3. **库存竞态：** 预订与支付回调之间存在时间窗口，必须依赖事务、状态机和幂等控制。
4. **财务可追溯性：** 禁止通过直接修改账本历史来修正错误。
5. **权限串店：** 物业上下文必须参与数据访问和授权判断。
6. **静态资源：** 页面 HTML 正常不代表 CSS/JS 正常，必须单独检查静态资源 HTTP 状态。
7. **安全配置：** 本地开发配置不能直接复制到生产环境。
8. **功能边界：** 第三方系统和未确定的业务流程不得提前做成假功能。

## 17. 结论

PMS 2.0.1 的核心目标是以当前 Django 模块化单体为基础，稳步完成单体酒店的预订、库存、履约和账务核心能力，并逐步迁移历史员工后台。系统以数据一致性、权限隔离、账务可追溯和渐进式迁移为主要技术原则。

当前 Phase 1 + Phase 2 已建立平台、员工身份基础、住客、房型房间、房价库存、预订、账务模型、API v1 和顾客端新预订页面；完整入住/退房、清洁、夜审、财务报表和员工后台全面迁移仍需后续完成。

本文作为 PMS 2.0.1 的需求与技术架构基线。后续实现、测试、文档和版本说明均应以真实代码和验收结果为准，不得将规划状态替代交付状态。
