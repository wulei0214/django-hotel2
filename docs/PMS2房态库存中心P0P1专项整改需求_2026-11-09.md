# PMS2 房态与库存中心 P0/P1 专项整改需求（2026-11-09）

> 目标：确保房型逐日可售量、Hold、订单占用、维修停房与房间履约状态一致，防止超卖和错误释放。先复用现有 RoomTypeInventory、InventoryHold、Room、RoomType、Reservation/ReservationRoom 等模型和服务，不重复建设。

## 1. 当前代码基础与盘点要求

项目已有 RoomTypeInventory（含 version 乐观锁字段）和 InventoryHold 等基础结构。实施前必须检查所有写入入口是否都经过统一库存领域服务、version 是否在所有路径参与条件更新、过期任务是否可靠、预订多房间/多日期是否原子占用。不能因字段存在就认定并发安全已完成。

## 2. 库存权威口径

按 Property + RoomType + stay_date（日粒度）核算。建议明确以下互斥口径：
- physical_rooms：该物业该房型纳入库存管理的物理房间数；
- out_of_order_rooms：维修/停用房间，不可售；
- closed_for_sale_rooms：人工停售数量（不得与维修停房重复）；
- confirmed_rooms：已确认且覆盖该住宿日的订单占用；
- active_held_rooms：有效 Hold 占用；
- available_rooms：可售余量。

概念公式：
`available = physical_rooms - out_of_order_rooms - closed_for_sale_rooms - confirmed_rooms - active_held_rooms`

必须明确总库存是否已扣除维修/停售；同一房间同一日期不得重复进入多个扣减项。若当前模型使用 total_rooms 或其他计数口径，先写清映射，不得机械新增字段。所有数字由服务端事实计算，前端只读。

## 3. P0 并发防超卖

所有库存写入通过单一 InventoryService/现有等价服务。对每个 Property/RoomType/日期：
- 在同一事务中按稳定顺序锁定/条件更新库存行；
- 校验版本或剩余量；
- 创建逐日 Hold/确认占用；
- 更新 version；
- 使用唯一约束阻止同一业务对象重复占用；
- 多日期、多房间预订必须全量成功或整体回滚，禁止部分占用后确认整单。
SQLite 不提供与 MySQL 等价的行锁语义；MySQL 必须真实测试最后一间房并发、条件更新和锁冲突。

必须覆盖：最后一间房两请求竞争、同一请求重放、两员工同时改库存、两个支付回调、取消与支付竞争、日期变更、房间变更、部分入住/退房、夜审与库存调整。

## 4. InventoryHold 状态机和生命周期

状态迁移至少明确：
- ACTIVE → CONFIRMED；
- ACTIVE → RELEASED；
- ACTIVE → EXPIRED；
- ACTIVE → EXTENDED（或以事件记录延长而不把 EXTENDED 当独立状态，按现有模型统一）。

Hold 需记录创建来源、关联 Reservation/PaymentIntent、逐日库存项、expires_at、max_expires_at、extension_count、释放原因、确认时间和审计。一个 Hold 的逐日明细必须可追溯。已确认 Hold 永不被过期任务释放；已释放/过期 Hold 不可再次确认，除非通过新 Hold 流程。

支付渠道等待窗口由 D2 规则驱动。PENDING/PROCESSING 在渠道策略窗口内有限延长；UNKNOWN 先查询渠道；达到最大等待上限进入补偿/人工核查，不能直接把 UNKNOWN 当失败释放。渠道成功与过期任务竞争时只允许一个有效状态迁移。

## 5. 房态、维修和库存联动

Room 的物理履约状态与房型库存可售状态不是同一个概念。维修/停房、人工停售、净房状态、在住房态必须保留各自语义。联动规则：
- 维修开始：校验当前占用/未来订单，按政策拒绝、调房或升级处理；只有确认不冲突才减少对应日期库存。
- 维修结束：完成检查/放行后恢复可售；不能仅把 Room.status 改回可用而漏恢复库存。
- 人工停售：按日期范围生效、记录原因和操作者；解除停售有审计。
- 换房：同事务或可靠补偿地释放旧房间占用并占用新房间，失败整体回滚/可恢复。
- 延住：先校验新增日期，再延长占用；失败不得部分延住。
- 提前退房/No-show：按已确认业务政策和营业日边界释放未来库存，不能以简单改状态代替。
- 多房预订、分房、分段入住：逐房逐日记录占用来源。

## 6. D4 库存对账与人工修复

定时扫描库存事实，生成 InventoryReconciliationRun/差异记录（可复用已有对账结构）。每条差异需保存物业、房型、日期、当前计数、重算计数、差额、关联订单/Hold/维修记录、版本和计算时间。

系统自动发现、分类、生成建议；不得自动覆盖 RoomTypeInventory。人工修复流程：
1. 生成差异报告和影响范围。
2. 授权人员发起修复申请，填写原因和证据。
3. 独立审批，申请人不得自批。
4. 执行前重新计算，version 不匹配则要求重新审批。
5. 通过统一服务在事务内修复并写审计。
6. 立即再次核对，未归零则保持异常并升级处理。

## 7. API、页面与权限

按现有 API 结构盘点后补充库存日历、Hold 详情、差异报告、修复申请/审批/执行、维修联动诊断。所有写操作校验 Property、日期范围、房型、角色权限、原因、幂等键和版本。页面展示物理总量、维修停用、停售、确认占用、有效 Hold、可售余量及更新时间；差异页提供只读明细与审批操作，不允许前端直接改权威计数。

## 8. P0/P1 验收

P0：最后一间房并发不超卖；多日期多房原子性；支付成功/过期/取消竞态；已确认 Hold 不释放；重复请求幂等；所有写入口版本/锁一致；MySQL 双事务并发测试。

P1：维修开始/结束联动、停售恢复、房间换房、延住、No-show、提前退房、库存差异扫描、人工审批修复、修复后对账、告警与审计。

测试必须包含 SQLite 业务逻辑与事务回滚，以及 MySQL InnoDB 并发/行锁/唯一约束真实测试。对账修复测试必须证明旧版本修复被拒绝、无审批不能执行、失败回滚不改变库存。
