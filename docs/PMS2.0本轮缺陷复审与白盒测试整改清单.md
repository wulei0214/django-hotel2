## 1. 本轮结论

本轮根据用户提供的 10 类缺陷描述和截图，对当前 main 进行了代码入口、模板脚本、API、服务调用、路由和已有测试的静态白盒检查，并对可以明确定位的问题实施了第一批修复。

**已提交的明确修复：**
- 通知、清洁维修、夜审、财务页面改为从页面内 Django CSRF 隐藏字段读取令牌，不再错误依赖 csrftoken Cookie。
- 财务收款、退款、冲销表单先读取字段值再替换 DOM，修复表单节点已移除后继续读取 .value 的空引用异常。
- 夜审页面 DOM 工具函数支持追加真实 DOM 子节点，修复表格出现 [object HTMLTableCellElement]；API 对 HTML/非 JSON 错误页显示 HTTP 状态和登录/CSRF/服务端排查提示，重开日期下拉不再静默吞错。
- 主界面预约预警限制最多 10 条，排序改为最近入住日期优先。
- 移除侧栏历史页面中的旧“客房管理”入口，并将旧 /show_room/ URL 兼容跳转到 PMS2 /manage/rooms/。
- 员工操作抽屉、通用管理抽屉、财务、清洁维修、夜审和审计详情中的键值表标签统一左对齐，其他布局规则保持不变。
- 前台账单抽屉把负数账本余额解释为“客人预存款”，正数显示“待收余额”，零显示“已结清”；不修改账本带符号金额。
- 修复前台多 Folio 摘要覆盖问题：按预订汇总所有 OPEN Folio，排除 CLOSED/VOIDED，MASTER Folio 单独决定收款表单状态；检测跨币种账单并提示人工核对。
- 前台详情抽屉明确区分预订状态和每间房实际入住状态；增加 Session CSRF 正确令牌成功、错误令牌 403 的自动化测试，以及多 Folio 汇总测试。
- 审计中心增加中文操作类型和实体名称，系统操作人显示为“系统”，员工操作人显示姓名（登录账号）；变更前/变更后 JSON 的常见字段名增加中文显示映射，并补充 API 回归断言。

**尚未完成最终验收的重点：**
- 分页页码跳转与每模块 page_size 选择尚未统一完成。
- 预订状态、Stay 入住状态、账单凭证和抽屉刷新需要使用真实数据库数据进行端到端核对。
- 维修登记修复 CSRF 后，仍须用九角色分别验证 hotelapp.no_show_handle 权限边界，不能将 403 一概视为 CSRF。
- 夜审重开申请接口和无已关账营业日场景需运行态验证。
- 截图中财务金额、账单来源、MOCK 支付和业务日归属需查明真实数据链路，不能只靠前端格式调整。
- 本文不宣称浏览器 E2E、Apifox、MySQL 生产配置或用户本地数据库验收已经完成。

## 3. 已提交修复明细

### 3.1 Session CSRF 令牌

受影响页面：
- templates/pms/notification_center.html
- templates/pms/housekeeping_center.html
- templates/pms/night_audit_center.html
- templates/pms/billing_center.html

修复原则：
1. 页面通过 {% csrf_token %} 渲染当前请求的隐藏令牌。
2. 页面 POST 请求从 input[name="csrfmiddlewaretoken"] 读取令牌。
3. 不再假设浏览器一定存在可读的 csrftoken Cookie。
4. CSRF 仍由 Django 中间件验证，不关闭 CSRF、不增加豁免、不放宽权限。

### 3.2 财务表单空引用

文件：templates/pms/billing_center.html

原问题：收款、退款、冲销提交时先执行 form.replaceWith(note)，后续再调用 document.getElementById(...).value。原表单节点已经离开文档，查询结果为 null。

修复：在替换表单之前，将金额、方式、参考号、退款原因、冲销原因读取到局部变量，再替换表单并提交已读取的值。不改变后端 BillingService、审批、冲销和幂等规则。

### 3.3 夜审 DOM 子节点

文件：templates/pms/night_audit_center.html

修复 DOM helper：传入文本时设置 textContent；传入真实 Node 时使用 appendChild。避免把 DOM 元素强制转换为字符串。

### 3.4 预约预警和旧客房入口

- apps/api/dashboard.py：预约预警最多 10 条，按 -check_in,-id 取最近记录。
- templates/_sidebar.html：移除历史页面中的旧“客房管理”入口。
- hotel/urls.py：旧 /show_room/ 兼容跳转到 /manage/rooms/。
- 新入口仍由 /manage/rooms/ 页面权限和 API 权限控制；兼容跳转不是授权绕过。

### 3.5 账单余额展示语义

文件：static/js/frontdesk.js、static/css/frontdesk.css

账本仍使用带符号口径：
- 正数 LedgerEntry：增加应收。
- 负数 LedgerEntry：支付、抵扣或其他贷方事实。
- balance = SUM(LedgerEntry.amount)。

前台抽屉现在按业务含义显示：
- balance > 0：待收余额。
- balance < 0：客人预存款（显示绝对值，不以欠款红色标记）。
- balance = 0：已结清。

注意：这只修正显示语义，不代表截图中的 34,144.00 或用户提及的 3,728.00 已经对账正确。若存在“已收款但没有对应应收/押金业务事实”、重复入账、错误 Folio 关联或 MOCK 支付进入非测试环境，必须继续追查源数据和服务层。

### 3.6 审计中文显示

文件：apps/api/audit_center.py、templates/pms/audit_center.html、apps/api/test_audit_center.py

新增 action_label、entity_type_label；原始 action、entity_type 保留供筛选和追溯。系统操作人展示为“系统”。before/after 详情继续只在有审计查看权限的详情 API 返回；前端将常见字段键映射为中文，不改变原始审计数据，不重写历史 JSON。

## 4. 必须继续完成的白盒复审

### 4.1 预订、入住与账单数据闭环（P0）

按同一预订编号追踪以下对象和数据，不允许仅检查页面金额：

1. Reservation：订单状态、总金额、币种、入住/离店日期。
2. ReservationRoom：每间房明细、房型、分配房间、房间日期金额。
3. Stay：实际入住状态、办理入住/退房时间。
4. StayRoomSegment：换房历史和房间占用区间。
5. Folio：账单归属、账单状态、币种、预订关联。
6. LedgerEntry：每一笔应收、支付、押金、退款、冲销的正负方向、凭证引用、营业日。
7. Payment / Refund：支付状态、MOCK/真实渠道标记、幂等引用、退款审批和执行状态。
8. ChargeLine / TaxLine：房费、税费与 LedgerEntry 是否一一匹配，避免重复或遗漏。

必须回答：
- 3,728.00（或截图金额）是哪一笔业务事实，是否只存在 Payment 而缺少 LedgerEntry？
- 是否把押金错误合并进普通账单？
- 是否在预订确认时就生成收款凭证，还是入住/夜审时才生成房费？
- Reservation.status=CONFIRMED 是否被误当作 Stay.status=IN_HOUSE？
- 前台抽屉、预订与入住中心、财务中心是否读取同一 Folio 和同一套账本口径？
- 收款/押金/退款/冲销后，抽屉是否重新请求服务端最新详情，而不是仅更新局部文本？
- MOCK 支付是否被严格限制在测试环境，生产环境是否拒绝模拟支付？

验收：账单明细逐笔相加等于汇总；应收、已收/抵扣、待收余额/预存款的符号和含义明确；跨页面同一预订数据一致；重放同一幂等请求不重复入账。

### 4.2 维修登记与九角色权限（P0）

- 前端按钮显隐不构成授权。
- API housekeeping_maintenance_change 和领域服务均需复核物业、用户任职、专项权限。
- 当前维修登记使用 hotelapp.no_show_handle，其高风险影响房间可售库存，不能为了消除 403 而改成普通查看权限。
- 用九角色账号分别验证：允许的角色成功；不允许的角色 403；跨物业房间 404；缺少原因 400；非法状态 400；状态幂等重放不重复审计。
- 验证停用、恢复后房态中心、库存可售数、前台可分配房间和审计记录同步。

### 4.3 分页标准（P1）

后端统一契约：
- page 默认 1。
- page_size 默认 20，最大 100。
- 非整数、空值、0、负数、超过最大值均返回 400。
- 列表稳定排序必须包含主键兜底。

前端待统一：
- 提供首页、上一页、页码按钮、下一页、末页；页数较多时显示省略号。
- 当前页高亮；不可用操作 disabled；跳页后保留筛选条件。
- 每个列表显示总条数、当前页/总页数。
- 允许选择每页 20/50/100 条（低密度或特殊列表可限制选项，但必须在模块规范中说明）。
- 修改 page_size 后回到第 1 页；筛选变化后回到第 1 页；删除/销项后若当前页为空则回退上一页。
- 不允许前端把当前已加载的局部数据伪装成总分页。

建议模块默认值（待产品冻结）：

| 模块/列表 | 默认 page_size | 可选 page_size | 说明 |
|---|---:|---|---|
| 通知与待办 | 20 | 20/50/100 | 未读/类别筛选后保持条件 |
| 前台预订/抵店/离店/在住 | 20 | 20/50/100 | 当前页面已有选择器，补齐页码跳转 |
| 清洁与维修房间 | 50 | 20/50/100 | 房间卡片视图，默认 50 |
| 财务账单/流水/收款/退款 | 20 | 20/50/100 | 账务列表默认 20，限制日期范围 |
| 营业日历 | 10 | 10/20/50 | 营业日低频记录 |
| 夜审运行/紧急重开记录 | 20 | 20/50/100 | 运行历史与审计记录 |
| 审计事件 | 20 | 20/50/100 | 大数据量时必须结合日期范围 |
| 员工/客人/会员/房态 | 20 | 20/50/100 | 详情抽屉独立加载，不随主列表全量加载 |

所有列表接口的服务端最大值仍以统一契约 100 为上限；页面可提供更小的选项。

### 4.4 页面与路由统一（P1）

- /show_room/ 仅作为兼容跳转，不再提供独立旧页面。
- 全量扫描侧栏、首页快捷入口、前台工作台卡片、页面内部返回链接、模板硬编码链接和 API 返回的 link。
- 每个业务操作必须指向 PMS2 正式工作台；只读历史数据可以进入明确标注的历史只读视图。
- 不允许同一业务保留两个可写入口；不允许 PMS2 页面通过旧页面完成写操作。
- 本轮仅处理了旧客房管理入口；其他旧路由退役仍需逐项核对，不能推断已全部清理。

### 4.5 审计中心（P1）

- 操作类型、实体类型、操作人、实体 ID、时间、原因、请求链路统一展示。
- 展示中文标签时保留原始代码，便于开发排障与证据追溯。
- before/after 必须并排、可折叠/滚动、格式化；字段键中文化，未知键保留原始名称。
- 无 before/after 时明确显示“无变更前数据/无变更后数据”，不能显示空对象造成误解。
- 审计列表不得回传 before/after；详情权限、物业隔离和 PII 脱敏继续有效。
- 补齐实际数据库中出现过的 action/entity 字典；未知动作显示“其他操作（原始代码）”，不得伪造翻译。

### 4.6 夜审和财务表单（P0/P1）

- 夜审：预览、阻挡原因、执行、营业日重开申请、双人审批、break-glass、事后复核全部按角色和状态测试。
- 夜审所有 API 错误应解析 JSON 错误封套；如果服务端返回 HTML，前端应显示 HTTP 状态和“服务器返回非 JSON”提示，不得把浏览器 JSON 解析异常当成业务错误。
- 财务：收款、退款、冲销、审批、执行失败、幂等重放、权限拒绝和余额回算全部测试。
- 表单：提交中防重复、字段保留、服务端校验错误就近显示；失败不能丢失已填写内容。

## 5. 白盒测试矩阵

| 测试层级 | 必测内容 | 通过标准 |

| 回归测试 | 九角色、11 个中心、关键旧入口 | 不引入权限回退或旧新业务双入口 |
