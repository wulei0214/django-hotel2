# PMS2 三大系统入口与后台管理界面整合设计方案

- 文档状态：实施基线
- 适用分支：`main`
- 基线提交：`fd4c209aa0b61e925f60aa3a502f932bf70e6121`
- 方案范围：入口整合、导航调整、平台首页与环境信息页视觉优化
- 身份域原则：平台治理、PMS 业务、Django Admin 数据维护相互隔离

## 1. 目标与非目标

### 1.1 目标

1. 对外保持三个系统入口：客人预约、PMS 员工前台、平台管理。
2. 平台管理作为平台超管专用治理门户，统一承载权限矩阵、运行与安全信息及数据维护入口。
3. 明确 Django Admin 的定位为“数据维护（Django Admin）”，不与平台治理混为一谈。
4. 优化平台首页、权限矩阵外围布局、环境信息页的视觉层次与响应式表现。
5. 移除 PMS 业务侧栏中的平台权限导航泄漏。
6. 平台首页可提供预约页和 PMS 登录页的跨入口链接，但不授予或传递业务身份。

### 1.2 非目标

- 不新增业务功能、业务页面或第四个顶层入口。
- 不改变登录认证、平台门禁、PMS 任职与角色授权逻辑。
- 不修改数据库结构、权限数据、角色注册表、权限矩阵保存逻辑。
- 不将 Django Admin 包装成员工工作台。
- 不开放审计记录卡片；待 AuditEvent 的 Admin 注册、字段脱敏和访问边界另行确认。
- 不在本轮改造 Session 后端、登录流程或 Cookie 安全策略。

## 2. 三个入口与身份域映射

| 入口 | 路径 | 使用者 | 身份域 | 主要职责 |
|---|---|---|---|---|
| 客人预约 | `/reserve/` | 客人 | 公开访问/现有订单访问机制 | 预约与公开预订流程 |
| PMS 前台 | `/login/` | 酒店员工 | PMS Session（`sessionid`） | 预订、入住、房态、住客、收银等 |
| 平台管理 | `/platform/` | 平台超管 | Admin Session（`admin_sessionid`） | 平台治理与管理入口 |

### 2.1 授权不变量

- 平台管理员必须满足现有平台门禁要求：`is_active=True`、`is_superuser=True`、`is_staff=True`。
- 平台超管不因平台身份自动获得 PMS 业务权限；进入 PMS 业务仍须具备有效任职和岗位授权。
- PMS 员工不因店长、经理等业务角色获得平台管理权限。
- 未登录访问平台页面按现有规则跳转 `/admin/login/`；已登录非超管返回 403；半状态超管返回 403 并记录安全审计。
- 不修改 `apps/identity/platform.py` 的平台门禁行为。

### 2.2 跨入口行为

平台首页可以链接至 `/reserve/` 和 `/login/`。这些链接只负责导航：
- 预约页按公开访问规则运行，不依赖平台身份。
- PMS 登录页按 PMS 认证与任职规则运行。
- 点击链接不会执行登录、身份转换、任职创建或角色授予。
- PMS 员工点击平台管理链接（若未来从独立入口提供）仍须通过平台门禁；无平台身份跳转平台登录页，已登录非超管 403。
- 平台超管进入 PMS 页面时仍须走 PMS 登录/任职授权流程；无有效任职时按 PMS 现有规则拒绝访问。

### 2.3 Cookie 传输边界说明

当前项目通过 `SplitSessionMiddleware` 按路径选择会话 Cookie：平台路径读取 `admin_sessionid`，PMS 路径读取 `sessionid`。这是认证读取隔离，不等同于浏览器网络层 Cookie 传输隔离。

当前平台路由同时包含 `/platform/*` 与 `/admin/*`，单个 Cookie 的 Path 无法同时精确覆盖这两个互不嵌套的路径前缀。若平台 Cookie Path 仍为 `/`，浏览器访问 PMS 页面时可能仍会发送 `admin_sessionid`，但 PMS 中间件不读取它。

本轮不修改认证与 Session 机制，因此不得宣称已经实现“HTTP 请求中完全不携带另一域 Cookie”。该项列为独立安全技术债：后续需在独立域名，或经专项设计验证的双 Path Cookie/会话轮换与登出清理方案中解决。不得通过简单改 Cookie Path 破坏 `/admin/` 或 `/platform/` 登录。

## 3. 信息架构

### 3.1 顶层

- `/reserve/`：客人预约。
- `/login/`：PMS 员工登录，登录后进入 PMS 业务页面。
- `/platform/`：平台管理门户，仅平台超管可访问。

不新建公开三入口总览页，避免形成第四个入口。

### 3.2 平台管理首页 `/platform/`

页面标题统一为“平台管理”。首页采用简洁卡片布局：

1. **权限与角色** → `/platform/permissions/`
2. **平台运行与安全** → `/platform/system/`
3. **数据维护（Django Admin）** → `/admin/`
4. **审计记录** → 本轮暂缓，不展示可点击卡片；待确认 Admin 注册、权限和敏感字段边界后再纳入。

首页底部仅保留一行身份边界提示。另提供“客人预约”和“PMS 员工登录”跨入口链接。

### 3.3 权限矩阵 `/platform/permissions/`

- 保留独立路由和现有保存逻辑。
- 本轮只优化外围页面布局、角色选择可读性、矩阵分组视觉和移动端横向滚动体验。
- 不接入新的注册表，不改变权限白名单，不引入未实现的 Diff、版本、审批或保存能力描述。
- 保存反馈沿用当前真实消息和重定向行为。

### 3.4 平台运行与安全 `/platform/system/`

按四组展示：

- **部署**：平台版本、运行模式、时区、系统语言。
- **运行**：DEBUG 状态。
- **安全**：HTTPS/安全 Cookie/CSRF 配置状态（只展示实际可读取的配置，不声称服务端探测结果）。
- **会话**：会话有效期、浏览器关闭过期策略、CSRF 是否存于 Session。

生产环境不展示 API 基址、Cookie 名称、默认物业编码。为减少内部配置暴露，本轮环境页统一不展示 API 基址、Cookie 名称和默认物业编码。DEBUG 开启使用明确红色风险状态；DEBUG 关闭显示正常状态。不得展示员工姓名、账号、工号、手机号等 PII。

### 3.5 PMS 个人页 `/system/`

保持现有 PMS Session 页面，只展示当前员工本人账号、任职、角色、会话相关个人信息及密码修改入口。不得放入平台环境信息或平台管理导航。

### 3.6 Django Admin `/admin/`

- 路由保持不变。
- 平台首页统一命名为“数据维护（Django Admin）”。
- 它是平台数据维护入口，不是员工业务工作台，也不是权限矩阵的替代品。

## 4. 路由兼容

本轮保持以下路由及行为不变：

| 路由 | 处理要求 |
|---|---|
| `/reserve/` | 保持公开预约页 |
| `/login/` | 保持 PMS 员工登录 |
| `/platform/` | 保持平台首页 |
| `/platform/permissions/` | 保持权限矩阵 |
| `/platform/system/` | 保持平台环境信息 |
| `/permissions/` | 保持 302 到 `/platform/permissions/` |
| `/permissions/save/` | 保持现有兼容重定向 |
| `/system/` | 保持 PMS 员工个人页 |
| `/admin/` | 保持 Django Admin |

不删除旧路由、不改变 URL 名称、不调整平台门禁中间件路径判定。

## 6. 视觉规范

### 6.1 布局与网格

- 桌面内容区域使用自适应网格，卡片最小宽度约 280px，间距 20–24px。
- 页面最大内容宽度建议 1440px；宽屏下卡片网格充分利用可用宽度，不集中挤在左上角。
- 页面主体左右留白 24–32px，内容区顶部间距 28–36px。
- 环境信息使用 2×2 或自适应卡片分组，不使用两张超宽信息卡承载所有配置。
- 权限矩阵保留表格语义；窄屏允许矩阵容器横向滚动，不压缩到不可读。

### 6.2 字体与间距

- 页面主标题 22–26px，分组标题 15–17px，正文 14px，辅助说明 12–13px。
- 卡片内边距 20–24px；标题与说明间距 8–12px。
- 避免大段身份解释，边界说明保持一行或短提示。

### 6.3 状态色

- 正常：中性/绿色状态。
- DEBUG 开启、HTTPS 不安全等风险：红色风险状态，配文字说明，不只依赖颜色。
- 未知/未配置：灰色或琥珀色提示，不得误标为正常。
- 不用状态色装饰普通导航或标题。

### 6.4 空状态与错误状态

- 没有可展示状态时明确显示“暂无可展示信息”，不伪造运行健康检查结果。
- 权限矩阵无角色/权限数据时显示空状态，不能静默显示全无权限。
- 403 页面保持系统统一错误语义，不暴露用户枚举或身份升级提示。

### 6.5 响应式

- ≥1200px：三列首页卡片；环境信息最多两列。
- 768–1199px：两列卡片。
- <768px：单列卡片，顶部导航可换行或折叠，账号信息不挤压导航。
- 权限矩阵在移动端横向滚动，表头和复选框仍可操作。
- 不允许页面产生横向整体溢出（矩阵局部滚动除外）。

## 7. 身份边界与登出行为

- `/platform/*` 和 `/admin/*` 保持 Admin Session 读取。
- PMS 页面继续只读取 PMS Session。
- PMS logout 不得清除平台 Session；Admin logout 不得清除 PMS Session。
- 平台首页的 `/reserve/`、`/login/` 链接仅为普通导航，不复制会话、不触发登录或角色授予。
- 平台超管无 PMS 任职时访问 PMS 受保护页面，按现有 PMS 门禁拒绝；不得自动创建任职。
- PMS 员工访问平台管理，按平台门禁跳转平台登录或返回 403；不得以 PMS 角色放行。
- 浏览器 Cookie 网络层是否向另一路径发送 `admin_sessionid`，与 Django 中间件是否读取是两个不同问题。当前共享主机名和两个不相邻路径前缀时，Cookie Path 无法用单个值同时精确限定两处。该限制必须在验收报告中如实注明，不能声称传输层完全隔离。

## 8. 验收标准

### 8.1 入口与路由

- [ ] 顶层业务入口保持预约、PMS 前台、平台管理三类，不新增第四入口。
- [ ] 平台门户名称统一为“平台管理”。
- [ ] Django Admin 的展示名称统一为“数据维护（Django Admin）”。
- [ ] 上述既有 URL 均可访问，旧 `/permissions/` 仍按原行为 302。
- [ ] PMS 侧栏不再出现“权限管理”或其他平台治理导航。

### 8.2 身份边界

- [ ] 匿名访问平台页面跳转 `/admin/login/`。
- [ ] 已登录非超管访问平台页面返回 403。
- [ ] 半状态超管访问平台页面返回 403 并产生安全审计。
- [ ] 平台超管无 PMS 任职时不能进入受保护 PMS 业务页面。
- [ ] PMS 员工不能访问平台治理页面。
- [ ] PMS 登出与 Admin 登出互不影响。
- [ ] 首页跨入口链接不执行身份转换或权限授予。
- [ ] Cookie 是否在网络层跨路径发送的限制有明确测试记录，不将认证读取隔离误报为传输隔离。

### 8.3 页面质量

- [ ] 首页宽屏卡片合理铺开，无大面积空白。
- [ ] 环境信息按部署、运行、安全、会话分组。
- [ ] 生产环境不展示 API 基址、Cookie 名称、默认物业编码。
- [ ] DEBUG 开启显示红色风险状态。
- [ ] 平台环境页不含员工 PII。
- [ ] 768px 以下布局可用，矩阵局部横向滚动。
- [ ] 权限矩阵保存逻辑和权限结果与改造前一致。

### 8.4 测试要求

至少运行现有平台身份测试、模板渲染测试、路由兼容测试和相关全量测试。记录实际命令、结果、失败项；未运行的测试不得标记通过。

## 9. 实施顺序

1. 平台首页与平台导航：统一命名、卡片与跨入口链接；PMS 侧栏移除平台权限链接。
2. 环境信息页：四组展示、敏感配置隐藏、DEBUG 风险状态。
3. 权限矩阵视觉：只改外围布局与响应式，不改保存逻辑和权限数据。
4. 审计入口最后评估：完成 AuditEvent Admin 注册与字段授权审查后再决定是否开放。

## 10. 回滚策略

- 本轮优先限制在模板、CSS 和平台环境展示上下文。
- 不修改数据库、不迁移权限、不修改业务服务和平台门禁。
- 每个文件单独提交，出现问题可按文件提交回滚。
- 回滚后确认平台首页、权限矩阵、环境页和 PMS 个人页路由正常。
