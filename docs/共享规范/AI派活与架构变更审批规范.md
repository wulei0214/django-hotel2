# AI 派活与架构变更审批规范

> 依据：ARCHITECTURE.md（架构宪法）§11 多 AI 协作与任务流程、§12 架构重构实施门禁、修改等级表；治理 V1.1 §2/§7。
> 效力：专项规范，细化宪法而不冲突；宪法为最高约束。修订走宪法 §13 流程（记录原因、基线 SHA、影响文件、审批记录）。

## 1. AI 固定前置指令（派活时随任务下发）

```text
你正在参与 PMS 仓库 wulei0214/django-hotel2。

唯一代码基线：main 最新 commit SHA（开始前读取并记录完整 SHA）。
最高架构规范：仓库根目录 ARCHITECTURE.md（注意区分"当前事实 / 强制规则 / 目标态"三态）。

开始任务前必须阅读 ARCHITECTURE.md、相关需求/决策文档，
并检查现有 Model、Service、Selector/Query、View/API、权限、页面、迁移和测试。
先给出现状、复用判断、影响范围、实施计划和测试计划，再修改代码。

未经批准，禁止：
1. 重复创建已有核心 Model、Service、Selector、API 或业务入口；
2. 绕过现有权限、审计、事务和核心业务 Service；
3. 擅自修改数据库结构、API 契约或其他模块；
4. 擅自改变业务规则或删除历史入口；
5. 未运行测试就报告测试通过；
6. 通过跳过检查、删除测试或滥用 ignore 掩盖失败。
```

## 2. 派活任务模板（五段式）

派单人（人或 AI）下发任务时按此模板填写；受派 AI 对模板缺项应先追问再动代码。

```markdown
## 任务：<一句话目标>

### ① 上下文契约
- 基线：main@<完整 SHA>（开始前重新读取）
- 规范：ARCHITECTURE.md + 本规范 + <相关需求/决策文档路径>
- 相关现状：<涉及模块的 Model/Service/API/测试 清单或"自查后填写">

### ② 范围与边界
- 允许修改：<文件/模块白名单>
- 禁止修改：<文件/模块黑名单——默认含 ARCHITECTURE.md、mypy-baseline.txt、
  其他并行会话在途文件；legacy 入口退役须走 §3 审批>
- 修改等级：<L1/L2/L3/L4（见宪法修改等级表）→ 对应审批要求>

### ③ 实施计划
- 复用判断：<检索到的现有实现与复用/扩展决定；确需新增时说明旧实现为何不能复用>
- 步骤：<有序步骤，含迁移/契约更新顺序>

### ④ 验收标准与测试计划
- 测试先行：<新用例清单（正常/异常/边界/权限/并发/幂等），先写测试确认失败再实现>
- 必跑门禁：<manage.py check / makemigrations --check / ruff / black / mypy 基线 /
  目标模块测试 / 关联回归 /（涉双库差异时）SQLite+MySQL>

### ⑤ 交付要求
- 交付报告含：基线 SHA、修改文件、修改原因、架构影响、契约兼容、迁移情况、
  测试命令与真实结果（含退出状态与数量）、未覆盖项、遗留风险、提交 SHA。
```

## 3. 架构变更审批（L3/L4）

### 3.1 触发清单（达到即须事前审批，不得拆分任务规避）

- Model、字段、关系、唯一约束、Migration；
- 核心 Service/Selector/状态机/事务边界/锁顺序/幂等键语义；
- API 请求/响应契约、错误码、兼容策略（含"统一响应格式"类改造）；
- RBAC、数据范围、敏感字段、审计规则；
- 财务/账本/退款/冲账/安全机制；
- 公共组件、跨模块依赖、旧业务入口退役（含 hotelapp 路由）；
- ARCHITECTURE.md 与专项规范本身。

### 3.2 变更说明八要素

申请必须包含：① 现状证据（路径+SHA）；② 变更原因与正式依据；③ 唯一职责与归属；
④ 影响模块清单；⑤ 兼容/迁移方案；⑥ 回滚方案；⑦ 测试方案（含双库差异）；⑧ 文档更新范围。

### 3.3 审批流程

1. 变更申请以任务模板（§2）+ 八要素提交到 Issue（治理主线 Issue #7 或专项 Issue）；
2. 项目负责人批准后方可实施；实施时遵循测试先行；
3. 实施完成的变更随交付报告（含真实测试结果）报验收，验收通过才关闭；
4. ARCHITECTURE.md 每次修订在"修订记录"登记（R-x 编号、原因、基线 SHA、影响文件、审批记录）。

### 3.4 禁止事项

- 不得把一个 L3/L4 变更拆成多个 L1 任务规避审批；
- 不得以"临时/试验"名义实施无审批的核心变更；
- 不得先实施后补审批；紧急修复涉及 L3/L4 范围的，事后 24h 内补齐审批记录并说明紧急性。

## 4. 多会话并行纪律

- 同一模块存在并行会话任务时，派单必须声明文件边界与集成负责人（宪法 §11）；
- 提交一律使用显式 pathspec（`git add <明确文件>`），禁止 `git add -A` / `git commit -a`
  ——工作区常驻其他会话的在途修改（如 apps/identity）；
- 提交前 `git status --short` 确认暂存区只含本任务文件；
- 发现暂存区被他人变更（如 reset）时，先核对再重建暂存，不猜测归属。

```markdown
## 交付报告：<任务名>
- 基线：main@<SHA>（分支/时间）
- 修改文件：<清单>；修改原因：<依据>
- Model/Migration/Service/Selector/API/页面变化：<逐项；无则"无">
- 契约兼容说明：<无破坏 / 兼容期方案>
- 测试：命令、退出状态、数量（通过/失败/跳过）、数据库引擎、未覆盖项
- 遗留风险：<清单>；回滚方式：<适用时>
- 提交 SHA：<完整 SHA>
```
