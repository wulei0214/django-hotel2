### 1.2 结论建议

**第一治理模块：员工身份与 RBAC（apps.identity）**——与负责人建议一致，且证据支撑成立：

1. **控制面杠杆最高**：授权服务（AuthorizationService/registry/权限码）是所有其他模块的公共依赖；先固化其契约与审批流，后续每个模块的迁移都在已验证的控制面之上进行，避免把错误的授权假设带进后续迁移；
2. **遗留面最小、风险最低**：无 legacy 写入，Staff 只读兼容，数据退役量最小——作为第三阶段**第一个模块**，正好用来验证"审查→归属→契约→测试→迁移→退役"的完整流程并形成模板；
3. **存在一个已登记的 L4 级安全缺口**（第一阶段 §5.2：平台权限矩阵高危变更无第二人审批流）——这是全仓安全控制面上唯一已知的流程缺口，应优先补齐；
4. 财务/账本数据退役（V1.1 第 1 序的核心工作）风险最高，放在第二模块，待首模块验证流程模板后执行。

## 3. 迭代-1 设计提案（八要素，L3/L4 审批对象）

### 变更 A：平台权限矩阵高危变更接入第二人审批流【L4】

- **① 现状证据**：permission_center.py 的 permission_save 对高危 diff 仅要求**操作者本人**持 TimestampSigner confirm-token 确认（10 分钟窗口）+ 乐观锁 + 审计同事务；无第二人审批。第一阶段 §5.2 已登记为缺口。
- **② 变更原因**：权限矩阵是全系统授权的控制面；高危变更（如授予平台管理、修改他人岗位授权面）目前可由单操作者完成，违反职责分离基线（对照 billing 退款 SoD 的 DB 级三环）。
- **③ 唯一职责**：复用 apps.billing 既有 ApprovalRecord 通用审批机制（request→approve→execute），为权限矩阵高危 diff 增加"申请人→审批人"两环；低危 diff 维持现状（确认令牌 + 审计）。
- **④ 影响模块**：apps/identity（permission_center）、apps/billing（ApprovalRecord 复用，只读其机制，不改账务语义）、平台前端 /platform/permissions/ 页面交互。
- **⑤ 兼容/迁移**：新增 approval 类型常量，不动既有 ApprovalRecord 结构；存量进行中的 confirm-token 在过渡期仍有效（1 个版本周期）。
- **⑥ 回滚**：审批流开关按 diff 高危等级判定函数独立成模块级函数，可单点回退。
- **⑦ 测试方案**：测试先行——新增用例（高危 diff 未审批拒绝/审批人=申请人拒绝（SoD）/审批后执行成功/审计事件断言/令牌过期/低危直通）；identity 全量 265 回归 + 双库。
- **⑧ 文档更新**：宪法不动；本规范与角色权限验证指南同步。

### 变更 B：P-07 home 静默回退口径统一【L1/L2】

- **① 现状证据**：hotelapp/views.py::home 在 request.property 为 None 时回退 DEFAULT 渲染（与 middleware "不静默回退" 口径不同源）。
- **② 原因**：消除口径分歧，防止模式被复制。**③ 职责**：home 展示面对 None property 显式走公开面渲染分支（等价现状行为，语义显式化）。**④ 影响**：hotelapp/views.py::home 单函数。**⑤ 兼容**：行为不变（展示数据相同），仅语义显式化。**⑥ 回滚**：单函数还原。**⑦ 测试**：无任职账号访问 /home/ 断言（现状回归 + 审计事件仍由 middleware 记录）。**⑧ 文档**：无。

### 变更 C：遗留只读入口退役评估【仅登记，本迭代不实施】

index/search_staff 页面（渲染 hotelapp.Staff 列表）的退役前提 = UI 使用确认（是否存在真实用户流量/书签）。本迭代仅登记评估结论模板（流量确认→替代页确认→退役审批→下线），实际退役在 UI 确认后的迭代-2 执行。staff_accounts 页面已在新栈，无动作。
