## 第二部分：架构统一与代码审查（治本）

### 2.1 统一契约：Architecture & Style Guide

**① 强制分层（消灭 Fat Views）**  
实测 `hotelapp/views.py` 有 **2207 行、94 个函数、0 个类**——典型 Fat Views。新架构 `apps/` 已用 Service Layer（`apps/billing/services.py`）。规范必须写死：

```
请求流：URL → View（薄，仅参数校验+调用）→ Service（业务编排）→ Selector（只读查询）→ Model
禁止：View 里直接写事务/复杂查询/跨聚合逻辑
```

**② 强制 API 风格 = DRF**  
实测 `apps/api/views.py` **使用了 DRF**（`import rest_framework`），但 `requirements.txt` 里**没有 djangorestframework**！这是依赖管理漏洞，AI 各自 install 但未固化到 requirements。必须：

- `requirements.txt` 补 `djangorestframework==3.14.*`
- 统一响应格式：封装 `ApiResponse(data, code, message)`，禁止裸 `Response({"ok":True})`
- 统一错误处理：自定义异常 + 全局 `exception_handler`

**③ 统一事务与一致性**

- 写操作统一用 `@transaction.atomic` 或 service 内显式事务
- 跨聚合操作（如 billing 改房态）走领域事件或显式 service 调用，禁止隐式耦合

### 2.2 自动化武器（让 AI 不敢乱写）

必须落地以下工具（配置已生成，见附录文件）：

| 工具             | 作用                                   | 配置位置                      |
| -------------- | ------------------------------------ | ------------------------- |
| **Ruff**       | Lint + import 排序，一条命令替代 flake8/isort | `pyproject.toml`          |
| **Black**      | 格式化，消灭风格差异                           | `pyproject.toml`          |
| **isort**      | import 分组排序                          | `pyproject.toml`          |
| **Mypy**       | 类型检查，逼出隐式契约                          | `pyproject.toml`          |
| **pre-commit** | 提交前自动跑上面全部                           | `.pre-commit-config.yaml` |
| **pytest**     | 测试驱动，防回归                             | `requirements-dev.txt`    |

执行：

```bash
pip install -r requirements-dev.txt
pre-commit install
# 此后每次 git commit 自动格式化+检查；CI 也跑同一套
```

### 2.3 模块化边界（告诉 AI "你只管这一块"）

- 每个 AI 任务必须**限定单一 app**，例如："你只负责 `apps/billing` 的退款逻辑，不准改 `inventory` 或 `hotelapp`"
- 跨模块交互通过 **service 接口 / 序列化器**，不共享内部模型细节
- 新增 app 必须在 `apps/<name>/` 下，禁止在根目录或 `hotelapp/` 新建业务模块

### 2.4 TDD：测试用例是防波堤

- **人类定接口与测试用例**，AI 写实现去通过测试
- 测试分两层：`apps/*/test_*.py`（单元）+ `tests/`（E2E，源自 `api_tests/`）
- 没有测试的 PR 一律打回（pre-commit/CI 强制）

## 第三部分：人类如何审查 AI 代码（Review 策略）

指定一名"**代码合并者**"（你或资深成员），所有 AI 产出的 PR 必须过审。审查清单：

**A. 架构红线（一票否决）**

- [ ] 是否新增了 `hotelapp/` 下的功能？（禁止）
- [ ] 是否绕过分层，在 View 写业务/事务？（禁止）
- [ ] 是否直接裸写 SQL 或 `raw()`？（需说明必要性）
- [ ] 是否改了共享模型却没同步迁移？（禁止）

**B. 重复与分裂**

- [ ] 是否与 `apps/` 已有 service/selector 重复？
- [ ] 是否又造了一套响应格式/错误码？
- [ ] import 是否绕过了 `apps.*` 规范路径？

**C. 安全**

- [ ] 用户输入是否经序列化器校验？
- [ ] 权限是否走 `identity` 的 RBAC，而非硬编码？
- [ ] PII（客人信息）是否走 guests 的加密治理？
- [ ] 是否有 SQL 注入 / 越权风险？

**D. 事务与一致性**

- [ ] 多步写是否在同一事务？
- [ ] 失败路径是否 rollback 干净？

**E. 可测性**

- [ ] 是否带了对应测试？
- [ ] 复杂逻辑是否可单测（无外部副作用）？

## 第四部分：给 AI 派活的正确姿势（Prompt 技巧）

多 AI 协作的混乱，60% 来自"派活姿势"不对。请按以下模板派活：

**① 永远先给契约，再给任务**

```
上下文：这是 Django PMS，架构是 Service Layer（View→Service→Selector→Model），
API 用 DRF，响应统一用 ApiResponse。完整规范见 ARCHITECTURE.md。
你的任务：ONLY 在 apps/billing/ 内实现"夜审对账" service，
不得修改其他 app。函数签名如下：def night_audit(shop_id: int) -> AuditResult
参考已有实现：apps/billing/services.py 的 refund()
```

**② 限定边界，禁止越权**  
"不准碰 inventory / hotelapp / 其他 app；不改 models.py 之外的表结构；如需新字段，先提迁移方案给我确认。"

**③ 给测试当验收标准**  
"用 pytest 写 3 个用例覆盖：正常对账、部分未结账、跨日边界。必须全部通过。"

**④ 禁止整体重写**  
"只做局部修改，不要重新生成整个模块/文件。保留现有 import 与函数签名。"

**⑤ 让它自己跑质量门**  
"完成后运行：ruff check . && black --check . && mypy apps/ 并修复所有报错。"
