# PMS 文档体系重构设计方案（文档治理阶段二）
> 文档编号：GOV-010 ｜ 类型：GOVERNANCE ｜ 状态：SUPERSEDED ｜ 版本域：跨版本 ｜ 业务模块：文档治理

> 依据：《PMS 项目文档体系重构与知识入口治理实施方案》阶段二；输入为阶段一五份交付（基线 f13e32f，提交 0df34df）。
> 性质：设计先行，零批量调整。本文与配套四份设计（权威关系矩阵/阅读路线/移动合并归档删除计划/自动化门禁设计）经项目负责人批准后，方可在阶段三执行。
> 修订规则：本文整体重写不追加节；执行偏差登记在阶段三交付报告中。

## 1. 设计原则（六条）

1. **导航与状态分离**：文档索引只做导航与权威指针；一切"当前值"（基线 SHA/测试数/OpenAPI 规模/遗留门禁）只存在于唯一状态入口（§6）。
2. **每个业务主题唯一权威**：四类权威（需求/决策/技术实现/测试验收）互不替代，全部落进权威关系矩阵。
3. **历史不可改写，替代必须指针化**：SUPERSEDED/ARCHIVED 文件保留原文，由后继文件或头部指针建立替代关系；禁止在历史文档内嵌"当前值"断言。
4. **活文档整体重写，禁追加节**：状态类、导航类文档的更新方式是整体重写固定章节；"追加校准节"模式自本方案起废止（既有追加节按历史保留，不改写）。
5. **路径稳定优先**：OpenAPI 双快照路径全仓强耦合（CI workflow + 守卫常量 + 31 个文件的引用，2026-11-14 复测；移动前必须重新清点），冻结不动；目录调整只处理明确的归置错位与断链。
6. **多 AI 并发纪律**（阶段一 R1）：阶段三每批次独立提交、操作前对齐远端、显式 pathspec、操作后全量链接复扫。

## 3. 文档类型与效力状态

- **类型**（13 类，与台账一致）：REQUIREMENT / DECISION / ARCHITECTURE / DATA_MODEL / API / IMPLEMENTATION / TEST / AUDIT / ACCEPTANCE / DEPLOYMENT / GOVERNANCE / RESOURCE / ARCHIVE。
- **效力状态**（5 态，方案 §4）：ACTIVE（当前正式有效）/ REFERENCE（参考资料）/ DRAFT（未批准，必须显式标注）/ SUPERSEDED（被替代，必须指向替代文件）/ ARCHIVED（历史归档）。
- **判定规则**：状态由权威关系矩阵裁定；头部标注与矩阵冲突时以矩阵为准并在矩阵登记勘误。历史测试/审计/验收文档默认 ARCHIVED，绑定原 SHA。

## 4. 文档编号规则

- 格式：`<版本域>-<类型>-<三位序号>`，如 `PMS2-DEC-001`、`PMS2-REQ-001`、`PMS2-TEC-001`（技术设计）、`PMS2-IMP-001`（实施记录）、`PMS2-TST-001`（测试审计）、`PMS2-ACC-001`（验收）、`PMS2-OPS-001`（部署运维）、`GOV-001`（跨版本治理规范）、`PMS3-PLN-001`。
- **存量文档不回填正文**：编号只登记于文档总台账与权威关系矩阵，避免为编号而全量触碰历史文件；新文档（含本专项后续文档）必须在头部元数据块携带编号。
- 业务 DEC 编号（NS-A/NS-B/NS-C 三命名空间）是决策编号体系，与本文档编号并行不悖；矩阵中互相映射，互引时 DEC 按其规则带命名空间前缀。

## 5. 元数据规范（新文档强制）

新建及实质修订的正式文档，头部必须包含一行式元数据块：

```
> 文档编号：<编号> ｜ 类型：<类型> ｜ 状态：<效力状态> ｜ 版本域：<PMS2.0 等> ｜ 业务模块：<模块>
> 基线：main@<SHA> ｜ 上位文档：<编号或"无"> ｜ 替代：<被替代文件或"无">
```

历史证据、日志、快照类文件豁免。DRAFT 状态文档禁止被索引列为正式依据（门禁检查）。

## 9. 历史归档规则

- ARCHIVED 判定即冻结：不更新、不改名（除非批次内明确登记）、不迁目录。
- 替代关系一律"新文件声明覆盖 + 旧文件头部/矩阵登记指针"，不在旧文件正文续写。
- 验收证据（acceptance、06/evidence）只允许追加新文件，禁止覆盖、改名、移动既有证据。
