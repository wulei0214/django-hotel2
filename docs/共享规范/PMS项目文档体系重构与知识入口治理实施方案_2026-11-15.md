## 1. 目标与问题定义

**目标**：让任一开发人员或 AI 代理从一个入口出发，即可确定「某主题该读哪份文件、该文件的效力、当前值在哪里、历史证据在哪」，且结论可由仓库现取现核，不依赖口头传承。

阶段一盘点确认的问题（依据 `docs/共享规范/文档治理阶段一_全仓文档资产盘点报告_2026-11-14.md` §4 与 `docs/共享规范/文档治理阶段一_文档治理风险清单_2026-11-14.md`）：

1. **当前值多入口竞合**：索引头部、校准报告 2026-11-12、治理总表追加节、更新日志四处各自续写「当前状态」，数字互相矛盾（CF-B1~B3）。
2. **台账腐化**：人工台账是静态快照，多 AI 并行下三天内清点数 161→199→209 漂移（R10）。
3. **权威关系不可裁定**：历史报告、被替代方案与现行规范并列，缺少「唯一权威 / 支撑 / 历史」的裁定表。
4. **重复与冲突**：DUP-01~12、CF-B1~B6、TD-1~3 需要在不破坏追溯性的前提下收敛。
5. **路径强耦合**：OpenAPI 双快照被 CI 工作流、守卫常量与数十处引用锁定，移动会造成断链。

**边界**：本专项不改写业务需求与正式决策，不碰业务代码、数据库、验收证据正文、phase0 历史审计正文，不迁移 OpenAPI 双快照路径；治理方案不能自行改写业务规则（与 `docs/共享规范/多AI协作治理文档结构与文件职责.md` §二 一致）。

## 2. 最高原则（六条）

| # | 原则 | 约束 |
|---|---|---|
| 1 | 导航与状态分离 | 索引只做导航与权威指针；一切「当前值」只写在《PMS当前状态总览》 |
| 2 | 每个业务主题唯一权威 | 需求 / 决策 / 技术实现 / 测试验收四类权威互不替代，全部登记进权威关系矩阵 |
| 3 | 历史不可改写，替代必须指针化 | SUPERSEDED / ARCHIVED 保留原文，由后继文件或头部指针建立替代关系；禁止在历史文档内嵌「当前值」断言 |
| 4 | 活文档整体重写，禁追加节 | 状态类、导航类文档按固定章节整体重写；旧轮次靠 Git 历史与更新日志追溯 |
| 5 | 路径稳定优先 | 目录调整只处理明确的归置错位与断链；OpenAPI 双快照路径冻结，禁止第三份快照 |
| 6 | 多 AI 并发纪律 | 每批次独立提交、操作前对齐远端、显式 pathspec、操作后全量链接复扫 |

## 3. 目录职责框架

沿用 PMS2.0 的 00 决策 / 01 需求 / 02 技术架构 / 03 接口 / 04 实施记录 / 05 测试审计 / 06 验收 / 07 部署运维，外加 PMS1.0 历史归档、PMS3.0 后续规划、共享规范、公共资源、接口文档、acceptance 六类目录；逐目录一句话职责载于 `docs/文档索引.md` §一。

**共享规范目录职责（明确定稿）**：跨版本治理规范、状态总览、专项报告三类共存于同一目录，**不按文件类型拆分子目录**。分类靠三件东西实现，而不是靠文件夹：

1. 头部元数据块里的类型与效力状态（§4/§5）；
2. `docs/共享规范/文档治理阶段二_文档权威关系矩阵_2026-11-14.md` 的主题域裁定；
3. `docs/文档索引.md` §六 的文件级分组导航表。

阶段二设计方案 §9 规定「ARCHIVED 判定即冻结：不更新、不改名、不迁目录」，§2 只从共享规范迁出 1 个归置错位文件（性能优化与生产部署升级说明 → 07 目录）。因此「过程报告与现行规范平铺同层」是本框架的既定结果，不是未执行的整理项。

## 4. 文档类型与效力状态

- **类型（13 类）**：REQUIREMENT / DECISION / ARCHITECTURE / DATA_MODEL / API / IMPLEMENTATION / TEST / AUDIT / ACCEPTANCE / DEPLOYMENT / GOVERNANCE / RESOURCE / ARCHIVE。
- **效力状态（5 态）**：ACTIVE（当前正式有效）/ REFERENCE（参考资料）/ DRAFT（未批准，必须显式标注，禁止被索引列为正式依据）/ SUPERSEDED（被替代，必须指向替代文件）/ ARCHIVED（历史归档）。
- **判定规则**：效力由权威关系矩阵裁定；头部标注与矩阵冲突时以矩阵为准并在勘误批次修正头部。历史测试、审计与验收文档默认 ARCHIVED，绑定原 SHA，只作证据不作当前说明。
- **四类权威不得互替**：正式决策规定应该怎样；代码和迁移说明当前实现怎样；测试报告说明在什么 SHA/环境验证过；验收签署说明谁独立确认通过。

## 5. 编号与元数据规范

- 编号格式 `<版本域>-<类型>-<三位序号>`，如 `GOV-001`（跨版本治理）、`PMS2-DEC-001`；业务 DEC 命名空间（NS-A/NS-B/NS-C）与本文档编号并行，在矩阵中互相映射。
- 存量文档**不回填正文编号**，只登记于总台账与权威关系矩阵，避免为编号全量触碰历史文件。
- 新建及实质修订的正式文档，头部必须包含两行式元数据块（历史证据、日志、快照类豁免）：

```text
> 文档编号：<编号> ｜ 类型：<类型> ｜ 状态：<效力状态> ｜ 版本域：<PMS2.0 等> ｜ 业务模块：<模块>
> 基线：main@<SHA> ｜ 上位文档：<编号或"无"> ｜ 替代：<被替代文件或"无">
```

## 6. 盘点范围与台账

- 全仓盘点覆盖 `docs/` 全部跟踪文件与根目录中承担正式规范作用的文档；工程资产（apps、templates、static、scripts 等）按目录汇总登记，不逐文件列入文档台账。
- 台账是**时点快照**，绑定该轮基线 SHA，不冒充当前结构；当前文件级导航以索引分组表为准，当前值以状态总览为准。
- 盘点方式：只读、`git show <SHA>:<path>` 现取现核；结论区分「已证实问题 / 待核实风险 / 治理建议」。

## 7. 处置与冻结规则

| 类别 | 规则 |
|---|---|
| 重复文档 | 默认保留；按合并归零 / 收缩 / 指针 / 维持 / 删除五类处置，16 组排除项防误合并 |
| 删除 | 仅零引用且逐字节重复的资源可删，先核对模板、样式与文档引用；台账登记删除原因（原方案 §7.4）；其余疑似重复一律不删 |
| 历史证据 | `docs/acceptance/` 与 06/evidence/ 只进不出：新证据只追加，永不改写、覆盖、改名或移动既有证据 |
| ARCHIVED | 冻结：不更新、不改名、不迁目录（批次内明确登记的除外） |
| 替代关系 | 一律「新文件声明覆盖 + 旧文件头部/矩阵登记指针」，不在旧文件正文续写 |
| 移动 | 用 `git mv` 保留文件历史；每批次独立提交可回滚；批次结束复跑链接扫描 |

## 10. 自动化门禁

| # | 检查 | 拦截级别 |
|---|---|---|
| C1 | 链接检查（markdown 链接、`docs/` 显式提及、省略前缀相对引用、根目录入口、目录引用） | error，存量冻结只拦新增 |
| C2 | 新增文档头部元数据块；SUPERSEDED 必须有指向；DRAFT 不得被索引引用 | error，仅对新增文件强制 |
| C4 | 重复检测（blob 哈希分组；OpenAPI 受控镜像与空 `__init__.py` 白名单） | error |
| C5 | 40 位提交 SHA 可解析性 | error，变基前对象登记 `c5_known` 豁免 |
| C6 | 证据保护（acceptance 与 06/evidence 既有文件禁改禁删禁改名） | error |
| C7 | 活文档追加节检测（同一 `##` 标题重复 ≥2 次） | warn |

基线冻结采用「渐进治理」：存量违规登记进 `docs_gate_baseline.json`，只拦新增；基线更新必须与修复同提交（修一条删一条），禁止清空基线伪造通过。本地等效命令：`python scripts/docs_link_check.py check`。

## 11. 阶段交付报告格式

每份阶段交付报告须包含：基线链（阶段起点 SHA 与批次提交）、批次与改动清单、发现问题与处理、验证方法与真实结果、遗留事项与移交、签署状态。不得只写「完成」或「测试通过」而无可核验证据；事实性结论必须注明对应 SHA、环境与证据路径。

## 12. 维护与冲突处理

1. 活文档（状态总览、索引、矩阵、阅读路线）按固定章节整体重写，禁止追加节；旧轮次靠 Git 历史追溯。
2. 新增治理文件：同一提交内更新索引 §六、目录职责树、矩阵行、状态总览 §6，并跑门禁 check。
3. 文件冲突时暂停受影响开发，登记冲突与证据，由项目负责人裁定修订哪个权威文件；AI 不得自行选定权威版本，也不得在裁定前改动受影响文件。
4. 结构性目录调整属 L2/L3：须按 AI 派活规范提交变更说明，批准前不得批量移动；§7 的冻结规则优先于视觉整洁。
5. 文档与代码不一致时以现取现核为准，修正唯一入口，不改写历史证据，并把偏差记入 `docs/更新日志.md`。
