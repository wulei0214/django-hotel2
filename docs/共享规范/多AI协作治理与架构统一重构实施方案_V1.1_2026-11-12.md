## 1. 治理目标与最高原则

本次治理要解决多 AI、多开发人员并行开发造成的架构分裂、重复 Model/Service/API/页面入口、接口风格不一致、业务逻辑跨层、测试滞后、文档与代码脱节等问题。

六项最高原则：

1. **唯一架构宪法**：所有开发人员和 AI 使用同一份当前生效的根目录 `ARCHITECTURE.md`。
2. **唯一代码基线**：所有工作以 `main` 最新 SHA 为准，任务记录完整 SHA。
3. **唯一业务归属**：同一业务事实只有明确的权威数据归属和受控写入路径。
4. **契约优先**：先确认数据、Service、API、权限和状态契约，再开发。
5. **测试先行**：先定义可验证的验收条件和测试，再实现。
6. **人工最终审批**：AI 不得自行批准核心架构、数据库、权限、财务、安全和审计变更。

不得因架构统一而无依据重写项目、替换现有技术栈或破坏已验收业务。目标架构与当前代码事实必须明确区分。

## 3. 分层架构、命名和契约

### 3.1 分层架构

所有新代码遵循当前 `ARCHITECTURE.md` 经确认的分层约定。治理目标为职责清晰、依赖方向稳定：

- **URL/Router**：路由映射，不承载业务规则。
- **View/API View**：HTTP 协议适配、认证授权入口、参数校验、调用业务层和组织响应；保持薄层。
- **Service**：业务用例、状态转换、跨模块编排、事务、幂等和关键业务约束。
- **Selector**：可复用只读查询、筛选和聚合，不执行写操作。
- **Domain/Model**：领域实体、持久化结构和稳定不变量。
- **Database**：通过迁移、约束和必要数据库机制保护数据完整性。

View 不堆积复杂业务流程；Selector 不写数据；关键状态不得绕过指定 Service。现有仓库的真实目录和调用方向必须先审查，再决定规范文本和迁移顺序，不得机械搬迁目录。

### 3.2 命名规范

Python 统一采用：

| 对象 | 规范 | 示例 |
|---|---|---|
| 变量 | `snake_case` | `booking_status` |
| 函数/方法 | `snake_case` | `create_reservation()` |
| 类 | `CamelCase` | `ReservationService` |
| 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_PAGE_SIZE` |
| 模块文件 | `snake_case.py` | `reservation_service.py` |
| 测试函数 | `test_snake_case` | `test_create_reservation()` |

遵循 Django、DRF 和第三方框架既有约定，不为风格统一破坏框架要求。前端命名、组件、状态和接口字段规则须依据仓库实际技术栈另行确认并写入规范。

### 3.3 禁止重复核心模块

新增核心对象前必须检索并说明现有实现：

- Model/领域实体和关联关系；
- Service/状态机/事务入口；
- Selector/公共查询；
- API endpoint/Serializer/响应格式；
- RBAC/权限常量/数据范围/审计机制；
- 页面入口和业务流程；
- 对应测试和需求文档。

默认复用、扩展或修复已有实现。确需新增时，必须说明旧实现为何不能复用、新模块唯一职责、依赖边界、数据迁移、兼容和回滚方式，并经审批。

### 3.4 核心骨架先统一，再并行开发

核心 Model、Service、Selector、状态机、权限边界和 API 契约先由架构负责人或指定负责人统一审查设计。项目负责人批准后，核心实现负责人建立骨架和测试接口；其他 AI 再按任务边界开发页面、Serializer、API View 适配和普通展示逻辑。

这不是禁止 AI 编写 Model/Service，而是禁止多个 AI 未经协调分别设计相互冲突的核心模块。涉及同一核心模块的并行任务必须有明确文件边界和集成负责人。

### 3.5 API 与数据契约

统一规范至少覆盖 URL、HTTP 方法、请求/响应字段、类型和可空性、错误码、认证授权、数据范围、脱敏、分页排序、幂等、并发冲突、事务边界、审计和版本兼容。

统一响应格式应先核实现有项目实现和调用方依赖，再制定迁移计划。不得仅凭示例直接改变现有响应结构。任何破坏性接口变更必须有兼容期、调用方清单和回归测试。

## 4. 自动化质量工具链

目标工具：

| 工具 | 用途 | 治理要求 |
|---|---|---|
| Ruff | Lint、基础静态检查、import 排序 | 配置统一、CI 执行 |
| Black | Python 格式化 | 固定版本、避免无关全仓格式化 |
| Mypy | 静态类型检查 | 渐进纳入，明确覆盖范围 |
| pytest / pytest-django | 自动化测试 | 作为提交和 CI 门禁 |
| pre-commit | 本地提交前检查 | 配置与 CI 保持一致 |
| GitHub Actions | 自动化质量门禁 | 结果绑定具体 SHA |

配置和依赖建议集中在 `pyproject.toml`、`requirements-dev.txt`、`.pre-commit-config.yaml`、`.editorconfig`。运行依赖与开发依赖分离。检查 `requirements.txt` 是否覆盖实际运行导入，不能凭猜测补依赖。Ruff 与 isort 的职责要避免重复冲突；若保留 isort，须明确其与 Ruff 的分工。

Mypy 分阶段建立基线、约束新增/修改代码、逐步治理历史代码。禁止用大量 `ignore` 或关闭规则伪造通过。工具版本必须锁定并验证与当前 Python/Django 版本兼容。

## 5. TDD 测试护城河

新功能和重要缺陷修复按以下流程：

1. 确认需求、业务规则、状态机、权限和数据约束；
2. 定义正常、异常、边界、权限、数据一致性、并发和回归用例；
3. 先编写测试，并确认测试因目标行为未实现而失败；
4. 实现最小必要代码；
5. 运行目标测试和模块回归；
6. 执行格式、Lint、类型和 Django 检查；
7. 记录真实命令、结果、未覆盖项和风险。

重点保护财务/退款/冲账/账本/审计、预订入住退房、房态库存并发、员工身份与 RBAC、顾客和会员数据、API 越权/CSRF/脱敏/限流，以及 SQLite/MySQL 行为差异。

测试必须验证业务结果和数据库最终状态，不得只断言 HTTP 200 或页面元素存在。高风险流程须覆盖事务回滚、重复请求、并发和不可变约束。

## 6. 四阶段实施路线

### 第一阶段：现状核实与仓库治理

2. 盘点目录、Django app、Model、Service、Selector、View、API、页面和路由；
3. 盘点重复模块、重复入口、历史实现和模块依赖；
4. 盘点 docs 的有效、过期、重复、缺失和待核实内容；
5. 核实 Python/Django/DRF 版本、运行依赖和开发依赖；
6. 盘点测试类型、运行命令、通过/失败情况；
7. 盘点 GitHub Actions、SQLite/MySQL 和 PMS2 回归工作流；
8. 检查 .gitignore、AI 缓存、临时文件和仓库跟踪情况；
9. 每项发现记录路径、证据、根因/风险、影响范围、参考文档和建议；

验收：报告绑定明确 SHA；关键结论有证据；不未经批准删除业务代码、Model、数据或历史入口；不做无关全仓格式化；阶段报告经项目负责人验收。

### 第二阶段：开发宪法与工具链统一

**前置：** 第一阶段验收通过。

任务：
1. 基于现状审查根目录 `ARCHITECTURE.md`，校正与实际代码不符或互相冲突的规则；
2. 明确分层、模块边界、依赖方向、命名和禁止事项；
3. 明确 Model/Service/Selector/View 职责、事务、并发、幂等和迁移规则；
4. 明确 API 响应、错误码、权限、数据范围、脱敏和兼容策略；
5. 建立 AI 派活模板和架构变更审批制度；
6. 配置 Ruff、Black、Mypy、pytest、pre-commit 和 EditorConfig；
7. 建立开发依赖管理和 CI 基础门禁；
8. 标注立即强制项与渐进治理项，避免历史代码一次性产生大规模无关 diff。

交付物：更新后的 `ARCHITECTURE.md`、`pyproject.toml`、`requirements-dev.txt`、`.pre-commit-config.yaml`、`.editorconfig`，以及 AI 派活、API、测试、审查和架构审批专项规范。

验收：规则与实际技术栈兼容；工具版本可复现；本地和 CI 检查可运行；新增代码有明确门禁；不以关闭检查或滥用忽略项换取通过。

### 第三阶段：核心架构审查与渐进重构

**前置：** 第二阶段验收通过。

任务：
1. 审查 Model、Service、Selector、View/API、前端入口和测试；
2. 建立模块归属表和权威数据来源清单；
3. 建立核心 Model/Service/Selector/API 契约清单；
4. 识别重复实现、跨层调用、循环依赖、分散状态规则和重复入口；
5. 按风险排序逐模块治理，每个模块单独设计、测试、实现和验收；
6. 核心结构变更先审批；
7. 新旧入口切换前进行兼容、数据核对和回归。

风险优先级建议：财务/账本/审计/安全；员工身份/RBAC/敏感数据；预订/入住/退房；房态/库存；顾客/Guest 360/会员。最终顺序以第一阶段证据和风险评估为准。

每模块流程：现状审查 → 数据归属确认 → 架构审批 → API/领域契约 → 测试先行 → 实现 → 回归 → 数据核对 → 文档更新 → 旧入口退役审批。

验收：权威数据归属明确；无未经批准的重复核心模块；写入路径、事务、权限和审计明确；核心测试通过；新旧功能无未处理回归；替代入口完整验收前不得退役旧入口。

### 第四阶段：CI 强制门禁与多 AI 制度固化

**前置：** 核心模块按计划完成治理，质量规则稳定。

任务：将 Ruff、Black、Mypy、pytest、Django check、适用的 SQLite/MySQL 测试、PMS2 回归和安全测试纳入 CI；明确失败阻断规则和历史债务例外；固化 AI 任务模板、审批、审查、提交和交付流程；定期复核架构规范。

验收：门禁结果绑定具体 SHA；关键业务和数据库测试自动执行；不允许跳过 CI、删除测试或放宽规则掩盖失败；无未处理 P0/P1 阻断问题；遗留项有责任人和计划；main 最新 SHA 的相关 CI 通过。
