# Guest 重复档案治理（A3）实施与冻结边界（2026-11-13）

> 治理任务 #45（A3）：Guest 重复档案「人工 + 预览 + 审计 + 保留映射」。
> 权威规范：《PMS2 身份认证与员工、住客账户体系改造开发方案 2.0_2026-11-10》§8.2、§18.1。
> 性质：实施记录 + 冻结边界声明 + 待确认清单（供业务负责人决策输入）。

## 0. 结论先行

1. A3 **已实现「只读候选报告 + 只读影响面盘点 + 人工重复关联标记（留痕）」**，并把**物理合并显式冻结**为恒定拒绝的入口。
2. 实现**未越界**：候选报告只列「证据信号」，**不输出置信度评分、不设自动阈值、不自动合并**；影响面盘点只陈述事实与冲突，`executable` 恒为 `False`；关联标记**只写审计映射，不移动任何业务引用、不物理删除源档案**。
3. **未新增 Model / Migration**（`makemigrations --check` → No changes detected）。理由见 §4。
4. 冻结边界依据 §8.2-7 与 §18.1：合并策略、匹配置信度、冲突处理、回滚与人工审批流程属**业务待确认项**，必须由业务负责人批准后才能解冻。
5. 待业务负责人确认的清单见 §6；**在确认前不得开放 API/页面入口执行任何写操作**。

## 1. 规范依据与逐条对照

| 规范条款 | 要求 | 本次落地 |
|---|---|---|
| §8.2-1 | 不自动按手机号、姓名、证件号合并 Guest | ✅ 候选报告只输出信号，**无任何自动合并路径**；`policy.auto_merge=False` |
| §8.2-2 | 复用 Guest 须先有匹配策略与人工确认流程；批准前不得擅自复用或合并 | ✅ 未实现任何「复用既有 Guest」的自动路径（该能力属策略批准范围） |
| §8.2-3 | 支持人工建立重复档案关联/疑似重复标记，但**不物理删除源档案** | ✅ `link_duplicate_guests()` 人工建立关联 + `dismiss_duplicate_candidate()` 人工否定；两者只写审计，源档案与其全部业务引用保持不变（有测试断言） |
| §8.2-4 | 合并一旦获批，必须保留主档案、源档案、操作者、时间、理由和完整关联映射 | ✅ 审计事件字段完整覆盖：`entity_id`=源档案、`after_json.mapping`=源/目标映射、`actor`=操作者、`created_at`=时间、`reason`=理由、`signals`=判定依据；`status="not_merged"` 明确标记未合并 |
| §8.2-5 | 合并必须审查 Reservation、ReservationGuest、Folio、LedgerEntry、Payment、Refund、AuditEvent、LegacyRecordLink 等引用关系；禁止改写或删除账务历史 | ✅ `preview_merge_impact()` 逐类统计 **15 类引用面**（含上述全部 8 类 + ReservationRoom 之外的 StayGuest、会员、电话、证件等）；本次实现**不触碰任何账务历史**，仅计数 |
| §8.2-6 | 旧 Client→Guest 映射必须使用 LegacyRecordLink 或经批准的迁移映射表 | ✅ 未新增第二套 legacy 映射载体；盘点时读取 `LegacyRecordLink(target_model="Guest")` 作为既有映射事实 |
| §8.2-7 | 合并策略/匹配置信度/冲突处理/回滚/人工审批属业务待确认项；**批准前只能做只读盘点和候选重复报告** | ✅ 候选报告与影响面盘点**均为只读**（有测试断言不写库、不产生审计）；关联标记属 §8.2-3「本期固定执行」；物理合并显式冻结 |
| §18.1 | 重复档案的正式匹配、人工合并审批与合并后主档案规则须业务负责人批准；未决事项不得被「悄悄决定」 | ✅ 未自造任何业务口径：无数值阈值、无比配评分、无主档案保留规则、无审批链；全部列入 §6 待确认 |

### 2.1 候选证据信号（**只陈述事实，不含评分**）

| 信号 | 含义 | 注意事项 |
|---|---|---|
| `SHARED_PHONE_HASH` | 两个档案登记了同一标准化号码（HMAC `phone_hash`） | **共享号码不等于同一自然人**（M-03 语义：号码可被家庭/公司共享）；已由既有 `GuestPhone.shared_review_required` 标记承接 |
| `SAME_NAME` | 同物业同名（去空格 + casefold 归一） | 弱信号，仅供人工参考 |
| `DOCUMENT_HASH_CONFLICT` | 同一证件号哈希出现在多个档案 | 正常写入会被 WB-102 `GuestDocumentIndex` 物业级唯一拦截，故本信号主要指向**历史遗留或绕过占用**的数据 |

### 2.2 影响面盘点覆盖的引用（§8.2-5）

`reservations`、`reservation_guests`、`stay_guests`、`folios`、`open_folios`、`ledger_entries`、`payments`、`refunds`、`refund_liabilities`、`audit_events`、`legacy_record_links`、`memberships`、`active_memberships`、`phones`、`documents`。

冲突事实类型：`BOTH_ACTIVE_MEMBERSHIP`、`BOTH_PRIMARY_PHONE`、`SHARED_PHONE_HASH`、`SHARED_DOCUMENT_HASH`、`EMAIL_MISMATCH`、`NAME_MISMATCH`、`SOURCE_HAS_LEDGER_ENTRIES`、`SOURCE_HAS_OPEN_FOLIO`。

### 2.3 权限

复用既有权限码 **`hotelapp.change_client`**（客人档案修改权限），**未新增权限码**，未改动 `apps/identity/permission_center.py`（避免与并发 WIP 冲突）。授权经 `AuthorizationService.has_permission(user, property, code)` 校验，与 §9「唯一权限码」口径一致。

## 3. 冻结边界（硬约束）

```python
execute_merge(...)  →  恒定 raise GuestMergePolicyFrozen(FROZEN_REASON)
```

- 冻结范围：物理合并、FK 迁移、源档案归档/删除、撤销与补偿。
- 解冻前提（全部满足方可）：业务负责人批准合并策略、匹配置信度、冲突处理、回滚与人工审批流程（§8.2-7 / §18.1）→ 按治理 V1.1 §2.3 走 L3/L4 变更审批 → 补充合并专项测试。
- 冻结期间允许的写操作**仅有一类**：人工重复关联/否定标记（§8.2-3），其本质是审计留痕，不改变任何业务事实。

---

## 4. 为什么本期不新增 Model

1. **§8.2-7 的直接约束**：批准前只能做只读盘点与候选报告；物理合并所需的正式载体（如 PMS3.0 规划的 `GuestMergeRequest`）尚未获批，提前建表会与未来批准的设计冲突，并形成「第二套映射机制」，违反治理 V1.1 §3.3「禁止重复核心模块」。
2. **既有载体重量足够**：`AuditEvent` 是全项目唯一审计事实载体（append-only + MySQL 触发器防篡改 + `idx_audit_entity_time` 索引），§8.2-4 要求的六项留痕要素可完整落入其既有字段。
3. **不触碰并发 WIP**：本期全部改动限定在 `apps/guests/**`，未新增迁移，未改动 `apps/identity/*`、`hotelapp/views.py`。
4. 获批后再评估是否升格为一等 Model（届时走 L3 审批 + 迁移）。

## 6. 待业务负责人确认清单（§18.1）

以下均为**业务口径**，开发人员不得自行补值；确认前相关能力保持冻结：

1. **匹配置信度与阈值**：哪些信号组合可判为「疑似同一人」？是否需要人工评级字段？（当前实现刻意不输出评分）
2. **主档案保留规则**：合并后保留哪一份档案，另一份如何归档？档案名、证件、电话、会员关系如何择一？
3. **会员关系冲突**：两个档案各有有效会员关系时的处置（会员编号保留/作废/重签）。
4. **账务与未结账单**：源档案存在未结 Folio 或已有账本凭证时的处理顺序（§8.2-5 禁止改写账务历史，需明确「先结清再迁移」的流程与责任人）。
5. **人工审批流程**：谁可提出、谁可复核（双人复核？）、高风险情形的审批层级（对应 PMS3.0 DEC-03 预留）。
6. **撤销与补偿**：合并后是否允许撤销；撤销如何补偿（对应 PMS3.0 DEC-06 预留）。
7. **入口与权限**：是否开放 API/页面入口执行关联标记；关联标记是否需要独立权限码（当前复用 `hotelapp.change_client`）。
8. **历史 Client 映射**：旧 Client→Guest 的业务 owner 与冲突处理人（§8.2-6 / §18.2）。
