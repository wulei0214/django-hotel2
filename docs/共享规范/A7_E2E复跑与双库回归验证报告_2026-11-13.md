## 三、E2E 复跑发现并修复的问题

### 3.1 【P0·业务缺陷】公开预订在房价计划与房型非 1:1 时必然 409

**现象**：冒烟实例中 5 个房型各挂 1 个房价计划（BAR_STD↔STD、BAR_SUP↔SUP、BAR_DLX↔DLX、BAR_FAM↔FAM、BAR_BUS↔BUS，属常见配置）。公开可售查询对全部房型返回 `available_count=4` 与正确房价，但公开预订创建返回 **HTTP 409「所选日期房量不足，请重新查询。」**。

**根因**：查询侧与下单侧**各自选房价计划**：

| 侧 | 位置 | 选法 | 结果 |
|----|------|------|------|
| 查询侧 | `apps/inventory/services.py::get_room_type_availability` | 按"该房型在住宿区间实际有价格行"选 | 命中本房型计划 → 价格与可售量正确 |
| 下单侧 | `apps/reservations/services.py::_get_rate_plan` | 按"物业下第一个有效计划"选 | 全部房型都取到 plan=1 |

下单侧对房型 2/3/4/5 取到的计划不含该房型的价格行 → `get_room_type_availability` 的每日价格行缺失 → 可售量被算成 **0** → 误报"房量不足"（409）。

**这是既有修复的覆盖不全**：`apps/inventory/services.py` 原文注释已明确登记该坑——"全局取第一个会导致只有碰巧挂在默认计划下的房型可售（其余房型恒 0 间）"——并已在**查询侧**修好，**下单侧未同步修复**。

**契约冲突**：`apps/api/openapi_schema.py` 中公开预订创建体的 `rate_plan_id` 已写明"可选；**不传由服务按有价计划自动选择**"，运行时行为与已提交契约相悖。

**修复（`39c8dba`）**：

1. `apps/inventory/services.py` 新增 `select_rate_plan_for_room_type()` 作为**唯一选价口径**（显式 `rate_plan_id` 优先 → 否则取该房型在区间内有价格行的计划 → 再兜底覆盖区间的首个有效计划）；`get_room_type_availability()` 改为调用它。
2. `apps/reservations/services.py::_get_rate_plan()` 改为同一函数的委托，并把 `room_type` 纳入选价入参——**从构造上消除两侧各选各的漂移**，而非各自再修一次。
3. 区分两类失败原因：`total_amount is None`（无价格/关房/停售/库存日历缺失）报"所选日期**暂不可预订**"，确有价格但房量不足才报"所选日期**房量不足**"，避免误导排查方向。

**回归**：`apps/reservations/test_rate_plan_selection_consistency.py`（6 项）——两侧口径一致 / 非 1:1 可正常创建且金额取自本房型计划 / 显式计划优先 / 无价与真售罄的报错区分。

### 3.2 【P1·工具缺陷】`seed_hotel_data` 抛 UnboundLocalError

函数体内 `from apps.reservations.models import ReservationRoom, Stay` 使 `ReservationRoom` 成为函数级局部变量，而该名字在本次 import **之前**（第 150 行）已被使用 → Python 在函数入口即判定其为局部变量，首次使用处未赋值即抛 `UnboundLocalError`。修复：函数内只导入 `Stay`（`20c26f9`）。

### 3.3 【P1·装置缺陷】p0 套件被环境代理劫持，全线 404

**现象**：首轮复跑 2 failed / 1 passed / 6 errors。服务端日志显示请求目标为 **absolute-form**：

```
"GET http://127.0.0.1:8000/api/v1/availability?check_in=... HTTP/1.1" 404
"GET /reserve/ HTTP/1.1" 200          ← 同一轮里却是 origin-form
```

**根因**：本机环境注入了 `http_proxy` / `HTTP_PROXY`（`127.0.0.1:59190` 本地拦截代理）。`requests` 默认继承该代理并把请求目标改写为 absolute-form 转发给 Django 开发服务器，而 Django 的路径解析**只接受 origin-form**（`GET /path HTTP/1.1`）→ 被测实例全线 404。

**修复（`26f68fa`，只改装置不改业务代码）**：

- `HttpApi` 对**回环地址**（`127.0.0.1`/`localhost`/`::1`/`0.0.0.0`）显式置空代理项（`requests` 的 `proxies` 字典中 `None` 表示该协议不走代理）；非回环地址保持继承环境代理的默认行为不变。
- 新增会话级 `autouse` 前置探针 `p0_instance_reachable`：实例不可达时**立即以一条可操作提示失败**（含代理劫持的定位线索），不再让 9 条用例各自以各自的 404 失败。
- README 补"环境代理隔离"与"常见故障"两节。

## 五、环境陷阱与操作要点（务必知悉）

### 5.1 全量回归**不要**带 `--keepdb`

`--keepdb` 会复用上一轮的测试库，而上一轮的 `TransactionTestCase` 在每个用例后 flush，**会清掉迁移播种的 `DEFAULT` 物业与岗位分组权限**；复用的库不再重跑迁移 → 播种数据不回来 → 大量用例在 `setUp` 阶段报
`apps.core.models.Property.DoesNotExist: Property matching query does not exist`。

**实测**：复用被 flush 过的 `test_hotel` 跑全量 → `Ran 1141 tests — FAILED (failures=71, errors=511)`（**伪失败**，与代码改动无关）。去掉 `--keepdb` 后重建测试库 → 全绿。

> 结论：**全量回归一律不带 `--keepdb`**（与 CI `python manage.py test --noinput` 同口径）。专项验证需要保留 `test_hotel` 时，用完须重新播种或重建。

### 5.2 p0 套件受环境代理影响（见 §3.3）

### 5.3 本机 pre-commit 无法初始化

pre-commit 需联网拉取钩子仓库，本机代理对 `github.com` 返回 **502（proxy after CONNECT）** → 钩子初始化失败。故本轮三次提交均以 `--no-verify` 提交，并在提交说明中载明**已预跑的等价校验**（ruff / black / ruff-format / mypy 触碰文件门禁）。**联网恢复后应立即重跑一次带钩子的提交做交叉验证。**

### 5.4 后台任务退出码不可信

本机后台 PowerShell 任务即使日志写 `OK` 也可能回显非 0（`2>&1 | Tee-Object` 的 `NativeCommandError` 噪声）。**一律以日志内的 `Ran N tests` / `OK` / `FAILED` 为准**，本次三个结论均取自日志正文。
