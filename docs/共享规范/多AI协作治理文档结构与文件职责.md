## 二、权威性与冲突处理

1. 根目录 ARCHITECTURE.md 是全项目架构规则的最高层级规范。
2. 多AI协作治理与架构统一重构实施方案 V1.1 规定治理目标、四阶段顺序、阶段交付和验收门禁。
3. AI 派发模板、API 规范、TDD 规范、代码审查规范和架构审批规范是专项执行文件，必须服从 ARCHITECTURE.md。
4. 业务需求、正式决策和验收签署仍以对应 PMS 版本目录中的权威文件为准；治理方案不能自行改写业务规则。
5. 测试报告和阶段盘点报告是带 SHA、环境和命令的事实证据，不得当作规范或需求。
6. 文件冲突时暂停受影响开发，登记冲突和证据，由项目负责人决定修订哪个权威文件；AI 不得自行选择对自己方便的版本。

## 三、文件维护要求

| 文件 | 维护时机 | 最低内容要求 |
|---|---|---|
| ARCHITECTURE.md | 架构规则变更时 | 规则、适用范围、例外审批、修订记录 |
| 四阶段实施方案 | 阶段策略变化时 | 变更原因、阶段影响、验收变化 |
| AI 派发模板 | 任务交付要求变化时 | 基线、规范、范围、测试、交付字段 |
| 架构审批规范 | 审批边界变化时 | 风险等级、审批人、材料和验收 |
| API 开发规范 | API 契约变化时 | 请求/响应、错误、权限、兼容和测试 |
| TDD 规范 | 测试体系变化时 | 测试层级、命令、覆盖和证据 |
| 代码审查规范 | 质量门禁变化时 | 审查项、阻断条件、CI 规则 |
| 阶段报告/问题清单 | 每阶段结束时 | 对应 SHA、事实证据、未验证范围、责任和结论 |

## 四、状态标记约定

- **现行规范**：当前必须遵守。
- **实施方案**：经批准后按阶段执行。
- **待审批**：不得当作已批准规则。
- **盘点事实**：仅对报告标注的 SHA、环境和时间有效。
- **历史记录**：保留原始结论，不覆盖、不倒改。
- **目标结构**：规划结构，不代表已存在或已实施。

## 五、落地顺序

1. 第一阶段先核实现有目录、规范和配置，避免重复创建已有文件。
2. 盘点后由负责人确认专项规范哪些已有、哪些缺失、哪些需要合并。
3. 第二阶段优先审查并完善现有 ARCHITECTURE.md，不另建第二份架构宪法。
4. 再补齐 AI 派发、架构审批、API、TDD 和代码审查规范。
5. 第一阶段报告与问题清单必须基于真实 main SHA 生成；不能提前填写未经检查的结论。
6. 更新 docs/文档索引.md，保持入口可发现；后续实质修改同步更新索引和相关规范。
