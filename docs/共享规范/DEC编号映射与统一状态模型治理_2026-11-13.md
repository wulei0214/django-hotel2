## 3. DEC 编号冲突与治理缺陷（重点）

1. **冲突 1 — DEC-01 双义**：在《硬冻结决策待确认清单》中 `DEC-01 = 员工再入职`（对应代码 `DEC-EMP-01`）；在《三项业务政策基础设施实施方案》《DEC-02 实施完成报告》中 `DEC-01 = 提前离店结算`（对应代码 `DEC-ED-01`）。两套语义指向完全不同的模块（identity vs reservations）。
2. **冲突 2 — DEC-02 双义**：在《硬冻结清单》中 `DEC-02 = 物业工号规则`（对应 `DEC-EMP-02`）；在《三项业务政策》《DEC-02 业务决策基线》中 `DEC-02 = 待退款负债`（对应 `DEC-02-A1/B2`）。
3. **代码侧已自洽**：代码用"域前缀"消歧——`DEC-EMP-*`（员工）、`DEC-ED-*`（提前离店）、`DEC-DEP-*`（押金）、`DEC-WALKIN-*`（散客）、`DEC-02-A1/B2`（负债子项）。但**文档侧《硬冻结清单》与《三项业务政策》仍沿用裸 `DEC-01/02/03`，未对齐到上述前缀**，导致人读文档与代码、文档与文档之间映射断裂。
4. **风险**：跨文档追溯 `DEC-01/02` 时无法唯一确定所指；新需求若沿用裸编号会加剧冲突。

**建议**：
- 冻结"裸 `DEC-01/02/03`"用法，统一改为带域前缀（`DEC-EMP-` / `DEC-ED-` / `DEC-DEP-` / `DEC-02-*`）。
- 以本文（或 docs 索引）作为"DEC 编号注册表"，新 `DEC` 须先查重再赋值。
- 《硬冻结决策待确认清单》补"历史快照"声明，注明 `DEC-01/02` 含义以带前缀映射为准，避免误读。

## 4. 统一状态模型现状与 A04/A09 父子拆分

### 4.1 现状：散落的状态枚举

| 应用 | 状态枚举（文件:行） |
|---|---|
| core | `StatusTransition` 通用状态机时间线模型（`core/models.py:402`，只追加、不可改/删）；另含 `Status`×4（:12/:202/:268/:365）、`MappingStatus`、`ReviewDecision`、`RunStatus`、`RecordStatus` |
| reservations | `Reservation.Status`（PENDING/CONFIRMED/CANCELLED/EXPIRED/CHECKED_IN/CHECKED_OUT/NO_SHOW，`:14`）、`Stay.Status`（IN_HOUSE/CHECKED_OUT/VOIDED，`:178`）、`HoldStatus`（`:398`）、`Role`、`PenaltyType`、`DepositType`、`PolicyType` |
| inventory | `OccupancyStatus`、`HousekeepingStatus`、`MaintenanceStatus`、`TaskStatus`、`TicketStatus`、`InspectResult`、`Status`×2（RoomStatus / InventoryItemStatus，`:435`/`:467`） |
| identity | `EmploymentStatus`、`Status`×2（员工任职 / 账号，`:65`/`:249`） |
| billing | `Status`×多（Payment / Refund / LedgerEntry / RefundLiability / BillingAdjustment / CheckoutExceptionRelease / Shift / CompensationTask，`:34/:122/:368/:516/:783/:953/:1232/:1309/:1402/:1735`）、`FolioType`、`EntryType`、`Direction`、`ChargeType`、`AdjustmentType`、`ReasonCode` |
| guests | `Status`（`:239`）、`PhoneType`、`DocType` |

**问题**：
- 每模型各自定义 `TextChoices`，状态 code 与中文 label 已多数分离，但**无中心注册/父类抽象**。
- 状态机"合法跃迁"散落在各服务/视图（如 Reservation 推进、Refund SoD 三环、BillingAdjustment 四步、CheckoutExceptionRelease 五步），**未统一由 `StatusTransition` 或状态机框架强制**。
- `StatusTransition`（`core/models.py:402`）已提供只追加业务时间线，但需确认**各状态变更是否都写入**，避免状态机与事实时间线脱节。
- 有状态机的表不能一律禁 UPDATE（《PMS2 MySQL 财务与审计不可变事实部署说明》§14）：Refund 按状态机推进、ProviderTransaction 由应用层状态机 + QuerySet 保护——说明状态推进是受控的，但缺统一父类。

### 4.2 A04 / A09 的两种上下文

- **上下文 A（验收门禁，docs/验收）**：`A04 = 数据库验收报告`（空库迁移/升级/对账，95 号报告 §2）；`A09 = MySQL 8 报告`（约束/事务/并发/数据核对，双引擎 887 OK）。二者是"验收父项"，各自下含多个子检查。
- **上下文 B（业务不变量，INV-A04 / INV-A09）**：`INV-A04 = Hold 与 Reservation 一致`（Hold 只能由唯一服务创建/确认/释放；过期不得释放已确认/已支付订单库存）；`INV-A09 = Folio 余额可重算`（余额由有效 LedgerEntry 按币种计算，不同币种不得混加，缓存非权威）。

### 4.3 父子拆分建议

将"统一状态模型"治理为两大**父状态族**，对应上述两条核心不变量（即 A04/A09 的本质）：

- **父族 A — 生命周期 / 库存一致性（对应 INV-A04 / 验收 A04 的"数据一致性"维度）**
  `Reservation.Status`、`Stay.Status`、`HoldStatus`、库存侧 `RoomStatus`/`OccupancyStatus` 归入"生命周期状态族"。其合法跃迁必须满足 **Hold↔Reservation 一致（INV-A04）**。
- **父族 B — 财务事实（对应 INV-A09 / 验收 A09 的"数据核对"维度）**
  `Payment.Status`、`Refund.Status`、`LedgerEntry.EntryType`、`Folio`/`FolioType`、`BillingAdjustment.Status`（DEC-02-A1）、`CheckoutExceptionRelease.Status`（DEC-02-B2）、`RefundLiability.Status`、`ShiftStatus` 归入"财务事实状态族"。其合法跃迁必须满足 **Folio 余额可重算不变量（INV-A09）**，且资金事实只能由受控通道推进（不得直接改状态伪造资金事实，见《PMS2 财务账务与营业日 P0P1 专项整改需求》§20）。

**拆分落点**：
1. 抽离 `apps.core.state` 或扩展 `core.models.StatusTransition`，定义 `StateFamily` 父枚举（`LIFECYCLE` / `FINANCIAL`），各模型 `Status` 标注所属 family。
2. 状态跃迁统一经 `StatusTransition` 记录（只追加），并增加 `family` 字段便于按族审计；非法跃迁在写入前由服务层集中校验（复用现有各服务逻辑，先抽公共校验器）。
3. 验收侧：将 `A04`/`A09` 由"单条门禁"拆为"父门禁 + 子检查清单"（`A04` 拆 迁移/字段/约束/索引/对账 5 子项；`A09` 拆 约束/事务/并发/核对 4 子项），每子项独立可验证、可签名，解决"已签署但子项未验"的模糊。

> 注：以上 A04/A09 父子拆分是治理**建议**，需负责人确认"父族"划分口径与是否引入 `StateFamily` 抽象。代码侧当前已通过分散枚举 + 服务内状态机 + `StatusTransition` 时间线达到同等效果；本建议为统一与可维护性增强，非紧急修复。
